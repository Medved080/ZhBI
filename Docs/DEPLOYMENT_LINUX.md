# Установка на Ubuntu Server и обновление без потери данных

Практическое руководство для человека, который будет ставить и
поддерживать ЖБИ на сервере под Ubuntu Server LTS (22.04/24.04).
Клиенты (пользователи в браузере) остаются на Windows — этот документ
только про сам сервер. Приложение разворачивается в **Docker**-
контейнере; вспомогательные скрипты — в `scripts/linux/` (запускаются
из терминала, `bash scripts/linux/....sh`).

Технический фон — `Docs/ARCHITECTURE.md`; что система умеет —
`Docs/TZ.md`. Здесь — только "как поставить и не потерять данные".

## 0. Главное правило на всю статью

**Данные и код — в разных местах, и это нарочно.** Код живёт внутри
Docker-образа и пересобирается/заменяется при каждом обновлении; данные
— обычные папки/файлы на диске сервера, примонтированные в контейнер
как bind-mount volume (`docker-compose.yml`) — пересборка образа их не
касается вообще.

Пути ниже — как задумывались изначально (относительно папки проекта).
**После слияния с веткой коллеги (см. 3.0) `docker-compose.yml`
монтирует их по АБСОЛЮТНЫМ путям `/opt/zhbi/data`/`Input`/`uploads` —
не проверено, совпадает ли это с тем, где данные реально лежат на
живых серверах сейчас.** Сам принцип "данные и код разделены и не
трогаются при обновлении" не изменился, изменилось только КУДА именно
смотрит том.

| Папка/файл | Что там | При обновлении |
|---|---|---|
| `data/zhbi.db` (или `/opt/zhbi/data/zhbi.db`) | Вся база: элементы, статусы, история, контракты, пользователи | **НИКОГДА не трогать, не удалять, не перезаписывать** |
| `Input/` (или `/opt/zhbi/Input`) | DXF-чертежи, которые сервер сам подхватывает при каждом запуске | **Не трогать** |
| `uploads/` (или `/opt/zhbi/uploads`) | DXF, загруженные через кнопку в браузере | **Не трогать** |
| `.env` (сборка на сервере, устарело — см. 3.9) / `.env.run` (генерируется CI, см. 3.0) | Настройки конкретного развёртывания — НИ ТО НИ ДРУГОЕ не в git | Не трогать вручную |
| `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `.env.example`, `.gitlab-ci.yml`, `app/`, `scripts/`, `Docs/`, `requirements.txt`, `CLAUDE.md`, `.gitignore` | Код программы | Это и есть то, что заменяется при обновлении |

Пути к данным внутри приложения (`app/db.py`, `app/main.py`,
`app/dxf_import.py`) — относительные (`data/zhbi.db`, `Input/`,
`uploads/` от корня проекта); `docker-compose.yml` монтирует ровно эти
же папки хоста на те же пути внутри контейнера (`/app/data`,
`/app/Input`, `/app/uploads`) — поэтому в коде приложения ничего не
пришлось менять ради Docker. Саму папку проекта на сервере можно
свободно переносить целиком — данные и код внутри неё не перепутаются
при обновлении, пока не путать `data/`/`Input/`/`uploads/` с остальным
при ручном копировании (см. раздел 4).

## 1. Первая установка (один раз)

### 1.1 Установить Docker и git

```
sudo apt update
sudo apt install -y ca-certificates curl gnupg git
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo usermod -aG docker "$USER"
```

Последняя команда добавляет текущего пользователя в группу `docker`
(чтобы не писать `sudo` перед каждой командой `docker`/`docker
compose`) — после неё нужно **выйти и зайти в SSH-сессию заново** (или
`newgrp docker`), иначе членство в группе не подхватится.

Проверка:
```
docker --version
docker compose version
```

Если прямой доступ в интернет с сервера закрыт (частая ситуация в
корпоративной сети) — установка потребует внутреннее зеркало
пакетов Docker или предварительно скачанные `.deb`-пакеты; уточнить у
ИТ-отдела.

### 1.2 Скопировать проект на сервер

Код версионируется на двух удалённых репозиториях (см. раздел 3) — на
сервер клонируется **корпоративный GitLab** (не GitHub — см. раздел
3.2, почему):
```
sudo git clone <адрес репозитория на корпоративном GitLab> /opt/zhbi-tool
```
(Путь `/opt/zhbi-tool` — пример, можно любой.) Доступ к репозиторию —
по SSH-ключу или токену, в зависимости от того, как настроен GitLab-
сервер (уточнить у того, кто выдаёт доступ).

### 1.3 Настроить и собрать

```
cd /opt/zhbi-tool
cp .env.example .env
```
Открыть `.env` и поправить при необходимости (порт, security-флаги —
комментарии в самом файле). Для обычной установки внутри корпоративной
сети без TLS менять по умолчанию ничего не нужно.

```
docker compose build
docker compose up -d
```
Первая сборка качает базовый Python-образ и ставит зависимости из
`requirements.txt` — нужен доступ в интернет (или внутреннее Docker-
зеркало/PyPI-зеркало, если прямой интернет закрыт — уточнить у ИТ-
отдела).

Журнал работы сервера:
```
docker compose logs -f
```
(Ctrl+C только останавливает просмотр журнала — сам сервер продолжает
работать в фоне; это отличается от прежнего `run.sh` в открытом
терминале, где Ctrl+C останавливал сервер.)

При первом старте в журнале появится строка вида `[startup] ВНИМАНИЕ:
без пароля (вход запрещён, пока не задан): admin` — это ожидаемо,
читайте дальше.

### 1.4 Первый пароль администратора

Пустой пароль у свежесозданного `admin` **не работает как вход**
(аудит безопасности 2026-07-23, см. `Docs/backlog.md`) — войти в
браузере сразу после установки не получится. Перед первым входом нужно
один раз задать пароль администратору:

```
cd /opt/zhbi-tool
docker compose exec zhbi python3 scripts/reset_password.py admin
```

Скрипт дважды спросит новый пароль (ввод не отображается на экране —
это нормально) и потребует не короче 8 символов, буквы и цифры. После
этого с любого компьютера в сети (Windows-клиента) открыть в браузере
`http://<IP-адрес-сервера>:8000` (или другой порт, если поменяли `PORT`
в `.env`) и войти как `admin` с только что заданным паролем.

Тот же `reset_password.py <логин>` через `docker compose exec` —
универсальный способ восстановить пароль ЛЮБОГО пользователя, если он
утрачен. Требует только доступа к самому серверу (SSH) и запущенного
контейнера — веб-UI для этого не нужен.

### 1.5 Доступ с клиентских компьютеров сети (Windows)

Контейнер публикует порт наружу (`ports:` в `docker-compose.yml`,
значение из `.env`), сервер слушает всю локальную сеть. Осталось:

1. **Узнать IP-адрес сервера**: `ip addr show` (или `hostname -I`) —
   обычно вида `192.168.x.x`.
2. **Разрешить порт в firewall** — если на сервере включён `ufw`:
   ```
   sudo ufw allow 8000/tcp
   ```
   (или другой порт, если меняли `PORT`). Если используется другой
   firewall (`firewalld`, правила ИТ-отдела на уровне сети) — попросить
   открыть входящий TCP-порт с клиентских подсетей.
3. С клиентского компьютера (Windows, обычный браузер — Chrome/Edge/
   Firefox, ничего дополнительно ставить не нужно) открыть
   `http://<IP-адрес-сервера>:8000`.

**Про HTTPS**: сейчас сервер работает по обычному HTTP (без шифрования)
— приемлемо для закрытой локальной сети. Если когда-нибудь появится
HTTPS (например, через reverse-proxy — nginx с TLS-сертификатом) —
раскомментировать `ZHBI_SECURE_COOKIES=1` в `.env` и перезапустить
(`docker compose up -d`), тогда cookie сессии будет помечена флагом
`Secure` (браузер перестанет отправлять её по обычному HTTP — поэтому
включать только вместе с реальным HTTPS, иначе вход перестанет
работать).

### 1.6 Автозапуск при перезагрузке сервера

Ничего дополнительно настраивать не нужно: `docker-compose.yml`
задаёт `restart: unless-stopped` — контейнер сам перезапускается при
сбое и после перезагрузки хоста, пока его явно не остановили
(`docker compose down`). Единственное условие — сама служба Docker
должна подниматься при загрузке сервера (обычно уже так после
установки, проверить/включить явно):
```
sudo systemctl enable docker
```

Полезные команды (вместо прежних `systemctl status/restart zhbi`):
```
docker compose ps          # состояние контейнера
docker compose logs -f     # журнал в реальном времени
docker compose restart     # перезапуск (после обновления .env, например)
```

## 2. Резервное копирование

Вся база — это один файл `data/zhbi.db` на диске хоста (bind-mount —
контейнер тут ни при чём, файл обычный). Резервная копия = копия этого
файла:

```
bash scripts/linux/backup.sh
```
Сохранит копию с меткой даты/времени в `data/backups/` (эта папка не
входит в код/git, только на этом сервере). Скрипт работает независимо
от того, запущен ли контейнер, и не зависит от того, по какому пути
реально лежат данные (относительный `data/` или новый абсолютный
`/opt/zhbi/data`, см. 3.0) — путь внутри скрипта нужно проверить/
поправить под то, что реально используется на сервере. Делать это
стоит:
- перед любым обновлением. **Важно**: старые `update-test.sh`/
  `update-prod.sh` делали бэкап автоматически перед обновлением — новый
  GitLab CI/CD-пайплайн (3.0, `Redeploy_backend_dev`/`_prod` в
  `.gitlab-ci.yml`) этого шага **не делает** (`docker compose down` +
  `docker pull` + `up -d`, без вызова `backup.sh`) — если CI теперь
  единственный способ обновления, бэкап перед деплоем стоит либо
  добавить в сам пайплайн, либо держать только на `cron` ниже (не
  проверено/не обсуждалось с `trubinov@mcy-1.ru`);
- периодически на всякий случай — можно добавить в `cron`, например
  ежедневно в 3 ночи:
  ```
  crontab -e
  # добавить строку:
  0 3 * * * /opt/zhbi-tool/scripts/linux/backup.sh >> /opt/zhbi-tool/data/backups/cron.log 2>&1
  ```

Для более надёжного хранения — копировать `data/backups/*.db` куда-то
за пределы этого же сервера (сетевой диск, другая машина) — локальная
копия не спасёт при поломке самого диска.

## 3. Разработка и обновление через git + GitLab CI/CD

Код версионируется на **двух** удалённых репозиториях с разными
ролями:

- **GitHub** (приватный) — основной репозиторий разработки, простое
  резервное зеркало. Разработка ведётся на Mac разработчика, туда
  пушится обычная работа. **Серверы (тестовый/продуктовый) с ним
  никогда не взаимодействуют** — они во внутренней сети и не должны (и
  зачастую не могут) обращаться наружу.
- **Корпоративный GitLab** — единственный источник кода для тестового
  и продуктового серверов. Пуш туда — отдельный явный шаг, когда
  изменения уже проверены и готовы к раскатке (не при каждом коммите).

### 3.0 Актуальная схема — GitLab CI/CD (с 2026-07-28)

**Настроено коллегой (`trubinov@mcy-1.ru`) напрямую на GitLab, не в
рамках работы с Claude Code** — обнаружено постфактум при попытке
обычного `git push gitlab main` (получили `[rejected] fetch first`,
на GitLab уже был коммит `add ci process`, не известный локально). Раз
это уже реальность на сервере — описываю как есть, по факту содержимого
`.gitlab-ci.yml`/`docker-compose.yml` в репозитории, а не по
пересказу.

Модель веток — **`develop`** (тестовый сервер) и **`production`**
(прод), **не `main` + теги**, как было раньше (старая схема — см. 3.9,
статус неясен). Пуш в `develop`/`production` на GitLab **автоматически**
запускает пайплайн:

```
Mac разработчика (Claude Code)
   │  git commit (ветка main, локально)
   │  git push origin main                  (GitHub, приватный — просто резервная копия)
   │
   │  git push gitlab main:develop          (или main:production — явный выбор, что раскатываем)
   ▼
Корпоративный GitLab — ветка develop / production
   │
   │ GitLab CI/CD пайплайн (.gitlab-ci.yml), 2 стадии:
   │  1) BuildPushImg — docker build -f Dockerfile . , docker push в Harbor registry,
   │     тег образа = $CI_PIPELINE_ID (только на develop/production)
   │  2) Redeploy_backend_dev / _prod — на раннере с тегом dev/prod:
   │     генерирует .env.run из переменной GitLab CI/CD (env_develop/env_production),
   │     docker compose down, docker pull, docker compose up -d
   ▼                                   ▼
Тестовый сервер (ветка develop)   Продуктовый сервер (ветка production)
```

Локальная ветка на Mac по-прежнему одна — `main`; на GitLab она нигде
не разворачивается напрямую, только `develop`/`production`. Пуш —
через refspec, без создания отдельной локальной ветки:
```
git push gitlab main:develop
git push gitlab main:production
```
(Второе — когда изменения проверены на `develop` и готовы в прод; сам
момент/порядок принятия такого решения с коллегой/ИТ не согласовывали
— пока просто технический способ отправить туда код, когда скажете.)

**`docker-compose.yml` теперь другой** (правки коллеги, слиты в `main`
после `git merge gitlab/develop`):
```yaml
services:
  zhbi:
    image: ${CONTAINER_IMAGE}:${CI_PIPELINE_ID}   # было: build: .
    restart: unless-stopped
    ports:
      - "${PORT:-8000}:8000"
    env_file:
      - .env.run                                   # было: .env
    volumes:
      - /opt/zhbi/data:/app/data                    # было: ./data (относительно)
      - /opt/zhbi/Input:/app/Input
      - /opt/zhbi/uploads:/app/uploads
```
Образ **собирается в CI**, не на сервере — сервер только `docker pull`.
Данные — теперь **абсолютные** пути `/opt/zhbi/data`/`Input`/`uploads`,
не относительно папки проекта — то есть где бы ни лежал git-чекаут на
сервере, реальные данные ожидаются строго по этому пути. `.env.run`
генерируется пайплайном из GitLab CI/CD-переменных (`env_develop`/
`env_production`) — не копия `.env.example` вручную, как раньше.

**Не проверено/не подтверждено этой сессией** (честно, без гадания):
- Существуют ли уже на реальных тестовом/продуктовом серверах папки
  `/opt/zhbi/{data,Input,uploads}` с настоящими данными, или пайплайн
  при первом прогоне создаст их пустыми — если раньше данные лежали в
  другом месте (например, при папке проекта не `/opt/zhbi`), нужен
  ручной перенос, иначе первый деплой по этой схеме "потеряет" всё, что
  было накоплено (не физически удалит — данные просто останутся по
  старому пути, а контейнер посмотрит по новому и увидит пустую БД).
- Кто владеет GitLab CI/CD-переменными (`HARBOR_TOKEN`/`HARBOR_USER`/
  `HARBOR_REGISTRY`/`HARBOR_PROJECT`/`env_develop`/`env_production`) и
  раннерами с тегами `docker-builder`/`dev`/`prod` — предположительно
  `trubinov@mcy-1.ru`/ИТ-отдел, не пользователь и не эта сессия.
  Работоспособность самого пайплайна (что раннеры реально подняты и
  умеют задеплоить) вживую не проверялась.
- Нужна ли ещё модель `main`+теги (3.9) хоть для чего-то (например,
  как метка "что считается официальным релизом" отдельно от того, что
  просто лежит в `production`), или полностью вытеснена веткой
  `production`.

Свяжитесь с `trubinov@mcy-1.ru`/ИТ-отделом, чтобы закрыть эти пункты —
без этого раздел 3.0 описывает МЕХАНИКУ (что буквально написано в
`.gitlab-ci.yml`), но не гарантирует, что она уже полностью рабочая на
живых серверах.

### 3.1 Разовая настройка обоих remote (на Mac разработчика)

```
git remote add origin <адрес приватного репозитория на GitHub>
git push -u origin main
git remote add gitlab <адрес репозитория на корпоративном GitLab>
```
Способ аутентификации (SSH-ключ или токен) — свой для каждой площадки,
настраивается один раз (см. документацию GitHub/конкретного GitLab-
сервера).

Репозиторий на GitHub — **приватный**: хотя сами данные заказчика
(чертежи, база) никогда не попадают в git (`.gitignore`), в истории
коммитов и в `Docs/backlog.md`/`CLAUDE.md` могут быть текстовые детали
о структуре чертежей/бизнес-процессе заказчика, которые не
предназначены для публичного доступа.

### 3.2 Повседневная разработка

Работа с кодом идёт на компьютере разработчика, ветка `main`:
```
git add -A
git commit -m "Что и почему изменилось"
git push origin main
```
Это только отправка в GitHub-резерв — **ни тестовый, ни продуктовый
сервер ничего не увидят**, пока изменения явно не отправлены на GitLab
в `develop`/`production` (см. 3.0):

### 3.7 Тестовые чертежи разработчика (`test_data/`)

### 3.9 Старая схема (main + теги релизов) — статус после 3.0 неясен

До того, как обнаружился пайплайн коллеги (3.0), здесь была описана
другая модель: ветка `main` на GitLab + теги `vГГГГ.ММ.ДД`,
`scripts/linux/update-test.sh`/`update-prod.sh` вручную по SSH на

compose ждёт `image:`/`.env.run`/абсолютные тома, не `build:`). Не
переписывал/не удалял скрипты без подтверждения — возможно, они ещё
нужны как резерв (например, если раннеры CI недоступны), возможно,
уже нет. Уточнить у пользователя/`trubinov@mcy-1.ru` перед тем, как
полагаться на них или удалять.

## 4. Обновление копированием файлов — резервный вариант, если git недоступен

Если разработчик присылает обновление архивом — **ни в коем случае не
распаковывать его прямо поверх рабочей папки с заменой всего** (велик
риск случайно затереть `data/`/`Input/`/`uploads/`/`.env`). Порядок
действий:

1. `bash scripts/linux/backup.sh` — резервная копия базы на всякий
   случай.
2. Остановить контейнер: `docker compose down` (данные в `data/` не
   удаляются — это папка хоста, а не часть контейнера).
3. Распаковать новый архив во **временную** папку (не поверх рабочей).
4. Скопировать из временной папки в рабочую **только** эти файлы/папки,
   заменяя старые:
   - `app/`
   - `scripts/` (все, кроме `scripts/linux/`, если в нём есть свои
     локальные правки — обычно можно смело заменять и его тоже)
   - `Docs/`
   - `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `.env.example`
   - `requirements.txt`
   - `CLAUDE.md`
   - `.gitignore`
5. **НЕ копировать и не трогать**: `data/`, `Input/`, `uploads/`,
   `.env`, `test_data/`, `output/` (если есть).
6. `docker compose build` — пересобрать образ на случай изменений в
   зависимостях/Dockerfile.
7. `docker compose up -d`, проверить, что всё открывается и данные
   (старые элементы, статусы) на месте.

## 5. Диагностика типичных проблем

- **`docker: command not found`** — Docker не установлен, см. 1.1.
- **`permission denied` при обращении к Docker** — пользователь ещё не
  в группе `docker` либо не перелогинился после `usermod -aG docker`
  (см. 1.1) — либо временно использовать `sudo docker compose ...`.
- **`docker compose build` падает на установке какой-то библиотеки** —
  обычно означает отсутствие сетевого доступа с сервера до PyPI —
  нужно внутреннее PyPI-зеркало (уточнить у ИТ-отдела) либо временный
  прямой доступ в интернет на время сборки.
- **`docker compose up` ругается, что не находит `.env`** — файл не
  скопирован из шаблона, см. 1.3 (`cp .env.example .env`).
- **С клиентского компьютера страница не открывается**, а на самом
  сервере (`curl http://localhost:8000`) — открывается — см. 1.5
  (`ufw`/firewall, IP-адрес). Также проверить, что клиент и сервер в
  одной сети/VLAN.
- **После обновления пропали чертежи/статусы** — значит на шаге 4
  раздела 4 что-то из `data/`/`Input/`/`uploads/` было случайно
  заменено. Если делали `backup.sh` перед обновлением — восстановить:
  `docker compose down`, скопировать нужный файл из `data/backups/`
  поверх `data/zhbi.db`, `docker compose up -d`.
- **Порт 8000 занят другой программой** — поменять `PORT=` в `.env` и
  сделать `docker compose up -d` заново — в адресе браузера тоже
  указывать новый порт.
- **`git clone`/`git pull` просит авторизацию** — зависит от того, как
  настроен GitLab-сервер (SSH-ключ на сервере, привязанный к аккаунту,
  либо персональный токен доступа вместо пароля) — уточнить у того, кто
  выдаёт доступ к репозиторию.
- **После `update-prod.sh` в `git status` написано "HEAD detached at
  ..."** — это ожидаемо и не ошибка (см. 3.6): продуктовый сервер
  специально закреплён за конкретным релизом, а не следует за `main`.
- **Контейнер запущен, но постоянно перезапускается (`docker compose
  ps` показывает `Restarting`)** — `docker compose logs` покажет
  причину падения приложения (чаще всего — опечатка в `.env` или
  повреждённый `data/zhbi.db`).

## 6. Не проверялось вживую

Все шаги в этом документе основаны на анализе кода проекта (все пути к
данным — относительные, зависимости — стандартные Python-библиотеки с
готовыми manylinux-сборками под linux/amd64, не требующие компилятора)
и на общей практике установки Docker/docker compose на Ubuntu Server —
но реальной установки на настоящем сервере, а также локальной сборки
`docker compose build`/`up` в рамках этой сессии **не производилось**:
на Mac разработчика, где готовился этот раунд правок, не был установлен
ни Docker, ни Homebrew (см. `Docs/backlog.md`). Перед тем, как
полагаться на это в боевой работе — обязательно один раз пройти весь
путь от начала до конца (включая `docker compose build`) на тестовом
сервере/чертеже и убедиться, что ничего не потребовало ручных доработок
сверх того, что здесь описано. (С тех пор Docker Desktop поставлен на
Mac разработчика, и сама сборка образа проверялась вживую много раз в
последующих раундах — см. `Docs/backlog.md` по датам; актуально не
проверенным остаётся именно разворачивание на настоящем Ubuntu-сервере.)

**GitLab CI/CD-пайплайн (раздел 3.0) — тоже не проверен этой сессией**,
описан по факту содержимого `.gitlab-ci.yml`/`docker-compose.yml` в
репозитории, а не по живому прогону: не подтверждено, что раннеры
(`docker-builder`/`dev`/`prod`) подняты и работают, что переменные
`env_develop`/`env_production`/`HARBOR_*` заданы, и что на серверах уже
существуют `/opt/zhbi/{data,Input,uploads}` с реальными данными по
новому пути. Настроил это коллега (`trubinov@mcy-1.ru`) вне этой
сессии — первый живой прогон стоит сверить с ним/ИТ-отделом напрямую.

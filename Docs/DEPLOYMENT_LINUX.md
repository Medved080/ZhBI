# Установка на Ubuntu Server и обновление без потери данных

Практическое руководство для человека, который будет ставить и
поддерживать ЖБИ на сервере под Ubuntu Server LTS (22.04/24.04).
Клиенты (пользователи в браузере) остаются на Windows — этот документ
только про сам сервер. Приложение разворачивается в **Docker**-
контейнере; вспомогательные скрипты — в `scripts/linux/` (запускаются
из терминала, `bash scripts/linux/....sh`).

Технический фон — `Docs/ARCHITECTURE.md`; что система умеет —
`Docs/TZ.md`. Здесь — только "как поставить и не потерять данные".

> **Действующая модель (уточнена 2026-08-02).** Код попадает на серверы
> ТОЛЬКО через git: пуш в `develop` (тестовый) или `production` (прод)
> запускает пайплайн GitLab CI/CD, тот собирает образ, кладёт его в
> реестр Harbor и перезапускает контейнер на сервере — см. раздел 3.
> Вручную код на сервер не выкладывается. По SSH на сервер заходят с
> админскими правами для ЭКСПЛУАТАЦИИ: резервные копии, восстановление,
> журнал, пароли, аварийный откат на предыдущий образ — раздел 4.
>
> Скрипты `scripts/linux/update-test.sh`/`update-prod.sh` (`git pull` +
> `docker compose build` на сервере) **удалены 2026-08-02**: они
> относились к прежней схеме со сборкой на месте и с нынешним
> `docker-compose.yml` физически не работают — в нём нет секции `build:`,
> а `image:` собирается из переменных, которые задаёт только пайплайн.
> История правок — `Docs/backlog.md`.
>
> Разделы ниже написаны по коду проекта и общей практике; **на живом
> Ubuntu-сервере этот путь целиком ни разу не проходился** (см. раздел
> 6). Всё, что помечено «уточнить», проверяется на месте.

## 0. Главное правило на всю статью

**Данные и код — в разных местах, и это нарочно.** Код живёт внутри
Docker-образа и пересобирается/заменяется при каждом обновлении; данные
— обычные папки/файлы на диске сервера, примонтированные в контейнер
как bind-mount volume (`docker-compose.yml`) — пересборка образа их не
касается вообще.

Пути на сервере — АБСОЛЮТНЫЕ: `docker-compose.yml` монтирует
`/opt/zhbi/data`, `/opt/zhbi/Input`, `/opt/zhbi/uploads` в `/app/data`,
`/app/Input`, `/app/uploads` внутри контейнера. (Изначально документ
писался под относительные пути в папке проекта — так осталось только на
машине разработчика.) Сам принцип «данные и код разделены и не трогаются
при обновлении» не изменился, изменилось КУДА смотрит том. **Не
проверено на живом сервере**, что каталоги действительно эти — первое,
что стоит подтвердить по SSH: `ls /opt/zhbi`.

| Папка/файл | Что там | При обновлении |
|---|---|---|
| `data/zhbi.db` (или `/opt/zhbi/data/zhbi.db`) | Вся база: элементы, статусы, история, контракты, пользователи | **НИКОГДА не трогать, не удалять, не перезаписывать** |
| `Input/` (или `/opt/zhbi/Input`) | DXF-чертежи, которые сервер сам подхватывает при каждом запуске | **Не трогать** |
| `uploads/` (или `/opt/zhbi/uploads`) | DXF, загруженные через кнопку в браузере | **Не трогать** |
| `.env.run` (генерируется пайплайном из переменных GitLab, см. 3.0) | Настройки конкретного развёртывания — в git НЕ входит | Не править вручную: пайплайн перезапишет |
| `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `.env.example`, `.gitlab-ci.yml`, `app/`, `scripts/`, `Docs/`, `requirements.txt`, `CLAUDE.md`, `.gitignore` | Код программы | Это и есть то, что заменяется при обновлении |

Пути к данным внутри приложения (`app/db.py`, `app/main.py`,
`app/dxf_import.py`) — относительные (`data/zhbi.db`, `Input/`,
`uploads/` от корня проекта); `docker-compose.yml` монтирует ровно эти
же папки хоста на те же пути внутри контейнера (`/app/data`,
`/app/Input`, `/app/uploads`) — поэтому в коде приложения ничего не
пришлось менять ради Docker. Саму папку проекта на сервере можно
свободно переносить целиком — данные и код внутри неё не перепутаются
при обновлении, пока не путать `data/`/`Input/`/`uploads/` с остальным
при ручном копировании (см. раздел 4).

## 1. Первая установка (один раз)

### 1.1 Установить Docker

(На сервере, где уже поднят GitLab-раннер, Docker почти наверняка стоит —
проверьте `docker --version` прежде чем ставить. `git` самому серверу
приложения не нужен: чекаут делает раннер, код на сервер не клонируется.)

```
sudo apt update
sudo apt install -y ca-certificates curl gnupg git
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo usermod -aG docker "$USER"
```

Последняя команда добавляет текущего пользователя в группу `docker`
(чтобы не писать `sudo` перед каждой командой `docker`/`docker
compose`) — после неё нужно **выйти и зайти в SSH-сессию заново** (или
`newgrp docker`), иначе членство в группе не подхватится.

Проверка:
```
docker --version
docker compose version
```

Если прямой доступ в интернет с сервера закрыт (частая ситуация в
корпоративной сети) — установка потребует внутреннее зеркало
пакетов Docker или предварительно скачанные `.deb`-пакеты; уточнить у
ИТ-отдела.

### 1.2 Подготовить сервер под пайплайн

Код на сервер НЕ клонируется и на сервере НЕ собирается: образ приезжает
из реестра Harbor, разворачивает его раннер GitLab (см. 3.0). На самом
сервере должно быть заведено:

1. **Каталоги данных** — те, что `docker-compose.yml` монтирует в
   контейнер. Пустые: базу и служебные папки приложение создаст само при
   первом запуске.
   ```
   sudo mkdir -p /opt/zhbi/data /opt/zhbi/Input /opt/zhbi/uploads
   ```
   Владелец и права — так, чтобы в них мог писать процесс контейнера
   (`uid`, под которым работает `Dockerfile`); уточнить на месте, если
   приложение стартует с ошибкой доступа.
2. **GitLab-раннер** с тегом `dev` (тестовый сервер) или `prod`
   (продуктовый) — именно по этим тегам `.gitlab-ci.yml` выбирает, куда
   разворачивать. Раннер должен уметь запускать `docker`/`docker-compose`
   на этом хосте.
3. **Доступ к реестру Harbor** — переменные `HARBOR_REGISTRY`,
   `HARBOR_PROJECT`, `HARBOR_USER`, `HARBOR_TOKEN` в настройках проекта
   на GitLab (не в репозитории).
4. **Переменные окружения приложения** — `env_develop` и
   `env_production` в настройках проекта на GitLab; пайплайн
   разворачивает их в файл `.env.run` рядом с `docker-compose.yml`
   (`echo "${env_develop}" | tr ' ' '\n' > .env.run`). Обратите внимание
   на разделитель: переменные в GitLab пишутся ЧЕРЕЗ ПРОБЕЛ, пробел
   внутри значения сломает файл.

Заведение раннера, Harbor и переменных — на стороне DevOps.

### 1.3 Первый запуск

Первый запуск — это обычный деплой: пуш в `develop` (или `production`).
Пайплайн соберёт образ, положит в Harbor и поднимет контейнер.

Проверка после того, как пайплайн отработал (по SSH на сервере):
```
docker ps                     # контейнер запущен, не Restarting
docker logs <имя-контейнера>  # журнал старта
```
В журнале при первом старте будут строка `[startup] структурных
изменений схемы применено: N` (миграции применяются автоматически) и
предупреждение `[startup] ВНИМАНИЕ: без пароля (вход запрещён, пока не
задан): admin` — это ожидаемо, читайте дальше.

### 1.4 Первый пароль администратора

Пустой пароль у свежесозданного `admin` **не работает как вход**
(аудит безопасности 2026-07-23, см. `Docs/backlog.md`) — войти в
браузере сразу после установки не получится. Перед первым входом нужно
один раз задать пароль администратору:

```
docker ps                     # узнать имя контейнера (в нём есть "zhbi")
docker exec -it <имя-контейнера> python3 scripts/reset_password.py admin
```
(`docker exec`, а не `docker compose exec`: у администратора по SSH может
не быть под рукой `docker-compose.yml` — он лежит в рабочей папке
раннера, а не в постоянном чекауте.)

Скрипт дважды спросит новый пароль (ввод не отображается на экране —
это нормально) и потребует не короче 8 символов, буквы и цифры. После
этого с любого компьютера в сети (Windows-клиента) открыть в браузере
`http://<IP-адрес-сервера>:8000` (или другой порт, если задан `PORT` в
переменных GitLab, см. 1.2) и войти как `admin` с только что заданным
паролем.

Тот же `reset_password.py <логин>` через `docker exec` —
универсальный способ восстановить пароль ЛЮБОГО пользователя, если он
утрачен. Требует только доступа к самому серверу (SSH) и запущенного
контейнера — веб-UI для этого не нужен.

### 1.5 Доступ с клиентских компьютеров сети (Windows)

Контейнер публикует порт наружу (`ports:` в `docker-compose.yml`,
значение из `PORT`, по умолчанию 8000), сервер слушает всю локальную
сеть. Осталось:

1. **Узнать IP-адрес сервера**: `ip addr show` (или `hostname -I`) —
   обычно вида `192.168.x.x`.
2. **Разрешить порт в firewall** — если на сервере включён `ufw`:
   ```
   sudo ufw allow 8000/tcp
   ```
   (или другой порт, если меняли `PORT`). Если используется другой
   firewall (`firewalld`, правила ИТ-отдела на уровне сети) — попросить
   открыть входящий TCP-порт с клиентских подсетей.
3. С клиентского компьютера (Windows, обычный браузер — Chrome/Edge/
   Firefox, ничего дополнительно ставить не нужно) открыть
   `http://<IP-адрес-сервера>:8000`.

**Про HTTPS**: сейчас сервер работает по обычному HTTP (без шифрования)
— приемлемо для закрытой локальной сети. Если когда-нибудь появится
HTTPS (например, через reverse-proxy — nginx с TLS-сертификатом) —
добавить `ZHBI_SECURE_COOKIES=1` в переменную `env_develop`/
`env_production` на GitLab и перезапустить пайплайн, тогда cookie сессии
будет помечена флагом
`Secure` (браузер перестанет отправлять её по обычному HTTP — поэтому
включать только вместе с реальным HTTPS, иначе вход перестанет
работать).

### 1.5а Доменная авторизация (если её будут включать)

Вход по доменной учётной записи (см. `Docs/TZ.md` §7) настраивается в
интерфейсе: «Действия → Администрирование → Доменная авторизация», там же
кнопка «Проверить» — пробная привязка, не сохраняя настройку. От сервера
требуется только одно, чего нельзя сделать из интерфейса: **сетевой доступ
от контейнера к контроллеру домена** — исходящий TCP на порт `389`
(обычный/STARTTLS) или `636` (LDAPS). Проверить с сервера:

```
docker exec <имя-контейнера> python3 -c "import socket;socket.create_connection(('dc01.corp.local',389),5);print('доступен')"
```

Если имя контроллера не резолвится изнутри контейнера — указывать в
настройке IP-адрес либо добавить контроллер в `extra_hosts`
`docker-compose.yml`. Библиотека `ldap3` входит в образ
(`requirements.txt`); если форма пишет, что её нет, — образ старый, нужен
свежий деплой.

**Важно перед включением**: хотя бы у одного администратора сервиса должен
остаться пароль сервиса. Иначе неполадка домена запирает всех, и
восстанавливаться придётся через `docker exec … scripts/reset_password.py
<логин>` (он же возвращает учётную запись с домена на пароль сервиса).

### 1.6 Автозапуск при перезагрузке сервера

Ничего дополнительно настраивать не нужно: `docker-compose.yml`
задаёт `restart: unless-stopped` — контейнер сам перезапускается при
сбое и после перезагрузки хоста, пока его явно не остановили
(`docker compose down`). Единственное условие — сама служба Docker
должна подниматься при загрузке сервера (обычно уже так после
установки, проверить/включить явно):
```
sudo systemctl enable docker
```

Полезные команды по SSH (без `docker-compose.yml` под рукой — по имени
контейнера из `docker ps`):
```
docker ps                        # состояние контейнера
docker logs -f <имя-контейнера>  # журнал в реальном времени
docker restart <имя-контейнера>  # перезапуск
```

## 2. Резервное копирование

Вся база — это один файл `zhbi.db` на диске хоста (bind-mount, контейнер
тут ни при чём, файл обычный). Резервная копия = копия этого файла:

```
bash /путь/к/scripts/linux/backup.sh
```

Скрипт ищет базу в таком порядке: явный `ZHBI_DATA_DIR` ->
`/opt/zhbi/data` (сервер) -> `data/` рядом с репозиторием (машина
разработчика), и печатает, какую именно базу скопировал. Копия ложится в
`backups/` рядом с базой, с меткой даты и времени. Работает независимо от
того, запущен ли контейнер.

**Скрипт лежит в репозитории, а на сервере постоянного чекаута может не
быть** — положите его на сервер один раз в удобное место (например
`/opt/zhbi/backup.sh`) или скачайте из GitLab. Обновлять его практически
не приходится.

**Пайплайн бэкап НЕ делает.** `Redeploy_backend_dev`/`_prod` в
`.gitlab-ci.yml` выполняют `docker-compose down` + `pull` + `up -d` и
только. Прежние `update-*.sh` вызывали `backup.sh` сами, теперь этого
шага нет ни у кого — значит резервные копии держатся на `cron` (и на
вашей привычке сделать копию перед рискованным деплоем):

```
crontab -e
# ежедневно в 3 ночи:
0 3 * * * /opt/zhbi/backup.sh >> /opt/zhbi/data/backups/cron.log 2>&1
```

Стоит обсудить с DevOps, не добавить ли бэкап отдельным шагом в пайплайн
перед `down` — тогда копия будет ровно перед каждым обновлением, а не
раз в сутки.

**Особенно важно перед обновлением, которое несёт миграцию схемы.**
Приложение применяет миграции на старте автоматически, отката у них нет;
единственный способ вернуться — восстановить файл базы из копии (см. 4.2).

Для надёжности — копировать `backups/*.db` за пределы этого сервера
(сетевой диск, другая машина): локальная копия не спасёт при поломке
диска.

## 3. Разработка и обновление через git + GitLab CI/CD

Код версионируется на **двух** удалённых репозиториях с разными
ролями:

- **GitHub** (приватный) — основной репозиторий разработки, простое
  резервное зеркало. Разработка ведётся на Mac разработчика, туда
  пушится обычная работа. **Серверы (тестовый/продуктовый) с ним
  никогда не взаимодействуют** — они во внутренней сети и не должны (и
  зачастую не могут) обращаться наружу.
- **Корпоративный GitLab** — единственный источник кода для тестового
  и продуктового серверов. Пуш туда — отдельный явный шаг, когда
  изменения уже проверены и готовы к раскатке (не при каждом коммите).

### 3.0 Актуальная схема — GitLab CI/CD (с 2026-07-28)

**Настроено DevOps-инженерами корпоративного контура (`trubinov@mcy-1.ru`)
напрямую на GitLab, не в
рамках работы с Claude Code** — обнаружено постфактум при попытке
обычного `git push gitlab main` (получили `[rejected] fetch first`,
на GitLab уже был коммит `add ci process`, не известный локально). Раз
это уже реальность на сервере — описываю как есть, по факту содержимого
`.gitlab-ci.yml`/`docker-compose.yml` в репозитории, а не по
пересказу.

Модель веток — **`develop`** (тестовый сервер) и **`production`**
(прод), **не `main` + теги**, как было раньше (старая схема — см. 3.9,
статус неясен). Пуш в `develop`/`production` на GitLab **автоматически**
запускает пайплайн:

```
Mac разработчика (Claude Code)
   │  git commit (ветка main, локально)
   │  git push origin main                  (GitHub, приватный — просто резервная копия)
   │
   │  git push gitlab main:develop          (или main:production — явный выбор, что раскатываем)
   ▼
Корпоративный GitLab — ветка develop / production
   │
   │ GitLab CI/CD пайплайн (.gitlab-ci.yml), 2 стадии:
   │  1) BuildPushImg — docker build -f Dockerfile . , docker push в Harbor registry,
   │     тег образа = $CI_PIPELINE_ID (только на develop/production)
   │  2) Redeploy_backend_dev / _prod — на раннере с тегом dev/prod:
   │     генерирует .env.run из переменной GitLab CI/CD (env_develop/env_production),
   │     docker compose down, docker pull, docker compose up -d
   ▼                                   ▼
Тестовый сервер (ветка develop)   Продуктовый сервер (ветка production)
```

### 3.3 Обновление ничего не требует от человека на сервере (с 2026-08-04)

Требование пользователя дословно: «давай деплоить так, чтобы не надо было
подключаться к серверу; добавляй все обработки в само обновление и пусть они
сами выполняются при старте после обновления». Что происходит при первом
старте новой версии, по порядку:

1. **Копия базы** — автоматически, ДО всего остального
   (`release_tasks.backup_before_update`), с пометкой «служебная — перед
   обновлением версии». Снимается только когда версия кода отличается от
   версии базы: рестарт при падении и `docker compose up` копий не плодят.
   Она и есть путь назад, если обновление пошло не так, — восстановление
   доступно из интерфейса, по SSH лезть не нужно.
2. **Миграции схемы** (`app/db.py`) — структура: колонки, индексы, таблицы.
   Непроходимая миграция РОНЯЕТ старт с понятной ошибкой в логе; это
   осознанно (см. `Docs/DECISIONS.md`).
3. **Обработки релиза** (`app/release_tasks.py`) — то, что новая версия
   делает с уже накопленными данными. Упавшая обработка старт НЕ роняет:
   сервис работает, в «Что нового» висит красная плашка с причиной и кнопкой
   «Повторить» для администратора сервиса.
4. **Версия базы догоняет версию кода** — только когда все обработки
   выполнены успешно. Именно это и означает «обновление завершено» в
   интерфейсе.

Версия одна на всё — верхняя запись `app/changelog.py`; в базе она лежит в
`app_settings.db_release_version`, выполненные обработки — в таблице
`release_tasks`.

**Правило релиза: только ДОБАВЛЯТЬ.** Новая версия заводит поля и таблицы и
заполняет их из старых, но старое в том же релизе не удаляет — пока данные не
сконвертированы на всех площадках и не проверены, удалять нечего. Уборка
отживших структур — отдельный вид обработок (`KIND_CLEANUP`): при старте не
выполняется никогда, ждёт кнопки администратора и снимает перед собой копию
базы. Так время от времени и подчищаем накопившееся.

**Проверка ДО деплоя — на копии боевой базы.** `scripts/dry_run_migration.py`
показывает оба шага сразу: что сделает миграция схемы и что сделает каждая
обработка релиза с реальными данными (сколько записей тронет, чем
закончится, догнала ли версия базы версию кода). Обработки прогоняются
дважды: первый раз как на сервере, второй — принудительно все, чтобы
проверить идемпотентность; повтор, изменивший строки, попадает в итог как
проблема. Зависимостей у скрипта нет, он запускается системным python3 прямо
на сервере и не трогает переданный файл:

```
python3 scripts/dry_run_migration.py /opt/zhbi/data/backups/zhbi_<дата>.db
```

Что осталось за SSH: аварийный откат образа, восстановление базы из копии
файлом, возврат пароля администратору и диагностика (раздел 4). Это
аварийные случаи, а не часть обновления.

## 4. Действия по SSH на сервере

Код сюда не выкладывают (это делает пайплайн, раздел 3). По SSH с
админскими правами делают эксплуатационные вещи.

### 4.1 Аварийный откат на предыдущий образ

Самый быстрый способ вернуть работоспособность, если новый деплой
сломал сервис. Образы в Harbor помечены НОМЕРОМ ПАЙПЛАЙНА
(`CI_PIPELINE_ID`), не версией — предыдущий номер виден в списке
пайплайнов GitLab или в `docker images`.

```
docker ps                       # какой образ и тег сейчас запущен
docker images | grep zhbi       # какие теги уже скачаны на этот сервер
```

Дальше — поднять контейнер с прежним тегом. Если рядом есть
`docker-compose.yml` и `.env.run` (рабочая папка раннера):
```
CI_PIPELINE_ID=<прежний-номер> docker-compose up -d
```
Если нет — запустить образ напрямую, повторив тома и порт из compose:
```
docker run -d --restart unless-stopped -p 8000:8000 \
  --env-file .env.run \
  -v /opt/zhbi/data:/app/data \
  -v /opt/zhbi/Input:/app/Input \
  -v /opt/zhbi/uploads:/app/uploads \
  <образ>:<прежний-номер>
```

**Важно про откат кода и базу.** Откат образа НЕ откатывает миграции
схемы: они применились при старте новой версии и остались. Если
поломка именно в миграции, одного отката образа мало — нужно ещё
восстановить базу из копии (4.2). Поэтому копия перед деплоем с
миграцией и нужна.

### 4.2 Восстановление базы из резервной копии

```
docker stop <имя-контейнера>
cp /opt/zhbi/data/backups/zhbi_ГГГГ-ММ-ДД_ЧЧ-ММ-СС.db /opt/zhbi/data/zhbi.db
docker start <имя-контейнера>
```
Останавливать контейнер обязательно: подменять файл базы под работающим
приложением нельзя.

### 4.3 Прочее

- Журнал: `docker logs -f <имя-контейнера>`.
- Пароль любого пользователя: `docker exec -it <имя-контейнера> python3
  scripts/reset_password.py <логин>` (см. 1.4).
- Место на диске: `du -sh /opt/zhbi/*`, старые образы — `docker image
  prune`.
- Резервная копия: раздел 2.

## 5. Диагностика типичных проблем

- **`docker: command not found`** — Docker не установлен, см. 1.1.
- **`permission denied` при обращении к Docker** — пользователь ещё не
  в группе `docker` либо не перелогинился после `usermod -aG docker`
  (см. 1.1) — либо временно использовать `sudo docker compose ...`.
- **Пайплайн падает на стадии `build-img`, на установке библиотеки** —
  у раннера-сборщика нет доступа до PyPI: нужно внутреннее зеркало
  (уточнить у DevOps). Сборка идёт НА РАННЕРЕ, а не на сервере
  приложения — искать проблему там же.
- **Пайплайн прошёл, а контейнер не поднялся** — смотреть `docker logs`
  на сервере. Частая причина — пустой или битый `.env.run`: пайплайн
  делает его из переменной `env_develop`/`env_production`, разбивая по
  ПРОБЕЛАМ, и пробел внутри значения ломает файл (см. 1.2).
- **С клиентского компьютера страница не открывается**, а на самом
  сервере (`curl http://localhost:8000`) — открывается — см. 1.5
  (`ufw`/firewall, IP-адрес). Также проверить, что клиент и сервер в
  одной сети/VLAN.
- **После обновления пропали чертежи/статусы** — проверить, что тома
  в `docker-compose.yml` указывают на те же `/opt/zhbi/*`, что и
  раньше: контейнер с другим путём тома стартует чисто и создаст
  ПУСТУЮ базу, выглядит это как «всё пропало». Восстановление — 4.2.
- **Порт 8000 занят другой программой** — поменять `PORT` в переменной
  `env_develop`/`env_production` на GitLab и перезапустить пайплайн; в
  адресе браузера тоже указывать новый порт.
- **`docker login` в Harbor не проходит** — токен в переменных
  проекта GitLab истёк или неверен (`HARBOR_USER`/`HARBOR_TOKEN`),
  уточнить у DevOps.
- **Контейнер запущен, но постоянно перезапускается (`docker ps`
  показывает `Restarting`)** — `docker logs` покажет причину падения
  (чаще всего — битый `.env.run` или повреждённый `zhbi.db`).
- **Приложение стартует, но пишет ошибку доступа к базе** — права на
  `/opt/zhbi/data` не позволяют писать процессу контейнера, см. 1.2.

## 1. Результат и границы задачи

В карточке проекта появляется раздел «Внешние 3D-модели». Пользователь загружает Ground.fbx, видит предпросмотр поверх проекта, сохраняет слой «Благоустройство», включает его в 3D ЖБИ и МФР. Если привязка не подтверждена, система ставит нижнюю точку модели на абсолютную отметку 0 и совмещает центры горизонтальных габаритов модели и проекта. В настройках можно перемещать весь слой в плоскости, мышью и численно; положение сохраняется на сервере и переживает обновление страницы.

Это визуальный контекст стройки. Меши FBX не становятся элементами учёта, блоками, зонами, позициями поставки или строками отчётов. Не переделывать существующие конвейеры DXF/Revit/PDF. Не создавать новый общий просмотрщик вместо двух существующих. Не реализовывать импорт второго файла с фасадами в этой итерации, но структура хранения должна допускать несколько внешних моделей проекта.

Принятые проектные решения, которые нельзя оставлять на усмотрение исполнителя:

- Единица хранения и расчёта приложения — мм. В полях интерфейса — метры, преобразование на границе UI.
- «Уровень 0» здесь означает **нижнюю точку полного габарита после корректного применения всех трансформаций**. Геометрия не сплющивается, рельеф сохраняется. Это технический способ первоначальной установки, а не распознавание геодезического нуля покрытия.
- Автоцентрирование выполняется при первоначальном размещении и по отдельной кнопке. Фильтр, повторный вход, новый этаж и изменение здания не пересчитывают сохранённое положение.
- Перемещение в первой версии только X/Y проекта. Поворот, вертикальный сдвиг и ручное изменение масштаба не входят в основной UI.
- Модель принадлежит проекту, не отдельному этажу или текущему отбору. Видимость можно хранить локально у пользователя; трансформация общая для проекта.
- Нет достоверной связи систем координат — режим `unreferenced`. Ненулевые координаты, имя файла, похожие габариты и адрес проекта не являются доказательством привязки.
- Автоматическая геопривязка произвольного FBX и перевод широты/долготы карты в координаты чертежа отложены. Не придумывать эвристику «большие координаты = геопривязка».

## 4. Зависимость и обязательный первый технический этап

Выбран прямой браузерный FBXLoader той же версии r160. Для файла около 11 МБ и трёх мешей не вводить серверный Blender, конвертацию в GLB, отдельный worker-сервис или очередь заданий. Сначала измерить реальный parse/render; оптимизацию основывать на измерениях.

Официальный код: [FBXLoader r160](https://raw.githubusercontent.com/mrdoob/three.js/r160/examples/jsm/loaders/FBXLoader.js).
Он импортирует `fflate.module.js` и `NURBSCurve.js`; проверить также транзитивный `NURBSUtils.js`. Все файлы должны быть одной версии с ядром, локальными, с лицензиями и перечнем источников. Использовать относительные импорты, сохраняя существующий bare specifier `three`; import map по возможности не менять.

**Организационное ограничение:** `CLAUDE.md`, раздел «Стоячие инструкции»: «Любой НОВЫЙ сторонний код вендорится только с явного подтверждения». Эта задача пока только проектирует разработку и ничего не вендорит. Исполнитель сначала готовит точный список файлов/версий/лицензий и запрашивает подтверждение, если в последующей сессии его ещё не будет. До этого может реализовать и проверить собственную математику, серверные контракты и синтетический UI. Не заменять загрузчик самописным полным FBX-парсером для обхода этого требования.

У r160 единица доступна через `sceneGraph.userData.unitScaleFactor`. Это метаданные, а не уже применённый переход в мм. Коэффициент `mmPerUnit = unitScaleFactor * 10`, исходя из сантиметров в FBX: [Autodesk FbxSystemUnit](https://help.autodesk.com/cloudhelp/2018/ENU/FBX-Developer-Help/cpp_ref/class_fbx_system_unit.html).

FBXLoader не предоставляет в публичном результате полный контракт осей. До интеграции реализовать ограниченный reader метаданных **GlobalSettings** бинарного FBX 7400 (не геометрии): строгие границы offset/length, ограниченная глубина, пропуск массивов без распаковки. Он возвращает Up/Front/CoordAxis и знаки; неизвестная комбинация отклоняется понятным сообщением, а не угадывается. Первая поддерживаемая комбинация — именно профиль данного файла. ASCII, другие версии и комбинации осей пока явно не поддерживаются. Это осознанно узкий первый импорт, а не обещание поддержки любого FBX.

Проверка этапа: на данном файле получены три видимых меша, четыре завершившие загрузку текстуры, конечный bbox ожидаемых размеров и корректная ориентация. Наличие объекта Group ещё не означает, что изображения загрузились. Ошибка текстуры не должна оставлять вечный индикатор.

## 5. Координатный контракт — реализовать буквально

Имеются четыре пространства:

1. `F`: результат FBXLoader с применением полной иерархии `matrixWorld`, в единицах файла.
2. `C`: канонические координаты модели в мм, X/Y — план, Z — вверх.
3. `P`: абсолютные координаты проекта, мм, X/Y — план, Z — отметка.
4. `V`: координаты конкретного просмотрщика.

Для подтверждённого профиля этого файла преобразование после FBX matrixWorld:

```text
C = 1000 * (F.x, -F.z, F.y)
```

Это преобразование Y-up → Z-up с сохранением ориентации. **Не применять ещё один поворот −90° к сырой геометрии:** FBXLoader уже учитывает локальный поворот моделей. Не обнулять transform каждого меша: так потеряются взаимные положения.

После `updateMatrixWorld(true)` вычислить bbox C по всем отображаемым мешам, включая растительность и элементы благоустройства. Для точного результата пройти реальные позиции с матрицами, а не только поворачивать уже собранный bbox. Свет/камеры из FBX удалить из импортируемого контекста. Сохранить числа bbox в double до формирования Float32-буферов.

```text
source_anchor = ((C.minX+C.maxX)/2, (C.minY+C.maxY)/2, C.minZ)
L = C - source_anchor
project_anchor = ((P.minX+P.maxX)/2, (P.minY+P.maxY)/2, 0)
Ppoint = L + project_anchor + (offset_x_mm, offset_y_mm, 0)
```

Для уменьшения потерь точности не запекать в Float32 огромную абсолютную трансляцию, чтобы затем вычитать её обратно. Вычитать anchor в составленной double-матрице перед записью новых локальных вершин. Исходный Group оставить доступным только как источник; не накапливать повторные нормализации на одних буферах.

Адаптер ЖБИ:

```text
V = (Ppoint.x, Ppoint.z, -Ppoint.y)
```

Адаптер МФР:

```text
V = (Ppoint.x - data.origin[0], Ppoint.y - data.origin[1], Ppoint.z - mfr3d.низ)
```

В МФР земля при выборе верхнего этажа закономерно окажется ниже локального нуля камеры. **Не поднимать её на текущий этаж**. На смену `origin` или `низ` менять только адаптер V, не сохранённые P/anchor/offset.

Нормали преобразовывать normal matrix, сохранить UV, indices и material groups. Для выбранных преобразований determinant положительный; если позже добавится отражение, нужна отдельная проверка winding/culling, а не глобальный DoubleSide для сокрытия ошибки.

Обязательные численные примеры для чистых тестов:

- bbox источника C: X=1000…5000, Y=2000…8000, Z=−500…2500 → source_anchor=(3000,5000,−500).
- bbox проекта: X=100000…140000, Y=200000…260000 → project_anchor=(120000,230000,0).
- Нижний угол C=(1000,2000,−500) → P=(118000,227000,0).
- offset=(1500,−2000) → P=(119500,225000,0).
- ЖБИ → (119500,0,−225000).
- МФР origin=(110000,220000), низ=12000 → (9500,5000,−12000).
- Повторная загрузка и смена фильтра сохраняют P до точности 0.01 мм на синтетике.

## 6. Центр проекта: стабильный источник, не текущая камера

Новый `get_project_bounds(conn, project_id)` работает с исходными данными всех объектов проекта, без текущих фильтров этажей, статусов, категорий или видимости. Возвращает `{bounds_mm, source_revision, object_ids}` только пользователю с правами настройки проекта. Обычным зрителям отдавать уже сохранённую трансформацию слоя, не подробности закрытых объектов.

Источники: актуальные (`is_current=1`) контуры элементов ЖБИ; абсолютные контуры актуальных `revit_elements`; действительная геометрия блоков МФР, включая проекты с PDF-фасадами без элементов. Для ЖБИ точка x/y допустима как fallback у элемента без контура. Для МФР использовать исходный абсолютный контур, а не уже смещённый `plan_data`. Переиспользовать вычисление действительных блоков, не включать ошибки/пустые блоки.

Объединить горизонтальные bbox. Исключить внешние модели, подписи, тени, площадку сцены, временные объекты. Дегенеративный конечный bbox (линия/точка) допускает центр; полностью пустой — `bounds_mm=null`.

В существующем проекте не установлена универсальная трансформация между независимыми локальными координатами объектов. Поэтому объединение означает именно объединение **существующих абсолютных координат чертежей**. Не объявлять его геодезически верным. В предпросмотре показать использованные объекты и габарит. Если у конкретного проекта объекты в несовместимых системах, это отдельная задача согласования координат; не исправлять скрытым автоцентрированием каждого объекта. Первый сквозной прогон делать на проекте с одним объектом либо с проверенной общей сеткой.

Если проект пуст: anchor=(0,0,0), сообщение «В проекте пока нет геометрии. Модель размещена в начале координат». После добавления геометрии не перемещать слой автоматически. Кнопка «Сцентрировать с проектом» пересчитывает anchor по новому полному bbox и обнуляет offsets, но сохраняет исходный source_anchor.

## 7. Хранение и API

Новая таблица `project_external_models`, одна строка на сохранённый слой. Не расширять `elements` и не превращать обычное вложение в модель неявно.

Поля и смысл:

```text
id INTEGER PK
project_id INTEGER NOT NULL REFERENCES projects(id)
name TEXT NOT NULL                          # «Благоустройство»
kind TEXT NOT NULL                         # сейчас ground, позднее facade
original_name TEXT NOT NULL
stored_name TEXT NOT NULL UNIQUE           # UUID.fbx; пользователь его не задаёт
sha256 TEXT NOT NULL
size_bytes INTEGER NOT NULL
format_version INTEGER NOT NULL            # сейчас 7400
placement_mode TEXT NOT NULL               # сейчас unreferenced
metadata_json TEXT NOT NULL                # версия схемы=1; единицы, оси, bbox, диагностика
source_anchor_x_mm/y_mm/z_mm REAL NOT NULL
project_anchor_x_mm/y_mm REAL NOT NULL      # Z не хранить: в этой версии всегда 0
centering_revision TEXT                     # ревизия/хэш исходного bbox проекта
offset_x_mm / offset_y_mm REAL NOT NULL DEFAULT 0
revision INTEGER NOT NULL DEFAULT 1
created_by INTEGER                         # существующая политика FK пользователей
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
```

Имена полей развернуть в отдельные колонки, `x/y/z` здесь сокращение описания. В JSON не хранить вершины или картинки. Не хранить локальные файловые пути клиента. На диске: `uploads/external_models/<uuid>.fbx`; внутри файла уже есть текстуры.

Предлагаемый контракт:

| Метод | URL | Действие |
| --- | --- | --- |
| GET | `/projects/{project_id}/external-models` | Список метаданных доступного проекта |
| GET | `/projects/{project_id}/external-models/bounds` | Полный bbox для настройки; права записи проекта |
| POST | `/projects/{project_id}/external-models` | Multipart: файл + JSON параметров предпросмотра; сохранение после успешного разбора в браузере |
| GET | `/projects/{project_id}/external-models/{id}/content` | FBX через проверку прав, не static URL |
| PATCH | `/projects/{project_id}/external-models/{id}` | Абсолютные offsets/name + expected_revision |
| POST | `/projects/{project_id}/external-models/{id}/recenter` | expected_revision; сервер считает новый anchor, offsets=0 |
| DELETE | `/projects/{project_id}/external-models/{id}` | Удаление по правам настройки проекта |

```
PATCH body example:
{"offset_x_mm":1500,"offset_y_mm":-2000,"expected_revision":3}
```

Перед POST клиент разбирает локальный файл, дожидается текстур, показывает предварительный результат. Клиент передаёт рассчитанные source bbox/anchor как метаданные отображения; сервер проверяет структуру, конечность, порядок min/max и допустимые диапазоны. **Это не серверная экспертиза геометрии:** семантическая корректность клиентского bbox не доказана. SHA/размер/version сервер считает сам, оси/единицы подтверждает ограниченным чтением GlobalSettings. При расхождении отвергает запрос. project_anchor сервер считает сам, не доверяет присланному полному bbox проекта. Передача `centering_revision` защищает от сохранения относительно уже изменившегося проекта: 409 и повторный предпросмотр.

Поддерживать одно сохранение за раз в UI. Ошибка POST оставляет локальный предпросмотр для повтора. После успеха отобразить серверные параметры. Не возвращать «успешно загружено» до завершения операции.

PATCH атомарно: `UPDATE ... SET revision=revision+1 ... WHERE id=? AND project_id=? AND revision=?`; отсутствие обновления из-за версии → 409. Никаких read-then-unconditional-update. Устаревший ответ не заменяет более свежую локальную трансформацию.

Права: запись — существующее `require_service_feature('projects','write')`; чтение — системный администратор либо доступ хотя бы к одному объекту проекта, по действующей политике `/projects`. После этого сверить принадлежность id проекту. Файл слоя является общим контекстом доступного проекта; если требуется изоляция частей контекста по объектам, это отдельная модель доступа, не молчаливое расширение. Защита content должна быть такой же, как списка. Не наследовать ограничения чтения проектных attachments бездумно.

Ограничения первой версии: файл ≤50 MiB, только .fbx с настоящим binary header/version7400, имя ≤255 символов, JSON ограничен по размеру, числа строго finite (без NaN/Infinity/строк), offsets по модулю ≤1e9 мм. Не принимать path, owner, stored_name, arbitrary matrix или creator от клиента. Метаданные клиента не использовать для путей и SQL.

Файл писать порциями во временное имя в том же каталоге, вычислять hash по потоку, после проверки делать atomic rename и транзакцию БД с компенсацией файловой операции при ошибке. При падении между rename/commit возможен orphan; опишите и реализуйте безопасную уборку старых temp/orphan при регламентном обслуживании без удаления файлов, упомянутых БД. DELETE сначала фиксирует удаление строки, затем убирает файл; сбой уборки логируется и подхватывается тем же механизмом. Не оставлять строку, ссылающуюся на файл, который уже удалён при откате SQL.

Полный экспорт/восстановление через db_transfer должен включать новый каталог (uploads уже включается, это проверить тестом). Обычный backup SQLite не объявлять полной копией моделей. Удаление проекта с внешними моделями блокировать понятным сообщением в духе существующего удаления только пустого проекта; каскадное молчаливое удаление не вводить.

## 8. UI и перемещение мышью

В разделе проекта: список моделей, название, файл, размеры в метрах, статус «Привязка не подтверждена», кнопки загрузки/настройки/удаления. На первой загрузке название по умолчанию «Благоустройство». Нет выбора второго файла автоматически.

Настройки: изолированный черновик сохранённых параметров; вид сверху на проект и контекст, X и Y в метрах (подписи именно координатные, не «вправо/вперёд» камеры), шаг 0.1 м, кнопки «Сцентрировать с проектом», «Сохранить», «Отмена». Величины допускают отрицательный знак; русскую запятую нормализовать на границе поля. «Отмена» возвращает сохранённое состояние даже после drag и recenter. До сохранения recenter в диалоге рассчитывать через GET bounds локально; POST recenter предназначен для непосредственной команды вне черновика либо заменить сохранением с явным recenter intent. Не вызывать записывающий endpoint при обычном предпросмотре.

Drag реализовать собственным небольшим контроллером pointer events, не добавляя ещё TransformControls:

1. Явный режим «Переместить» в настройках. Обычная навигация вне него не меняется.
2. pointerdown на модели: запомнить start offsets и пересечение луча с горизонтальной плоскостью уровня 0 в сцене; захватить pointer, временно отключить OrbitControls.
3. pointermove: пересечь новую позицию луча с той же плоскостью; получить delta в координатах проекта обратным адаптером. Применить к стартовым offsets, а не складывать погрешности каждого события.
4. Меняется только transform группы/числовые поля; не парсить FBX, не пересобирать геометрию, не отправлять PATCH на каждый кадр. Перерисовка максимум один раз на rAF.
5. Если луч параллелен плоскости, пропустить движение без NaN. Вид сверху в настройках обеспечивает нормальный рабочий сценарий.
6. pointerup завершает черновой drag; pointercancel/потеря захвата/закрытие окна/смена проекта освобождают pointer, восстанавливают controls. Escape во время drag возвращает его стартовое положение.
7. Событие drag не доходит до выбора элементов. Порог движения отделяет drag от клика; обычный клик вне настроек работает как прежде.

В рабочих 3D-сценах внешний слой по умолчанию видим после сохранения; переключатель «Благоустройство» не влияет на серверные координаты и фильтры модели. Смена проекта очищает старый слой немедленно.

## 9. Интеграция, материалы и жизненный цикл

Контроллер слоя получает зависимости явно: THREE, scene, camera/controls при необходимости, requestRender, projectId, адаптер координат и функция получения актуального view origin. Не читает state из глобального window.

Группа внешней модели отдельна от слитого буфера ЖБИ и категорий МФР. Она не попадает в массивы picking элементов/блоков, подсветку статусов и подсчёт элементов. В настройках её raycast выполняется отдельно.

Сохранить исходные материалы и UV. Дождаться встроенных карт цвета и альфы; растительность проверить на отсутствие прямоугольных непрозрачных карточек. Не заменять все материалы серыми и не включать бездумно transparency/DoubleSide для всей модели. При проблемах альфы диагностировать конкретный материал; порог alphaTest допустим только после визуальной проверки результата.

LoadingManager разрешает встроенные blob/data изображения текущей загрузки; внешние file/http/сетевые пути из FBX не загружать. Для отсутствующей картинки — локальная заглушка и явное предупреждение. blob URL учитывать и отзывать после окончания использования, в том числе после неуспешного разбора. Если стандартный loader создаёт URL внутри, продумать ограниченный адаптер/патч с отдельным тестом очистки; не переопределять глобальный URL.createObjectURL на время параллельных загрузок.

Существующая искусственная земля/площадка может закрыть FBX. При включённом готовом ground отключать конфликтующую искусственную поверхность, при выключении/ошибке возвращать её штатное состояние. Не лечить конфликт произвольным подъёмом на 100 мм. В МФР проверить также плоскости этажей и фасадные изображения. Камеру на каждом drag не подгонять. Предусмотреть «Показать всё» по union bbox здания и видимого внешнего слоя; адаптировать near/far при необходимости. Предпросмотр должен работать и для пустого проекта, хотя buildMfr3D сейчас выходит при !data.size.

Смена объекта/проекта, версии слоя или teardown увеличивает generation token и abort-ит незавершённый fetch. После каждого await сверять поколение. Устаревший Group утилизируется, в новую сцену не добавляется. В ключ МФР включить object/project identity и ревизии внешних моделей; существующий ключ только по фильтрам для этого недостаточен. Не путать смену камеры с инвалидированием исходного FBX.

В пределах одного экземпляра сцены не разбирать файл повторно при drag/включении видимости. Для первых интеграций достаточно HTTP-кеша приватного content по hash и одного активного экземпляра на viewer. Не создавать общий изменяемый Group на две сцены. При clone материалы/текстуры общие по ссылке: нужна явная модель владения; предпочтительнее независимый экземпляр и уникальные Set при disposal.

Освобождение: listeners, abort controller, controls, геометрии, массивы материалов, все используемые texture maps, blob URL. Текущий disposeMfr3D предполагает одиночный material и только map; добавление слоя требует исправить это допущение или удалить/dispose слой до общего обхода, чтобы не вызвать двойную очистку. Проверить также controls.dispose(), сейчас в показанном коде его нет. Не запускать второй бесконечный цикл рендера; ЖБИ пользуется requestRender3D, МФР — своим существующим циклом.

## 10. Этапы реализации с критериями перехода

**A. Подготовка.** Прочитать CLAUDE.md, релевантные DECISIONS/MAP/TZ. Проверить git status и актуальные точки интеграции. В дереве при составлении плана уже были чужие изменения CLAUDE.md, Docs/OPEN.md и документы block-works-schedule; не включать их в свой коммит и не откатывать. Для параллельной реализации использовать отдельный worktree по правилам проекта. Не выполнять слепое git add -A поверх чужих изменений.

**B. Парсер и математика.** Согласовать точный vendor-набор при отсутствии прежнего разрешения. Реализовать ограниченный metadata reader, единицы, координаты, cleanup; загрузить реальный Ground в отдельном dev-предпросмотре. Зафиксировать actual mesh/triangle counts, bbox и размеры текстур; сравнить с разделом 2. Написать численные проверки раздела 5. Не начинать прикручивать неверно ориентированную модель к основной сцене.

**C. Сервер.** Миграция + schema doc, storage, права, bbox проекта, роуты, журнал. Изолированная временная БД и временный uploads. Проверки 401/403/404/409/413/422, persistence и откат при ошибке записи. Server upload header-check не считать полной валидацией структуры FBX; окончательная отрисовка должна обрабатывать parse error сохранённого файла.

**D. Вертикальный сценарий МФР.** Сначала подключить один ground к МФР: импорт → preview → сохранение → обновление страницы → фильтр верхнего этажа → возврат. Сделать настройки и drag; слой остаётся на абсолютном 0. Настройки должны работать независимо от пустого data.size. После этого подключить ЖБИ через второй адаптер, не копируя loader и математику.

**E. Надёжность.** Быстрое переключение проектов во время fetch, cancel, повторный save, конфликт двух вкладок, отсутствующая текстура, искусственная земля, dispose и совместимость с CSP. Полный экспорт/восстановление во временном окружении. Проверить лимиты геометрии после разбора: ≤2 млн треугольников, конечные позиции/bbox, текстура ≤8192 по стороне и суммарно ≤128 млн пикселей; при превышении понятная ошибка и cleanup. Эти post-parse лимиты не гарантируют отсутствие пика памяти самого FBXLoader: прямо зафиксировать этот предел прямого клиентского импорта.

**F. Приёмка и документация.** Реальный браузер только с обезличенной базой data/zhbi.anon.db на 8020 либо собственной её копией. Не запускать миграции/сервер на data/zhbi.db. Обновить TZ/MAP и соответствующие решения после фактической реализации, в CLAUDE добавить краткую ссылку без переписывания чужих правок. Changelog — только после согласования текста. Новые события: external_model_upload/update/recenter/delete с русскими подписями в activity_actions. Вызвать существующие проверки undefined names, activity actions, миграции/schema doc по актуальному CLI --help. Не приписывать проверкам успешность, если они не запускались.

Показатели производительности измерять, а не обещать: parse ms, загрузка текстур ms, время до первого кадра, triangles, draw calls, оценка texture bytes, длительность drag-кадров. Цель на рабочей машине — ≥30 fps при drag и отсутствие повторного parse; если не достигнута, сначала найти bottleneck, не внедрять автоматически merge/decimation, теряющие материалы. На слабом профиле сохранить отзывчивость UI, явно записав фактические показатели и устройство теста.

Итоговый отчёт исполнителя: список изменённых файлов; фактические bbox/масштаб; результаты тестов; скриншоты вида сверху и перспективы с текстурами; подтверждение reload/фильтра/drag; ограничения. Доступность диалога загрузки без успешной загрузки **этого** Ground.fbx не является выполнением задания.

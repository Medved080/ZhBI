# Архитектура реализованного решения

Подробное техническое описание того, **как** система построена и **почему**
именно так — для анализа человеком или моделью: оптимальность решений,
безопасность, узкие места, технический долг. В отличие от `Docs/TZ.md`
(что система делает) и `Docs/backlog.md` (хронология изменений), этот файл
— про внутреннее устройство: компоненты, потоки данных, алгоритмы,
инварианты, компромиссы.

Все факты в этом документе проверены непосредственно по коду на момент
написания (2026-07-15), включая номера строк там, где это важно для
проверки. Раздел 9 «Безопасность» **обновляется по мере фиксов** —
если что-то отсюда исправлено, статус меняется на «исправлено», а не
удаляется, чтобы сохранить историю находки.

## 1. Обзор архитектуры

```
Браузер (один HTML-файл, vanilla JS, SVG)
        │  fetch() + cookie-сессия
        ▼
FastAPI-приложение (app/main.py + роутеры auth/users/contracts)
        │  sqlite3, соединение на каждый запрос
        ▼
SQLite-файл (data/zhbi.db)

Отдельно: scripts/*.py — тот же код парсинга DXF, что использует и
веб-загрузка (app/dxf_import.py), но с CLI-обвязкой для запуска руками/
скриптами в обход браузера.
```

Никаких внешних сервисов (очередей, кэшей, отдельной СУБД, объектного
хранилища) — сознательный выбор для инструмента такого масштаба
(один проект/стройка, десятки пользователей, тысячи элементов). Загруженные
DXF-файлы хранятся на диске сервера (`uploads/`), не в БД.

## 2. Технологический стек и обоснование

| Слой | Технология | Почему |
|---|---|---|
| Бэкенд-фреймворк | FastAPI | Автовалидация тел запроса через Pydantic, автогенерация OpenAPI (не используется в UI, но полезна для отладки), синхронные хендлеры автоматически уходят в threadpool — не пришлось вручную городить async там, где библиотеки (ezdxf, sqlite3) синхронные. |
| БД | SQLite (файл) | Не нужен отдельный процесс/сервер БД для инструмента с одним развёртыванием на объект; файл легко бэкапить копированием. Компромисс — см. раздел 8 (конкурентность). |
| Парсинг DXF | `ezdxf` | Единственная зрелая чистопитоновская библиотека для чтения DXF с поддержкой `MULTILEADER`/`ATTDEF`/блоков — альтернатив с сопоставимой полнотой на Python нет. |
| Фронтенд | Ванильный JS, один HTML-файл, SVG | Инструмент внутренний, интерфейс не гигантский (один экран + модалки) — сборочный пайплайн (webpack/vite) и фреймворк (React и т.п.) добавили бы сложность разработки/деплоя без соразмерной выгоды на этом масштабе. SVG выбран для схемы вместо `<canvas>`, т.к. нужны нативные события клика по фигурам (`.element-shape`) без ручной геометрии попадания и нативная поддержка `viewBox` для zoom/pan. |
| Экспорт XLS | `openpyxl` | Прямая генерация `.xlsx` без промежуточного Excel/LibreOffice-процесса. |
| Экспорт PDF | `reportlab` + `svglib` | `reportlab` — низкоуровневая, но полностью серверная генерация PDF (не требует headless-браузера); `svglib` нужен только для отрисовки логотипа (SVG) на PDF-канве. |

## 3. Организация кода

```
app/
  main.py            — FastAPI-приложение, большинство REST-эндпоинтов
  auth.py            — сессии, хэширование паролей, /login /logout /me
  users.py           — CRUD пользователей (роутер, prefix /users)
  contracts.py        — контракты+строки, наследование по истории (роутер, prefix /contracts)
  db.py              — подключение к SQLite, схема, миграции
  schema.sql         — DDL для новой БД
  dxf_import.py      — оркестрация загрузки DXF из веб-UI
  history_import.py  — импорт истории статусов из XLS
  export.py          — экспорт в XLS (снимок/история)
  pdf_export.py       — экспорт схемы в PDF-отчёт
  models.py          — Pydantic-модели запросов/ответов, константы (статусы, формы маркеров)
  static/index.html  — весь фронтенд (HTML+CSS+JS одним файлом)
scripts/
  parse_zhbi.py      — парсинг DXF → маркированные элементы (ядро)
  assign_axes.py     — построение сетки осей + адресация элементов
  import_elements.py — запись элементов/сетки осей в БД (CLI и веб-путь используют одни и те же функции)
  render_plan.py     — ранний CLI-инструмент статичной SVG-отрисовки (сейчас не используется веб-приложением)
  generate_test_dxf.py — генерация синтетических DXF для разработки без реальных файлов заказчика
```

**Ключевой архитектурный принцип, проведённый последовательно**: CLI-путь
(`scripts/*.py`, запуск руками) и веб-путь (`app/dxf_import.py`, загрузка
через браузер) **не дублируют логику** — оба вызывают одни и те же функции
(`parse_zhbi.parse_dxf_from_doc`, `assign_axes.assign_address`,
`import_elements.build_row`/`upsert_elements`/`save_axis_grid`). Веб-путь
читает DXF **один раз** (открытый `ezdxf`-документ переиспользуется и для
парсинга марок, и для сетки осей), тогда как последовательный запуск трёх
CLI-скриптов читает файл трижды — на файле ~45МБ это разница между ~19с и
~8с обработки.

## 4. Модель данных

```
users ──┬──< sessions
        └──< status_history >── elements
                  │                │
                  └── contract_id ─┴── contract_id (кэш, см. ниже)
                                        │
contracts ──< contract_lines           │
    │                                  │
    └──< default_contracts             │
                                        │
axis_lines (по source_file, без FK к elements — привязка по строке)
status_colors / label_visibility / element_shapes — настройки, PRIMARY KEY = ключ настройки
```

### 4.1 Таблицы и инварианты

- **`elements`** — один физический элемент ЖБИ. `UNIQUE(source_file, dxf_handle)`
  — идентичность элемента между повторными импортами того же файла
  держится на паре «имя файла + DXF-хэндл», не на позиции/марке (хэндл в
  DXF стабилен между сохранениями того же файла в большинстве CAD-систем,
  но **не переживает пересборку файла с нуля** — известное ограничение,
  см. `Docs/TZ.md`, раздел 10). `current_status` и `contract_id` — не
  источники истины, а **денормализованные кэши**, всегда пересчитываемые
  из `status_history` (см. 4.3) — сделано ради дешёвого чтения (фильтрация/
  раскраска схемы по статусу без JOIN на каждый рендер) ценой обязанности
  пересчитывать кэш при каждой мутации истории.
- **`status_history`** — источник истины по статусу и контракту. `changed_by`
  (текстовый снимок ФИО) обособлен от `changed_by_user_id` (FK,
  `ON DELETE SET NULL`) — история переживает удаление/переименование
  пользователя.
- **`contracts` + `contract_lines`** — контракт как агрегат (поставщик) со
  строками (тип элемента → план). `contract_lines.UNIQUE(contract_id, element_type)`
  — один тип элемента не может быть продублирован внутри одного контракта.
- **`element_shapes`** — составной `PRIMARY KEY (layer, element_type)`,
  без суррогатного id — естественный ключ настройки, отсутствие строки
  означает «форма по умолчанию» (круг), а не NULL/отсутствие данных.
- **`axis_lines`** — **не** имеет FK на `elements` — связь по `source_file`
  (строковое совпадение). Осознанное упрощение: сетка осей — это данные
  чертежа, не связанные с жизненным циклом конкретных элементов, и
  перезаписывается целиком при каждом импорте того же файла.

### 4.2 Схема миграций

`app/db.py` — два независимых механизма, оба идемпотентны (можно
безопасно вызывать `init_db()` на уже актуальной БД):

1. **`_COLUMN_MIGRATIONS`** — список `(таблица, колонка, тип)`, применяется
   через `ALTER TABLE ADD COLUMN`, если колонки ещё нет. Используется для
   всех аддитивных изменений после первого релиза схемы (`contract_id`,
   `outline_json` и т.п.) — новые колонки **никогда** не добавляются
   напрямую в `schema.sql`, только через этот список, иначе накопленные
   БД молча остались бы без новых полей (`CREATE TABLE IF NOT EXISTS` не
   трогает существующие таблицы).
2. **`_migrate_contracts_structure`** — разовая структурная миграция
   (единственная на сегодня): перестройка таблицы `contracts` из старой
   формы (одна строка = контракт+тип+количество) в новую (контракт +
   `contract_lines`). Обнаружена и исправлена реальная ловушка SQLite при
   разработке этой миграции: `ALTER TABLE contracts RENAME TO contracts_old`
   **молча переписывает FK-констрейнты в других таблицах** (`elements.contract_id`,
   `default_contracts.contract_id`), которые ссылались на `contracts`, —
   они начинают ссылаться на `contracts_old`. Без `PRAGMA foreign_keys = OFF`
   на время миграции последующий `DROP TABLE contracts_old` запускал
   `ON DELETE SET NULL` по этим констрейнтам и обнулял только что
   перенесённые ссылки. Воспроизведено и проверено в изолированном тесте
   до и после исправления.

## 5. Конвейер импорта DXF

```
ezdxf.readfile()
    │
    ├─→ parse_dxf_from_doc()          — марки: атрибут блока → выноска → голый текст
    │       │
    │       ├─ iter_candidate_elements()  — геометрия: INSERT-блоки ИЛИ замкнутые LWPOLYLINE
    │       │      (замкнутость: DXF-флаг ИЛИ первая точка == последней)
    │       ├─ collect_annotations()      — LEADER/MULTILEADER/TEXT/MTEXT с слоёв-аннотаций
    │       ├─ build_leader_pool()        — унифицирует все источники марки в один пул
    │       └─ resolve_via_leaders()      — глобальное жадное сопоставление элемент↔марка
    │
    ├─→ build_axis_grid()              — сетка координационных осей (CIRCLE+ATTDEF либо блок)
    │
    └─→ assign_address() на каждый элемент — адрес по осям (on_axis/offset/outside/no_grid)
            │
            ▼
    build_row() → upsert_elements() / save_axis_grid()   — запись в SQLite (upsert по dxf_handle)
```

### 5.1 Сопоставление марки с элементом — `resolve_via_leaders()`

Наивный подход «для каждого элемента — ближайшая выноска» ошибается, когда
одна выноска геометрически ближе всего сразу к нескольким элементам.
Реализован **жадный алгоритм по глобальной сортировке**: строятся ВСЕ
пары (элемент, выноска) в пределах порога расстояния, сортируются по
возрастанию расстояния, разбираются жадно (каждый элемент и каждая
выноска — не более одного раза). Сложность — `O(E·L·log(E·L))`, где `E` —
число элементов без атрибута, `L` — число доступных выносок/текстов; на
реальных файлах (сотни элементов) это доли секунды, при кратном росте
(десятки тысяч элементов на файл) стало бы узким местом — на сегодняшних
объёмах не является.

Порог расстояния (`MAX_LEADER_MATCH_DISTANCE = 1800.0` мм) — подобран
эмпирически под два разных профиля элементов (колонны: марка у выноски
~50мм от центроида; ригели: марка — голый текст, до ~1540мм от центроида
вытянутого элемента) и проверен на неоднозначность: для каждой реальной
марки посчитано расстояние до второго по близости кандидата-элемента —
подтверждено, что общий порог не приводит к путанице между соседними
элементами на всех имеющихся тестовых файлах (см. `Docs/backlog.md`,
четвёртый раунд, п.5/13 — детали проверки).

### 5.2 Замкнутость контура — не только DXF-флаг

`is_effectively_closed()` — контур считается замкнутым, если явно
выставлен DXF-флаг `closed`, **или** геометрически первая точка контура
совпадает с последней (найдено на реальном файле — часть ригелей
нарисована с повторением первой точки в конце, без выставления флага).
Проверено, что это расширение не меняет поведение ни на одном из ранее
работавших файлов (побайтовое сравнение результата парсинга до/после
изменения).

### 5.3 Что не извлекается

- Геометрия `INSERT`-блоков — извлекается только точка вставки, не
  реальный контур блока (см. `Docs/TZ.md`, раздел 10). Технически
  возможно (блок содержит свою геометрию, которую можно трансформировать
  по матрице вставки), но не понадобилось ни на одном файле заказчика —
  колонны из блоков всегда компактные и хорошо представляются точкой.
- Слои, отсутствующие в `LAYER_CONFIG` — молча игнорируются, без ошибки
  и без записи в лог. Это ускоряет разработку (не нужно поддерживать
  полный список слоёв «в никуда»), но создаёт риск незаметной потери
  данных — реальный случай см. `Docs/backlog.md`, находка про ригели.

## 6. Ключевые алгоритмы фронтенда

### 6.1 Разводка коллизий подписей — bucket-based, не полный перебор

И `computeLabelOffsets()` (выбор направления подписи один раз при
загрузке), и `updateLabelCollisionVisibility()` (скрытие/показ подписей
по текущему масштабу) используют **пространственную сетку бакетов**
вместо попарного сравнения всех подписей со всеми (`O(n²)`): каждый
элемент кладётся в бакет по своим координатам, при проверке коллизии
просматриваются только 9 соседних бакетов (3×3). Сложность —
приблизительно `O(n)` при равномерной плотности элементов на чертеже.
Проверено на реальном файле (332 элемента) без заметной задержки при
скролле/зуме.

Обе функции пересчитываются **при каждом изменении `viewBox`** (колесо
мыши/перетаскивание) — `updateSizesForZoom()` вызывается на каждое такое
событие без троттлинга/дебаунса. На сегодняшних объёмах (сотни-тысяча
элементов) не создаёт видимой задержки; при кратном росте числа
элементов на чертеже это стало бы кандидатом на оптимизацию (например,
дебаунс на `wheel`/`mousemove`).

### 6.2 Рендеринг схемы — SVG в мировых координатах, масштаб через `viewBox`

Все геометрические сущности (маркеры элементов, линии осей, контуры
"как в оригинале") рисуются **в исходных координатах DXF**, без
пересчёта в экранные пиксели на стороне JS — масштабирование и
панорамирование выполняет сам SVG через атрибут `viewBox` на корневом
`<svg>`. Единственное, что реально пересчитывается в JS при каждом
зуме — это то, что **обязано** оставаться постоянного экранного размера
несмотря на масштаб: радиус условных маркеров (кэп по `MAX_MARKER_PX`),
размер шрифта подписей, отступ закреплённых подписей осей от края
экрана. Форма «как в оригинале» (`outline`) сознательно исключена из
этого пересчёта — она уже в мировых координатах и корректно
масштабируется самим `viewBox`, как и линии сетки осей.

Инверсия оси Y: DXF использует Y-up (математическая ориентация), SVG —
Y-down (экранная) — решается одной трансформацией `scale(1,-1)` на
группе-обёртке (`#flip`), а не пересчётом координат каждой фигуры вручную;
подписи внутри этой группы получают **вторую**, локальную `scale(1,-1)`,
чтобы не оказаться отражёнными по вертикали (двойное отражение = обычная
ориентация текста).

### 6.3 Разграничение клика и перетаскивания

`DRAG_THRESHOLD_PX = 4` — перетаскивание схемы включается только после
того, как курсор сдвинулся более чем на 4px от точки `mousedown`; клик
без реального перетаскивания (в пределах порога) не двигает `viewBox` и
не блокирует последующий `click` на фигуре. Без этого порога обычное
дрожание руки при клике (1-2px между `mousedown`/`mouseup`) трактовалось
как намеренное перетаскивание — найдено и исправлено в четвёртом раунде
(см. `Docs/backlog.md`).

### 6.4 Состояние — единый глобальный объект, без реактивного фреймворка

Весь клиентский стейт живёт в одном объекте `state` (элементы, выбор
файлов/слоёв, текущий вид, кэши DOM-узлов по id элемента и т.д.).
Перерисовка — императивная: каждая функция (`renderElements`,
`renderLegend`, `showCard`...) явно вызывается после мутации
соответствующих данных, нет автоматического отслеживания зависимостей
(как в React/Vue). Осознанный компромисс для проекта такого размера —
подходит, пока число независимо мутируемых частей интерфейса невелико;
при дальнейшем росте интерфейса ручная синхронизация «где ещё нужно
перерисовать после этого изменения» станет источником багов рассинхронизации.

## 7. API-дизайн

REST-подобный, но не строго RESTful в паре мест — осознанно:
- `POST /plan-data` (не `GET`) — тело запроса содержит произвольной
  длины список `{source_file, layers[]}`, что не укладывается в
  query-параметры чисто технически (список пар файл+слои переменной
  длины); выбран `POST` с телом вместо, например, `GET` с
  JSON-encoded query-параметром — это отступление от идиомы «GET для
  чтения» ради простоты кода на обеих сторонах.
- `PATCH /elements/{id}/status` принимает `contract_id` как часть тела
  того же запроса, различая «поле не передано» (наследовать контракт от
  предыдущей записи истории) от «поле передано как `null`» (явно
  «без контракта») через `body.model_fields_set` (Pydantic v2) — тонкость,
  которую легко нарушить будущими изменениями модели, если не знать про
  это различие (задокументировано в комментарии в коде рядом).

Авторизация — на уровне зависимостей FastAPI (`Depends(get_current_user)`
/ `Depends(require_editor)` / `Depends(require_admin)`), проверяется **на
каждом эндпоинте отдельно**, нет глобального middleware, накладывающего
проверку роли по паттерну пути. Это значит: добавление нового эндпоинта
без явного `Depends(...)` с нужной ролью **не будет автоматически
защищено** — ответственность лежит на том, кто пишет новый роут, ничего
не проверяет это на уровне архитектуры/тестов автоматически (см. раздел 10
про отсутствие тестов).

## 8. Модель конкурентности

- Все обработчики маршрутов — синхронные (`def`, не `async def`);
  Starlette/FastAPI автоматически уводит их в threadpool, поэтому
  блокирующие вызовы (`sqlite3`, `ezdxf.readfile` на большом файле) не
  блокируют event loop для других запросов.
- Подключение к SQLite — **одно на запрос** (`get_connection()` в начале,
  `conn.close()` в `finally`), без пула соединений. Для SQLite это
  нормально (открытие соединения дёшево), но при высокой частоте
  запросов создаёт накладные расходы на открытие файла на каждый вызов.
- `PRAGMA journal_mode` **не** переключён в WAL (используется режим по
  умолчанию — rollback journal) — при **одновременной записи** от разных
  запросов SQLite последовательно блокирует писателей (только один writer
  в любой момент времени), и в non-WAL режиме запись блокирует
  параллельное чтение на время транзакции. Для типичного профиля
  использования (несколько человек на объекте, редкие одновременные
  записи) это не проблема; при росте одновременных пользователей —
  первый кандидат на переключение в WAL-режим (`PRAGMA journal_mode=WAL`),
  что позволило бы читателям не блокироваться писателем.
- Загрузка и обработка DXF (`/import-dxf`) — **полностью синхронная в
  рамках одного HTTP-запроса**: клиент ждёт завершения парсинга/записи в
  БД без промежуточного прогресса. На файле ~45МБ это секунды, не
  минуты — приемлемо на сегодняшних объёмах; при кратном росте размера
  файлов стало бы кандидатом на фоновую обработку с поллингом статуса.

## 9. Безопасность

### 9.1 Аутентификация и сессии

- Пароли — PBKDF2-HMAC-SHA256, 260 000 итераций, соль на пользователя
  (`secrets.token_hex(16)`, криптографически случайная). Величина
  итераций — в пределах текущих рекомендаций OWASP для PBKDF2-SHA256
  (≥210 000 на 2023 год).
- Токен сессии — `secrets.token_urlsafe(32)` (криптографически случайный,
  256 бит энтропии), хранится в БД как есть (не хэшируется дополнительно
  — компрометация БД даёт готовые сессионные токены; для внутреннего
  инструмента с доверенным хранилищем принято как допустимый риск, но
  стоит знать при анализе).
- Cookie сессии: `httponly=True` (недоступна из JS — снижает ущерб от XSS
  до «действия от имени пользователя», без прямой кражи токена),
  `samesite="lax"` (даёт частичную защиту от CSRF для кросс-сайтовых POST/PUT/DELETE
  запросов в большинстве современных браузеров), **`secure` НЕ выставлен**
  — cookie передаётся и по обычному HTTP, не только HTTPS. Приемлемо при
  развёртывании за HTTPS-терминирующим прокси в закрытой сети; при прямой
  публикации сервиса по HTTP на незащищённой сети — реальный риск
  перехвата сессии. **Статус: не исправлено, задокументировано.**
- Истечение сессии проверяется на сервере при каждом запросе
  (`WHERE expires_at > datetime('now')` в `get_user_by_session`), не
  только через истечение самой cookie на клиенте — корректно.
- `GET /login-users` — публичный (без авторизации) эндпоинт, отдающий
  список ФИО+логинов для выпадающего списка на форме входа. Осознанный
  компромисс, явно задокументированный в коде (`app/auth.py`): упрощает
  вход ценой раскрытия списка валидных логинов неаутентифицированному
  клиенту — облегчает подбор пароля по известному логину (особенно в
  сочетании с отсутствием ограничения частоты попыток входа, см. ниже).
- **Нет ограничения частоty попыток входа** (`/login`) — ничего не мешает
  перебору паролей скриптом, кроме затрат на PBKDF2 (260к итераций
  делают каждую попытку заметно медленнее, но не останавливают
  целенаправленный перебор). **Статус: не исправлено.**

### 9.2 Авторизация

Три роли (`admin`/`user`/`view`), проверяются **и в UI** (скрытие
элементов управления), **и на бэкенде** (403 при прямом обращении к API
в обход интерфейса, через `Depends(require_admin)`/`Depends(require_editor)`
на каждом чувствительном эндпоинте) — подтверждено прямыми запросами в
обход UI в ходе разработки (см. `Docs/backlog.md`, первый раунд, п.8).

### 9.3 SQL-инъекции

Не найдено ни одного места, где значения, пришедшие от клиента,
подставляются в SQL-строку напрямую. Везде, где используется f-string
для построения запроса, интерполируется только **структура** запроса
(текст `WHERE`/`AND`, список `?`-плейсхолдеров нужной длины для `IN (...)`)
— сами значения всегда передаются отдельным параметризованным аргументом
в `conn.execute(query, params)`. Проверено по всем вхождениям f-string
рядом с `SELECT`/`INSERT`/`UPDATE`/`DELETE`/`WHERE`/`FROM` во всём `app/`.

### 9.4 XSS — найдена подтверждённая уязвимость (stored XSS)

**Не исправлено на момент написания документа.** При разработке этого
документа обнаружено: рендеринг схемы (маркеры и подписи марок на самой
SVG-схеме) выполняется безопасно — через `textContent`
(`app/static/index.html:904`, `flippedText()`), который не интерпретирует
HTML. **Но** карточка элемента в сайдбаре (`fieldRowsHtml()`,
`app/static/index.html:1347-1354`) вставляет значения полей элемента
(включая `mark`, `address` и другие текстовые поля, извлечённые из
содержимого DXF-файла) в DOM через `innerHTML` **без экранирования**:

```js
return `<tr><td class="k">${FIELD_LABELS[k] || k}</td><td>${v}</td></tr>`;
```

Марка элемента (`mark`) — это текст, извлечённый парсером напрямую из
содержимого DXF-файла (текст выноски/аннотации, см. раздел 5) — то есть
**полностью контролируется тем, кто загружает DXF**. Роль, необходимая
для загрузки чертежа — `user` или `admin` (не `view`), но не обязательно
самая привилегированная. Если такой пользователь загрузит DXF с
аннотацией, содержащей, например, `<img src=x onerror="...">` в качестве
текста марки, при открытии карточки ЭТОГО элемента **любым** другим
пользователем (в том числе `admin`) полезная нагрузка выполнится в его
браузере. Поскольку cookie сессии `httponly` (JS не может её прочитать),
прямая кража токена сессии через `document.cookie` невозможна — но
скрипт может выполнять **любые действия от имени открывшего карточку
пользователя** через обычные `fetch()`-запросы к тому же origin (браузер
автоматически приложит httpOnly-cookie) — включая, если жертва админ,
создание нового администратора, смену чужих паролей, изменение
настроек. Это классическая цепочка «низкопривилегированный аккаунт →
эскалация через администратора, который просматривает данные».

Аналогичный паттерн (интерполяция без экранирования в `innerHTML`)
встречается ещё в нескольких местах, где данные менее очевидно
«вражеские», но всё равно приходят из пользовательского ввода без
серверной валидации на допустимые символы: ФИО/должность пользователя
(`renderUsersTable`, только `admin`-ввод — ниже приоритет, но тоже
реальный вектор при компрометации одного администратора), название/
поставщик контракта. История статусов (`changed_by`, происходит из ФИО
пользователя) — та же категория.

**Рекомендация:** завести один хелпер экранирования (`escapeHtml(s)`,
замена `& < > " '` на HTML-сущности) и применить его ко всем местам, где
в `innerHTML`-шаблон подставляется значение, пришедшее не от самого кода
(поля элемента, ФИО, названия контрактов, статусы истории и т.п.) —
затрагивает порядка 13 мест использования `innerHTML` с шаблонными
литералами в `app/static/index.html`. Альтернатива с меньшим риском
регрессии — там, где вставляется единственное текстовое значение внутрь
готовой разметки, заменить конкретный узел на `textContent`.

### 9.5 Загрузка файлов

- Имя файла очищается через `Path(upload_file.filename or "").name`
  (`app/dxf_import.py`) — отрезает компоненты пути, защита от
  path traversal (`../../etc/...`) корректна.
- Содержимое файла не проверяется до попытки разбора `ezdxf.readfile()` —
  единственная защита от не-DXF содержимого — то, что `ezdxf` не сможет
  его распарсить (перехватывается широким `except Exception`,
  превращается в понятную 422-ошибку).
- **Нет явного ограничения размера загружаемого файла** — ни на уровне
  приложения, ни видимой конфигурации ASGI-сервера. Открывает
  теоретическую возможность DoS через загрузку огромных файлов
  (исчерпание диска/памяти при парсинге). На сегодня смягчается тем, что
  загрузка доступна только аутентифицированным `user`/`admin`.

### 9.6 Раскрытие чувствительных данных

`GET /settings/export` (только `admin`) сознательно включает
`password_hash`/`password_salt` пользователей в экспортируемый JSON —
задокументировано в коде и в `Docs/TZ.md` как целенаправленное решение
(перенос между серверами без пересоздания паролей). Файл экспорта
следует защищать так же, как резервную копию БД — при анализе
безопасности учитывать как ещё одну точку, где может произойти утечка
(хранение файла экспорта, права доступа к нему на диске/в почте и т.п. —
вне периметра, который контролирует само приложение).

### 9.7 CORS

Middleware CORS не подключён — по умолчанию браузер блокирует
кросс-origin запросы к API с других доменов (frontend раздаётся тем же
FastAPI-приложением, что и API — кросс-origin доступ не требуется и не
открыт).

## 10. Тестирование

**Автоматических тестов в репозитории нет** (ни unit, ни integration).
Вся верификация в ходе разработки выполнялась вручную — либо прямыми
`curl`-запросами к API, либо через управление headless Chrome по Chrome
DevTools Protocol (симуляция реальных кликов/событий мыши, проверка
DOM/состояния после действий, скриншоты для визуальной проверки). Это
позволило поймать ряд реальных багов (см. `Docs/backlog.md`), но:
- Не защищает от регрессий при будущих изменениях — каждая проверка
  делалась вручную один раз в моменте, не оставляя воспроизводимого
  теста, который можно перезапустить.
- Не покрывает граничные случаи систематически (полагается на то, что
  разработчик догадается их проверить).

**Рекомендация при дальнейшем развитии:** зафиксировать хотя бы
критичные пути (парсинг DXF на референсных файлах — сравнение с
сохранённым ожидаемым результатом; миграции БД — на копии реальной
структуры; авторизация — 403 на попытку доступа не той ролью) как
автоматические тесты (`pytest`), чтобы не полагаться на ручную проверку
каждый раз заново.

# Архитектура реализованного решения

Подробное техническое описание того, **как** система построена и **почему**
именно так — для анализа человеком или моделью: оптимальность решений,
безопасность, узкие места, технический долг. В отличие от `Docs/TZ.md`
(что система делает — функциональный спек, обновляется на каждое
изменение) и `Docs/backlog.md` (хронология изменений, по датам), этот
файл — про внутреннее устройство: компоненты, потоки данных, алгоритмы,
инварианты, компромиссы. В отличие от обоих — это **разовый снимок**,
обновляемый только по явной просьбе (см. `CLAUDE.md`), поэтому при
чтении сверяйте дату ниже с текущей: если прошло много раундов работы
без обновления этого файла, детали (особенно номера строк) могли
разойтись с кодом сильнее, чем обычно.

Все факты в этом документе проверены непосредственно по коду на момент
написания (2026-07-20 — второй сквозной пересмотр; первый был
2026-07-15 и не покрывал зоны/3D/партии, добавленные позже), включая
номера строк там, где это важно для проверки. Раздел 9 «Безопасность»
**обновляется по мере фиксов** — если что-то отсюда исправлено, статус
меняется на «исправлено», а не удаляется, чтобы сохранить историю
находки.

## 1. Обзор архитектуры

```
Браузер (один HTML-файл, vanilla JS, SVG + опционально Three.js для 3D)
        │  fetch() + cookie-сессия
        ▼
FastAPI-приложение (app/main.py + роутеры auth/users/contracts/batches)
        │  sqlite3, соединение на каждый запрос
        ▼
SQLite-файл (data/zhbi.db)

Отдельно: scripts/*.py — ДВА параллельных конвейера парсинга DXF (см.
раздел 5), общая для обоих логика адресации по осям, а также разбор
зон/захваток/кранов/стоянок (только новый конвейер). Тот же код
переиспользуется веб-загрузкой (app/dxf_import.py) и CLI-запуском.
```

Никаких внешних сервисов (очередей, кэшей, отдельной СУБД, объектного
хранилища) — сознательный выбор для инструмента такого масштаба
(один проект/стройка, десятки пользователей, тысячи элементов). Загруженные
DXF-файлы хранятся на диске сервера (`uploads/`), не в БД. Библиотека
3D-визуализации (Three.js) вендорена локально в `app/static/vendor/three/`
— не CDN, не npm-пакет (см. раздел 6.5) — тот же принцип "минимум внешних
зависимостей во время выполнения", что и у остального стека.

## 2. Технологический стек и обоснование

| Слой | Технология | Почему |
|---|---|---|
| Бэкенд-фреймворк | FastAPI | Автовалидация тел запроса через Pydantic, автогенерация OpenAPI (не используется в UI, но полезна для отладки), синхронные хендлеры автоматически уходят в threadpool — не пришлось вручную городить async там, где библиотеки (ezdxf, sqlite3, shapely) синхронные. |
| БД | SQLite (файл) | Не нужен отдельный процесс/сервер БД для инструмента с одним развёртыванием на объект; файл легко бэкапить копированием. Компромисс — см. раздел 8 (конкурентность). |
| Парсинг DXF | `ezdxf` | Единственная зрелая чистопитоновская библиотека для чтения DXF с поддержкой `MULTILEADER`/`ATTDEF`/блоков — альтернатив с сопоставимой полнотой на Python нет. |
| Геометрия зон/привязка | `shapely` | Полигональные операции (пересечение, площадь, `contains`/`distance`, `make_valid` для самопересекающихся контуров) для сопоставления элементов и текстовых подписей с зонами (захватка/кран/стоянка) — писать это вручную поверх голых списков координат было бы избыточным риском геометрических багов. |
| Фронтенд | Ванильный JS, один HTML-файл, SVG (2D) + Three.js (3D) | Инструмент внутренний, интерфейс не гигантский (один экран + модалки) — сборочный пайплайн (webpack/vite) и фреймворк (React и т.п.) добавили бы сложность разработки/деплоя без соразмерной выгоды на этом масштабе. SVG выбран для 2D-схемы вместо `<canvas>`, т.к. нужны нативные события клика по фигурам (`.element-shape`) без ручной геометрии попадания и нативная поддержка `viewBox` для zoom/pan. Three.js — единственная зрелая опция для WebGL-визуализации такого уровня без написания собственного рендерера; вендорена локально (не через CDN/npm), т.к. проект принципиально без сборочного шага. |
| Экспорт XLS | `openpyxl` | Прямая генерация `.xlsx` без промежуточного Excel/LibreOffice-процесса. |
| Экспорт PDF | `reportlab` + `svglib` | `reportlab` — низкоуровневая, но полностью серверная генерация PDF (не требует headless-браузера); `svglib` нужен только для отрисовки логотипа (SVG) на PDF-канве. |

## 3. Организация кода

```
app/
  main.py             — FastAPI-приложение, большинство REST-эндпоинтов
  auth.py             — сессии, хэширование паролей, rate-limit входа, /login /logout /me
  users.py            — CRUD пользователей + self-service (пароль, цвет подписей)
  contracts.py        — контракты+строки, наследование по истории (роутер, prefix /contracts)
  batches.py          — партии (детализация контракта до марки + плановая дата, роутер, prefix /batches)
  db.py               — подключение к SQLite, схема, миграции
  schema.sql          — DDL для новой БД
  dxf_import.py       — оркестрация загрузки DXF из веб-UI (оба конвейера, см. раздел 5)
  history_import.py   — импорт истории статусов из XLS
  export.py           — экспорт в XLS (снимок/история)
  pdf_export.py       — экспорт схемы в PDF-отчёт
  models.py           — Pydantic-модели запросов/ответов, константы (статусы, формы маркеров, типы ЖБИ)
  static/index.html   — весь фронтенд (HTML+CSS+JS одним файлом, ~5400 строк)
  static/vendor/three/ — Three.js 0.160.0, вендорено локально (module + OrbitControls.js)
scripts/
  parse_zhbi.py         — СТАРЫЙ конвейер: DXF → маркированные элементы по LAYER_CONFIG (ядро парсинга,
                           переиспользуется и новым конвейером — see resolve_via_leaders/is_effectively_closed и т.п.)
  layer_naming.py        — грамматика НОВОГО стандарта имён слоёв (WEB_констр_.../WEB_тех_...), строгая валидация
  new_standard_pipeline.py — оркестрация нового конвейера: группировка слоёв → элементы+зоны → привязка к зонам
  zone_parser.py          — реестр зон (захватка/кран/стоянка): полигоны + сопоставление названий + связь стоянка→кран
  zone_binding.py          — привязка элементов к зонам (точка/площадь пересечения) + "лесенка" сужения стоянки с высотой
  assign_axes.py         — построение сетки осей + адресация элементов (общая для обоих конвейеров)
  import_elements.py     — запись элементов/сетки осей/зон в БД (CLI и веб-путь используют одни и те же функции)
  render_plan.py          — ранний CLI-инструмент статичной SVG-отрисовки (сейчас не используется веб-приложением)
  generate_test_dxf.py / generate_test_zones_dxf.py — генерация синтетических DXF для разработки без реальных файлов заказчика
  verify_zone_pipeline.py — сквозной синтетический тест конвейера зон (единственный сквозной тест в проекте)
```

**Ключевой архитектурный принцип, проведённый последовательно**: CLI-путь
(`scripts/*.py`, запуск руками) и веб-путь (`app/dxf_import.py`, загрузка
через браузер) **не дублируют логику** — оба вызывают одни и те же функции.
Веб-путь читает DXF **один раз** (открытый `ezdxf`-документ переиспользуется
и для парсинга марок старым конвейером, и для сетки осей, и для нового
конвейера слоёв/зон), тогда как последовательный запуск CLI-скриптов читал
бы файл трижды и более — на файле ~45МБ это заметная разница во времени
обработки.

## 4. Модель данных

```
users ──┬──< sessions
        └──< status_history >── elements ──┬── zone_zakhvatka_id ─┐
                  │                        ├── zone_crane_id ─────┼──> zones ──< zone_colors (по имени, не FK)
                  │                        └── zone_stance_id ────┘        (zones.parent_zone_id: Стоянка → Кран)
                  └── contract_id ─┬── contract_id (кэш, см. 4.3)
                                   │
contracts ──< contract_lines      │
    │        ── contract_incidents│
    ├──< batches ──< batch_lines  │
    │                    ↑        │
    └──< default_contracts        │
                                   │
elements.batch_id ─────────────────┘ (живое поле, БЕЗ версионирования по status_history — см. 4.4)

axis_lines (по source_file, без FK к elements — привязка по строке)
allowed_subtypes (справочник, не FK — сравнивается по значению в layer_naming.py)
status_colors / label_visibility / element_shapes — настройки, PRIMARY KEY = ключ настройки
```

### 4.1 Таблицы и инварианты

- **`elements`** — один физический элемент ЖБИ. `UNIQUE(source_file, dxf_handle)`
  — идентичность элемента между повторными импортами того же файла
  держится на паре «имя файла + DXF-хэндл», не на позиции/марке (хэндл в
  DXF стабилен между сохранениями того же файла в большинстве CAD-систем,
  но **не переживает пересборку файла с нуля** — известное ограничение,
  см. `Docs/TZ.md`, раздел 10). `current_status` и `contract_id` — не
  источники истины, а **денормализованные кэши**, всегда пересчитываемые
  из `status_history` (см. 4.3) — сделано ради дешёвого чтения (фильтрация/
  раскраска схемы по статусу без JOIN на каждый рендер) ценой обязанности
  пересчитывать кэш при каждой мутации истории. Поля нового стандарта
  (`subtype`, `elevation_mm`, `zone_*_id`, `zone_*_status`, `batch_id`) —
  NULL у элементов старого конвейера (`LAYER_CONFIG`), заполняются только
  когда элемент пришёл через `new_standard_pipeline`.
- **`status_history`** — источник истины по статусу и контракту. `changed_by`
  (текстовый снимок ФИО) обособлен от `changed_by_user_id` (FK,
  `ON DELETE SET NULL`) — история переживает удаление/переименование
  пользователя. `changed_at` — не обязательно момент вставки строки: UI
  «рабочей даты» (workdate/backdating, см. 4.4) позволяет явно задать
  дату/время, на которые применяется статус, включая задним числом.
- **`contracts` + `contract_lines`** — контракт как агрегат (поставщик) со
  строками (тип элемента → план). `contract_lines.UNIQUE(contract_id, element_type)`
  — один тип элемента не может быть продублирован внутри одного контракта.
  `contracts.contract_date`/`code` (добавлены в раунде «Партия») — бизнес-
  дата подписания и короткий код контрагента, оба nullable, участвуют
  только в формуле метки партии (см. 4.4), нигде не заменяют `name`/`supplier`.
- **`batches` + `batch_lines`** — см. 4.4 ниже, отдельная сущность.
- **`zones`** — захватка/кран/стоянка (см. раздел 5.4). Полигон в мировых
  координатах чертежа, как и `elements.outline_json`. `match_status`
  ("matched"/"unmatched"/"ambiguous") — результат сопоставления полигона с
  текстом-названием, `parent_zone_id`/`parent_match_status` — только у
  category='Стоянка': какому крану принадлежит эта стоянка (найдено
  point-in-polygon центроида стоянки внутри полигона крана).
  `UNIQUE(source_file, dxf_handle)` — та же идентичность, что у `elements`.
- **`zone_colors`** — ключ `(source_file, category, name)`, **не**
  `zones.id` — id не стабилен между переимпортами (`upsert_zones` делает
  DELETE+INSERT на каждый импорт того же файла), имя зоны — единственное,
  что переживает переимпорт. На сегодня раскрашивается только категория
  "Кран" (стоянки наследуют цвет родителя на фронтенде через
  `parent_zone_id`, без отдельной записи здесь).
- **`allowed_subtypes`** — справочник допустимых подтипов по типу
  элемента, редактируется через UI (только admin), НЕ зашит в код разбора
  — `layer_naming.parse_layer_name()` принимает его параметром. Сравнение
  без учёта регистра.
- **`element_shapes`** — составной `PRIMARY KEY (layer, element_type)`,
  без суррогатного id — естественный ключ настройки, отсутствие строки
  означает «форма по умолчанию» (outline — реальный контур), а не NULL/
  отсутствие данных.
- **`axis_lines`** — **не** имеет FK на `elements` — связь по `source_file`
  (строковое совпадение). Осознанное упрощение: сетка осей — это данные
  чертежа, не связанные с жизненным циклом конкретных элементов, и
  перезаписывается целиком при каждом импорте того же файла.

### 4.2 Схема миграций

`app/db.py` — два независимых механизма, оба идемпотентны (можно
безопасно вызывать `init_db()` на уже актуальной БД):

1. **`_COLUMN_MIGRATIONS`** — список `(таблица, колонка, тип)`, применяется
   через `ALTER TABLE ADD COLUMN`, если колонки ещё нет. Используется для
   всех аддитивных изменений после первого релиза схемы (`contract_id`,
   `outline_json`, все поля нового стандарта слоёв/зон, `contracts.contract_date`/
   `code`, `elements.batch_id`, `users.label_color` — список растёт с
   каждым функциональным раундом) — новые колонки **никогда** не
   добавляются напрямую в `schema.sql`, только через этот список, иначе
   накопленные БД молча остались бы без новых полей (`CREATE TABLE IF NOT
   EXISTS` не трогает существующие таблицы). Порядок в списке важен там,
   где новая колонка ссылается FK на таблицу, которая должна уже
   существовать — например, `elements.batch_id → batches(id)` безопасен,
   т.к. `batches` создаётся в `schema.sql` до применения `_COLUMN_MIGRATIONS`
   (`executescript` в `init_db()` идёт первым шагом).
2. **`_migrate_contracts_structure`** — разовая структурная миграция
   (единственная на сегодня): перестройка таблицы `contracts` из старой
   формы (одна строка = контракт+тип+количество) в новую (контракт +
   `contract_lines`). Обнаружена и исправлена реальная ловушка SQLite при
   разработке этой миграции: `ALTER TABLE contracts RENAME TO contracts_old`
   **молча переписывает FK-констрейнты в других таблицах** (`elements.contract_id`,
   `default_contracts.contract_id`), которые ссылались на `contracts`, —
   они начинают ссылаться на `contracts_old`. Без `PRAGMA foreign_keys = OFF`
   на время миграции последующий `DROP TABLE contracts_old` запускал
   `ON DELETE SET NULL` по этим констрейнтам и обнулял только что
   перенесённые ссылки. Воспроизведено и проверено в изолированном тесте
   до и после исправления.
3. **`_normalize_element_type_vocabulary`** — идемпотентная нормализация
   `element_type` из старых английских значений (`"column"`/`"beam"`,
   остаток от раннего `LAYER_CONFIG`) в единый русский словарь
   («Колонна»/«Ригель»). Затрагивает не только `elements`, но и все
   таблицы, где `element_type` — часть первичного/уникального ключа
   (`label_visibility`, `default_contracts`, `element_shapes`,
   `contract_lines`) — при коллизии с уже существующей русской строкой
   оставляет русскую (считается уже осмысленно настроенной), английскую
   удаляет, а не перезаписывает поверх.

### 4.3 Денормализованные кэши статуса/контракта — пересчёт, не запись

`elements.current_status` и `elements.contract_id` **никогда** не
устанавливаются напрямую отдельным эндпоинтом — оба всегда пересчитываются
как значение из **самой поздней ПО `changed_at`** записи `status_history`
(`recompute_element_contract_cache` в `app/contracts.py`, аналогичный
инлайн-запрос для статуса рядом). Важное следствие: "самая поздняя по
`changed_at`" — это не то же самое, что "последняя вставленная" — при
backdating (см. 4.4) новая запись с более ранней датой **не** становится
текущим статусом, если в истории уже есть запись с более поздней датой.
Это осознанный дизайн (поддержка правки истории задним числом), но именно
он стал причиной реального бага: кнопка "Сейчас" в тулбаре заполняла поле
рабочей даты текущим временем, но не деактивировала его — устаревшее
backdated-значение могло молча пролежать в `localStorage` браузера между
сессиями и заставить новую запись статуса выглядеть "не применившейся"
(на самом деле применившейся, но не ставшей текущей, т.к. в истории уже
была запись с более поздней датой — например, дата импорта файла). Фикс —
на стороне UI (явный диалог даты/времени при каждой смене статуса,
отдельная кнопка очистки рабочей даты, см. `Docs/backlog.md`, "Партия —
правки по итогам первой живой проверки"), не на стороне модели данных:
сам пересчёт "по последней дате" остаётся правильным поведением.

Пересчёт вызывается из трёх мест: `apply_status_change` (обычная смена
статуса), `delete_history_entry` (`app/main.py`, удаление записи истории
— пересчёт работает даже если удалена не последняя по времени запись), и
неявно не вызывается больше нигде — единая точка логики, не продублирована.

### 4.4 Партия (`batches`/`batch_lines`) — независимая от статуса сущность

Партия детализирует план контракта до **марки** (в отличие от
`contract_lines`, план по **типу** на весь контракт) и добавляет плановую
дату конкретной поставки. Назначение элемента на партию
(`elements.batch_id`) — **простое живое поле, БЕЗ версионирования по
`status_history`** (в отличие от `contract_id`) — сознательный компромисс:
назначение партии не привязано к смене статуса, это независимое действие,
доступное в любой момент из того же контекстного меню. Побочный эффект
этого решения: система не хранит, на какой партии элемент был "вчера, до
исправления" — если такая история понадобится, это отдельный лёгкий лог
(`batch_assignment_log`), сознательно не реализованный в этом раунде (не
запрошено).

Ключевые инварианты (реализованы в `app/batches.py`):
- **Жёсткий отказ при несовпадении марки** — назначить элемент на партию
  можно только если в `batch_lines` этой партии есть строка с точно тем же
  `(element_type, subtype, mark)` (NULL-safe сравнение через SQL `IS`, не
  `=` — `subtype`/`mark` часто NULL). `validate_and_resolve_batch_assignment`
  — единая точка валидации и для одиночного (`PATCH /elements/{id}/batch`),
  и для массового (`PATCH /elements/bulk-batch`) назначения (последний
  атомарен: сперва валидируются ВСЕ элементы пачки, при любой ошибке не
  применяется ничего).
- **Мягкое предупреждение при овербукинге** — `batch_line_warning`, та же
  форма ответа, что `contract_line_warning` (не блокирует, только
  информирует).
- **NULL-safe уникальность строк партии** — обычный SQLite `UNIQUE` не
  считает `NULL=NULL`; без `COALESCE`-индекса
  (`idx_batch_lines_unique`) две "одинаковые" строки (тип, без подтипа, без
  марки) продублировались бы молча. `sqlite3.IntegrityError` от этого
  индекса перехватывается в `create_batch`/`update_batch` и превращается в
  понятный 400 (без обёртки исходно возвращался бы сырой 500).
- **`clear_stale_batch_assignment`** — если контракт элемента меняется (или
  снимается), а назначенная партия принадлежит другому контракту —
  `batch_id` сбрасывается в NULL автоматически. Вызывается сразу после
  `recompute_element_contract_cache` в обоих местах, где тот пересчёт
  происходит (`apply_status_change`, `delete_history_entry`) — без этого
  смена контракта могла бы молча оставить элемент "привязанным" к партии
  чужого контракта.
- **Метка партии** — не хранится, а собирается на сервере
  (`compose_batch_label`, единственный источник форматирования: «Контрагент.
  Номер и дата контракта. Дата») из `contracts.supplier`/`name`/
  `contract_date` + `batches.planned_date`; у старых контрактов без
  `contract_date` часть «от …» просто опускается.
- **`enrich_element_row`** — общий хелпер, добавляющий денормализованные
  скаляры `contract_code`/`batch_planned_date` в уже собранный словарь
  ответа элемента. Вызывается в каждом месте, где элемент возвращается
  клиенту одиночно (`apply_status_change`, оба батч-эндпоинта, `delete_history_entry`)
  — нужен, чтобы допстрока подписи на схеме (см. `Docs/TZ.md` §5.1)
  обновилась сразу после действия, без перезагрузки всей схемы. `GET
  /plan-data` делает то же самое, но не через этот хелпер, а отдельной
  парой лёгких lookup-запросов `id → скаляр` на весь список элементов
  разом (см. раздел 7) — вызывать `enrich_element_row` в цикле по каждому
  элементу означало бы 2 SQL-запроса на элемент вместо 2 на весь список.
- **`batches.contract_id` → `ON DELETE CASCADE`**, но `elements.batch_id`
  → `ON DELETE SET NULL` — партия без контракта бессмысленна (метку не
  собрать), удаление контракта каскадно удаляет все его партии; удаление
  же партии не должно каскадно удалять/портить элементы, только снимать
  привязку.

## 5. Конвейер импорта DXF

Два параллельных конвейера, сосуществующих в одном импорте одного файла
(`app/dxf_import.py:process_upload`, вызывает оба, объединяет результаты
перед записью в БД). **Не дублировать логику при правке одного — они
читают разные, явно непересекающиеся наборы слоёв.**

### 5.0 Общая схема

```
ezdxf.readfile()
    │
    ├─→ [СТАРЫЙ] parse_zhbi.parse_dxf_from_doc()   — слои из LAYER_CONFIG (см. 5.1-5.3)
    │
    ├─→ assign_axes.build_axis_grid_auto()          — сетка осей (общая для обоих конвейеров,
    │                                                   строится ДО зон — нужна "лесенке", см. 5.4.3)
    │
    ├─→ [НОВЫЙ] new_standard_pipeline.process()      — слои WEB_констр_.../WEB_тех_..., НЕ распознанные
    │       │                                          старым конвейером (см. 5.4)
    │       ├─ layer_naming.classify_layers()        — строгая грамматика имён, LayerNameError на отклонении
    │       ├─ parse_new_standard_elements()          — элементы + марки (тот же resolve_via_leaders/
    │       │                                            resolve_via_polygon_texts, что у старого конвейера)
    │       ├─ zone_parser.build_zone_registry_from_classified() — захватка/кран/стоянка + сопоставление имён
    │       └─ zone_binding.bind_element_to_zones()   — привязка каждого элемента к зонам (точка/площадь,
    │                                                    с "лесенкой" сужения стоянки по высоте)
    │
    └─→ assign_axes.assign_address() на КАЖДЫЙ элемент (из ОБОИХ конвейеров) — адрес по осям
            │
            ▼
    import_elements.build_row() → upsert_elements() / save_axis_grid() / upsert_zones() / apply_zone_bindings()
```

Старый конвейер не поддерживает зоны/подтипы/отметки/3D — файлы, размеченные
только по нему, отображаются в 2D-схеме без зон, без 3D-извлечения (3D
опирается на `elevation_mm`, заполняемый только новым конвейером). Оба
конвейера могут дать элементы из одного и того же файла одновременно
(разные слои того же чертежа) — типичный сценарий на реальных файлах
заказчика, где сетка осей и часть старых слоёв ещё по старому стандарту, а
элементы ЖБИ уже переразмечены по новому.

### 5.1 Сопоставление марки с элементом — `resolve_via_leaders()`

Наивный подход «для каждого элемента — ближайшая выноска» ошибается, когда
одна выноска геометрически ближе всего сразу к нескольким элементам.
Реализован **жадный алгоритм по глобальной сортировке**: строятся ВСЕ
пары (элемент, выноска) в пределах порога расстояния, сортируются по
возрастанию расстояния, разбираются жадно (каждый элемент и каждая
выноска — не более одного раза). Сложность — `O(E·L·log(E·L))`, где `E` —
число элементов без атрибута, `L` — число доступных выносок/текстов; на
реальных файлах (сотни-тысячи элементов) это доли секунды, при кратном
росте (десятки тысяч элементов на файл) стало бы узким местом — на
сегодняшних объёмах не является. Используется ОБОИМИ конвейерами (общая
функция в `parse_zhbi.py`, новый конвейер лишь ограничивает пул выносок
слоем "Марка" своей группы, см. 5.4.2).

Порог расстояния (`MAX_LEADER_MATCH_DISTANCE = 1800.0` мм) — подобран
эмпирически под разные профили элементов (колонны: марка у выноски ~50мм
от центроида; ригели: марка — голый текст, до ~1540мм от центроида
вытянутого элемента) и проверен на неоднозначность: для каждой реальной
марки посчитано расстояние до второго по близости кандидата-элемента —
подтверждено, что общий порог не приводит к путанице между соседними
элементами на всех имеющихся тестовых файлах.

### 5.2 Замкнутость контура — не только DXF-флаг

`is_effectively_closed()` — контур считается замкнутым, если явно
выставлен DXF-флаг `closed`, **или** геометрически первая точка контура
совпадает с последней (найдено на реальном файле — часть ригелей
нарисована с повторением первой точки в конце, без выставления флага).
Используется тоже обоими конвейерами (одна и та же функция).

### 5.3 Что не извлекается (старый конвейер)

- Геометрия `INSERT`-блоков — извлекается только точка вставки, не
  реальный контур блока (см. `Docs/TZ.md`, раздел 10). Технически
  возможно, но не понадобилось ни на одном файле заказчика — колонны из
  блоков всегда компактные и хорошо представляются точкой.
- Слои, отсутствующие в `LAYER_CONFIG` — молча игнорируются, без ошибки и
  без записи в лог — это принципиальное отличие от нового конвейера (5.4),
  где нераспознанный `WEB_`-слой — явная ошибка (`LayerNameError`), не
  тихий пропуск. Историческая причина такой разницы: старый конвейер
  проектировался раньше и под менее строгую договорённость с заказчиком
  о слоях; новый стандарт разрабатывался вместе с требованием "ловить
  отклонения от стандарта у проектировщиков сразу".

### 5.4 Новый конвейер: стандартные имена слоёв + зоны

#### 5.4.1 Грамматика имён (`scripts/layer_naming.py`)

Два паттерна, оба под префиксом `WEB_`:
```
Слои ЖБИ:    WEB_констр_<Тип>[_<Подтип>][_ОТМ<знак><высота_мм_5цифр>]_<Роль>
Слои зон:    WEB_тех_<Категория>[_ОТМ<знак><высота_мм_5цифр>]_<Роль>
```
Токенизация по `_`; сравнение каждого токена (тип, роль, подтип, буква
знака отметки, категория зоны) — **без учёта регистра**, но результат
всегда приводится к канонической форме (не сохраняется написание из
файла) — так вся цепочка ниже (группировка слоёв, БД, UI) не зависит от
того, как именно был написан конкретный слой в конкретном файле.
Валидация **строгая**: `LayerNameError` на любом слое с префиксом `WEB_`,
не подходящем ни под одну грамматику — прерывает весь импорт файла с
понятным сообщением (какой слой, какая часть не распознана). Тип элемента
(`ZHBI_TYPES` = Колонна/Ригель/Плита/Панель/Плита перекрытия) и роль
(`Элемент`/`Марка`) зашиты в код; допустимые подтипы — нет, читаются из
таблицы `allowed_subtypes` (параметр функции, редактируется через UI).
Отметка (`ОТМ<П|М><5 цифр>`) — знаковое число в мм, разбирается отдельным
регэкспом (`parse_elevation_token`), обязательна только для зон категории
"Стоянка" (у каждого яруса свой набор стоянок), для "Захватка"/"Кран" —
запрещена (эти зоны сквозные на всю высоту).

Единственная точка, где раньше существовавший (уже отменённый заказчиком)
альтернативный словарь зон мог бы потребовать обратной совместимости —
сознательно НЕ поддерживается: старый вариант ("доп" вместо "тех",
единственное число без "крана") в новых файлах больше не появится, код
для него не пишется заранее "на всякий случай".

#### 5.4.2 Разбор элементов (`new_standard_pipeline.py`)

Слои группируются по ключу `(Тип, Подтип, Отметка)` — внутри каждой
группы ищется пара слоёв ролей "Элемент"/"Марка". Один элемент — один
замкнутый `LWPOLYLINE` на слое роли "Элемент"; марка ищется **только**
среди аннотаций на парном слое роли "Марка" ЭТОЙ ЖЕ группы (не глобально
по всему чертежу) — так разные группы (например, ригели разных ярусов)
не путают друг другу выноски, в отличие от старого конвейера, где весь
пул выносок общий для всего слоя типа.

Для марок плит перекрытия (несколько TEXT-фрагментов без единой выноски,
например "4П"+"-"+"1") используется `resolve_via_polygon_texts` —
группировка голых текстов, лежащих геометрически внутри контура элемента.
**Критично**: этот путь применяется **только когда на слое марок нет ни
одной настоящей выноски** (`LEADER`/`MULTILEADER`) — иначе часть текстов,
которые на самом деле принадлежат выноске (и должны разбираться через
`resolve_via_leaders`), по ошибке уходит в группировку по контуру раньше,
чем до них доходит очередь резолвинга через выноски. Найдено на реальных
данных: применение этого пути безусловно ко всем группам роняло точность
распознавания Ригеля с 2004/2004 через leader до 1746 leader + 128
unresolved. Урок, зафиксированный в коде и здесь: **всегда сверять
mark_source-статистику по ВСЕМ типам после любого изменения в резолвинге
марок, не только по типу, который правился**.

#### 5.4.3 Привязка к зонам (`zone_binding.py`) — метод зависит от типа элемента

- **Точечные** (Колонна) — привязка по точке вставки внутри полигона
  зоны (`Point.distance(polygon) <= 1мм`, допуск компенсирует независимое
  округление координат в DXF между точкой и полигоном).
- **Протяжённые/площадные** (Ригель, Плита, Панель, Плита перекрытия) —
  привязка по доле площади пересечения контура элемента с полигоном
  зоны (`intersection.area / element.area`). Единая метрика (площадь) для
  всех типов, не отдельная "по длине" для ригелей — при примерно
  постоянной ширине ригеля перекрытие по площади пропорционально
  перекрытию по длине, а отдельная метрика длины потребовала бы
  вычислять ось/направление элемента без ощутимой выгоды в точности.
  Порог `OVERLAP_MIN_FRACTION = 0.5` — ниже него зона не присваивается
  вообще (needs_review); `OVERLAP_CLOSE_MARGIN = 0.1` — если два
  кандидата дают близкий результат, тоже needs_review, не гадаем.

**"Лесенка" сужения зоны стоянки крана с высотой** (`build_stance_level_polygons`
+ `compute_column_tier_elevations`) — самый сложный алгоритм в этом модуле.
Физическая модель: кран стоит у ближнего к себе края своей текущей стоянки
и наклоняет стрелу в сторону начала ряда стоянок; на каждом следующем
ярусе здания ближний к крану край окна стоянки отступает на 1 реальный
пролёт сетки осей (считается по факту существующим соседним осям, не по
разнице номеров — пропуски осей допустимы), освободившееся место
подхватывает следующая по номеру стоянка того же крана. Первая стоянка
ряда никогда не отступает своим дальним краем (начало ряда), последняя —
своим ближним (забирает всё, что осталось выше). На нулевом ярусе
(уровень земли) используется исходный, нарисованный полигон стоянки без
подрезки по сетке (есть небольшой технологический зазор, который подрезка
срезала бы без причины); на ярусах выше — подрезка режется из полигона
рабочей зоны КРАНА целиком (не отдельной стоянки — с яруса 1 "родное" окно
стоянки может выйти за пределы её собственного нарисованного полигона,
подхватывая уступленное соседом). Стоянки без однозначно определённого
крана (`parent_match_status != "matched"`) или без номера в названии — не
участвуют в лесенке, используют исходный полигон на всех ярусах
(безопасный fallback, не отказ). Проверено сквозным синтетическим тестом
`scripts/verify_zone_pipeline.py` на `test_data/synthetic_zones.dxf`.

Индекс яруса — по уникальным отметкам элементов типа "Колонна" (тот же
приём, что и вычисление высоты элемента в 3D — `computeColumnLevels()` во
фронтенде, см. 6.5); отметки вне диапазона известных ярусов зажимаются
к крайнему, чтобы ни один элемент не остался без возможности отнесения к
стоянке.

#### 5.4.4 Сопоставление названий зон (`zone_parser.py`)

Название зоны на реальных чертежах приходит как `MULTILEADER` (выноска с
текстом), не `TEXT`/`MTEXT` — точка для сопоставления с полигоном берётся
как **остриё выноски** (`arrow`), а не место, где висит сам текстовый блок
(текст обычно вынесен за пределы зоны, остриё указывает непосредственно
на неё). Тот же допуск по расстоянию (`NAME_MATCH_TOLERANCE_MM = 1.0`),
что и у привязки элементов — компенсирует независимое округление координат
между выноской и полигоном. Не сопоставилось ни с одним полигоном, или
сопоставилось сразу с несколькими — явно помечается `unmatched`/`ambiguous`
в `review`, не гадаем. Та же логика (`_link_stances_to_cranes`) определяет,
какому крану принадлежит каждая стоянка (point-in-polygon центроида
стоянки внутри полигона крана).

## 6. Ключевые алгоритмы фронтенда

### 6.1 Разводка коллизий подписей — bucket-based, не полный перебор

И `computeLabelOffsets()` (выбор направления подписи один раз при
загрузке), и `updateLabelCollisionVisibility()` (скрытие/показ подписей
по текущему масштабу) используют **пространственную сетку бакетов**
вместо попарного сравнения всех подписей со всеми (`O(n²)`): каждый
элемент кладётся в бакет по своим координатам, при проверке коллизии
просматриваются только 9 соседних бакетов (3×3). Радиус маркера/оценка
плотности (`estimate_marker_radius`, `app/main.py`) с раунда "плотные
многоярусные файлы" построена на `shapely.strtree.STRtree` — наивная
медиана расстояния до ближайшего соседа рушилась почти до нуля на файлах
с многоярусными геометрическими двойниками по X,Y (несколько ярусов
колонн, спроецированных в одну точку плана).

Обе функции пересчитываются **при каждом изменении `viewBox`** (колесо
мыши/перетаскивание) — без троттлинга/дебаунса. На сегодняшних объёмах
(сотни-тысяча элементов) не создаёт видимой задержки; при кратном росте
числа элементов это стало бы кандидатом на оптимизацию.

### 6.2 Рендеринг 2D-схемы — SVG в мировых координатах, масштаб через `viewBox`

Все геометрические сущности рисуются **в исходных координатах DXF**, без
пересчёта в экранные пиксели на стороне JS — масштабирование и
панорамирование выполняет сам SVG через атрибут `viewBox`. Единственное,
что реально пересчитывается в JS при каждом зуме — то, что **обязано**
оставаться постоянного экранного размера несмотря на масштаб: радиус
условных маркеров, размер шрифта подписей, отступ закреплённых подписей
осей от края экрана.

Инверсия оси Y: DXF использует Y-up, SVG — Y-down — решается одной
трансформацией `scale(1,-1)` на группе-обёртке (`#flip`); подписи внутри
получают **вторую**, локальную `scale(1,-1)`, чтобы не оказаться
отражёнными по вертикали. Допстрока подписи марки (партия, см. 4.4)
рендерится **отдельным** `<text>`-элементом со своей независимой мировой
Y-координатой, а не вторым `<tspan>` внутри существующего — пересчитывать
знак смещения `dy` внутри уже контрперевёрнутой группы для второй строки
был признан лишним риском визуальной ошибки без возможности проверить её
в браузере (см. раздел 10 про отсутствие браузерного тестирования).
Контраст подписи на любом фоне — не буквальная подложка (риск
позиционирования того же класса), а белый контур вокруг букв
(`stroke`+`paint-order: stroke` в CSS).

### 6.3 Разграничение клика и перетаскивания

`DRAG_THRESHOLD_PX = 4` — перетаскивание схемы включается только после
того, как курсор сдвинулся более чем на 4px от точки `mousedown`; клик
без реального перетаскивания (в пределах порога) не двигает `viewBox` и
не блокирует последующий `click` на фигуре. Без этого порога обычное
дрожание руки при клике трактовалось как намеренное перетаскивание.

### 6.4 Состояние — единый глобальный объект, без реактивного фреймворка

Весь клиентский стейт живёт в одном объекте `state` (элементы, выбор
файлов/слоёв, текущий вид, кэши DOM-узлов по id элемента, `subLabelById`,
`batchCache` и т.д.). Перерисовка — императивная: каждая функция
(`renderElements`, `renderLegend`, `showCard`, `updateElementSubLabel`...)
явно вызывается после мутации соответствующих данных, нет автоматического
отслеживания зависимостей (как в React/Vue). Точечные обновления (партия/
статус одного элемента) вызывают точечные функции перерисовки, а не полный
`renderElements()` — компромисс, требующий от каждого нового изменения
явно решить, "что ещё нужно перерисовать после этого", без автоматической
проверки на уровне архитектуры.

### 6.5 3D-режим схемы (Three.js)

Отдельный визуальный режим, включаемый по требованию (не заменяет 2D,
переключение — та же схема, тот же `state`). Three.js **0.160.0**,
вендорено **локально** в `app/static/vendor/three/` (только
`three.module.min.js` + `examples/jsm/controls/OrbitControls.js`, никаких
`CSS2DRenderer`/`TextGeometry`/`Line2`/`LineMaterial` — эти возможности
специально избегались, чтобы не тянуть больше стороннего кода, см. ниже).
**Правило проекта**: вендоринг НОВОГО стороннего кода требует явного
подтверждения пользователя каждый раз отдельно — уже было получено для
Three.js, но действует заново при любом дополнительном модуле оттуда же.

#### 6.5.1 Координаты и построение мешей

`world.X = dxf.x`, `world.Y = высота (elevation)`, `world.Z = -dxf.y` —
геометрия элемента строится через `THREE.ExtrudeGeometry` из 2D-контура
(в локальных XY, глубина экструзии = высота элемента), затем
`geometry.rotateX(-Math.PI / 2)` переводит локальную ось экструзии Z
(0..height) в мировую Y (вверх), позиция задаётся `mesh.position.set(0,
elevation_mm, 0)`. Знак у `Z` — не случаен: без минуса геометрия
зеркалилась по одной из горизонтальных осей относительно 2D-вида (найден
и исправлен реальный баг, см. `Docs/backlog.md`, "Баг: зеркальность
3D-плана"). Высота яруса колонн — `computeColumnLevels()`, тот же принцип
уникальных отметок по возрастанию, что у `compute_column_tier_elevations`
в бэкенде (5.4.3), но независимая реализация на фронтенде (не общий код —
разные языки/рантаймы).

#### 6.5.2 Граница элементов — три версии, текущая работает от обратного

Задача: однотипные примыкающие элементы одного статуса (одинаковая
заливка) не должны визуально сливаться в одно пятно без видимой границы
между соседями. История трёх версий важна не только как факт, но и как
предостережение от повторения тех же двух ошибок:

1. **`THREE.EdgesGeometry` + `THREE.LineSegments`** — формально верный
   подход (рёбра силуэта как отдельная геометрия), провалился на практике:
   `THREE.LineBasicMaterial.linewidth` не работает в большинстве браузеров
   — WebGL1/ANGLE клэмпит толщину GL-линии к 1px независимо от заданного
   значения (задокументированное ограничение самого WebGL, не баг
   реализации). Тонкая 1px линия на масштабе всего чертежа (десятки-сотни
   метров) визуально теряется. Настоящий "толстый line" в Three.js требует
   `Line2`/`LineMaterial` из `examples/jsm/lines/` — новый сторонний код,
   отклонено ради избежания повторного вендоринга.
2. **Меш границы ШИРЕ основного на 8% от центроида и НИЖЕ на фиксированные
   25мм** (`build3DOutlineMesh`, дочерний объект основного меша) —
   работала только там, где у элементов был реальный зазор. Для впритык
   примыкающих элементов (плиты перекрытия) расширенная граница одного
   элемента заходила на территорию соседа, где её закрывал уже ЕГО
   собственный полноразмерный основной меш — граница между плитами не
   появлялась вообще, ровно то, что сообщил заказчик по скриншоту. Плюс
   оба меша (граница/заливка) делили одну нижнюю Y-координату — z-fighting
   (мерцание) при взгляде снизу.
3. **Текущая версия (2026-07-19) — ролями наоборот.** Граница строится по
   **истинному** контуру и истинной высоте элемента, без масштабирования.
   Цветной (статусный) меш, наоборот, **уже** истинного контура на
   `OUTLINE_INNER_SCALE = 0.94` (6%, равномерно от центроида) и **выше/
   ниже своей истинной высоты на `OUTLINE_VERTICAL_MARGIN_MM = 15` мм с
   ОБЕИХ сторон** (не только сверху, как во второй версии). Граница —
   по-прежнему дочерний объект, но теперь дочерний объект ЦВЕТНОГО меша,
   смещён на `+15мм` по Y относительно родителя, чтобы совпасть по
   вертикали с истинным положением элемента. Эффект: контуры границ
   соседних элементов сходятся ровно по истинной общей грани без захода на
   территорию друг друга (работает и для впритык примыкающих элементов);
   диапазон Y цветного меша охватывает диапазон Y границы на 15мм с обеих
   сторон при любом ракурсе (включая снизу) — z-fighting исключён
   геометрически, не эвристикой рендер-порядка. Цвет границы —
   затемнённая версия того же статусного цвета (`darkerColor`, множитель
   0.55 на канал, не фиксированный чёрный — читается при любом цвете
   статуса, включая уже тёмные), пересчитывается вместе с заливкой при
   каждой смене статуса/выбора. Геометрия/материал дочернего меша границы
   освобождаются явно при очистке сцены (дочерние объекты не диспозятся
   автоматически при диспозе родителя в Three.js).

   Проверено изолированным Node-тестом с мок-стабом THREE.js (8/8
   геометрических утверждений: охват Y с обеих сторон, истинность размера
   контура границы, корректное уменьшение цветного меша) — **живой
   браузерной проверки не было** (инструмент автоматизации браузера
   недоступен в CLI-сессиях этого проекта, см. раздел 10), это открытый
   пробел на момент написания.

#### 6.5.3 Подписи марок — постоянные спрайты с подложкой

`THREE.Sprite` + `canvas`-текстура (не `CSS2DRenderer`, чтобы не тянуть ещё
один сторонний модуль) — билборд, всегда развёрнут к камере, размер не
меняется при вращении. На canvas перед текстом рисуется полупрозрачная
белая подложка (`rgba(255,255,255,0.72)` + `fillRect` на весь холст) —
даёт контраст на любом цвете элемента под спрайтом, буквальная реализация
запроса заказчика (в отличие от 2D, где подложка заменена контуром букв,
см. 6.2, — риск позиционирования в 3D ниже, т.к. спрайт целиком строится
на одном canvas без внешнего SVG-флипа). Допстрока партии (`elementSubLabelText`,
см. 4.4/`Docs/TZ.md` §5.1) дополняет тот же canvas вторым `fillText` меньшим
шрифтом — высота canvas увеличивается только когда вторая строка есть.
Цвет текста — персональная настройка пользователя (`currentLabelColor()`,
`DEFAULT_LABEL_COLOR = "#222222"`, см. раздел 7 — единый дефолт, заменивший
два ранее рассинхронизированных значения `#333`/`#222` в 2D/3D по
отдельности).

Известный риск, принятый как компромисс: порядка тысяч дополнительных
объектов сцены (меш + дочерняя граница + спрайт на каждый видимый
элемент) — на сегодняшних объёмах (сотни-тысяча элементов) не создаёт
заметной просадки FPS по ручной проверке, отдельного профилирования не
проводилось.

#### 6.5.4 Управление камерой и зоны в 3D

`OrbitControls.zoomSpeed = 4` — дефолт библиотеки (1) рассчитан на
"стандартный" масштаб сцены, для чертежей в миллиметрах/метрах ощущается
как заметно медленный на трекпаде. Зоны (захватка/кран/стоянка) в 3D
рендерятся полупрозрачными плоскостями на своей отметке; **не участвуют в
raycasting** (клик всегда "сквозь" них — реагируют только элементы) —
не мешают выбору элементов, даже если визуально перекрывают их сверху.
Подсказка при наведении — если курсор задерживается на одном и том же
элементе дольше 1 секунды без вращения/панорамирования камеры.

## 7. API-дизайн

REST-подобный, но не строго RESTful в паре мест — осознанно:
- `POST /plan-data` (не `GET`) — тело запроса содержит произвольной
  длины список `{source_file, layers[]}`, что не укладывается в
  query-параметры чисто технически. Эндпоинт также обогащает список
  элементов денормализованными скалярами `contract_code`/`batch_planned_date`
  **одной парой lookup-запросов на весь список** (`id → code`/`id →
  planned_date`, две выборки по всем контрактам/партиям сразу, не по
  одному запросу на элемент) — при сотнях элементов с назначенной партией
  отдельный запрос на партию/контракт под каждый был бы неприемлем.
- `PATCH /elements/{id}/status` принимает `contract_id` как часть тела
  того же запроса, различая «поле не передано» (наследовать контракт от
  предыдущей записи истории) от «поле передано как `null`» (явно «без
  контракта») через `body.model_fields_set` (Pydantic v2) — тонкость,
  которую легко нарушить будущими изменениями модели.
- `PATCH /elements/{id}/batch` / `PATCH /elements/bulk-batch` — назначение
  партии, **независимое** от `/status` (свой отдельный эндпоинт, не
  параметр в теле смены статуса) — отражает бизнес-решение "партия не
  привязана к смене статуса" (см. 4.4). `bulk-batch`, как и `bulk-status`
  до него, атомарен: валидация всех элементов пачки до применения любого
  изменения, единый 400 со списком проблем при любой ошибке.
- `DELETE /elements/{id}/history/{history_id}` — единственный DELETE, не
  укладывающийся в чистую CRUD-модель "элемент неизменяем после создания":
  нужен, потому что backdating (workdate) иногда требует убрать ошибочно
  добавленную запись истории, а не просто добавить исправляющую — с явным
  запретом удалить последнюю оставшуюся запись элемента (иначе элемент
  остался бы без статуса вовсе).

Авторизация — на уровне зависимостей FastAPI (`Depends(get_current_user)`
/ `Depends(require_editor)` / `Depends(require_admin)`), проверяется **на
каждом эндпоинте отдельно**, нет глобального middleware, накладывающего
проверку роли по паттерну пути. Добавление нового эндпоинта без явного
`Depends(...)` с нужной ролью **не будет автоматически защищено** —
ответственность на том, кто пишет новый роут (см. раздел 10 про
отсутствие тестов на этот случай). Self-service паттерн (менять можно
только себе, если не admin: `current["role"] != "admin" and
current["id"] != user_id` → 403) — установлен для `set-password`
(`app/users.py`), переиспользован без изменений для `PATCH
/users/{id}/label-color` — эталон для любых будущих личных настроек.

## 8. Модель конкурентности

- Все обработчики маршрутов — синхронные (`def`, не `async def`);
  Starlette/FastAPI автоматически уводит их в threadpool, поэтому
  блокирующие вызовы (`sqlite3`, `ezdxf.readfile`/`shapely` на большом
  файле) не блокируют event loop для других запросов.
- Подключение к SQLite — **одно на запрос** (`get_connection()` в начале,
  `conn.close()` в `finally`), без пула соединений. Для SQLite это
  нормально (открытие соединения дёшево), но при высокой частоте запросов
  создаёт накладные расходы на открытие файла на каждый вызов.
- `PRAGMA journal_mode` **не** переключён в WAL (используется режим по
  умолчанию — rollback journal) — при **одновременной записи** SQLite
  последовательно блокирует писателей (только один writer в любой момент
  времени), и в non-WAL режиме запись блокирует параллельное чтение на
  время транзакции. Для типичного профиля использования (несколько
  человек на объекте, редкие одновременные записи) не проблема; при росте
  одновременных пользователей — первый кандидат на переключение в WAL.
- Загрузка и обработка DXF (`/import-dxf`) — **полностью синхронная в
  рамках одного HTTP-запроса**, клиент ждёт завершения без промежуточного
  прогресса. На файлах ~45МБ — секунды, не минуты; при кратном росте
  размера файлов или сложности (два конвейера + зоны + shapely-геометрия
  теперь считаются в одном запросе) это стало бы более заметным
  кандидатом на фоновую обработку с поллингом статуса, чем на момент
  первой архитектурной ревизии.

## 9. Безопасность

### 9.1 Аутентификация и сессии

- Пароли — PBKDF2-HMAC-SHA256, 260 000 итераций, соль на пользователя
  (`secrets.token_hex(16)`, криптографически случайная). В пределах
  текущих рекомендаций OWASP для PBKDF2-SHA256 (≥210 000 на 2023 год).
- Токен сессии — `secrets.token_urlsafe(32)` (256 бит энтропии), хранится
  в БД как есть (не хэшируется дополнительно — компрометация БД даёт
  готовые сессионные токены; для внутреннего инструмента с доверенным
  хранилищем принято как допустимый риск).
- Cookie сессии: `httponly=True` (недоступна из JS), `samesite="lax"`
  (частичная защита от CSRF), `secure` — **управляемый флаг**
  (`ZHBI_SECURE_COOKIES=1`, `app/auth.py:31`), по умолчанию выключен, т.к.
  текущее развёртывание — чистый HTTP в закрытой сети без
  TLS-терминирующего прокси (`Docs/DEPLOYMENT_WINDOWS.md`); включить
  переменной окружения, когда/если появится HTTPS. **Статус: механизм
  реализован (было — жёстко `False`), включение — эксплуатационное
  решение, не код.**
- Истечение сессии проверяется на сервере при каждом запросе
  (`WHERE expires_at > datetime('now')`), не только через истечение самой
  cookie на клиенте — корректно.
- `GET /login-users` — публичный эндпоинт, отдающий список ФИО+логинов
  для формы входа. Осознанный компромисс, задокументированный в коде:
  упрощает вход ценой раскрытия списка валидных логинов
  неаутентифицированному клиенту. **Статус: не менялось, остаётся
  осознанным компромиссом**, приемлемым для внутреннего инструмента.
- **Ограничение частоты попыток входа — реализовано** (`app/auth.py:39-49`,
  `_check_login_rate_limit`): по IP клиента (не по логину — логины и так
  публичны через `/login-users`, блокировка по логину позволила бы
  атакующему намеренно запереть чужого пользователя), окно 300 секунд,
  максимум 5 попыток, превышение → `429`. In-memory (`_login_attempts`,
  один процесс uvicorn, без внешнего кэша) — сбрасывается при перезапуске
  сервера и не разделяется между несколькими воркерами/процессами, если
  таковые появятся. **Статус: исправлено** (было "не исправлено" на
  снимке 2026-07-15).

### 9.2 Авторизация

Три роли (`admin`/`user`/`view`), проверяются **и в UI** (скрытие
элементов управления), **и на бэкенде** (403 при прямом обращении к API
в обход интерфейса) — подтверждено прямыми запросами в обход UI в ходе
разработки.

### 9.3 SQL-инъекции

Не найдено ни одного места, где значения, пришедшие от клиента,
подставляются в SQL-строку напрямую (проверено повторно при этом
пересмотре, включая новые модули `app/batches.py`/`scripts/zone_*.py` —
везде f-string интерполирует только структуру запроса, значения всегда
идут отдельным параметризованным аргументом).

### 9.4 XSS — исправлено

**Было подтверждённой уязвимостью (stored XSS) на снимке 2026-07-15,
теперь исправлено** (`Docs/backlog.md`, "Исправления по безопасности —
✅ реализовано", 2026-07-17). Ядро проблемы: карточка элемента и
множество других мест вставляли значения, пришедшие из пользовательского
ввода (марка элемента — текст, извлечённый парсером напрямую из
содержимого загруженного DXF; ФИО, названия контрактов/партий и т.п.), в
DOM через `innerHTML` без экранирования. Добавлен единый хелпер
`escapeHtml()` (`app/static/index.html:969`) и применён во всех местах
интерполяции в `innerHTML`-шаблоны — подтверждено `grep`
(порядка 20+ вызовов на момент этого пересмотра, во всех местах,
включая новые, добавленные после исходного фикса — карточка партии,
модалки контракта/партии). **Правило для будущих правок: любой НОВЫЙ
код, вставляющий данные пользователя в `innerHTML`, обязан использовать
`escapeHtml()` — регрессия сюда была бы возвратом уже закрытой
уязвимости.**

### 9.5 Загрузка файлов

- Имя файла очищается через `Path(upload_file.filename or "").name`
  (`app/dxf_import.py:59`) — защита от path traversal корректна.
- Содержимое файла не проверяется до попытки разбора `ezdxf.readfile()` —
  единственная защита от не-DXF содержимого — то, что `ezdxf` не сможет
  его распарсить (перехватывается широким `except Exception`, превращается
  в понятную 422-ошибку).
- **Нет явного ограничения размера загружаемого файла** — ни на уровне
  приложения, ни видимой конфигурации ASGI-сервера. **Статус: не
  исправлено**, тот же риск, что и на предыдущем снимке — теоретическая
  возможность DoS через загрузку огромных файлов, смягчается тем, что
  загрузка доступна только аутентифицированным `user`/`admin`. С учётом
  того, что теперь на каждый импорт приходится ДВА конвейера плюс
  shapely-геометрия зон, стоимость обработки одного файла выросла
  относительно снимка 2026-07-15 — риск не увеличился качественно, но
  стал чуть заметнее количественно.

### 9.6 Раскрытие чувствительных данных

`GET /settings/export` (только `admin`) сознательно включает
`password_hash`/`password_salt` пользователей в экспортируемый JSON —
задокументировано в коде и в `Docs/TZ.md` как целенаправленное решение
(перенос между серверами без пересоздания паролей). Без изменений с
предыдущего снимка.

### 9.7 CORS

Middleware CORS не подключён — frontend раздаётся тем же FastAPI-
приложением, что и API, кросс-origin доступ не требуется и не открыт.

## 10. Тестирование

**Автоматических тестов в классическом смысле (`pytest`-сюита) в
репозитории по-прежнему нет**, но появился один сквозной синтетический
тест: `scripts/verify_zone_pipeline.py`, гоняемый вручную против
`test_data/synthetic_zones.dxf` (генерируется
`scripts/generate_test_zones_dxf.py`) — покрывает конвейер зон/привязки
целиком, включая "лесенку" сужения стоянки. Остальная верификация —
как и раньше, вручную: изолированные Python/Node-скрипты в `/tmp`,
тестирующие извлечённые функции на РЕАЛЬНЫХ данных из `data/zhbi.db`,
плюс прямые `curl`-запросы к живому серверу.

**Живого браузерного тестирования (реальные клики мышью, визуальная
проверка позиционирования/z-fighting/цвета) по-прежнему нет** — это
ограничение СРЕДЫ разработки этого проекта (CLI-сессии Claude Code без
включённых инструментов автоматизации браузера на момент написания), не
архитектурное решение продукта. Каждый раунд UI-правок, затрагивающий
визуальное позиционирование (2D-подписи, 3D-геометрия границ, подложки),
явно помечен как "проверено изолированным тестом логики, не проверено
визуально" — эта оговорка стоит воспринимать буквально при дальнейшей
работе: свежая сессия, продолжающая проект, должна либо включить
браузерные инструменты (`/chrome` в Claude Code), либо явно просить
пользователя проверить golden path глазами после каждой такой правки.

**Рекомендация при дальнейшем развитии**, без изменений с прошлого
снимка: зафиксировать хотя бы критичные пути (парсинг DXF на референсных
файлах, миграции БД, авторизация) как автоматические тесты (`pytest`).

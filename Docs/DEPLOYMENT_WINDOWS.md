# Установка на Windows 11 и обновление без потери данных

Практическое руководство для человека, который будет ставить и
поддерживать ЖБИ на конкретном компьютере с Windows 11 — не требует
знания Python. Вспомогательные скрипты лежат в `scripts/windows/`
(запускаются двойным кликом).

Технический фон — `Docs/ARCHITECTURE.md`; что система умеет —
`Docs/TZ.md`. Здесь — только "как поставить и не потерять данные".

## 0. Главное правило на всю статью

**Данные и код — в разных местах, и это нарочно:**

| Папка | Что там | При обновлении |
|---|---|---|
| `data\zhbi.db` | Вся база: элементы, статусы, история, контракты, пользователи | **НИКОГДА не трогать, не удалять, не перезаписывать** |
| `Input\` | DXF-чертежи, которые сервер сам подхватывает при каждом запуске | **Не трогать** |
| `uploads\` | DXF, загруженные через кнопку в браузере | **Не трогать** |
| `.venv\` | Установленные Python-библиотеки | Можно пересоздать, но обычно просто обновляется |
| `app\`, `scripts\`, `Docs\`, `requirements.txt`, `CLAUDE.md`, `.gitignore` | Код программы | Это и есть то, что заменяется при обновлении |

Все пути внутри программы — относительные (`data/zhbi.db` и т.п.
считаются от папки, где лежит `app/`), поэтому саму папку проекта можно
свободно переносить/переименовывать целиком — главное не путать код и
данные ВНУТРИ неё при обновлении.

## 1. Первая установка (один раз)

### 1.1 Установить Python

Скачать с официального сайта: https://www.python.org/downloads/windows/
— любая версия 3.11 или 3.12 подходит. При установке **обязательно**
отметить галочку **«Add python.exe to PATH»** на первом экране мастера
установки — без неё команда `python` не будет находиться в терминале.

Проверка: открыть **PowerShell** (кнопка Пуск → набрать "PowerShell") и
выполнить:
```
python --version
```
Должно показать что-то вроде `Python 3.12.x`. Если пишет "не является
внутренней или внешней командой" — Python либо не установлен, либо PATH
не подхватился (переустановить с галочкой выше, либо перезайти в
Windows после установки).

### 1.2 Скопировать проект на компьютер

Код версионируется в приватном репозитории на GitHub (см. раздел 3) —
получить его на компьютер:
```
git clone https://github.com/<ваш-аккаунт>/zhbi-tool.git C:\zhbi-tool
```
(Понадобится Git для Windows — https://git-scm.com/download/win,
обычный мастер установки, значения по умолчанию подходят. При первом
обращении к репозиторию Windows попросит войти в GitHub — см. раздел
3.2.)

Если git по каким-то причинам недоступен — можно и через ZIP-архив
папки проекта от разработчика (флешка/сетевая папка), но тогда
обновляться придётся вручную копированием файлов — см. раздел 4, там
это на порядок муторнее и рискованнее git.

### 1.3 Установить зависимости

Двойной клик по `scripts\windows\install.bat` в папке проекта. Скрипт
сам:
- проверит, что Python найден;
- создаст папку `.venv` (изолированное окружение для библиотек проекта,
  не влияет на остальной Python на компьютере);
- поставит все нужные библиотеки (`requirements.txt`).

Первый запуск качает несколько десятков мегабайт из интернета — нужен
доступ в сеть на этом шаге. Если скрипт ругается на установку какой-то
библиотеки — см. раздел 6 (диагностика).

### 1.4 Первый запуск

Двойной клик по `scripts\windows\run.bat`. Окно останется открытым и
будет печатать журнал работы сервера — **это нормально, окно не
закрывать**, пока сервер должен работать.

В браузере на этом же компьютере открыть **http://localhost:8000**.
Должна открыться страница входа. Логин по умолчанию — `admin`, пароль —
**пустой** (просто нажать «Войти», ничего не вводя в поле пароля).

**Сразу после первого входа** — «Настройки → Сменить пароль» и задать
реальный пароль администратору. Пустой пароль у `admin` — это
состояние "только что установили", оставлять его в таком виде для
реальной работы не стоит.

### 1.5 Доступ с других компьютеров сети

`run.bat` запускает сервер так, что он слушает не только сам себя, а
всю локальную сеть (`--host 0.0.0.0`) — это уже сделано за вас. Осталось:

1. **Узнать IP-адрес компьютера** в локальной сети: PowerShell →
   `ipconfig` → строка "IPv4-адрес" (обычно вида `192.168.x.x`).
2. **Разрешить порт в Брандмауэре Windows** — при первом запуске
   `run.bat` Windows обычно сама покажет всплывающее окно "Разрешить
   доступ для приложений Python в этой сети?" — нажать **Разрешить** для
   "Частных сетей". Если окно не появилось (или нажали "Отмена" по
   ошибке) — Панель управления → Брандмауэр Windows Defender →
   Дополнительные параметры → Правила для входящих подключений → Создать
   правило → Порт → TCP → указать `8000` → Разрешить подключение.
3. С другого компьютера в той же сети открыть в браузере
   `http://<IP-адрес-сервера>:8000`.

**Про HTTPS**: сейчас сервер работает по обычному HTTP (без шифрования)
— приемлемо для закрытой локальной сети. Если когда-нибудь появится
HTTPS (например, через reverse-proxy с TLS-сертификатом) — задать
переменную окружения `ZHBI_SECURE_COOKIES=1` перед запуском `run.bat`,
тогда cookie сессии будет помечена флагом `Secure` (браузер перестанет
отправлять её по обычному HTTP — поэтому включать только вместе с
реальным HTTPS, иначе вход перестанет работать).

### 1.6 Чтобы сервер работал постоянно (не только пока открыто окно)

Базового варианта (`run.bat` + не закрывать окно) достаточно, если
компьютер не выключается и в окно никто случайно не нажмёт Ctrl+C. Для
надёжной постоянной работы — на выбор, от простого к надёжному:

- **Простой**: ярлык на `run.bat` в папке автозагрузки Windows
  (`Win+R` → `shell:startup` → положить туда ярлык) — сервер стартует
  при каждом входе в систему. Минус: если из системы выйти (не просто
  заблокировать, а именно выйти), сервер остановится вместе с сессией.
- **Надёжный**: Планировщик заданий Windows (Task Scheduler) — создать
  задачу с триггером "При запуске компьютера", действие — запуск
  `run.bat`, в свойствах задачи отметить **"Выполнять вне зависимости от
  того, выполнен ли вход пользователя в систему"**. Тогда сервер
  переживёт и выход пользователя, и перезагрузку.
- **Как настоящая служба Windows** (для тех, кто хочет от системы
  максимальной автономности) — сторонний бесплатный инструмент [NSSM](https://nssm.cc/)
  оборачивает `run.bat` в настоящую службу Windows с автоматическим
  перезапуском при сбое. Не обязательно для старта — но стоит держать в
  уме, если инструмент станет критичным для ежедневной работы бригад.

## 2. Резервное копирование

Вся база — это один файл `data\zhbi.db`. Резервная копия = копия этого
файла.

Двойной клик по `scripts\windows\backup.bat` — сохранит копию с меткой
даты/времени в `data\backups\` (эта папка не входит в код/git, только
на этом компьютере). Делать это стоит:
- перед любым обновлением (см. раздел 3/4 — обновление и так делает это
  автоматически, но лишняя копия не помешает);
- периодически на всякий случай (например, раз в неделю — можно
  добавить `backup.bat` в тот же Планировщик заданий с триггером "По
  расписанию").

Для более надёжного хранения — копировать `data\backups\*.db` куда-то
за пределы этого же компьютера (сетевой диск, другой сервер) — локальная
копия не спасёт при поломке самого диска.

## 3. Разработка и обновление через git (рекомендуемая схема)

Код версионируется в приватном репозитории на GitHub. Модель — одна
ветка `main` (всё, что готово к использованию) + **теги релизов**
(конкретные проверенные точки, которые устанавливаются на продуктовую
машину). Данные (`data\`, `Input\`, `uploads\`) не в git вообще — `git
pull`/`git checkout` физически не могут их задеть.

```
Mac разработчика (Claude Code)
   │  git commit, затем git push
   ▼
GitHub — ветка main + теги релизов (v2026.07.20 и т.п.)
   │                                   │
   │ update-git-test.bat               │ update-git-prod.bat
   │ (всегда последняя версия main)    │ (только выбранный тег)
   ▼                                   ▼
Тестовая установка                Продуктовая установка
(проверяем новое до продакшена)   (то, чем реально пользуются бригады)
```

### 3.1 Разовая настройка репозитория на GitHub

Уже сделано локально на компьютере разработчика: `git init` +
первый коммит со всем кодом (без `data\`/`Input\`/`uploads\`/
`test_data\` — тестовые чертежи разработчика решаем отдельно, см. ниже).
Осталось создать сам репозиторий на GitHub и связать его — самый простой
путь, раз уже установлен VS Code:

1. Открыть папку проекта в VS Code (Файл → Открыть папку).
2. Слева — иконка **Control source** («Система контроля версий», три
   точки на ветке). Там уже будет виден 1 коммит.
3. Нажать **«Опубликовать в GitHub» / «Publish to GitHub»**. VS Code
   попросит один раз войти в GitHub (откроется браузер) — войти тем же
   аккаунтом.
4. Выбрать **приватный репозиторий** (Private) — обязательно, в коде и
   истории могут быть детали реальных чертежей/контрактов заказчика.
   Имя можно оставить `zhbi-tool`.
5. VS Code сам создаст репозиторий на GitHub и запушит первый коммит.

(Альтернатива без VS Code — через сайт github.com: создать новый
**private**-репозиторий БЕЗ инициализации README/.gitignore, затем на
компьютере разработчика `git remote add origin <адрес>` и
`git push -u origin main`.)

### 3.2 Подключение тестовой и продуктовой установок

На каждом из двух Windows-компьютеров вместо копирования ZIP-архива
(п.1.2) — клонирование репозитория:
```
git clone https://github.com/<ваш-аккаунт>/zhbi-tool.git C:\zhbi-tool
```
При первом обращении к приватному репозиторию Windows попросит войти в
GitHub — стандартный **Git Credential Manager** (ставится вместе с Git
для Windows) откроет окно браузера для входа, дальше запоминает сессию,
повторно логиниться не придётся. Дальше — обычная установка (п.1.3
install.bat и т.д.), только пропускаем ручное копирование файлов.

### 3.3 Повседневная разработка

Работа с кодом (через Claude Code — в терминале или в расширении Claude
Code для VS Code — без разницы, какой вход использовать) идёт на
компьютере разработчика. После того как изменения проверены локально:
```
git add -A
git commit -m "Что и почему изменилось"
git push
```
На этом этапе изменения появились на GitHub, но **ни тестовая, ни
продуктовая установки ещё не обновились** — обновление всегда
происходит отдельным явным шагом на нужной машине (ниже).

### 3.4 Обновление тестовой установки — всегда последняя версия

На тестовой машине: двойной клик по
`scripts\windows\update-git-test.bat`. Скрипт делает резервную копию
базы, `git pull` (подтягивает всё, что запушено в `main`), переустанавливает
зависимости на случай изменений в `requirements.txt`. Дальше — обычная
проверка вживую (открыть в браузере, попробовать то, что менялось).

### 3.5 Выпуск релиза для продакшена

Когда изменения на тестовой установке проверены и всё в порядке — **на
компьютере разработчика** помечаем эту точку тегом и отправляем на
GitHub:
```
git tag v2026.07.20 -m "Краткое описание, что вошло в релиз"
git push origin v2026.07.20
```
(Формат тега — например `vГГГГ.ММ.ДД`, можно и просто по возрастанию:
`v1`, `v2`... — главное, чтобы легко было отличать релизы друг от
друга.)

### 3.6 Обновление продуктовой установки — только по выбранному релизу

На продуктовой машине: двойной клик по
`scripts\windows\update-git-prod.bat`. Скрипт делает резервную копию
базы, скачивает список тегов и **спрашивает, какой именно релиз
поставить** — вводится точное имя тега (например `v2026.07.20`) из
показанного списка. Продуктовая установка **никогда** не подтянет что-то
новое сама по себе, даже если это уже есть на GitHub — только то, что
явно выбрали. После обновления `git status` может показать "detached
HEAD" — это нормальное, ожидаемое состояние для установки, закреплённой
за конкретным релизом, а не "едущей" вместе с разработкой.

### 3.7 Тестовые чертежи разработчика (`test_data\`)

Папка `test_data\` (147 МБ реальных чертежей, используются в разработке
для проверки) сейчас **не включена** в первый коммит — большие бинарные
файлы, попав в git, остаются в истории репозитория навсегда (даже если
файл потом удалить, место не освобождается без отдельной "хирургии"
истории). Решить отдельно, до следующего коммита: включать ли их
(GitHub справится с репозиторием такого размера, просто он не будет
"лёгким") или держать эти файлы только локально у разработчика/на общем
диске, вне git. На тестовую/продуктовую установки эта папка в любом
случае не нужна — не используется работающим сервером.

## 4. Обновление копированием файлов — резервный вариант, если git недоступен

Если разработчик присылает обновление как новый ZIP-архив/папку — **ни
в коем случае не распаковывать его прямо поверх рабочей папки с заменой
всего** (велик риск случайно затереть `data\`/`Input\`/`uploads\`, если
они окажутся в архиве пустыми папками-заглушками). Порядок действий:

1. Двойной клик по `scripts\windows\backup.bat` — резервная копия базы
   на всякий случай.
2. Закрыть окно `run.bat` (остановить сервер).
3. Распаковать новый архив в **отдельную** временную папку (не поверх
   рабочей).
4. Скопировать из временной папки в рабочую **только** эти файлы/папки,
   заменяя старые:
   - `app\`
   - `scripts\` (все, кроме `scripts\windows\`, если в нём есть свои
     локальные правки — обычно можно смело заменять и его тоже)
   - `Docs\`
   - `requirements.txt`
   - `CLAUDE.md`
   - `.gitignore`
5. **НЕ копировать и не трогать**: `data\`, `Input\`, `uploads\`,
   `.venv\`, `test_data\` (тестовые файлы разработчика, не нужны на
   рабочем сервере), `output\` (если есть — черновой мусор от ручных
   запусков скриптов).
6. Двойной клик по `scripts\windows\install.bat` ещё раз — на случай,
   если в обновлении поменялся список зависимостей (`requirements.txt`)
   — команда безопасна, если ничего не изменилось, просто ничего не
   переустановит заново.
7. Запустить `run.bat`, проверить, что всё открывается и данные (старые
   элементы, статусы) на месте.

## 5. Диагностика типичных проблем

- **"python не является внутренней или внешней командой"** — Python не
  в PATH, см. 1.1 (переустановить с галочкой "Add to PATH").
- **`install.bat` падает на установке какой-то библиотеки** — обычно
  помогает: обновить `pip` вручную (`python -m pip install --upgrade
  pip`) и повторить; либо переустановить Python более новой версией
  (3.11/3.12) — у используемых библиотек (`ezdxf`, `shapely`, `lxml`,
  `reportlab` и др.) есть готовые сборки под Windows для актуальных
  версий Python, старые версии Python иногда таких сборок не находят.
- **PowerShell пишет про "выполнение сценариев отключено"** при попытке
  запустить `.ps1` напрямую — не запускайте `backup.ps1` напрямую,
  используйте `backup.bat` (он обходит это ограничение только для
  своего собственного запуска, ничего не меняя в системе).
- **С другого компьютера сети страница не открывается**, а на самом
  сервере — открывается — см. 1.5 (Брандмауэр/IP-адрес). Также
  проверить, что оба компьютера в одной сети (не гостевой Wi-Fi с
  изоляцией клиентов).
- **После обновления пропали чертежи/статусы** — значит на шаге 4
  что-то из `data\`/`Input\`/`uploads\` было случайно заменено. Если
  делали `backup.bat` перед обновлением — восстановить: остановить
  сервер, скопировать нужный файл из `data\backups\` поверх
  `data\zhbi.db`, запустить сервер заново.
- **Порт 8000 занят другой программой** — открыть `scripts\windows\
  run.bat` в Блокноте, поменять строку `set PORT=8000` на другой номер
  (например `8080`), сохранить, запускать как обычно — просто в адресе
  браузера тоже указывать новый порт.
- **`git clone`/`git pull` просит логин и пароль, пароль не принимается**
  — GitHub больше не принимает обычный пароль аккаунта для git по HTTPS.
  Обычно всплывающее окно от Git Credential Manager решает это само
  (вход через браузер) — если окно не появилось, убедиться, что при
  установке Git для Windows не отключали Git Credential Manager (это
  значение по умолчанию, отключать его незачем).
- **После `update-git-prod.bat` в `git status` написано "HEAD detached
  at ..."** — это ожидаемо и не ошибка (см. 3.6): продуктовая установка
  специально закреплена за конкретным релизом, а не следует за `main`.

## 6. Не проверялось вживую

Все шаги в этом документе основаны на анализе кода проекта (все пути —
относительные, зависимости — стандартные Python-библиотеки с готовыми

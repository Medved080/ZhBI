## 0. Зачем

Изначально на объекте было три зоны кранов — вертикальные призмы (контур в
плане без отметки, от земли до верха). Позже их детализировали стоянками с
ярусами по высоте. Краны работали параллельно и в соседние зоны не заходили.

Теперь соседние краны могут работать над одним и тем же местом: то, что на
нижних этажах монтирует кран 1, выше монтирует кран 2. Жёсткая вертикальная
зона крана этого не описывает.

**Решение пользователя:** отдельная зона крана (зона работы крана)
упраздняется. Стоянки остаются как есть. Зона работы крана — это набор всех
его стоянок, объёмная фигура из «коробок» по уровням. Это может быть
лесенка, вертикальный столб — что угодно. Захватки не трогаем: они остаются
вертикальными призмами на прежнем механизме.

## 1. Правило привязки (инвариант, не пересматривать)

1. **Уровни объекта** `L0 < L1 < … < Ln` — уникальные `elevation_mm` всех
   рабочих ярусов ВСЕХ стоянок ВСЕХ кранов в данной редакции (черновике).
   Служебные отметки сохранённых назначений (§4.3) в этот набор не входят.
2. **Ярус стоянки** на отметке `Lk` — «коробка»: его контур по X/Y ×
   полоса по высоте `[Lk, Lk+1)`. Ярус на верхнем уровне `Ln` действует до
   верха здания.
   - В действующем ядре без лесенки сначала определяется кран, затем
     ближайшая нижняя отметка среди ВСЕХ его стоянок; кандидатами становятся
     только стоянки на этой отметке. Если кран не определён однозначно,
     поиск уровня идёт среди всех стоянок. Это НЕ правило «до следующего
     яруса той же стоянки». Другие читатели и визуализация могут отличаться
     от ядра: при конверсии эталон — сохранённые назначения изделий (§4).
   - Если стоянка должна покрывать несколько уровней, у неё несколько
     ярусов, по одному на уровень. Контур копируется или меняется.
   - Если на уровне ни у одной стоянки нет яруса над данной точкой, деталь
     там не относится ни к какому крану. Так и задумано.
3. **Уровень детали** — последний `Lk ≤ elevation_mm`. Для
   `TIER_CAPPING_TYPES` (ригель, плита перекрытия) — последний
   `Lk < elevation_mm`: они венчают ярус снизу. Правило из
   `Docs/DECISIONS.md` «Импорт DXF, зоны, геометрия» сохраняется. Деталь
   ниже `L0` относится к `L0`, как и сейчас (зажим к крайнему).
4. **Кандидаты** — ярусы ВСЕХ стоянок на уровне детали. Сужения «сначала
   свой кран» больше нет: крана до стоянки ещё не знаем. Метод сопоставления
   прежний: точка вставки с допуском `POINT_MATCH_TOLERANCE_MM` для колонн и
   деталей без контура, доля площади для остальных, пороги
   `OVERLAP_MIN_FRACTION` / `OVERLAP_CLOSE_MARGIN` и статус `needs_review`.
5. **Кран детали = `parent_zone_id` найденной стоянки.** Статус крана равен
   статусу стоянки (`matched` / `unmatched` / `needs_review`).
6. **Деталь без `elevation_mm`** → стоянка и кран `not_applicable`, крана
   нет. Сейчас такой детали кран давал плоский полигон — см. §4, конверсия.
7. **Стоянки разных кранов на одном уровне не пересекаются по площади.**
   Касание гранями допустимо. Проверка идёт между ВСЕМИ стоянками объекта по
   полосам уровней, а не только внутри одного крана, как сейчас.
   Историческое наложение, уже бывшее в основе черновика, не ухудшать —
   сохраняется действующий допуск `validate_zones` «не больше исходной
   площади пересечения».
8. **Ручное назначение** (overrides черновика) сохраняется целиком, включая
   «кран без стоянки» и «без зоны». Инвариант 7 из
   `crane-zone-versions-design.md` не меняется. Ярус ручной стоянки
   определяется отметкой детали по тем же уровням объекта. Исключения
   перехода сохраняют прежние статусы и отчётную отметку явно (§4.3);
   их нельзя молча пересчитывать как новое ручное назначение.
9. **Автоматической «лесенки» больше нет.** `build_stance_level_polygons`
   строила ярусы из контура крана по сетке осей. Её однократно
   материализуют в явные ярусы стоянок — при конверсии (§4) и при импорте
   однотипного чертежа (§6). Дальше ярусы правят руками.

## 2. Модель данных

- Строки `zones` с `category = 'Кран'` **остаются**: идентичность (номер),
  имя, цвет (`zone_colors`), родитель стоянок, ключ `schedule_flow` по
  имени. Их строки `zone_levels` удаляются конверсией, `zones.outline_json`
  и `zones.elevation_mm` крана → NULL.
- Снимок НОВОЙ редакции и черновика (`zones_json`): у крана `levels: []`. Читатели
  старых опубликованных снимков, где у крана есть контур, обязаны это
  выдерживать: история и сравнение редакций показывают старый контур как
  исторический и ничего не пересчитывают.
- `elements.zone_crane_id/_status`, `zone_stance_id/_status`,
  `zone_stance_level_id` и `crane_zone_version_assignments` **без изменений
  схемы**. Это главный рычаг: отчёты, фильтры, план-график, Ганта, экспорт,
  каталог изделий читают готовые поля и переписываться не должны — только
  проверяться.
- Новых таблиц и колонок задание не требует. Если понадобятся — описание в
  `app/db_schema_doc.py` и перегенерация `scripts/gen_db_schema_drawio.py`.
  В частности, сохранение старой отчётной отметки отдельно от активной
  геометрии (§4.3) может потребовать расширения `zone_levels` и формата
  снимка. Схема полей назначений изделий и исторических назначений остаётся
  прежней. Служебные отметки не участвуют в геометрической привязке.
- Новое значение `crane_zone_versions.kind = 'conversion'` (§4). Описать в
  `db_schema_doc.py` рядом с `baseline / published / rollback`.
  Этот вид допустим только для перехода с доказанно неизменными назначениями.

## 3. Что меняется в коде (найдено разведкой 2026-09-26)

### 3.1. Ядро привязки — `scripts/zone_binding.py`
- Новая чистая функция без SQL, например `object_stance_levels(zones)`, и
  привязка по стоянкам: вход — стоянки с ярусами и деталь (тип, x, y,
  контур, отметка); выход — стоянка, отметка яруса, кран, статусы.
- `bind_element_to_zones`: категория «Кран» больше не ищется по полигону, а
  выводится из стоянки. «Захватка» — без изменений.
- `_candidates_for_category` для стоянки: полоса по уровням объекта вместо
  ближайшего нижнего уровня среди стоянок предварительно выбранного крана.
- `build_stance_level_polygons`, `compute_column_tier_elevations`: остаются
  только как инструмент материализации (§4, §6), не в рабочей привязке.
- Одно правило на весь проект. Дубли снэпа привести к ядру:
  - `app/crane_zone_editor.py` — ярус ручной стоянки в
    `preview_assignments`;
  - `app/db.py` — `_heal_zone_stance_levels`;
  - `app/zone_recalc.py` — старый путь, для кранов и стоянок
    версионированных объектов уже отвечает 409; проверить, что обходного
    пути нет.
- Старую семантику привязки сохранить как явно отделённый инструмент
  конверсии и совместимости неподготовленных объектов (§4.1, §4.4).
  Инвентаризация вызовов через AST должна включать `app/shaft_panels_host.py`
  и построение родителя в `_zone_records`: после удаления ярусов крана
  родитель стоянки не может зависеть от наличия `zone_levels` у крана.

## 4. Конверсия существующих данных — обработка релиза

Запись в `app/release_tasks.py`, НЕ скрипт. Идемпотентна: повторный запуск
ничего не меняет. Упавшая не роняет старт. Копия базы перед обработкой
делается штатно. Преобразование выполняется для каждого ЖБИ-объекта с
версионностью; успех фиксируется только после полной сверки.

### 4.1. Общий алгоритм и исходное состояние

- Этап 2 «только отчёт» и обработка релиза вызывают ОДИН преобразователь:
  вход — неизменённый снимок зон, изделий, осей, ручных назначений и
  редакций; выход — кандидат новой геометрии, назначения, расхождения и
  причины. Сам преобразователь не пишет в БД. Отдельный алгоритм для
  предварительного отчёта не допускается.
- До любых изменений прочитать все старые контуры кранов и стоянок,
  отметки, происхождение, текущие назначения, действующую и ожидающие
  активации редакции. Не фильтровать ярусы крана в `snapshot_zones`:
  иначе `build_stance_level_polygons` потеряет исходный материал.
- Эталон по каждому актуальному изделию: `element_id`, `element_uid`,
  `crane_zone_id`, `crane_status`, `stance_zone_id`, `stance_status`,
  `stance_elevation_mm` через текущий `zone_stance_level_id`. Сравнивать
  отметку, а не нестабильный числовой ID яруса; различать NULL и статусы.
  Отдельно сохранить ручной источник, поступления после последней редакции
  и контрольные значения контракта, поставщика и статуса изделия.
- Сопоставить текущий снимок с действующей редакцией и зарегистрированными
  поступлениями. Изменения вне редакции не узаконивать конверсией:
  сообщить о них и не записывать преобразование объекта.

### 4.2. Преобразование геометрии

1. **Один физический ярус с лесенкой.** Материализовать результаты
   `build_stance_level_polygons` на отметках колонн, используя исходные
   контуры кранов и сетку осей. `None` означает намеренное отсутствие
   рабочего объёма. Такие окна НЕ заполняются нижним контуром. При
   добавлении промежуточных уровней других кранов делить фактическую
   полосу лесенки, сохраняя её контур либо пустоту. Отсутствие необходимых
   осей/отметок — отдельная причина невозможности автоматического
   преобразования, а не повод подставить произвольную геометрию.
2. **Исходные многоярусные стоянки.** Восстановить интервалы кандидатур по
   действующему ядру (§1.2): между соседними отметками данного крана
   участвуют только стоянки выбранной отметки. Делить эти интервалы по
   общим уровням объекта, копируя только реально действовавшие контуры.
   Продлевать отдельно каждую стоянку до следующего её собственного яруса
   запрещено. Особые случаи, в том числе отсутствие однозначного крана,
   фиксировать сравнением со старой привязкой, без обещания геометрической
   эквивалентности там, где её нет.
3. После материализации убрать геометрию крана из КАНДИДАТА. Рабочие
   таблицы до публикации остаются неизменными. Посчитать новые назначения
   ядром §1 и сравнить полный набор полей из §4.1 с эталоном.
4. Старые пересечения вывести в сводку. Они не мешают конверсии с
   сохранением назначений; последующие черновики не могут ухудшать их
   (§1.7). Сохранение назначений не разрешает создавать новые пересечения
   ошибочным заполнением пустых полос.

### 4.3. Сохранение назначений и публикация

- Рекомендуемый вариант В1 — сохранить прежние назначения. Все
  расхождения, включая только статус или только отметку яруса, становятся
  наследуемыми исключениями `source = 'conversion'`. Исключение хранит
  полный прежний набор полей §4.1 и причину; оно не сводится к двум ID.
  Прежние ручные назначения сохраняют приоритет, даже если сейчас
  совпадают с геометрией. Их происхождение не теряется при преобразовании.
- Если прежняя отчётная отметка не представлена активным ярусом новой
  геометрии, сохранить её служебной ссылкой отдельно от рабочих объёмов
  (§2). Нельзя создавать фиктивный рабочий контур ради ссылки: это меняет
  общие уровни объекта и назначения остальных изделий. Исторический слой
  отчётов должен восстанавливать и такие отметки. Формат этого хранения
  определить на этапе 2 по выявленным случаям, реализовать на этапе 3.
- Исключения наследуются обычным и импортным черновиком, проходят через
  сохранение, предпросмотр и публикацию без нормализации статусов и
  повторного вычисления сохранённой отметки. Явная отмена возвращает
  геометрическое правило; явное переназначение становится обычным
  `manual`. Несовместимость сохранённого назначения с изменённым
  родителем стоянки или удалением нужной ссылки требует понятной ошибки
  и явного решения оператора. Нельзя терять исключение молча.
- После применения исключений повторить поштучную сверку. Только при
  полном равенстве опубликовать `kind = 'conversion'`,
  `effective_date` = день ФАКТИЧЕСКОЙ успешной конверсии по Москве,
  `note` «Переход: зона крана = объединение стоянок», полный снимок
  назначений. В одной транзакции сохранить редакцию, материализовать
  текущие зоны и назначения, выполнить проверки и зафиксировать успех.
  Перед записью под `BEGIN IMMEDIATE` повторно проверить основу и состав
  ожидающих редакций: результат предварительного отчёта не разрешает
  применить кандидат к изменившемуся объекту.
  Предусмотреть конверсию в день уже действующей публикации: равенство дат
  допускается только для этого технического перехода с равными назначениями,
  обычные правила дат публикации не ослаблять.
- Только такие редакции `conversion` исключаются из `period_corrections`.
  Метки зон, принадлежность стоянок и состав доступных на дату изделий
  также сохраняются. Предыдущие обычные корректировки на ту же дату
  продолжают разделять период. Отчёты через конверсию должны давать те же
  назначения, включая ярус, что до неё; поступления учитываются по своей
  дате. Исходные опубликованные снимки не переписываются.
- Альтернатива В1 «без крана» меняет назначения и требует явного изменения
  пользователем требования о сохранности. Такой переход оформляется
  обычной корректировкой с разрешённой датой, учитывается в
  `period_corrections`; исключать его из границ отчётов под видом
  `conversion` запрещено. Проверки отчётов тогда ожидают разделения периода.
- Открытые черновики после успешного перехода получают устаревшую основу.
  Изменения контракта, поставщика, статуса изделия и захватки запрещены.

### 4.4. Будущие редакции и незавершённый переход

- Этап 2 отдельно перечисляет объекты с опубликованными будущими и уже
  наступившими, но ещё не активированными редакциями. При их наличии
  задать В4 (§8) и закрепить стратегию ДО этапа 3. До решения такие
  объекты не конвертировать; наличие отложенных объектов не является
  успешным завершением обработки.
- Рекомендация В4 — выполнить переход объекта после штатного вступления
  опубликованной редакции в силу, сохранив её дату и снимок. Альтернативная
  поддержка параллельного перехода требует отдельного описания активации
  и выбора редакций. Нельзя переписывать или отменять будущую редакцию,
  применять её раньше даты либо после конверсии возвращать её старую
  геометрию в новые рабочие таблицы.
- Явно различать последнюю опубликованную редакцию и действующую на дату.
  Проверить `_latest`, `version_for_date`, создание черновика, сверку
  текущего состояния и `activate_due`; порядок `revision_no` не заменяет
  выбор по дате действия. Зафиксировать порядок обработки релиза и
  активации при старте, после полуночи и при повторе обработки кнопкой.
- При ошибке или отложенном переходе сервер продолжает работу: старые
  данные и отчёты доступны для чтения в старой семантике, новый редактор и
  запись крановых назначений для неподготовленного объекта закрыты с
  объяснением причины. Штатная активация ранее опубликованного снимка
  выполняется совместимым старым путём до конверсии. Старый формат нельзя
  подавать в новую материализацию или незаметно считать новым ядром.
- Состояние готовности определить явно; пустой список ярусов крана сам по
  себе не является признаком успешной конверсии. Повтор после ошибки
  сверяет актуальную основу и не дублирует уже выполненные переходы.
  Успех одного объекта не скрывает ошибку другого. Автоматические
  «исправления» в `init_db`, включая `_heal_zone_stance_levels`, не вправе
  менять версионированные назначения вне этого протокола.

### 4.5. Проверки конверсии

- `scripts/dry_run_migration.py` прогоняет обработки дважды ВНУТРИ одного
  запуска. Его текущего сравнения количеств строк недостаточно: расширить
  проверку содержимым `zones`, `zone_levels`, полями назначений `elements`,
  таблицами редакций, исторических назначений, поступлений и черновиков.
  После повтора не меняются значения, источники, ID и число редакций;
  все старые опубликованные снимки остаются неизменными. Служебный журнал
  попыток обработки сравнивать отдельно от предметных данных.
- Поштучное равенство итоговых назначений эталону; неизменность контрактов,
  поставщиков, статусов изделий и захваток. Отдельные сравнения до/после
  для ручных назначений, NULL, `needs_review`, изменения только яруса и
  зарегистрированных поступлений после последней редакции.
- Сбой после записи снимка и посередине материализации полностью
  откатывает изменения объекта; повтор после сбоя и обычный повтор после
  успеха безопасны. Проверить перезапуск сервера после каждого случая.
- Наследование `conversion` через два обычных черновика и импортный,
  публикации, явную отмену и ручное переназначение; фильтр исключений и
  счётчики совпадают с сервером.
- Отчёты на дату до/после и за период через конверсию: «Статус
  комплектации», «График поставки», «Аналитическая справка» (включая
  группировку по ярусам), Ганта; экран, PDF и XLSX. Обычная корректировка
  в том же периоде по-прежнему даёт отказ с датой разделения.
- Сводка: геометрическое совпадение 1:1; итоговое совпадение после
  исключений; расхождения по причинам, включая только ярус/статус;
  пересечения; неподготовленные объекты и ожидающие редакции.
- Перед выкладкой пользователь делает холостой прогон на копии боевой базы
  ИМЕННО того сервера, куда выкатываем (`CLAUDE.md`, «Git и деплой»).

## 6. Импорт DXF

- `scripts/zone_parser.py` `_link_stances_to_cranes` определяет родителя
  стоянки пересечением с контуром крана и разрезает общую стоянку на краны.
  По умолчанию контур крана из чертежа используется ТОЛЬКО для этого и в
  черновик как геометрия не попадает (решение — вопрос В2, §8).
- `app/crane_zone_import.py` (предвалидация и черновик) и `app/dxf_import.py`:
  - однотипный чертёж (один ярус стоянок) → лесенка материализуется в явные
    ярусы черновика по §4.2;
  - черновик проходит новую валидацию (§1.7). Нарушение — это черновик с
    ошибкой, которую видит оператор, а не падение импорта. Разделить ошибки
    геометрии, допускающие сохранение черновика, и нераспознанные имена,
    номера или родителей, при которых импорт по-прежнему останавливается
    до записи изделий. Предпросмотр/публикация ошибочной геометрии запрещены;
    сохранение промежуточного черновика должно позволять её исправление.
  - импортный черновик наследует `manual` и `conversion` по §4.3;
    существующие назначения и опубликованные редакции импорт не меняет.
- `scripts/new_standard_pipeline.py` — первичная загрузка нового объекта без
  версий: привязка тем же ядром §1.
- `scripts/verify_zone_pipeline.py` обновить под новое правило.

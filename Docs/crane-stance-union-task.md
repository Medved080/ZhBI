## 0. Зачем

Изначально на объекте было три зоны кранов — вертикальные призмы (контур в
плане без отметки, от земли до верха). Позже их детализировали стоянками с
ярусами по высоте. Краны работали параллельно и в соседние зоны не заходили.

Теперь соседние краны могут работать над одним и тем же местом: то, что на
нижних этажах монтирует кран 1, выше монтирует кран 2. Жёсткая вертикальная
зона крана этого не описывает.

**Решение пользователя:** отдельная зона крана (зона работы крана)
упраздняется. Стоянки остаются как есть. Зона работы крана — это набор всех
его стоянок, объёмная фигура из «коробок» по уровням. Это может быть
лесенка, вертикальный столб — что угодно. Захватки не трогаем: они остаются
вертикальными призмами на прежнем механизме.

## 1. Правило привязки (инвариант, не пересматривать)

1. **Уровни объекта** `L0 < L1 < … < Ln` — уникальные `elevation_mm` всех
   ярусов ВСЕХ стоянок ВСЕХ кранов в данной редакции (черновике).
2. **Ярус стоянки** на отметке `Lk` — «коробка»: его контур по X/Y ×
   полоса по высоте `[Lk, Lk+1)`. Ярус на верхнем уровне `Ln` действует до
   верха здания.
   - Это изменение против текущего поведения: сейчас ярус тянется до
     следующего яруса ТОЙ ЖЕ стоянки.
   - Если стоянка должна покрывать несколько уровней, у неё несколько
     ярусов, по одному на уровень. Контур копируется или меняется.
   - Если на уровне ни у одной стоянки нет яруса над данной точкой, деталь
     там не относится ни к какому крану. Так и задумано.
3. **Уровень детали** — последний `Lk ≤ elevation_mm`. Для
   `TIER_CAPPING_TYPES` (ригель, плита перекрытия) — последний
   `Lk < elevation_mm`: они венчают ярус снизу. Правило из
   `Docs/DECISIONS.md` «Импорт DXF, зоны, геометрия» сохраняется. Деталь
   ниже `L0` относится к `L0`, как и сейчас (зажим к крайнему).
4. **Кандидаты** — ярусы ВСЕХ стоянок на уровне детали. Сужения «сначала
   свой кран» больше нет: крана до стоянки ещё не знаем. Метод сопоставления
   прежний: точка вставки с допуском `POINT_MATCH_TOLERANCE_MM` для колонн и
   деталей без контура, доля площади для остальных, пороги
   `OVERLAP_MIN_FRACTION` / `OVERLAP_CLOSE_MARGIN` и статус `needs_review`.
5. **Кран детали = `parent_zone_id` найденной стоянки.** Статус крана равен
   статусу стоянки (`matched` / `unmatched` / `needs_review`).
6. **Деталь без `elevation_mm`** → стоянка и кран `not_applicable`, крана
   нет. Сейчас такой детали кран давал плоский полигон — см. §4, конверсия.
7. **Стоянки разных кранов на одном уровне не пересекаются по площади.**
   Касание гранями допустимо. Проверка идёт между ВСЕМИ стоянками объекта по
   полосам уровней, а не только внутри одного крана, как сейчас.
   Историческое наложение, уже бывшее в основе черновика, не ухудшать —
   сохраняется действующий допуск `validate_zones` «не больше исходной
   площади пересечения».
8. **Ручное назначение** (overrides черновика) сохраняется целиком, включая
   «кран без стоянки» и «без зоны». Инвариант 7 из
   `crane-zone-versions-design.md` не меняется. Ярус ручной стоянки
   определяется отметкой детали по тем же уровням объекта.
9. **Автоматической «лесенки» больше нет.** `build_stance_level_polygons`
   строила ярусы из контура крана по сетке осей. Её однократно
   материализуют в явные ярусы стоянок — при конверсии (§4) и при импорте
   однотипного чертежа (§6). Дальше ярусы правят руками.

## 2. Модель данных

- Строки `zones` с `category = 'Кран'` **остаются**: идентичность (номер),
  имя, цвет (`zone_colors`), родитель стоянок, ключ `schedule_flow` по
  имени. Их строки `zone_levels` удаляются конверсией, `zones.outline_json`
  и `zones.elevation_mm` крана → NULL.
- Снимок редакции и черновика (`zones_json`): у крана `levels: []`. Читатели
  старых опубликованных снимков, где у крана есть контур, обязаны это
  выдерживать: история и сравнение редакций показывают старый контур как
  исторический и ничего не пересчитывают.
- `elements.zone_crane_id/_status`, `zone_stance_id/_status`,
  `zone_stance_level_id` и `crane_zone_version_assignments` **без изменений
  схемы**. Это главный рычаг: отчёты, фильтры, план-график, Ганта, экспорт,
  каталог изделий читают готовые поля и переписываться не должны — только
  проверяться.
- Новых таблиц и колонок задание не требует. Если понадобятся — описание в
  `app/db_schema_doc.py` и перегенерация `scripts/gen_db_schema_drawio.py`.
- Новое значение `crane_zone_versions.kind = 'conversion'` (§4). Описать в
  `db_schema_doc.py` рядом с `baseline / published / rollback`.

## 3. Что меняется в коде (найдено разведкой 2026-09-26)

  только как инструмент материализации (§4, §6), не в рабочей привязке.

## 4. Конверсия существующих данных — обработка релиза

Запись в `app/release_tasks.py`, НЕ скрипт. Идемпотентна: повторный запуск
ничего не меняет. Упавшая не роняет старт. Копия базы перед обработкой
делается штатно. На каждый ЖБИ-объект с версионностью:

1. Взять текущий снимок: `snapshot_zones` плюс текущие `elements.zone_*`.
2. **Материализовать лесенку.** Если в объекте один физический ярус стоянок
   и есть сетка осей — ярусы каждой стоянки строятся на отметках колонн
   через `build_stance_level_polygons`, как сейчас делает
   `preview_assignments`. Пустые окна (None) — яруса нет.
3. **Сохранить высоту полос.** Для каждой стоянки на каждом уровне объекта
   `Lk`, где у неё нет своего яруса, но действовал её нижележащий ярус (по
   старому правилу «до следующего своего»), дописать ярус с копией этого
   контура.
4. Убрать ярусы кранов.
5. Пересчитать привязку новым ядром (§1) и **поштучно сверить** с текущими
   `elements.zone_crane_id / zone_stance_id / zone_stance_level_id`
   (отметкой).
6. Опубликовать новую редакцию `kind = 'conversion'`:
   - `effective_date` = день обновления;
   - `note` «Переход: зона крана = объединение стоянок»;
   - полный снимок назначений;
   - `period_corrections` не считает `conversion` корректировкой, потому что
     назначения идентичны по построению (п. 5 и 7). Отчёты за период через
     дату обновления не блокируются.
7. **Расхождения** — детали, которым новая геометрия дала другой результат.
   Типичные случаи: кран без стоянки по старому полигону; деталь без
   отметки; два крана на одном уровне пересекаются.
   - По умолчанию — сохранить прежнее назначение ручным override с
     `source = 'conversion'`. Такие детали должны быть видны в редакторе
     отдельным фильтром.
   - Счётчики — в сводку обработки.
   - Окончательное решение — вопрос пользователю В1 (§8) по реальным
     числам.
8. Пересечения стоянок разных кранов, найденные конверсией, не мешают
   публикации конверсионной редакции: это исходные данные. Они выводятся в
   сводку и блокируют только ухудшение в последующих черновиках (§1.7).
9. Опубликованные редакции не переписываются. Открытые черновики получают
   «устаревшую основу» штатным механизмом, и оператор создаёт новый.

Проверка:
- `scripts/dry_run_migration.py` на копии обезличенной БД прогоняет
  обработки дважды: второй проход — 0 изменений;
- сводка: объектов, совпавших 1:1; деталей с override `conversion` в
  разбивке по причинам; найденных пересечений;
- перед выкладкой пользователь делает холостой прогон на копии боевой базы
  ИМЕННО того сервера, куда выкатываем (`CLAUDE.md`, «Git и деплой»).

## 6. Импорт DXF

- `scripts/zone_parser.py` `_link_stances_to_cranes` определяет родителя
  стоянки пересечением с контуром крана и разрезает общую стоянку на краны.
  По умолчанию контур крана из чертежа используется ТОЛЬКО для этого и в
  черновик как геометрия не попадает (решение — вопрос В2, §8).
- `app/crane_zone_import.py` (предвалидация и черновик) и `app/dxf_import.py`:
  - однотипный чертёж (один ярус стоянок) → лесенка материализуется в явные
    ярусы черновика по §4.2;
  - черновик проходит новую валидацию (§1.7). Нарушение — это черновик с
    ошибкой, которую видит оператор, а не падение импорта.
- `scripts/new_standard_pipeline.py` — первичная загрузка нового объекта без
  версий: привязка тем же ядром §1.
- `scripts/verify_zone_pipeline.py` обновить под новое правило.

  `conversion` (рекомендация — ничего не меняется в отчётах, чистится в
  редакторе) или отпустить в «без крана»?
- **В2 (перед этапом 7).** В новых чертежах контур крана ещё рисуется?
  Использовать его только для определения родителя стоянки (рекомендация)
  или определять кран по подписи стоянки или слою?
- **В3 (этап 5).** Верх верхнего уровня в 3D — до верха модели, как сейчас:
  подтвердить на живой картинке.

Новые разночтения, найденные по ходу, — тоже вопросом, а не решением
исполнителя (`CLAUDE.md`, стоячие инструкции).

## 9. Вне области

- Захватки (остаются призмами).
- Учёт по блокам МФР.
- Публикация задним числом (по-прежнему запрещена).
- Автоматическая раскладка стоянок по дуге стрелы крана.

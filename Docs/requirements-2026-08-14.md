Подсистема настройки прав и новые роли делаются в СОСЕДНЕЙ сессии
(`app/features.py`, `app/roles.py`, таблица `feature_access`). Здесь только

- комплектовщику открывается импорт контрактации (0:04) — настройкой
  порога раздела.

Работы этой ветки к правам не прикасаются, но АРМ прораба заводится с
ключом раздела, чтобы его можно было выдать роли.

## B. АРМ прораба — новое рабочее место

**B1. Левая панель — полный набор фильтров «Модели»** (2:20–3:51).
Те же фильтры, что во вкладке «Фильтры» модели, всегда развёрнуты слева.
По высоте не помещаются — прокрутка ползунком плюс сворачиваемые группы,
чтобы каждый развернул нужные ему и уложился в один экран (механизм
сворачивания групп уже есть, `state.topFilterCollapsed`).

**B2. Правая панель — свойства, статус, вид** (3:51). Как сейчас: выбор
элементов слева, работа со статусом и свойствами справа.

**B3. Закрепление панели свойств — во ВСЕХ режимах** (4:20–5:00).
Сейчас клик в рабочей области сворачивает свойства и возвращает к выбору
элементов; при работе с отфильтрованным набором свойства приходится
включать заново на каждое изделие. Панель свойств должна оставаться
закреплённой. Требование общесистемное, не для одного АРМа — **в первую
очередь для режима «Модель»**.

**B4. Закрепить верхнюю строку правой панели** (5:10–5:38). Строка вкладок
(«Свойства / Статус / Фильтры / Вид») уходит за верхний край при прокрутке
панели вниз — зафиксировать. Тоже во всех режимах с закреплённой правой
панелью, в первую очередь в «Модели».

## E. Планирование: базовый и актуализированный график

**E1. Два набора дат, у актуализированного — история версий** (8:22–9:23,
21:45–22:10). Даты начала и окончания у изделия — **директивные**:
отвечают на вопрос «когда это надо», а не «насколько мы отстаём». Базовый
график загружен и не меняется. Рядом загружается **актуализированный**
(текущий прогноз); при загрузке — явный выбор, какой из двух грузим.
Актуализация у заказчика идёт раз в неделю, при необходимости чаще;
пересчёт снаружи занимает ~10 минут (20:00–20:50).

Каждая загрузка актуализированного графика — **новая версия, предыдущие
сохраняются** (решение пользователя 14.08). Отсюда: хранить не пару полей
у изделия, а таблицу версий (дата загрузки, автор, файл) и даты изделий по
версии. Видно, как менялся прогноз по одному и тому же изделию от
загрузки к загрузке. Базовый график — такая же сущность, но помеченная
базовой и единственная.

**E2. Отклонение от базового графика** (8:22–9:33). Разница
актуализированного и базового — отставание в днях/неделях, по изделию и по
срезам. Считается **по обеим датам** — и по монтажу, и по поставке
(решение пользователя 14.08). Это то, по чему заказчик докладывает.

**E3. Прогноз завершения** (9:33–10:13). На S-кривой от текущей точки факта
— штрихпунктирная линия прогноза завершения, рассчитанная по
актуализированному графику, а не нарисованная.

**E4. Исходные данные расчёта — редактируемые таблицы в системе**
(12:19–17:36). Сейчас живут в Excel-обработке Power Query
(`!_Обработка данных из WEB.xlsx`) и задаются заказчиком вручную. Разбор
файла показал ровно ТРИ таблицы ручного ввода — их и заводим в системе:

1. **Темп монтажа** — изделий в сутки на один кран; задаётся по паре
   **тип + подтип** (лист `hide`, 13 строк на все 9,4 тыс. изделий).
   Значения: от 5 (колонна средняя нижний ярус) до 50 (плиты перекрытия на
   верхних отметках). К объекту и захватке не привязан.
2. **Порядок монтажа** — очередь видов работ внутри одного этажа стоянки,
   тоже по паре тип + подтип (лист `02_Technology`, 13 строк): колонна
   нижняя → ригель периметральный → колонна средняя нижний ярус → ригель
   +15.000 → плита +15.000 → и так вверх по отметкам.
3. **Поток** — очередь фронтов работ крана, по тройке **кран + стоянка +
   этаж** (лист `03_Flow`, 200 строк): в каком порядке кран проходит свои
   стоянки и этажи.

Количество изделий в каждом фронте берётся из модели — четвёртая таблица
(`01_WBS`, 663 строки: захватка/кран/стоянка/этаж/вид работ/количество/темп)
целиком выводится из этих трёх и выгрузки ВОР, руками в ней ничего не
задаётся.

**E5. Порядок: сначала загрузка, потом расчёт** (17:45–18:13). Сначала
система принимает уже рассчитанные снаружи данные (MS Project + макрос).
Собственный расчёт — вторым шагом, когда данные E4 будут в системе. При
расчёте внутри график обязан пересчитываться от факта: запланировано 10
колонн, смонтировано 20 — остаток пересчитывается, иначе на стыке факта и
плана разрыв (19:49–20:26).

**Механика расчёта восстановлена по файлам** (см. разбор ниже) — MS Project
для второго шага не нужен, движок воспроизводится внутри системы.

**E6. Формат загрузки** — Excel-выгрузка MS Project, 6-й уровень структуры;
колонки: работа, начало, окончание, кран, захватка, стоянка, этаж.
Разобран реальный пример, см. ниже.

## Разбор присланного файла актуализированного графика

`grafik_ms_project (москвич 14.08.2026).xlsx`, один лист, 663 строки.

Колонки: `Название задачи | Начало | Окончание | Кран | Захватка | Стоянка |
Этаж`. Даты — текст MS Project («Чт 03.09.26»), срок графика **30.08.2026 —
01.02.2027**. Краны 1–3, захватки 1–4, стоянки 01–21, этажи 1–4, 13 видов
работ.

Прогнал файл через действующий парсер (`app/schedule_import.py`) и
сопоставление — на обезличенной копии базы:

- **все 13 видов работ распознаются** закрытым списком `TYPE_SUBTYPE_ALIASES`,
  ни одной нераспознанной строки;
- даты, номера кранов/стоянок/этажей разбираются без ошибок; ведущие
  отступы уровня структуры (`«        Колонна…»`) съедаются нормализацией;
- **покрытие 98,8%**: 9309 изделий из 9422 получают даты, строк «ни один
  элемент не найден» — ноль;
- ключ (кран, стоянка, этаж, вид работ) уникален на всех 663 строках.

Что мешает загрузить файл как есть:

1. **Заголовок первой колонки — «Название задачи», а импорт требует «Тип и
   Подтип»** и отвергает файл целиком. Правка на строку, но её надо сделать
   осознанно: принимать оба имени.
2. **Захватка не выводится из стоянки.** В `schedule_import.py` записано,
   что «стоянка уже однозначно определяет захватку», и захватка при
   сопоставлении игнорируется. В этом файле это **не так**: стоянки 4, 5,
   10, 11, 16, 17 у каждого из трёх кранов относятся к двум разным
   захваткам. Сейчас это не приводит к ошибке (ключ со стоянкой и этажом
   всё равно уникален), но допущение в коде надо снять и добавить захватку
   в сопоставление — иначе на следующем графике даты уедут в соседнюю
   захватку молча.
3. **Импорт графика не привязан к объекту** (известный хвост этапа E,
   см. CLAUDE.md): сопоставление идёт по всем изделиям базы. Пока объект
   один — работает; со вторым зданием даты применятся не туда. Загрузку
   актуализированного графика заводить сразу с выбором объекта.

## Разбор обработки Power Query: механика расчёта графика

Файлы `01_Выгрузка ВОР из WEB.xlsx` (штатная массовая выгрузка реквизитов,
9418 изделий) и `!_Обработка данных из WEB.xlsx` (листы `hide`, `ВОР`,
`Витрина`, `01_WBS`, `02_Technology`, `03_Flow`).

**Цепочка обработки.** Выгрузка ВОР → к каждому изделию по паре тип+подтип
приписывается темп монтажа и порядок (лист `hide`) → свод по фронтам работ
(`01_WBS`: захватка, кран, стоянка, этаж, вид работ, количество, темп) →
три листа с цифрами (`01`, `02`, `03`) уходят в MS Project, где макрос
раскладывает работы по датам.

**Алгоритм.** Реконструирован и проверен на присланных данных:

1. длительность работы = `количество / темп` (в сутках, дробные);
2. внутри одного фронта (кран+стоянка+этаж) работы идут в порядке
   `02_Technology`;
3. фронты одного крана идут в порядке `03_Flow`, встык, без простоев;
4. краны работают независимо и параллельно;
5. календарь **семидневный**, выходных нет (в графике есть субботы и
   воскресенья).

Прогнал эту модель против присланного актуализированного графика: из 663
работ **245 совпадают день-в-день, остальные расходятся ровно на 1 день**
по началу и/или окончанию — расхождений больше суток нет ни одной. Разница
объясняется тем, как MS Project округляет дробные длительности до
отображаемых дат; чтобы совпало 1:1, нужно доопределить правило округления
(рабочих часов в сутках, начало смены).

**Вывод для E5.** Собственный расчёт графика внутри системы реалистичен:
все входные данные известны, движок MS Project не нужен, `.mpp` (макрос
`КСГ ЖБИ Москвич_260813 (ТГ).mpp`) нужен только чтобы сверить правило
округления. Отдельный плюс — расчёт от факта (E5) в этой модели получается
сам собой: смонтированные изделия убираются из количества фронта, и
остаток раскладывается дальше.

**Расхождение, которое надо решить.** Темп задан по паре тип+подтип
единым числом на объект, а кранов три, и их производительность в модели
не различается. Пока считаем «темп — свойство вида работ, одинаковое для
всех кранов»; если это не так, таблица темпов получает второй ключ (кран).

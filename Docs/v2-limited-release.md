# Ограниченный выпуск: V1 + экспериментальный V2 (2026-09-21)

Выпускается **V1 как основной интерфейс** и **экспериментальный V2**, который заказчик открывает явно и оценивает. V2 не
считается готовым к промышленной работе: непроверенные операции записи в нём отключены (`Docs/v2-write-policy.md`).
Отдельного демонстрационного экземпляра, домена и БД нет — всё в существующем приложении.

## 2. Поверхность риска для V1 (целевой обзор)

| Участок | Что изменено | Вывод |
| --- | --- | --- |

| Загрузка JS/CSS, CSP, маршруты | Новых маршрутов нет, кроме прежних `/v2` и `/?ui=`. V2 — модульные скрипты того же origin, без инлайна; CSP (`script-src 'self'` + хэш importmap V1) не менялась, importmap V1 не трогался. | Проверено: V2 грузится под действующей CSP, ошибок JS нет. |
| Выбор проекта/объекта | V1 — без изменений (проверен: `last_object_id` сохраняется). V2 выбор на сервер не пишет; принимает разовый `?object_id=`. | Без риска для V1. |
| Новые параметры переходов в V1 | `?object_id=`, `?ws=`, `?view=`, `?open=menu&item=`, `?open=user-security&user_id=` (уже в `main`). | Общие настройки и обработчики | Изменён один обработчик (`#menu-ui-v2`): вместо cookie — переход на `/v2?object_id=`. | Проверено V1 → V2 → V1. |
| Backend | Только МФР-коммит и выбор интерфейса (см. п. 1). Права, бизнес-правила, схема БД, авторизация — без изменений. | Проверено на настоящем backend. |
| Влияние V2 на обычный запуск V1 | V2 не подключается из V1; V1 не подключает файлы V2 (V1 → V2 только по клику / прямому адресу). | Подтверждено сетевым журналом: при запуске V1 файлы `/static/v2/*` не запрашиваются. |

## 3. Политика записи V2

Единая таблица — `Docs/v2-write-policy.md` (генерируется скриптом из `write-gate.js`). Коротко: **разрешено 20 операций** (личные настройки: гамма,
цвет подписей, «Ознакомился»; справочники СМУ, подтипы, префиксы; карточка объекта, заметки отчётов, порог опоздания; цвета зон/статусов/МФР, форма
маркеров; базовый срок ЗР; вход); **отключено:** пользователи, пароли, права и роли, контрагенты/договоры/спецификации/контракты, плановые даты
поставки, проекты и объекты, фото и вложения, физлица, завершение сеансов, прогноз и примечание ЗР, смена пароля в V2. Всё, чего нет в таблице, отключено
(запрет по умолчанию). Защита стоит в `api.js`, то есть в обработчике действия: Enter, «Сохранить и продолжить» из диалога ухода, повторная отправка и
любая новая кнопка получают отказ без сетевого запроса; над содержимым экрана — пояснение и ссылка в V1.

Шлюз не заменяет серверные права и не мешает им: разрешённые операции тоже проходят серверную авторизацию. На V1 шлюз не влияет.

## 5. Развёртывание и откат

**Куда и что запустится.** Команда (по VPN, выполняет пользователь): `git push gitlab release/v2-limited:develop` (ветку `main` и каталог порта 8000 не трогает).
Пуш запускает GitLab CI (`.gitlab-ci.yml`): `BuildPushImg` (сборка образа, Harbor, тег `CI_PIPELINE_ID`),
затем `Redeploy_backend_dev` на раннере `dev`: `docker-compose down` → `up -d` на сервере ветки `develop` (по документации — 10.190.15.25, **боевые данные**).
Простой — время перезапуска контейнера. `production` не затрагивается. При старте приложение само снимает служебную копию БД, миграций нет,
обработок релиза нет (версия `0.85`, как у `develop`).

**До пуша (делает пользователь по VPN):**
1. Зафиксировать текущую версию: `docker ps --format '{{.Names}}  {{.Image}}'` и `docker images | grep zhbi` — записать тег (номер пайплайна) работающего образа.
2. Сверить `git ls-remote gitlab develop` → `78af0ddf901a9aec229011d47238b1b034070ca2` (иначе — сообщить, версии разошлись).
3. Снять согласованную копию БД **штатным механизмом (не `cp` и не `scripts/linux/backup.sh` — они не учитывают WAL)**: V1 → «Действия → Администрирование →
   Резервные копии → Создать копию» (комментарий: «перед выпуском V2») или
   `docker exec <контейнер> python3 -c "from app import backups; print(backups.create_backup(kind='manual', user_name='релиз', comment='перед выпуском V2')['name'])"`.
   Проверить: копия в списке «Резервные копии»; на диске `/opt/zhbi/data/backups/zhbi_*_manual.db` (+ `.json`), размер ≈ размеру `zhbi.db`;
   `docker exec <контейнер> python3 -c "import sqlite3,sys; c=sqlite3.connect('file:/app/data/backups/<имя>.db?mode=ro',uri=True); print(c.execute('pragma integrity_check').fetchone())"` → `('ok',)`.
   Скопировать файл за пределы сервера (см. `Docs/DEPLOYMENT_LINUX.md` §2).

**После пуша (5–7 минут, без записи в рабочую БД):** дождаться зелёного пайплайна; `docker logs --tail 100 <контейнер>` — старт без ошибок; открыть
адрес сервера: вход → V1 (не V2); выбрать объект, открыть схему; «Действия → Настройки → Общие → Новый интерфейс — экспериментальный» → V2 с пометкой и объектом →
«← Текущий интерфейс» → V1. Прямой `/v2` под сессией открывается. **Тестовых изменений на рабочей БД не делать.**

**Откат.** Откат кода и восстановление БД — разные операции. Схема БД не менялась, поэтому старый образ работает на текущей БД без восстановления:
`CI_PIPELINE_ID=<записанный прежний номер> docker-compose up -d` (`Docs/DEPLOYMENT_LINUX.md` §4.1) — вернёт `78af0dd`-образ; V2 исчезнет, V1 прежний.
**БД поверх новых пользовательских записей автоматически не восстанавливать.** Восстановление копии (V1 «Резервные копии» → «Восстановить», перед ним приложение
само снимает страховочную копию) — только осознанное решение при порче данных, с пониманием, что записи после копии будут потеряны.

## 6. Что не проверено / ограничения

- **Ограниченная роль на настоящем backend** — не проверена живьём (нужен вход человека). Основание считать риск низким: серверные права не менялись; ссылки V1 проходят ту же
  проверку видимости, что клик мышью; V2 строже сервера (шлюз). Пакет ручных действий — ниже.
- Вход паролем (V1 и V2) и смена пароля выполняет только человек; экран входа V2 проверен на стенде. Состояние удалённых веток и текущего образа на сервере из среды не проверялось.
- Экспорт PDF/XLSX других отчётов и 3D-сцены глубоко не перепроверялись — эти участки не менялись, кроме отчёта «Линейный трек» (проверен).

**Пакет ручных действий (≈5 минут).** В панели браузера открыть `http://127.0.0.1:8061`, выйти, войти как `qa_overnight_2` (роль «Пользователь», пароль знает
человек), сообщить. Проверяется: V1 открывается; пункт «Новый интерфейс — экспериментальный» есть; `/v2` открывается, раздел «Пользователи и доступ» скрыт по правам; разрешённая запись
(например, СМУ) при отсутствии права получает отказ сервера, а не «успех»; глубокая ссылка на недоступный пункт меню даёт сообщение «недоступен вашей роли».

## 7. Замечания без блокировки выпуска (в backlog)

1. Разделы «Пользователи и доступ», «Контрагенты», «Проекты и объекты» показывают формы полностью, запись отклоняется шлюзом при попытке (с пояснением). Улучшение —
   спрятать кнопки записи в этих модулях.
2. Прежние сценарии UA/PO/CP/SS проверяют операции, отключённые в выпуске; они прогоняются на стенде с заглушкой шлюза. Нужны «режимные» варианты.
3. 18 VIS-сцен «Проекты и объекты» нестабильны в безголовом Chrome (карта) — прогонять в обычном браузере.
4. Метаданные штатной копии БД (`stats`) при создании через API возвращаются пустыми — на содержимое копии не влияет (проверено сверкой).
5. `GET /settings/info-plate` для объекта МФР отвечает 403 (штатное поведение V1, вызывается при выборе МФР-объекта; в консоли — «Failed to load resource»).
6. Устаревшие снимки в `Docs/v2-acceptance-shots/` показывают прежнюю подпись «Предварительная версия».

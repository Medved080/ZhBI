# Подсистема «Калькулятор»: данные, роль, отправка на серверы

Статус на 2026-10-04: реализовано в ветке `claude/calc-subsystem`, проверено двумя временными серверами
(`scripts/verify_calc_subsystem.py`) и на полном объёме данных (1008 изделий, 453 МБ источников).
**Не выкачено** ни на тест, ни на бой, не влито в `main`. Решения пользователя 2026-10-04: калькулятор живёт
на серверах целиком; текущие расчёты привязаны к проекту «Москвич»; роль «Калькулятор»; в пакет отправки
входит всё, включая PDF; при повторной отправке приоритет у расчётов на принимающем сервере.

## Устройство

* Код — `app/calc/` (перенос `CalcZhBI/backend`, расчёт Decimal и версии расчётов без изменений), фронтенд —
  `app/calc/web/`, адрес `/calc/`. Права и вход — ЖБИ: разделы `calc` (чтение/изменение) и `calc_sync`, роль
  «Калькулятор» (`db._seed_calculator_role`, один раз за маркером). Администратор сервиса проходит в обход.
  CSRF подсистемы — HMAC от токена сессии (`app/calc/auth.py`).
* Данные — **отдельный файл** `data/calc/calczhbi.sqlite3` (схема калькулятора, версия 6, свои миграции),
  вложения `data/calc/uploads/`, источники `data/calc/assets/` (PDF-альбомы, каталоги, 3D; в git и в образ не
  входят), очередь отправки `data/calc/sync-staging/`. Всё лежит в томе `data/`. Таблицы `users/sessions` калькулятора
  не используются (при импорте очищаются).
* Привязка к проекту: `projects.zhbi_project_id/name` в базе калькулятора. При старте ищется проект ЖБИ «Москвич»
  (имя можно сменить `ZHBI_CALC_PROJECT`), проект **не создаётся**. Нет проекта — `linked:false`, подпись «не привязан»,
  ручная привязка `PUT`-ом администратора не реализована в UI (команда `python -m app.calc.manage link-project`
  повторяет поиск по имени).
* Перед миграцией схемы калькулятора сервис снимает ZIP-копию в `data/calc/backups/`. Регулярное резервное
  копирование ЖБИ (`app/backups.py`) папку `data/calc` **не включает**: копируйте том `data/` целиком.

## Интерфейс: оформление и два режима

* Оформление — ЖБИ: токены и семь цветовых гамм V2 (`app/calc/web/theme.css`, копия значений из `v2/styles.css` — при
  смене палитры править оба), гамма берётся из `users.ui_theme`, кнопки/заголовки/диалоги по образцу V2. Калькулятор
  сохранил собственную разметку (вкладки изделия, таблица калькуляции, 3D), её цвета теперь — токены.
* Новый интерфейс (V2): экран «Калькулятор» (`#/calc`, группа «Рабочие места», `v2/calc-embed.js`) — страница `/calc/`
  кадром (`srcdoc`, как схема) внутри оболочки. Прежний (V1): пункт меню «Калькулятор ЖБИ» открывает `/calc/?ui=v1`
  в отдельной вкладке. Нужен раздел `calc` («Чтение»).

## Переход с элемента схемы в калькулятор (по марке)

Карточка элемента (V1 — `#card`, общая для 2D и 3D; V2 — карточка рабочего места «Модель») показывает «Открыть в калькуляторе ·
<изделие>», если у человека есть раздел `calc` (иначе сервер отвечает 403 и блока нет). Сопоставление — на сервере,
`POST /calc/api/marks/resolve` (`app/calc/marks.py`): верхний регистр, пробелы и `-./,_` убраны, латиница→кириллица,
`З`→`3`, `КВ`≡`К8`; сначала строгое совпадение с точками, затем без них; сравнивается название изделия без слова-типа,
полное название и `alias` каталога. Связь автоматическая только при единственном кандидате: несколько — показываются
кандидаты, ни одного — «Изделия нет в калькуляторе». Статусов и ручного подтверждения связи (`calc_mark_links`) пока нет.
Переход: V2 — экран `#/calc` с нужным изделием, V1 — вкладка `/calc/?ui=v1#product=<id>`.

## Обработка чертежей нейросетью: ход и устойчивость

* Чтение листа — отдельными запросами (общий вид + 4 фрагмента), в каждом число фактов ограничено самой схемой (60/80): структурированная
  генерация обязана закрыть массив, и ответ завершается. Оборванный ответ (лимит или зацикливание) не повторяется с большим лимитом — из него
  спасаются готовые факты, остальное помечается непрочитанным; в журнале — конец ответа. Для моделей Qwen к запросу добавляется `/no_think`.
* Ответ модели читается потоком (SSE у OpenAI-совместимых API/LM Studio, NDJSON у Ollama): «Тайм-аут» — это тайм-аут простоя (нет ни байта), общий
  предел ответа 30 минут. Не пришёл первый токен (модель грузится в память) — запрос повторяется до трёх раз. Ответ обрезан лимитом — повтор
  с лимитом ×2 и ×4 (до 32768), затем чтение листа по частям. Комплект листов — только листы самого изделия.
* Ход виден в окне «Обработка изделий · Qwen»: баннер «Идёт обработка…», в таблице заданий полоса прогресса и текущее действие, в карточке
  открытого задания — фаза, лист N из M, текущий запрос (состояние, секунды, токены и скорость, «рассуждение», нет данных N с), сколько фактов
  прочитано, и построчный журнал (`recovery_events`, до 600 записей на задание; снимок `recovery_live` пишется раз в секунду). Данные в базе, поэтому
  работает и при отдельном процессе-обработчике. Схема калькулятора 8.

## Закладки изделия: «Расхождения и вопросы» и «Коллизии»

* «Расхождения и вопросы» — технические вопросы по изделию из реестра расхождений и незавершённое в модели; записи о пересечениях
  (по словам «пересеч», «коллиз», «проникнов») перенесены на закладку «Коллизии». «Файлы и основания» оставлена только для файлов и
  оснований расчёта.
* «Коллизии» — пересечения деталей и арматуры из отчёта проверки модели (`solidModel.qa.geometricViolations`, `app/calc/collisions.py`):
  классы пар, число пар, максимальное проникновение, примеры с координатами и листами. Отчёт приводит только примеры, поэтому
  рядом написано «показано N из M пар». На вкладке «Модель и параметры» флажок «Коллизии» включает метки на 3D (постоянного
  экранного размера, поверх модели); клик по метке открывает карточку коллизии справа, «Показать в 3D» из списка наводит камеру.
* Статус (открыта / передана проектировщику / принята без изменений / устранена) и комментарии ведут пользователи с правом
  изменения (`calc`); хранятся в `collision_state`/`collision_notes` (схема калькулятора 7), привязаны к модели, ничего не удаляется.
  При отправке на другой сервер комментарии объединяются по идентификатору, статус ставится только там, где его ещё не было.
* Нет восстановленной 3D-модели — вместо списка пояснение. Замечания реестра без координат показываются текстом и на 3D не отмечены.
* Проверка труб (`app/calc/geometry_check.py`, numpy): для каждой трубы (`metalParts` группы `pipe`/`tube`, круглый профиль с отверстием)
  и каждого стержня арматуры считается перекрытие кольца стенки сечением стержня (шаг по ломаной 1 мм, допуск 0,5 мм). В карточке: проникновение
  (в пределах толщины стенки: для 50×5 максимум 5 мм, для 68×1 — 1 мм) и длина участка. Классы «Труба × группа стержней» помечены «проверка
  калькулятора» и перечислены полностью, остальные классы — примеры из отчёта поставщика (часть пар там та же, например «ЗД анкер × Труба»).
  Прямоугольные трубы не поддержаны (пропускаются). Результат кешируется по модели. Пакетная проверка всех моделей:
  `python -m app.calc.geometry_check --products data/calc/calczhbi.sqlite3 --json отчёт.json` (читает только assets, ~40 с);
  `scripts/verify_tube_collisions.py` — проверка на синтетике. Нужен numpy (в `requirements.txt`).
* Пересечения в отчёте поставщика не вычисляются заново.

## Отправка на тестовый и боевой серверы (только из-под VPN, делает человек)

**Всё делается в интерфейсе, терминал не нужен** (под VPN):

1. На принимающем сервере войдите в ЖБИ администратором → «Калькулятор» → «Передача на серверы» → «Токены приёма»: укажите логин
   пользователя с ролью «Калькулятор» и название токена → «Выдать токен». Токен показывается один раз, скопируйте его.
   Пользователь без роли токен получить не может; снятие роли отключает токен.
2. У себя в том же окне нажмите «+ Тестовый сервер» / «+ Боевой сервер», введите адрес и вставьте токен → «Сохранить» → «Настроить» →
   «Проверить связь» (проверяет адрес, VPN, сертификат, токен и роль, ничего не передаёт). Токен хранится в `data/calc/sync-secrets.json`
   с правами 600 (вне git и вне базы), обратно в интерфейс не возвращается; адреса — в `data/calc/sync-targets.json`. Для боевого сервера
   по умолчанию включено подтверждение вводом имени цели. Если сервер использует самоподписанный/корпоративный сертификат (проверка связи пишет `CERTIFICATE_VERIFY_FAILED`), в настройках цели нажмите «Доверять сертификату этого сервера…»: показывается SHA-256 отпечаток, после подтверждения передача идёт только на сервер с этим сертификатом (смена сертификата или подмена адреса — отказ). Либо укажите путь к корпоративному `.pem`.
3. «Проверить данные» (ничего не меняет: покажет, что будет создано/обновлено/оставлено серверным и какие файлы уйдут) → «Отправить».

Настраивать цели и выдавать токены может только администратор сервиса; отправлять — любой с ролью «Калькулятор». Прежние способы
(`sync-targets.json` с `tokenEnv`/`tokenFile` и `python -m app.calc.manage create-token`) продолжают работать.

Порядок на приёмнике: `plan` → блочная загрузка файлов по 8 МБ с проверкой SHA-256 (докачка после обрыва) → `commit`
(одна транзакция БД, затем атомарная замена файлов источников и пересчёт реестра расхождений).

### Правило повторной отправки

* Нет на сервере — создаётся. Совпадает — не трогается.
* Изделие, нормы, профиль, изменённые на сервере людьми с прошлой отправки, **не перезаписываются** и попадают в отчёт
  как «оставлено серверное» (`serverPriority`). Если с отправки на сервере ничего не менялось — обновляется.
* Файлы источников и каталогов обновляются по SHA-256 (там, где сумма отличается). Вложения изделий только добавляются.
* Ничего на принимающем сервере не удаляется. Версии расчётов (неизменяемые снимки) только дописываются.
* Не передаются: журнал и очередь разбора чертежей Qwen (`recovery_*`, `assets/recovery/`) — они локальны.
  Фоновый разбор на серверах выключен (`ZHBI_CALC_RECOVERY_WORKER=1` включает).
* Схема калькулятора отправителя и получателя должна совпадать: сначала выкатывается код, потом отправка.

## Расценки, нормы и пересчёт изделий (2026-10-05)

Раздел «Расценки и нормы» (кнопка в шапке карточки изделия) — единое место настроек сервиса. Три блока, у каждого своя версия и журнал аудита «было → стало»:

* **Прайс-лист** (`price_list`, `app/calc/prices.py`): цена бетона по классам (+ «по умолчанию» для класса без цены и «не указан»), ставка труда, цена каждого материала каталога по его коду
  (арматура по диаметру и классу, проволока, трубы; материалов 45). Цена 0 = «не задана»: стоимость такого изделия занижена, в карточке строка помечена.
* **Профиль расчёта** (`calculation_profiles`): страховые взносы, энергоуслуги, общепроизводственные, административные, коммерческие, маржа, доставка, НДС.
* **Нормы** (`production_norms`): коэффициент проектный/производственный расход и труд на м³ (основание — две колонны, помечено как предварительное), коэффициенты по типам арматуры. Цен в нормах больше нет.

**Пересчёт — на лету, без пересохранения.** `repository.get_product` считает изделие из каталога по ТЕКУЩИМ нормам и прайсу: объём, труд, цена бетона по классу, расход и цена ресурсов, стоимость материалов.
Поэтому смена любой расценки меняет все затронутые изделия сразу, а история изделий не раздувается. Версии прайса и профиля пишутся в снимок расчёта (`pricesVersion`, `profileVersion`).
Рабочая область (`/api/workspace`) кеширует ответ по подписи, в которую входят версии прайса, профиля и норм.

**Ручные правки сохраняются.** Корректировки строк расчёта (`line_overrides`) и дополнительные статьи накладываются поверх расчёта как раньше. Поля изделия `volume`, `hours`, `concreteRate`, `otherMaterials`,
заданные пользователем, перечислены в `products.manual_fields` (JSON) и не пересчитываются; их выставляет клиент через `manualFields` в `POST /api/products` (`null` — не менять, `[]` — вернуть к расчёту).
При создании прайса (старт сервиса) поля существующих изделий, расходящиеся с расчётом по начальным расценкам, помечаются ручными автоматически (`prices._mark_manual_fields`).
Изделия вне каталога (две исходные колонны из Excel, ручные) считают на лету только цену бетона по классу; остальное у них сохранённое.

**Эндпоинты:** `GET/PUT /api/prices` (версия-условие `expectedVersion`, 409 при устаревшей), `PUT /api/profile`, `PUT /api/norms` (без цен); `POST /api/norms/apply` оставлен для совместимости и ничего не пересохраняет.

**Передача на серверы:** прайс едет в пакете как нормы (`prices`, правило `serverPriority`), колонка `manual_fields` — вместе с изделием. Схема калькулятора теперь 9: сначала выкатывается код, потом отправка.

**Ещё не сделано (этап B):** закладные детали, трубы, петли — в расчёте их стоимости нет (в каталоге нет их количества); нужны номенклатура с ценами, количества по изделию и строка расчёта.

## Главная: готовность калькуляций (2026-10-05)

Страница `/calc/` открывается на главной (`app/calc/web/home.js`, кнопка «Главная · готовность» в боковой панели возвращает на неё из любого раздела). Данные — `GET /calc/api/readiness`
(`app/calc/readiness.py`): считаются на лету от каталога, чтений с листов и текущих расценок, кешируются по подписи рабочей области (в подпись входят версии прайса, норм и файл `promka-readings.json`).

У изделия **семь условий готовности**: объём бетона; класс бетона; арматура по диаметрам и классам; закладные, трубы, петли; цены на все его материалы (бетон класса, ставка труда, ресурсы);
подтверждённые нормы группы; проверка человеком. Изделие «готово», когда выполнены все семь. Нормы и проверка человеком пока нигде не хранятся, поэтому у всех изделий они не выполнены:
группы с подтверждёнными нормами заводятся в `NORMS_CONFIRMED` (позже — в базу), для проверки человеком нужен отдельный механизм подтверждения.

Страница показывает: число готовых изделий и общую готовность (среднее долей по семи условиям); «что осталось по исполнителям» (разработка / вы / технолог / проверка); воронку (изделие проходит шаг, если выполнены все
предыдущие; рядом — «само по себе»); таблицу «группа × условие»; самые большие пробелы; расценки (материалы без цены, бетон по классам, ставка труда, ссылка в «Расценки и нормы»); откуда данные (каталог поставщика /
чтение листа / вручную); 3D-модели (в готовность не входят: стоимость от них не зависит).

Побочная правка расчёта: если у изделия класс бетона «Не указан», а лист даёт класс, цена бетона берётся по классу с листа (`repository.dynamic_values`).
Проверка: `verify_calc_readings.py` (раздел 7).

## Подтверждение изделий, нормы по группам, класс бетона по типам (2026-10-05, схема 10)

* **Проверено человеком.** Кнопка «Отметить: проверено по чертежу» в карточке изделия (вкладка «Модель и параметры»), снимается той же кнопкой. Хранится в таблице `product_verifications` (миграция 010: изделие, кто, когда, примечание),
  аудит `product.verified` / `product.unverified`, эндпоинт `POST /calc/api/products/{id}/verification`. Отметка едет в пакете передачи (дочерняя таблица изделия) и входит в его контрольную сумму. Это седьмое условие готовности.
* **Нормы по группам.** В «Расценки и нормы» → «Нормы по группам изделий»: у группы можно задать свой труд на м³ и коэффициент расхода бетона (пусто — общая норма) и отметить «Подтверждено технологом» (кто и когда записываются).
  Хранится в нормах (`norms.parameters.groups`), расчёт группы берёт её значения (`norms.parameters_for`). Подтверждённая группа — шестое условие готовности; «Вне каталога» (две исходные колонны Excel — основание общей нормы) считается подтверждённой.
  Исправлено попутно: сохранение норм падало (обращалось к полям цен, которых после переноса цен в прайс в схеме нет).
* **Класс бетона по типам.** «Расценки и нормы» → «Класс бетона по типам изделий»: для типов, у которых на листах класса нет (плиты `4Пд`, `4ПИ`, `Пл`; тип — группа и буквенная часть марки, `norms.type_key`), записывается класс (В30…).
  Цена бетона таких изделий считается по нему (`repository.dynamic_values`); хранится в нормах (`classByType`).

### Массовый ввод и история изменений настроек

* **Массовые кнопки** только заполняют поля формы, сохранение — обычной кнопкой «Сохранить расценки и нормы», одной новой версией: «Нормы по группам» — заполнить труд/расход бетона/арматуру у всех групп, подтвердить все группы, снять подтверждения;
  «Класс бетона по типам» — один класс всем типам; «Материалы» — цена всем показанным строкам (поиск и «только без цены» работают как фильтр). В списке изделий (режим «Выбрать несколько») — «Проверено · N»: массовая отметка
  «проверено по чертежу» (`POST /calc/api/products/verification/bulk`, до 3000 изделий, одна запись в истории на всю пачку).
* **Версионность и история.** Каждое сохранение расценок, начислений и норм создаёт новую версию (`price_list`, `calculation_profiles`, `production_norms`) и запись в журнале аудита «было → стало»; вкладка «Цены и нормы» → «История»
  (`GET /calc/api/history/settings`, фильтр по виду: нормы, расценки, начисления, проверка изделий) показывает версию, автора, время и список изменений с подписями (группа, поле, материал). Прежние значения не теряются.
  Модуль — `app/calc/settings_history.py`.

## Слой «прочитано с листа» (2026-10-05)

Файл `assets/promka-readings.json` лежит рядом с каталогом (в git не входит, данные заказчика) и передаётся на серверы как остальные файлы каталога. Собирает его офлайн
`scripts/build_calc_readings.py` по листам изделий (`sources/docNN.pdf`, метод — `scripts/prototypes/vector_ocr/`, `Docs/calc-vector-ocr.md`). В нём на каждое изделие: лист, объём и класс бетона из строки
«Бетон кл. … м³» спецификации, арматура по классам и диаметрам из «Ведомости расхода стали» (принимается только при сошедшихся самопроверках суммами) или сборкой по каркасам и сеткам листов-составляющих
(принимается при нераспознанном остатке не больше 3% массы).

`app/calc/readings.py` накладывает прочитанное в `document_models.catalog()` **только на пробелы**: нет объёма, класс «Не указан», нет ресурсов. Значения поставщика не перезаписываются; у наложенных моделей есть
`readings` («не подтверждено человеком», лист, источник арматуры) и заметка в `notes`. Ручные правки изделия главнее, как раньше. Стоимость считается на лету по прайсу, так что появившаяся арматура
получает цену, как только та задана в «Расценки и нормы».

**Объём бетона.** Порядок источников: строка «Бетон кл. … м³» спецификации → таблица плит (одна таблица на несколько марок, строки сопоставляются с изделиями по порядку) →
масса изделия ÷ 2500 (в проекте масса = объём × 2500 кг/м³: колонны, подъёмники, шахты, лестничные балки, панели сходятся на 100%, ригели ±3%). Источник записан в чтении (`volumeSource`) и в пометке изделия.
У ригелей серии 3Р… на листе изделия только чертёж («спецификацию и ведомость стали смотри лист 2»): спецификация берётся со следующей страницы, если она не лист другого изделия.

**Закладные, трубы, петли.** Сборка собирает их по спецификации листа изделия и рекурсивно по листам составляющих (количества умножаются на количество узлов). В каталог ложатся три вида ресурсов:
`embeddedParts` («Закладные детали», т), `loopParts` («Петли и петлевые выпуски», т) — по массе, цена за тонну; трубы — по типоразмеру в метрах (`pipe50` = 50×5, `pipe68` = 68×1 как у поставщика, остальные `pipeДДxТ`), цена за метр.
Каждый вид добавляется, только если у модели нет ресурсов этого вида; перечень позиций (марка, масса единицы, количество) остаётся в чтении и показан в карточке. Новые ресурсы появляются в «Расценки и нормы» с ценой «не задана».
Лист, на котором закладных нет, засчитывается прочитанным (`embeddedChecked`), чтение прежнего формата без раздела `embedded` ничего не утверждает.

Охват сейчас: колонны 476, подъёмники 53, шахты лифтов 52, лестничные балки 3 — объём и класс у всех 584 (совпадение с каталогом у 552 из 552 с объёмом); арматура получена у 454 из 584 (ведомость 357, сборка 97), наложено на 173 изделия, у которых ресурсов в каталоге не было.
Проверка: `ZHBI_CALC_ASSETS_DIR=… [READINGS_JSON=…] .venv312/bin/python scripts/verify_calc_readings.py`.

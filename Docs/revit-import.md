# Загрузка данных из Revit — проект решения

Статус: **предложение**, код не начат, ветка не заведена (2026-08-10).
Первый шаг сознательно узкий: довести данные модели до сервиса и ПОКАЗАТЬ
их. Статусы монолита, объёмы, контрактация новых типов и зоны из Revit — вне
этого шага, см. «Что отложено».

Конкретные имена файлов и пути заказчика в этот файл не выносятся — он в
git (см. CLAUDE.md, раздел про обезличенную копию).

## 1. Исходные данные

Один объект = девять моделей Revit 2022 (русская локаль), суммарно ~2,7 ГБ.
Разбиение — **по разделам проекта**, а не по частям здания:

| Раздел | Порядок размера | Отношение к трекеру |
|---|---|---|
| КР | ~125 МБ | конструктив: монолит и сборный ЖБИ — главный |
| АР | ~410 МБ | архитектура: кладка, ГВЛ, перегородки |
| А | ~35 МБ | оформление/общие виды |
| ВК, ИТП, ОВ1, ОВ2, СС, ЭОМ | ~1,37 ГБ суммарно | инженерия, к конструкциям отношения не имеет |

Три факта, установленных чтением самих файлов (служебные потоки OLE
читаются без Revit), которые прямо определяют конструкцию:

* **Имя файла не идентификатор.** У одного из разделов внутренний путь
  центральной модели отличается от имени выданного файла: между выдачами
  файлы переименовывают.
* **`Central Model Identity` не идентификатор тоже** — у всех девяти он
  одинаковый (следствие detach/save-as при подготовке выдачи). Привязывать
  «модель ↔ область элементов» к нему нельзя.
* **Содержимое читается, но не разбирается.** Уточнено 2026-08-10: первый
  вывод «закрыто наглухо» был ОШИБОЧНЫМ — он опирался на поиск открытых
  строк, а потоки просто сжаты gzip. Файл КР разложен: 12 потоков OLE,
  из них главный (`252`, 121 МБ) после восьмибайтового заголовка —
  обычный gzip; распаковалось 30,9 МБ, и в них нашлись предметные термины
  (Level 1228, Бетон 413, Стена 365, Плита 319, Балка 136, Марка 119,
  Арматура 79, Пилон 26, Секция 9). То есть прочитать `.rvt` можно.

  Полностью разложено: поток `252` — это 9101 gzip-блок по 16-байтовому
  заголовку каждый; распаковалось 7290 блоков, 539 МБ из 121 МБ сжатых,
  1811 блоков (20%) не взялись.

  **Что оттуда извлекается:** каталог семейств и типоразмеров
  (`Перекрытие_Плита_Бетон_180`, `Пилон монолитный`, `Пилон
  Пс.200.30.290.В1`), имена параметров (`Мрк.МаркаКонструкции`,
  `Мрк.МаркаИзделия`, `Мтрл.МаркаБетонаW/F`, `Арм.МаркаТипаАрмирования`),
  общие параметры `MCY_*`, правила фильтров видов и значения-строки —
  например, секции корпуса: **С01 и С02**. Всего 11 441 уникальная
  кириллическая строка.

  **Что НЕ извлекается — и это блокирует:** связка «элемент → его
  параметры → его геометрия». Строки лежат отдельно, элементы — двоичными
  записями со ссылками по идентификаторам; чтобы получить строку нашей
  таблицы импорта, надо декодировать сериализацию объектов Revit, включая
  геометрию (солиды, выдавливания, трансформации). Формат
  недокументирован и меняется между версиями Revit. Плюс 20%
  нераспаковавшихся блоков — это дыры в данных ещё до разбора.

  Итог: прямое чтение `.rvt` годится, чтобы ЗАРАНЕЕ наполнить справочники
  (секции, уровни, каталог типов, правила сопоставления) до первой
  выгрузки, и как перекрёстная проверка выгрузки. Заменить экспортёр оно
  не может. Граница системы остаётся прежней — по причине «дорого и
  ненадёжно», а не «невозможно».

Отсюда первый инвариант: **область-источник элемента приходит явным полем
в самой выгрузке** (код раздела), а не выводится из файла.

## 2. Граница системы

`.rvt` на сервер не попадает никогда. Извлечение данных происходит там, где
есть Revit — на машине проектировщика; наружу выходит компактный **пакет
выгрузки**. Сервису от элемента нужно около полутора десятков полей, это
единицы мегабайт против сотен.

Передача — обычным файлом (почта, сетевая папка), а не HTTP-запросом от
плагина. Причина не в простоте: проектировщик внешний по отношению к
сервису, учётной записи в нём у него нет, а сам сервис живёт только внутри
корпоративного контура и наружу не смотрит. Прямая отправка по API с
сервисным токеном — возможное продолжение, когда выгрузку будет запускать
сотрудник, у которого доступ и так есть.

Экспортёр запускается на отсоединённой копии, а не на центральном файле.

## 3. Пакет выгрузки

Один пакет = один раздел. Файл `*.zhbi.json.gz`.

Почему один раздел на файл, а не архив из девяти: раздел — это область, в
границах которой считается «элемент исчез из модели». Один файл = одна
область = единица, которую можно перевыгрузить отдельно. Загружать при этом
можно сразу несколько.

Почему gzip-JSON, а не xlsx: контуры — вложенные массивы точек, в таблицу
не ложатся; и объём в 5–10 раз меньше. Порядок: элемент ≈ 600–900 байт,
50 000 элементов ≈ 40 МБ JSON ≈ 5 МБ в gzip. Лимит загрузки 200 МБ
(`app/upload_limits.py`) с запасом.

```
{
  "формат": "zhbi-revit-package",
  "версия_схемы": 1,
  "выгрузка": {
    "раздел": "КР",              // область-источник, задаёт экспортёр
    "модель": "<имя файла>",
    "дата": "2026-08-10T12:00:00",
    "экспортёр": "1.0",
    "revit": "2022 20241107_1515",
    "единицы": "мм",
    "координаты": "общие"
  },
  "оси": [ {"имя": "1", "тип": "цифровая", "точки": [[x,y],[x,y]]} ],
  "уровни": [ {"имя": "Этаж 3", "отметка": 12000} ],
  "элементы": [ { ... } ]
}
```

Элемент:

| Поле | Источник в Revit | Зачем |
|---|---|---|
| `uid` | `Element.UniqueId` | идентичность между выгрузками |
| `категория`, `семейство`, `типоразмер` | BuiltInCategory, FamilyName, TypeName | сопоставление с нашим словарём типов |
| `марка` | параметр «Марка» | у сборных изделий |
| `уровень`, `отметка_низа` | Level + смещение | ярус |
| `высота` | габарит | снимает наши эвристики расчёта высот |
| `контур` | проекция низа в плане, замкнутая, мм | 2D-схема и 3D-выдавливание |
| `точка` | точка вставки x,y,z | |
| `объём`, `площадь` | штатные параметры | монолит и кладка (пока просто хранятся) |
| `материал` | класс бетона/материал | |
| `рабочий_набор` | Workset | фильтр |
| `секция`, `корпус`, `тип_этажа`, `часть_здания` | общие параметры `MCY_*` | адресация блоков, см. ниже |
| `параметры` | свободный словарь | всё остальное, без правки экспортёра |

### Адресация уже стандартизована заказчиком

Вычитано из модели КР 2026-08-10: в ней заведено семейство общих
параметров с префиксом `MCY_` (МСУ-1), и адресный набор среди них —
готовый:

| Параметр | Роль |
|---|---|
| `MCY_Корпус` | корпус |
| `MCY_Секция` | **секция** — то самое измерение, которого не было у нас |
| `MCY_Этаж` | этаж |
| `MCY_Тип этажа` | значения: Автостоянка, 1 этаж, Типовой этаж, Кровля |
| `MCY_Часть здания` | часть здания |
| `MCY_Раздел` | раздел проекта |

В модели встречается и строка-перечисление «MCY_Этаж, MCY_Секция,
MCY_Тип этажа, MCY_Часть здания» — эти четыре параметра используются как
единый адресный набор.

Значит договариваться с проектировщиками о том, ЧЕМ задавать секцию, не
нужно: параметр уже есть. Остаётся проверить, ЗАПОЛНЕН ли он у элементов —
имена параметров видны в файле, а заполненность по строкам не определяется.
Это первое, что должна показать пробная выгрузка.

Прочие параметры семейства (`MCY_Площадь`, `MCY_Площадь застройки`,
`MCY_Вид объекта`, `MCY_Кадастровый номер участка`, `MCY_Номер ГПЗУ`,
`MCY_Описание`, `MCY_Назначение вида`) относятся к объекту и участку, а
`MCY_Аннотация_*` — к оформлению; в выгрузку элементов они не нужны.

Обязательные условия: **общие координаты** на все разделы (иначе они не
совместятся) и миллиметры.

Сопоставление «категория/семейство Revit → наш тип» живёт правилами **на
стороне сервиса**, а не в экспортёре: эти правила будут меняться чаще
всего, а менять их в сервисе может администратор, тогда как правку
экспортёра надо доносить до проектировщиков.

## 4. Идентичность и области

* Ключ элемента — `uid` (`Element.UniqueId`), устойчив к правкам,
  пересохранению и detach.
* Геометрическая сверка `app/element_identity.py` остаётся ЗАПАСНЫМ уровнем
  — на случай, если модель пересобрали и uid обнулились (ровно то, что уже
  дважды случалось с `dxf_handle`).
* «Исчез из модели» считается **строго внутри раздела**, пришедшего в этом
  комплекте. Без этого загрузка АР списала бы весь КР.

## 5. Путь данных

1. **Экспорт.** Кнопка в Revit на открытой отсоединённой копии → пакет
   рядом с моделью. Ни сети, ни прав, ни настроек.
2. **Передача.** Пакет уезжает как обычный файл.
3. **Приём.** Форма «Загрузка из Revit»: явно выбирается Проект · Объект,
   прикладываются один или несколько пакетов. Комплект = то, что загрузили
   за один заход.
4. **Анализ.** В базу не пишется ничего. Разбор, сопоставление по `uid`,
   сводка.
5. **Применение.** По подтверждению.

Повторяет двухфазную схему `analyze → apply` из `app/dxf_import.py`
(решение И3) с тем же токеном отложенного разбора. Отличия: принимается
СПИСОК пакетов, сверка по `uid`, списание ограничено разделами комплекта.

**Первичная загрузка** и **дозагрузка** — одна и та же операция. Первый раз
кладут все нужные разделы, дальше — только тот, что менялся. Дельту на
стороне Revit считать не нужно: выгрузка всегда полная по своему разделу,
расхождения считает сервер.

## 6. Экран загрузки

Три шага, как у DXF (`app/static/app.js`, «Загрузка чертежа»):

1. Объект — явно, без догадок по имени файла.
2. Пакеты — можно несколько. Таблица: раздел, модель, дата выгрузки,
   элементов, результат разбора.
3. Сводка и применение.

Сводка — четыре блока:

* **Что приехало** — по каждому разделу: всего элементов, разбивка по
  категориям Revit и по нашим типам, отдельно — сколько НЕ сопоставилось с
  типом. Несопоставленное не отбрасывается молча: первый шаг называется
  «просто показать», значит показываем и то, для чего у нас типа пока нет.
* **Что изменится** — новых / изменённых / исчезнувших, по каждому разделу
  отдельно, потому что списание ограничено разделом.
* **Предупреждения** — единицы не мм; координаты не общие; дубли `uid`;
  элементы без контура; отметки вне диапазона уровней; этот раздел уже
  загружен выгрузкой более свежей даты.
* **Превью геометрии** — план контуров комплекта, наложенный на то, что уже
  есть в объекте, разными цветами: имеющееся / новое / исчезающее. Это
  главный визуальный контроль. Девять разделов обязаны стоять в одних
  координатах, и промах с системой координат ловится только глазом — до
  записи в базу, а не после.

## 7. Минимальные изменения в базе

* `elements`: `revit_uid`, `source_section` (код раздела).
* Реестр загруженных пакетов: объект, раздел, имя модели, дата выгрузки,
  дата загрузки, актуальность — по образцу `object_drawings`.
* Справочник правил «категория/семейство Revit → тип», редактируемый в UI.

Всё, что новая версия должна сделать с накопленными данными, — записью в
`app/release_tasks.py`, а не скриптом (стоячее правило проекта).
## 8. Второй контур учёта: блоки «этаж + секция»

Уточнено 2026-08-10 по документам заказчика («WBS МФР типовой»,
«Концепция автоматизации календарного планирования v3.1»). Помимо
поштучного учёта сборных ЖБИ-изделий появляется ОТДЕЛЬНАЯ ветка учёта:
вид работ × блок (этаж + секция) → План / В работе / Выполнено. Контуры
не влияют друг на друга.

Проект этого контура — `Docs/block-accounting.md`. Здесь важно только то,
что он требует от выгрузки Revit:

* поле `секция` у элемента (новая сущность, захваткой не является);
* секция пакета `помещения` (Rooms) — для квартир, под 8 операций отделки
  в единице `кв.эт/сек`;
* уровни — уже предусмотрены.

Снятая развилка: монолит выше нуля меряется в `эт/сек`, а не в
кубометрах, поэтому отдельные статусные цепочки монолита не нужны.

## 9. Что отложено

Необязательность марки и контракта для невыпускаемых изделий, зоны из
Revit, инженерные разделы как источник геометрии.

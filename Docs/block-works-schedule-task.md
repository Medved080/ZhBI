# Задание: «Запланированная работа по блоку» как основной объект управления МФР

Статус: **согласовано 2026-09-10**, передано в реализацию (промпт —
`Docs/block-works-schedule-prompt.md`). Решения пользователя внесены в текст;
незакрытые вопросы — §11 (их задаёт исполнитель перед этапом документов
факта).
Исходное состояние контура — `Docs/block-accounting.md` (§8–§12) и
`Docs/TZ.md` §3в; инвентаризация кода, на которую опирается этот документ,
сделана 2026-09-10 (все ссылки на файлы и строки — на этот день).

## 1. Суть изменения

Сейчас в контуре «Учёт по блокам» центром является **блок** (секция + этаж):
у него есть отбор операций (`block_work_types` — пара `block_id ×
work_type_id` без единого собственного поля), а факт живёт документами
«отчёт о выполнении» **по блоку** (`work_fact_reports` +
`work_fact_items`). Пара «операция × блок» самостоятельной сущностью не
является: у неё нет id, нет сроков, нет своих реквизитов.

Новый центр — **запланированная работа** (далее ЗР): операция справочника
видов работ, поставленная в план на конкретный блок. У ЗР появляются:

| Группа | Поля | Кто задаёт |
| --- | --- | --- |
| 1. Базовые (директивные) сроки | `plan_start`, `plan_end` | ручной ввод (карточка ЗР, групповая форма); не меняются «по ходу» |
| 2. Актуализированные сроки | `forecast_start`, `forecast_end` | приходят снаружи — ручной ввод; версии накапливаются |
| 3. История факта | документы «отчёт о выполнении»: процент → статус, дата, кто зафиксировал (учётная запись) | ответственный со стройки под своей учётной записью, документы редактируемы |

Статус ЗР остаётся производным от процента (`План` = 0, `В работе` =
1–99, `Выполнено` = 100), а сроки добавляют второй, независимый признак —
**отклонение** (см. §4).

Аналогия внутри системы уже есть — график СМР ЖБИ (`Docs/TZ.md` §5.7):
базовый график неизменяем, актуализации накапливаются версиями, отклонение
считается по обеим датам. Здесь та же идея переносится с изделия на ЗР.

## 2. Модель данных

### 2.1 Таблица `block_works` (замена `block_work_types`)

```
block_works
  id              INTEGER PK
  object_id       FK objects        -- дублируется ради отчётов по объекту без джойна через blocks
  block_id        FK blocks CASCADE
  work_type_id    FK work_types CASCADE
  plan_start      TEXT  (ISO-дата, NULL — не задана)
  plan_end        TEXT
  forecast_start  TEXT
  forecast_end    TEXT
  forecast_at     TEXT  -- когда актуализировали (дублирует последнюю версию)
  forecast_by     FK users SET NULL
  note            TEXT
  created_at, created_by, updated_at, updated_by
  UNIQUE(block_id, work_type_id)
```

Причины:

* пара без id нельзя адресовать из истории, из URL, из отчёта — а ЗР
  теперь адресуется отовсюду;
* `SQLite` не умеет добавить PK в существующую таблицу — миграция
  пересоздаёт таблицу с переносом строк (`app/db.py`, тем же приёмом, что
  прежние реструктуризации; на копии → `dry_run_migration.py` → боевой);
* `block_work_types` после переноса удаляется; все чтения
  (`work_fact.py` — 9 мест, `import_reset.py`, `db_schema_doc.py`)
  переводятся на `block_works`.

### 2.2 Явность плана (решение пользователя, В1)

Сегодня ненастроенный блок (`blocks.work_types_configured_at IS NULL`)
означает «все операции BLOCK_UNITS объекта». Для ЗР с датами неявного
«всё» быть не может — срок ставится на КОНКРЕТНУЮ строку. Решено:

* **у ненастроенного блока перечень ЗР ПУСТОЙ** — никакой материализации
  «всех операций»; обработка релиза переносит в `block_works` только
  явные пары из `block_work_types` (1:1);
* строки `work_fact_items`, у которых пары в `block_work_types` нет (факт
  зафиксирован на блоке, который никогда явно не настраивали), — ЗР
  создаётся той же обработкой с `note = 'восстановлена по факту'`, чтобы
  историю не потерять;
* «по умолчанию всё» больше не существует: новый блок создаётся ПУСТЫМ,
  новая операция после перезагрузки WBS в блоки сама не попадает — её
  добавляют «Настройками» (или групповой формой);
  `work_types_import.apply` в сводке показывает «новых операций
  BLOCK_UNITS: N — в план блоков не добавлены»;
* поле `blocks.work_types_configured_at` читать перестают
  (`work_fact.block_settings`, `_op_included_percents`,
  `board_block_values`, `used_planning_tracks`), удалять не обязательно.

### 2.3 Версии актуализации (решение пользователя, В3 — «как у ЖБИ»)

Таблица `block_work_forecasts(id, block_work_id, forecast_start,
forecast_end, created_at, created_by, note)`; текущими считаются значения
последней записи, они денормализованы на ЗР (`forecast_start/forecast_end/
forecast_at/forecast_by`) для скорости отчётов. Каждое сохранение прогноза
(карточка ЗР, групповая форма) — НОВАЯ запись, старые не правятся. Это
даёт отчёт «как плыл прогноз» и динамику по срокам за период тем же
приёмом, что `blocks_fact_changes`.

### 2.4 Документы факта — что меняется

Схема `work_fact_reports`/`work_fact_items` сохраняется (документ ПО
БЛОКУ на дату — решение пользователя 2026-09-02), дополняется:

* ответственный, кто зафиксировал факт, — **учётная запись** (решение
  пользователя, В5): `created_by`/`updated_by` документа и строки, без
  отдельного поля и без справочника физлиц;
* `work_fact_items.block_work_id FK block_works` — вместо `work_type_id`
  (пара `report.block_id + work_type_id` и так однозначно даёт ЗР, но
  ссылка на ЗР делает выборки истории прямыми). Миграция заполняет по
  джойну; строки, для которых ЗР нет (операцию сняли с блока после
  фиксации факта), — ЗР создаётся с пометкой `note='восстановлена по
  факту'`, чтобы историю не терять;
* `work_fact_items.updated_at`, `updated_by` — кто и когда менял ИМЕННО эту
  строку внутри документа (сегодня подсказка истории показывает автора
  документа целиком — `Docs/block-accounting.md` §9, оговорка в конце);
* журнал документа: при правке ранее сохранённого отчёта старые значения
  задетых строк пишутся в `work_fact_item_history(report_id,
  block_work_id, percent_old, percent_new, changed_at, changed_by)` —
  иначе «редактируемый документ» теряет то, что в нём было (см. В6).

### 2.5 Схема и документация

* `app/schema.sql` — новые таблицы и индексы: `block_works(object_id,
  work_type_id)`, `(block_id)`, `block_work_forecasts(block_work_id,
  created_at)`, `work_fact_items(block_work_id)`.
* `app/db_schema_doc.py` — описание каждого нового поля (иначе генератор
  `scripts/gen_db_schema_drawio.py` откажет, а «Состояние БД» покажет
  красную плашку); перегенерировать `Docs/db-schema.drawio`.
* `app/release_tasks.py` — две обработки: перенос явных пар → ЗР плюс
  восстановление ЗР по факту (§2.2) и заполнение
  `work_fact_items.block_work_id`.
  Обе идемпотентны; порядок: сначала ЗР, потом факт.
* `app/import_reset.py` (`POST /objects/{id}/clear-import-data`, группа
  `work`) — чистит и новые таблицы.

## 3. Источники сроков

Обе пары дат **приходят снаружи** (решение пользователя, В4/В8): в первой
версии — только ручной ввод в карточке ЗР и групповой формой «Сроки»
(§6.2). Загрузка графика из xlsx и собственный пересчёт прогноза по факту
**в область НЕ входят**: импорт разработаем, когда появится реальный файл
заказчика (MS Project → xlsx), пересчёт — отдельной задачей позже.
Правила, которые остаются в силе уже сейчас:

* базовая дата, однажды заданная, меняется только явной правкой с
  правом «Изменение» и записью в журнал (`block_work_plan_set`, старое и
  новое значение);
* каждое сохранение актуализированных дат — новая версия (§2.3), ручная
  правка версий задним числом не предусмотрена.

## 4. Производные величины (не хранятся)

Считаются в одном месте (`app/block_works.py`, `derive(zr, today)`) и
используются всеми экранами и отчётами:

| Величина | Правило |
| --- | --- |
| статус | по проценту, как сейчас (`_status_from_percent`) |
| агрегаты по секции / объекту / виду работ | считаются ПО ЗР блоков (решение пользователя, В2): план = min(`plan_start`) / max(`plan_end`), прогноз = min/max `forecast_*`, факт = среднее процентов, статус — по порогам от среднего; ЗР без дат в min/max не участвуют |
| отклонение по началу / по окончанию, дней | `forecast − plan`, плюс — отставание (как у ЖБИ) |
| признак сроков | `в графике` (нет отклонения либо опережение) · `отстаёт` (отклонение > 0) · `просрочена` (сегодня > plan_end и < 100 %) · `не начата в срок` (сегодня > plan_start и 0 %) · `без сроков` (нет plan-дат) |
| ожидаемый процент на дату | линейно между plan_start и plan_end — для сравнения «должно быть / есть» в отчётах |

Порог «отстаёт» — 0 дней в первой версии; параметр объекта не заводим,
пока не попросят.

## 5. Сервер: модули и эндпоинты

Новый модуль `app/block_works.py` (ЗР как сущность: CRUD, даты, версии,
производные, агрегаты); `app/work_fact.py` остаётся про документы факта,
но переводится на ЗР.

| Метод и путь | Назначение |
| --- | --- |
| `GET /objects/{id}/block-works?block_ids&track_code&status&deadline&date_from&date_to` | список ЗР с производными; общий источник для карточки, фильтров, «Шахматки», отчётов |
| `GET /objects/{id}/block-works/{bw_id}` | карточка ЗР: реквизиты, версии актуализации, история факта |
| `PATCH /objects/{id}/block-works/{bw_id}` | ручная правка дат, ответственного, примечания |
| `PUT /objects/{id}/block-works/bulk` | групповая правка: список `bw_id` + поля (даты сдвигом «на N дней» или значением) |
| `PUT /objects/{id}/blocks/work-types-settings` (существует) | остаётся «состав работ»: создаёт/удаляет ЗР; удаление ЗР с зафиксированным фактом — запрет с текстом, либо пометка `retired_at` (см. В7) |
| `GET/POST/PUT .../fact-reports` (существуют) | + построчный аудит `updated_by/updated_at`; `DELETE` отчёта — по решению В6 |
| `POST /reports/block-schedule` (+ `.xlsx`, `.pdf`) | отчёт «График работ по блокам» (§8) |
| `POST /reports/block-status` (существует) | + режим «сроки» (§8) |

Права (`app/features.py`): раздел `work_progress` («Виды работ и статус
по блокам») расширяется описанием — ЗР, сроки, документы факта. Новый раздел `report_block_schedule` («Отчёты →
График работ по блокам», `_все(READ)`), и, раз он появился, заодно
`report_block_status` для существующего отчёта, который сейчас закрыт
разделом `work_progress` без своей строки в матрице прав. Оба — в
`_ТОЛЬКО_МФР`. Обучение: учебный блок на каждый новый раздел
(`app/training_content.py`, страж `check_training_coverage.py`), правка
блока `work_progress` — он до сих пор описывает клик-цикл 2025-08-25 и
«четвёртую закладку „Статусы“», которой уже нет.

Журнал действий (`app/activity_actions.py`, новые коды с подписью и
категорией — иначе pre-commit не пустит): `block_work_add`,
`block_work_remove`, `block_work_plan_set`, `block_work_forecast_set`,
`block_work_bulk_edit`.
Документы факта в общий журнал **по-прежнему не пишутся** (решение
2026-09-02) — их собственная история теперь построчная (§2.4).

## 6. Интерфейс: что переделывается

### 6.1 «Модель МФР», вкладка «Свойства» — карточка блока

Дерево операций (`renderBlockProgressTree`) — строка операции становится
строкой ЗР: имя · полоса и процент (как сейчас) · **план: дд.мм–дд.мм ·
прогноз: дд.мм–дд.мм · отклонение ±N дн** (компактно, второй строкой
мельче; в узком режиме панели — только цветная метка признака сроков с
подсказкой). Клик по строке открывает **карточку ЗР** (новая модалка
`#block-work-backdrop`): реквизиты, обе пары дат с правкой, ответственный,
версии актуализации (список с датой/источником/автором), история факта
(та же таблица, что в подсказке `#bp-history-tooltip`, плюс «кто менял
строку»). Кнопки «Настройки» (состав работ) и «Факт» — остаются;
добавляется «Сроки» (групповая правка дат по отобранным строкам — §6.2).
В шапке карточки блока — агрегат по блоку (план/прогноз/средний процент),
в дереве у узлов-разделов — агрегат по их операциям (§4).

Групповое выделение блоков (Ctrl/Cmd-клик, §8 `block-accounting.md`):
«Сроки» работает и на группу (все ЗР выделенных блоков по текущему отбору
«Виды работ»).

### 6.2 Формы

* **«Настройки»** (`#block-settings-backdrop`) — смысл прежний, но текст:
  «Состав работ блока». Снятие галочки с ЗР, у которой есть факт или
  даты, — предупреждение с числом документов (см. В7).
* **«Факт»** (`#block-fact-backdrop`) — у каждой строки — кто и когда
  менял (после сохранения); прежние отчёты открываются и правятся как
  сейчас, с записью в построчную историю (если согласована, В6).
* **«Сроки» (новая, `#block-works-dates-backdrop`)** — таблица ЗР (по
  выделенным блокам и отбору): план-начало/план-окончание/прогноз-начало/
  прогноз-окончание, правка по ячейке; операции «сдвинуть все на N дней»,
  «прогноз = план» (для ещё не начатых). Сохранение — `PUT
  .../block-works/bulk`.
* **«Учёт по блокам»** (`#blocks-backdrop`) — новая закладка **«График»**:
  сводка «ЗР всего / с планом / с прогнозом / отстают / просрочены» по
  объекту и вход в групповую форму «Сроки» по всем блокам; место для
  будущей загрузки xlsx (не сейчас).

### 6.3 Вкладка «Фильтры»

К Этаж / Секция / Виды работ / Статус выполнения / Динамика добавляются:

* **«Сроки»** — чекбоксы признака: в графике · отстаёт · просрочена ·
  не начата в срок · без сроков (`blockProgressFilter.deadline`, режет
  дерево карточки как «Статус выполнения»);
* **«Период по плану»** — две даты: ЗР, чей план пересекается с периодом
  (что должно идти «на этой неделе»); та же пара дат может переключаться
  на «по прогнозу»;
* «Динамика факта за период» — без изменений, но область сравнения
  считается по ЗР (`blocks_fact_changes` переводится на `block_works`).

«Сбросить все фильтры» (`#mfr-reset-all-filters`) — чистит и новые группы.

### 6.4 Вкладка «Вид» — «Шахматка»

Доска получает **режим раскраски**: «по выполнению» (как сейчас — среднее
процентов) и **«по срокам»** — цвет блока по худшему признаку сроков
среди его ЗР доски (просрочена > отстаёт > не начата в срок > в графике;
«без сроков» — серый «неприменимо», как сейчас у блока вне отбора).
Подпись на грани (`mfrChessLabelLayout`/`buildMfrChessLabelMesh`, 2D и
3D одной раскладкой) — в режиме сроков к строке операции добавляется
«±N дн» справа от процента; легенда `#mfr-chess-legend` меняет палитру
по режиму. `board_block_values` возвращает обе сводки разом, чтобы не
дёргать сервер при переключении режима. `MFR_CHESS_COLORS_3D` — вторая
палитра hex-константами.

### 6.5 Отчёт «Учёт по блокам: статусы» (`renderBlockStatusReport`)

Ячейка BLOCK_UNITS по-прежнему процент на дату; добавляется переключатель
**«показать: процент · план · прогноз · отклонение»** — те же ячейки, другая
величина (правка возможна только в режиме «процент», как сейчас). Ожидаемый
процент на выбранную дату (§4) — подсказкой в ячейке: «есть 40 %, по плану
должно быть 65 %».

## 7. «Сек», «компл» и вышестоящая иерархия (решение пользователя, В2)

Сроки нужны **только блокам**. Секция, объект и вид работ целиком — не
самостоятельные носители дат, а **агрегаты по ЗР блоков** (правила — §4):
и план, и прогноз, и факт — в разрезе видов работ. Операции с единицами
`сек`/`компл` остаются на старой модели `work_progress` (клик-цикл) без
изменений; в отчёте §8 они показываются как сейчас, без сроков, с
пометкой «вне графика».

## 8. Отчёты

* **«Учёт по блокам: статусы»** — режимы показа (§6.5); в матрицу прав
  заводится своим разделом (§5).
* **Новый «График работ по блокам»** (`app/report_block_schedule.py`,
  `POST /reports/block-schedule`): таблица ЗР с планом, прогнозом,
  процентом, отклонением, признаком сроков, ответственным; группировка
  строк выбирается тем же органом, что у «Графика поставки»
  (`createGroupChooser`): Трек → Раздел WBS → Операция → Секция → Этаж и
  обратно (Секция → Этаж → …). Итоги по группе: доля выполненных,
  среднее отклонение, число отстающих. Выгрузка XLSX/PDF — по образцу
  `schedule_gantt_export.py`, включая **вид «Гант»** (полоса плана и
  полоса прогноза на строку) — переиспользовать рисование сетки по

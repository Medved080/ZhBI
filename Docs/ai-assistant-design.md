# ИИ-помощник по строительству и контрактации

Реализовано 05.10.2026. Настройки доступны в «Администрирование → Интеграция с ИИ»; помощник — после входа в V1, V2 и самостоятельном Калькуляторе. Встроенная сцена и Калькулятор используют кнопку оболочки V2. В окне обработки изделий есть отдельная кнопка вызова.

## Сценарий пользователя

Пользователь открывает помощника и задаёт вопрос. По умолчанию поиск охватывает всю доступную систему и уточняет объект/проект по смыслу вопроса; страница служит подсказкой. Все параметры задаются текстом: «по всем проектам за сентябрь», «по объекту … на 01.10», «по отбору на текущей странице, с разбивкой по этажам». Настроек области/периода/дат в панели нет. Новый диалог без периода использует последние семь дней по Москве; продолжение без нового периода сохраняет ранее обсуждавшийся. «За месяц» — последние 30 дней, «за сентябрь» — календарный месяц. Область и фактические даты показаны под ответом.

При вопросе по текущей странице передаются видимый текст и значения видимых фильтров, текущий объект, отбор схемы/отчёта и до 100 выбранных изделий. Скрытые поля, пароль, поле вопроса и сам диалог исключены. Из Калькулятора передаются видимая калькуляция/открытое окно и сведения о текущем изделии. Изображение схемы не анализируется: помощник использует её отбор, выбранные изделия и текст. При явной области «Текущая страница» страница без объекта обсуждается по её тексту. В области по умолчанию вопрос о данных ищет источники во всей доступной системе. Калькулятор не связывается автоматически с объектом, выбранным в оболочке ЖБИ.

Область и период показаны явно; начало интервала исключается, конец включается. Для календарного месяца начало — последний день предыдущего месяца. При переходе на другую страницу/объект или смене отбора/выбранных изделий предыдущий запрос отменяется и диалог очищается. Уточнение проекта или периода текстом сохраняет диалог. При выходе из V1 панель удаляется; V2 перезагружает оболочку. История последних восьми реплик живёт только в памяти вкладки. Данные и документы через помощника не изменяются.

Под ответом показаны время подготовки данных, период, модель, предупреждения и ссылки на источники. Источник поиска открывается в отдельной таблице с числом возвращённых строк и отметкой ограничения. Отчёт открывается в той же вкладке с датой окончания периода, источником плана и отбором из ответа. ID отбора сохраняются в запросе помощника, а показатели отчёт пересчитывает по актуальной базе. При истечении запроса/перезапуске сервера пользователь получает объяснение, что отчёт будет открыт с обычными параметрами.

## Поиск по системе

`app/assistant_data.py` содержит явный каталог разрешённых бизнес-полей. Модель сначала выбирает 1–4 набора данных, доступные объекты и период; однозначные русские периоды дополнительно нормализуются `app/assistant_period.py`. Явная область старого API — жёсткая граница (совместимость сохранена); обычный UI передаёт область/даты только через вопрос. Область «по текущей странице» выводится из вопроса и применяет отбор до SQL. Затем сервер создаёт отдельный снимок SQLite в памяти, без секретов и без строк чужих объектов. Модель составляет до шести SELECT, получает результаты и может исправить/дополнить поиск вторым набором до шести запросов. Итоговый ответ формируется только после поиска. Используется одна диалоговая модель; на вопрос обычно приходится четыре её вызова, что увеличивает задержку.

Наборы: ЖБИ и полная история статусов; контракты, документы контрактации и связанные количества; графики и примечания; работы/блоки, планы, актуализации и документы факта; Revit и помещения; справочники; метаданные вложений; Калькулятор; разрешённое администрирование и обучение. Проекты Калькулятора не связываются с проектами ЖБИ по совпадению ID. Содержимое бинарных вложений, геометрические изображения и неизвестные новые поля автоматически не открываются. Для их анализа нужен отдельный механизм распознавания/индексации.

На основной/расчётной БД исполняется только фиксированный SQL реестра. SQL модели исполняется исключительно на копии в памяти с `query_only` и авторизатором: разрешены SELECT, чтение таблиц каталога и ограниченный список функций. Запрещены DML/DDL, PRAGMA, ATTACH, системные таблицы и расширения. Бюджет запроса — три секунды; списки — максимум 200 строк / 16000 символов. COUNT/SUM вычисляются по всему разрешённому набору, до ограничения возвращаемого списка. Ограниченные строки явно помечаются; в контекст не отправляется вся БД.

Права проверяются при копировании каждой таблицы, перед итоговым ответом и при чтении результата/выборки. Обучение без права истории других людей включает только собственные попытки. Разные виды документов контрактации фильтруются по своим правам. Для итогов монтажа/поставки доступен `period_facts` по определению штатной динамики; это предотвращает подсчёт повторных записей истории как нескольких изделий. Штатные отчёты дополняют поиск для областей до восьми объектов, общие итоги по всем объектам доступны через агрегирование снимка.

Источники `search-N` сохраняют SQL, таблицы и ограниченные результаты в памяти задания. API отдаёт их владельцу только после повторной проверки прав. В UI показываются значения через `textContent`, служебный SQL пользователю в диалоге не показывается. Источники отчётов сохраняют прежние ссылки с датой и отбором. Полнота текста зависит от модели; сервер гарантирует границы доступа и проверяемость выборки, но не правильность любого сгенерированного аналитического SQL.

## Серверные показатели и смысл сравнения

| Источник | Что получает модель | Область и ограничение |
| --- | --- | --- |
| Динамика ЖБИ | Накопительные план/факт/прогноз поставки и монтажа на начало и конец, разность фактов, покрытие и окончания | Текущие изделия; в режиме страницы тот же отбор. Даты фактов и текущие статусы берутся из штатного отчёта. Изменение за `(начало, конец]`, не архивный снимок базы |
| Аналитическая справка | Итоги обеспечения/дефицита, этапы, критические позиции, выводы | Объект целиком; первые 12 марок по дефициту и первые 12 критических строк, итоги по всем. Контракты текущие, неархивные; дата задаёт горизонт |
| Контрактация по датам спецификаций | Количество до начала/конца и разность, шт. | Текущие количества неархивных контрактов по датам спецификаций. Изменение задних дат, количеств или архивирование меняет расчёт; это не история правок контрактов |
| График работ по блокам | Итоги на две даты и первые 15 работ | Документы факта на дату, текущий состав и сроки; итоги по всем работам. Поддерживает МФР |
| Выбранные изделия | Марка, тип, этаж, статус и даты поставки | Только текущие изделия выбранного объекта при праве на схему |

Штатные отчёты и основной снимок поиска одного ответа читаются в одной транзакции SQLite. Калькулятор имеет отдельную БД и отдельный снимок чтения; общего атомарного снимка двух БД нет. Числа не рассчитываются моделью из DOM: в системном сообщении приоритет отдан серверным источникам. Модель даёт ответ с нужной вопросу подробностью, объясняет показатели, отмечает конкретные пробелы и не должна придумывать причины. Надёжность числовых утверждений самой модели требует проверки на выбранной реальной модели.

## Подключение и память моделей

Один адрес и тип API (`Ollama` либо OpenAI-совместимый сервер), два имени модели: диалог и чтение чертежей. Пользователь выбрал отдельную модель для диалога на том же сервере; можно указать одинаковые имена. Размер контекста помощника задаётся отдельно: 8192–65536 токенов, по умолчанию 16384. Для Ollama отправляется `num_ctx`; для OpenAI-совместимого API размер задаётся на сервере загруженной модели. Ответ ограничен 4096 токенами и общим меньшим лимитом ответа, если он задан.

Если обе модели с их контекстом помещаются в память и сервер сохраняет их загруженными, переключение не требует постоянной загрузки. При нехватке памяти сервер может выгружать одну и загружать другую; первый ответ после переключения будет медленнее. Удержание, TTL и число одновременно загруженных моделей настраиваются на сервере моделей. Помощник не меняет эти настройки и не прогревает модели при каждом открытии страницы.

Запрос помощника резервирует GPU тем же механизмом, что очередь чтения чертежей и проверка изображения. При занятом GPU выдаётся понятное сообщение для повтора после завершения обработки; очередь партий Калькулятора ждёт освобождения ресурса. Несколько диалогов одновременно также защищены локальной блокировкой. Уже созданные партии продолжают работать с сохранённой конфигурацией, новые используют общую настройку.

Адрес проверяется существующим локальным HTTP-клиентом: внутренние IP/loopback, без перенаправлений и облачной подстановки. Собственные DNS/разрешённые внешние адреса требуют явной серверной настройки `CALCZHB_QWEN_ALLOWED_HOSTS`. Ключ читается из существующего `CALCZHB_QWEN_API_KEY`; в UI показывается только факт наличия. Адрес `127.0.0.1` обозначает сервер ЖБИ, а в Docker — его контейнер. Настройки логирования и хранения запросов на сервере моделей задаются отдельно.

## Облачный роутер red_mad_robot (08.10.2026)

Помощник может отвечать не локальной моделью, а через облачный роутер red_mad_robot (`https://rmrrouter.redmadrobot.com/`, OpenAI-совместимый, один ключ — модели разных поставщиков). Механизм перенесён из проекта «Радар тендеров» (`radar/llm_client.py`, `llm_store.py`, `rmr_pricing.py`); потоковое чтение ответа (тайм-аут простоя, отмена, обрыв по лимиту, зацикливание, токены) осталось общим с локальным клиентом.

**Границы (решение пользователя 08.10.2026).** Через роутер идёт ТОЛЬКО помощник. Чтение чертежей Калькулятора остаётся на локальной модели, изображения чертежей наружу не уходят. Локальный клиент по-прежнему отвергает любой адрес вне внутренней сети; роутер — единственное исключение, адрес жёстко привязан к `rmrrouter.redmadrobot.com` (HTTPS, порт 443). Ключ роутера не уходит на локальный сервер и наоборот.

**Данные уходят наружу.** Вопрос, выдержки данных сервиса (названия объектов, контрагентов, договоров, количества, даты) и видимый текст страницы попадают на внешний сервер. Поэтому роутер выключен по умолчанию, включается только администратором (`ai_settings/write`) и только после явного подтверждения в форме («согласовано со службой ИБ», `dataConsent`); без подтверждения, ключа и модели включение отвергается сервером. В ответе помощника указано «(облачный роутер)», в журнале — события `ai_router_settings`, `ai_router_key`, `ai_router_usage`.

**Хранение.** Настройки — `app_settings`, ключ `service_ai_router` (отдельно от `service_local_ai`: схема БД не меняется, откат версии просто не видит запись, помощник возвращается к локальной модели). Секрет — файл `<файл базы>.ai-secrets.json` рядом с базой (права 0600, создаётся атомарно): не в БД, поэтому не попадает в резервные копии, перенос базы, образ и обезличенную копию. Альтернатива — переменная окружения `ZHBI_RMR_API_KEY` (форма её заменяет). Наружу отдаётся только «задан / не задан» и источник; ключ вычищается из любого текста ошибки (роутеры иногда повторяют его в ответе 401).

**Сеть.** Серверу нужен исходящий доступ к `rmrrouter.redmadrobot.com:443` (заявка DevOps; в корпоративном контуре его по умолчанию нет). Выход через прокси: `HTTPS_PROXY`/`NO_PROXY` из окружения либо `ZHBI_RMR_PROXY` (пустое значение — напрямую), туннель CONNECT на стандартной библиотеке; прокси с подменой сертификата — `SSL_CERT_FILE` с корпоративным корневым сертификатом. Редиректы запрещены.

**Подбор параметров** (перенесён из Радара и дополнен). Формат ответа `json_schema` → `json_object` → без формата и параметр лимита `max_tokens` ↔ `max_completion_tokens` меняются по тексту отказа 400/422; параметры, названные в отказе (`temperature`, `reasoning_effort` и др.), снимаются; найденное запоминается в процессе на пару «адрес + модель». Временные отказы 429/502/503/504 повторяются дважды с паузой. Переполнение контекста облака (`maximum context length is …, resulted in …`) разбирается структурно (`ContextOverflow`), и диалог сокращает контекст вдвое. У облака контекст диалога берётся из настройки целиком (у локального сервера — не больше 8192). Пустой ответ при исчерпанном лимите считается рассуждением (облако не присылает его потоком). Тело отказа читается ДО закрытия соединения — при keep-alive иначе оно приходило пустым, и подбор по тексту ответа не работал (исправлено и в общем читателе потока для локальных серверов).

**GPU и очередь.** Запрос к роутеру GPU сервера не занимает и ожидания освобождения GPU не требует; один выполняющийся вопрос на пользователя остаётся.

**Стоимость и биллинг** (`app/rmr_pricing.py`, `app/rmr_prices.json`). Прайс — рубли за 1 млн токенов с наценкой сервиса 15%, НДС 22% сверху (галочка «с НДС»); файл собирается `scripts/import_rmr_prices.py <прайс.docx>` и коммитится (курс и цены меняются — обновлять при выходе нового прайса). Токены каждого вопроса берутся из usage ответа (нет usage — оценка по длине, 2,2 знака на токен, с пометкой), пишутся в журнал действий событием `ai_router_usage` вместе со стоимостью по прайсу (также и при отказе или остановке: токены платные) и сворачиваются в сводку за сутки и 30 дней по моделям. Это ОЦЕНКА, а не счёт роутера: кэш токенов и курс на день списания не учитываются; баланса у роутера по API нет — только ссылка на `…/billing`. Очистка журнала администратором стирает и этот учёт. «≈ за вопрос» — среднее по фактическим вопросам (от пяти), до этого типичные 12 тыс. вх. и 1,2 тыс. вых. токенов; «до …» — три вызова с полностью заполненным контекстом.

**API** (все — право `ai_settings/write`): `GET/PUT /ai/router/config` (ревизия SHA-256), `PUT/DELETE /ai/router/key`, `POST /ai/router/models`, `POST /ai/router/test` (список моделей + один короткий платный ответ), `GET /ai/router/billing`. Интерфейс — V2 «Администрирование → Интеграция с ИИ» (`app/static/v2/router-settings.js`); V1 открывает тот же экран V2.

**Проверка.** `scripts/verify_rmr_router.py` (97 проверок: адрес и привязка к хосту, права, подтверждение/ключ/модель, конфликт ревизии, файл секретов 0600, ключа нет в БД/журнале/ответах, список моделей и проверка, помощник через макет роутера, журнал расхода, сводка, подбор формата и параметров, 429, переполнение, перенаправление, рассуждение, неверный ключ без утечки, ключ из окружения, прокси CONNECT с логином, отмена посреди потока) на копии обезличенной БД и локальном HTTP/1.1-макете (`scripts/rmr_router_mock.py`); регрессия `scripts/verify_ai_assistant.py` (166 проверок) не изменилась. Живая проверка V2 на стенде с макетом (`zhbi-server-anon-rmr`): ключ, список моделей, проверка, включение, вопрос, учёт расхода, узкий экран.

**Не проверено.** Настоящий роутер не вызывался: цены, имена моделей, поддержка `json_schema`/`reasoning_effort` конкретными моделями и поведение через настоящий корпоративный прокси подтверждаются только на сервере с выходом наружу. Качество ответов облачных моделей на данных сервиса и их расход на реальных вопросах не оценены. Решение службы ИБ о передаче данных — вне кода.

## Совместимость и хранение

Общая конфигурация — существующая таблица `app_settings`, ключ `service_local_ai`, `object_id=NULL`. Схема базы не меняется. Пока общей записи нет, читается старое подключение из `recovery_settings` Калькулятора; первая явная запись администратора сохраняет его в настройках сервиса. Старый файл не удаляется, диалоговая модель автоматически не подставляется. Перенос не требует обработки накопленных бизнес-данных.

Подключение на странице обработки Калькулятора заменено ссылкой на настройки сервиса и информацией о модели/проверке. Старый endpoint сохранения в составе ЖБИ возвращает 409 с объяснением переноса. Автономное приложение Калькулятора сохраняет прежний механизм настройки. Основные роутеры ИИ подключаются вместе с доступной подсистемой Калькулятора (Python 3.12); старый runtime не должен ломать основной сервис при импорте.

Сохранение защищено ревизией SHA-256: чужая параллельная правка не перезаписывается. Доступ — системный администратор или право `ai_settings/write`, которое можно назначить в матрице ролей. Изменение фиксируется событием `ai_settings`; учебный материал содержит общий блок помощника и блок настройки интеграции.

## Доступ и API

Модель может составлять SELECT только для разрешённого снимка в памяти; операции записи и обращения к исходным БД недоступны. Сервер сам определяет доступные объекты и проверяет права `report_dynamics`, `report_analytics`, `report_block_schedule`, `plan`. ID отбора и выбора проверяются на принадлежность текущему объекту/чертежу. Клиент не может добавить системную реплику. Текст страницы и названия рассматриваются как недоверенные данные.

Ответ — JSON `answer` + `sourceIds`. Отображение только через `textContent`; неизвестные ссылки отклоняются. URL формируются сервером. Чтение результата и параметров источника разрешено владельцу запроса; права на источники повторно проверяются, в том числе после отзыва доступа.

| API | Назначение |
| --- | --- |
| `GET/PUT /ai/config` | Общая настройка с ревизией, только `ai_settings/write` |
| `POST /ai/models` | Модели на введённом локальном сервере |
| `POST/GET /ai/drawing-test` | Существующая фоновая проверка изображений/JSON |
| `POST /ai/dialog-test` | Проверка диалога без бизнес-отчётов |
| `GET /assistant/status` | Включён/настроен, без адреса и ключа |
| `POST /assistant/requests` | Асинхронный вопрос, HTTP 202 |
| `GET /assistant/requests/{id}` | Состояние/ответ, этапы, длительность, ожидание/получение данных модели владельцу |
| `POST /assistant/requests/{id}/cancel` | Отмена |
| `GET /assistant/requests/{id}/sources/{source}` | Дата и отбор для проверки ответа в отчёте |

## Границы и проверка

Поиск охватывает все доступные объекты; отдельный набор штатных отчётов ограничен восемью объектами и 90000 символами источников; отдельная консервативная оценка общего контекста учитывает историю, текст страницы и лимит ответа. Каждый этап ограничивается бюджетом отдельного запроса до 8192 токенов с резервом на ответ/схему; при переполнении выполняются до двух сокращённых повторов. Перечень объектов для маршрутизации при необходимости заменяется подсказками, однако все доступные объекты остаются в снимке для SQL. Сокращаются детали/история и повторяющиеся выводы отчётов с отметкой; итоговые агрегаты и исходные строки проверяемых выборок сохраняются. При достаточном плане без ошибок уточняющий вызов пропускается. Оценка размера консервативная, без токенизатора конкретной модели; при невозможности сокращения выводится понятная ошибка. Детальные строки ограничены и подписаны как примеры, а не полный перечень. Причины изменения ситуации, которых нет в данных, помощник достоверно установить не может.

Задания находятся в памяти одного процесса API: один активный запрос на пользователя, до 200 заданий, завершённые удаляются после часа при следующем запросе. Перезапуск теряет запросы и параметры ссылок. Для нескольких процессов/реплик потребуются общая очередь и хранилище; текущая конфигурация сервиса — один процесс API. GPU-аренда при доступной базе Калькулятора общая между процессами, однако сама история заданий — нет.

Проверено на временной копии `data/zhbi.anon.db` и локальном HTTP-стенде без настоящей модели: 73 сквозные проверки (`scripts/verify_ai_assistant.py`), автоматический/ручной период, сумма по всем проектам, поиск контрактов/работ/калькуляций, исправление SQL, запреты SQL и отсутствие секретов, права и отзыв доступа, конфликт ревизии, сохранение старой конфигурации, разные модели, `num_ctx`, числа штатного отчёта, отбор, асинхронность, отмена, занятость GPU, неизвестные ссылки и параметры источника. Живой браузер: V1/V2/Калькулятор, настройка и проверка диалога, ответ и источники, сброс при выходе, вызов из окна обработки. Стражи имён, журнала и учебного материала пройдены; предупреждения покрытия трёх старых разделов остаются прежними. Проверка качества и задержек на настоящей модели, а также чтение изображения реальной моделью не выполнены.

Диалог с рассуждающими моделями: помощник запрашивает отключение Thinking для любой диалоговой модели, включая Gemma: `reasoning_effort=none` и `chat_template_kwargs.enable_thinking=false` (OpenAI-совместимый API), `think=false` (Ollama). Неподдержанный параметр удаляется только при явном отказе сервера; это не подтверждает отключение режима. Рассуждение показывается отдельным статусом и счётчиком знаков, его текст не сохраняется в задании и не выводится пользователю. Унаследованный порог 75% количества фрагментов остаётся для клиента чтения чертежей, для диалога отключён: фрагмент не равен токену. Тайм-аут простоя, отмена, предел ответа/общей длительности и размера остаются. Если лимит израсходован только рассуждением, выполняется один повтор с резервом результата до 4096 токенов/половины контекста и общего лимита настройки, с пересчётом бюджета входа. После повторного отказа выводится объяснение настройки Thinking на сервере.

Простое «с 20 сентября» включает 20-е число, верхняя дата сохраняется; запрос с явно заданным концом оставляется разбору модели. Продолжение «из них» получает историю с предыдущими типом/этажом/объектом. `period_facts` агрегирован по объекту и не применяется к отдельному типу/этажу: монтаж выбранного поднабора считается по текущим элементам и первому подходящему переходу истории.

Последний успешный ответ передаётся как `previousRequestId`. Для вопросов об использованных источниках сервер проверяет владельца и все права, берёт сохранённые подтверждающие выборки/отчёты, период и capturedAt, назначает новые ссылки текущего задания. Для основного периода запросы общего итога и разбивки должны суммировать одинаковые поля с одинаковым отбором. События истории не считаются числом изделий. Определение не изменяет штатные отчёты и не является миграцией БД.

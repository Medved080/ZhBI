# Производственная программа в деньгах (ПП)

Статус (2026-10-23): **ядро, загрузчик, сервер, права и экран V1/V2 готовы и проверены на обезличенных данных** (ветка `worktree-pp-money-core`,
в `main` не влита). Поведение для пользователя — `Docs/TZ.md` §12б. Это пункт B3 из `Docs/requirements-4Q26.md`; B1 (карточка объекта)
и B2 (проектная команда) уже сделаны.

Решения заказчика (2026-10-23): право отдельное, заводски только администратор; объекты ПП без пары в сервисе показываются с пометкой «не в
сервисе»; дивизион и СМУ — вид подразделения (одно поле); правки сроков и группы объектов — ОБЩИЕ; шкала и стартовая дата — фиксированные.

## Что это

Дашборд сроков работ и остатка денег по объектам: диаграмма Ганта на четыре уровня вложенности (объект → работа → задача → подзадача),
правка сроков перетаскиванием, и сразу пересчёт распределения остатка денег по месяцам. Просмотр — по одному объекту, по СМУ и по
произвольной группе объектов (группы в сервисе пока нет, см. «Открытое»).

Прототип — автономная страница `ПП-автономный.html` (описание — «Описание проекта.md» заказчика). Его стек тот же, что у сервиса: vanilla JS и
SVG без сборщика, поэтому расчётное ядро перенесено как есть, а не переписано.

### Правила (не менялись относительно прототипа)

- Сроки считаются **снизу вверх**: у работы с детьми начало — минимум, окончание — максимум по детям. Правка работы с детьми сдвигает все
  листья её поддерева на ту же величину.
- Деньги стекают к **листовым** работам: собственный остаток родителя (и полученная им доля) делится по прямым детям пропорционально их
  остатку, последний ребёнок забирает остаток. Отрицательные остатки не участвуют.
- Распределение по месяцам — **равномерно по дням** листовой работы. (Требование B3 говорило о нормальном распределении с коэффициентами
  по видам работ — это не сделано; точка замены одна, `addLeafDistribution`.)
- Начало работы не раньше стартовой даты расчёта, окончание не раньше начала.

### Что изменено относительно прототипа (логика — нет)

- Состояние (объекты, правки, предпросмотр перетаскивания) внутри модели `createModel()`, а не в глобальных переменных.
- Стартовая дата (в прототипе зашита 01.10.2026) и число помесячных колонок шкалы (15) — параметры `createModel({startDay, monthCount})`.
- Запасной срок объекта без работ в «Ввод» (в прототипе зашит 01.01.2026–30.12.2027) — параметры `fallback_start`/`fallback_end`.
- Поиск денег для строки срока — по индексу, а не перебором (результат тот же).
- Выбор объектов: `selectObjects({division, codes})` — один объект, СМУ или произвольный список кодов; `computeView` работает по любому списку.
- Миграция правок v5→v6 не перенесена: нужна только `localStorage` старого прототипа.
- Не перенесено (это оболочка): геометрия шкалы в пикселях, отрисовка, события мыши, подсказки, `localStorage`, SheetJS.

### Правила загрузки (из `transform.js`, в описании прототипа их нет)

- «Ввод» — не таблица, а **блоки**: строка с кодом проекта и названием в колонке E открывает объект, ниже его работы. СМУ и дивизион тянутся
  вниз от последней заполненной строки. Ячейка с ошибкой Excel (`#REF!` и т. п.) считается **пустой** (так читал SheetJS; на этом `openpyxl`
  отдавал `#REF!` вместо названия СМУ).
- Иерархию строит **номер в названии** («3.2.1. …» → родитель «3.2.»); колонка «Родитель по кодификатору» не используется.
- Одинаковые названия внутри объекта (разные PBI-блоки) склеиваются: начало — минимум, окончание — максимум (на файле 20.10.2026 — 49 дублей).
- Деньги — из «Лист6», сумма по паре (код, «Наименование работ по кодификатору»); цена — колонка J, выполнено — L, остаток — M. Деньги кодов,
  которых нет в «Ввод», отбрасываются (99 из 310 кодов). Узлы без срока получают срок родителя с тем же номером раздела, иначе размах объекта.
- «Дивизион» в прототипе — это колонка **СМУ**; колонка «Дивизион» читается (`objects[].div`), но нигде не используется.

## Проверка

```
# эталон: data.js или JSON результата transform.js; книга и эталон лежат ВНЕ репозитория (реквизиты заказчика)
.venv/bin/python scripts/verify_pp_import.py 20.10.2026.xlsx data.js --dump /tmp/pp.json
node scripts/verify_pp_core.mjs /tmp/pp.json --prototype ПП-автономный.html [--steps 300] [--seed 1]
```

Результат на 20.10.2026 (2026-10-23): загрузчик — 8 051 строка сроков и 5 449 строк денег совпали с прототипом полностью (все поля),
213 объектов, 49 дублей, остаток 442 284 млн. Ядро — инварианты и контрольные числа прототипа (443,82 млрд; БП-000193 — 55 работ и
10,79 млрд; 19/41/45 строк первого объекта), плюс сверка с исходным скриптом прототипа на 300 случайных правках: срок, стоимость, доля
родителя каждой из 8 051 работ, деньги по месяцам (побитово), строки дерева, строки выгрузки, предпросмотр перетаскивания. Намеренная
порча правила распределения тестом замечается.

## Открытое

- Учебный блок на разделы `pp`/`pp_admin` и запись в «Что нового» (текст согласуется с заказчиком).
- Проверка на боевых данных; выдача права `pp` ролям (заводски только администратор сервиса). Миграция схемы — 7 аддитивных таблиц `pp_*`;
  перед боевой базой — `scripts/dry_run_migration.py` на копии.
- Данные грузятся в браузер целиком (≈0,5 МБ в сжатом виде, 213 объектов); при росте — выдача по выбранным объектам (`GET /pp/data?ids=` уже есть).
- Объект ПП связывается с объектом сервиса только по совпадению названия; ручной привязки (по образцу `guid_1c`) нет.
- Группы собираются вручную списком; правило отбора (СМУ, проект, статус) не сделано.
- Распределение денег равномерное по дням; «нормальное распределение с коэффициентами по видам работ» (B3) не сделано — точка замены `addLeafDistribution`.
- Объект, исчезнувший из выгрузки и вернувшийся в следующей, теряет правки и участие в группах (ключ — код проекта, объект удаляется каскадом);
  `analyze` предупреждает заранее.
- Загрузка и редактирование на узком экране (телефон) не проверялись.
- `scripts/gen_db_schema_drawio.py` уже не собирается (в `COLUMNS` нет 9 таблиц — `headcount_*`, `work_codifier`, `team_*` и др.), таблицы `pp_*`
  в него тоже не внесены.

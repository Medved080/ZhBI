# Учёт численности персонала по объектам — ТЗ (черновик на согласование)

Статус: **ТЗ согласуется, кода нет** (2026-10-09). Источник требований — папка заказчика «Численность ЖБИ»
(приказ П-ОД-38 от 2022 г., выгрузка факта за 2026 г., справочник видов работ из Power BI, макеты отчётов,
описание Telegram-бота) и ответы пользователя от 2026-10-09 (см. §9). Пункт B4 из `Docs/requirements-4Q26.md`.

## 1. Зачем

Ежедневно, по каждому объекту, по каждому подрядчику и виду работ фиксируется, сколько рабочих он вывел на
площадку. Сейчас это делается на внутреннем SharePoint-сервисе (форма «Сбор численности»), отчёты строятся в
Power BI. Задача — перенести ввод, историю и отчёты факта в трекер.

Регламент (приказ): вносит менеджер проекта, при замещении — начальник участка; данные за рабочий день — до 11:00
того же дня, за субботу и воскресенье — до 11:00 понедельника.

## 2. Что входит в первый этап и что нет

Входит: справочники (кодификатор работ, подрядчики объекта), форма ввода, загрузка исторической выгрузки,
история правок, отметка о просрочке, отчёты факта (по объектам, подрядчикам, работам), Excel-экспорт, права.

Не входит: **план** (оперативный план центра ресурсного планирования и план по ПП 2026 считаются по объёмам и
нормативам выработки с поправочным коэффициентом, источника у нас нет); столбцы «План» и «Δ» в отчётах не
показываем, структура под них оставляется. Telegram-бот — второй этап. «Выгрузка для Фин.Ком» — после
получения образца. СКУД — справочно, позже.

## 3. Что показала выгрузка 2026 (48 094 строки, 01.01–29.09.2026)

- Колонки: дата и время ввода, дата, число рабочих, код кодификатора, ИНН, GUID объекта в 1С, название объекта в 1С.
  74 объекта, 263 подрядчика, 185 кодов работ, ≈1 800 человек в день в сумме. Нулей и пустых нет, максимум в строке — 256.
- Выходные: ≈10 тыс. строк — субботы и воскресенья вносятся как обычные дни.
- **Дубли** ключа «дата + объект + подрядчик + код работы»: 176 ключей, у 41 из них числа различаются
  → правило «последнее значение актуально, остальные — история» нужно реально.
- **ИНН не везде ИНН:** в 16 строках вместо ИНН записано название «БСТ-ГРУПП ООО»; 25 строк с 9-значным ИНН,
  275 — с 12-значным (ИП и физлица, допустимо). 9-значные — подозрительны. Грузим как есть, подсвечиваем.
- Все 185 кодов есть в справочнике кодификатора (593 строки, 26 разделов, коды уникальны).

## 4. Данные

Новые таблицы (описания полей — в `app/db_schema_doc.py`, иначе генератор схемы откажется собирать):

- **`work_codifier`** — общий кодификатор видов работ (НЕ на объект, отличается от WBS `work_types`):
  `code` (уникален, `250-01-01`), `name` («16.1.1. …»), `parent_name`, `section_name`, `unit`, `sort_order`,
  `retired_at`. Загрузка и обновление — из xlsx «Справочник по видам работ (PBI)», лист
  `РаботыНаименовКодифМСУ`, ключ — код.
- **`headcount_contractors`** — подрядчики объекта («пул подрядчиков проекта» из SharePoint):
  `object_id`, `counterparty_id` (nullable), `name_raw`, `inn_raw`. Связь с контрагентом — по ИНН, когда ИНН задан
  и совпал; иначе запись живёт сама по себе до ручной привязки пользователем (решение 6: «грузим как есть»).
- **`headcount_records`** — актуальное значение на ключ: `object_id`, `work_date`, `contractor_id`, `codifier_id`,
  `workers`, `entered_at`, `entered_by`, `late` (внесено позже срока), `source` (`form` | `import` | `bot`).
  Уникальность — ключ `(object_id, work_date, contractor_id, codifier_id)` (запрет дубля как в SharePoint).
- **`headcount_history`** — все прежние значения по ключу: было/стало, кто, когда, источник. Запись о каждой
  замене (в т.ч. из импорта); отчёты берут только актуальное, экран ввода показывает историю.
- **`smu_catalog`**: добавить поле `archived` (0/1) — «Дивизион» и прочие прежние подразделения заводятся
  туда же, как архивные (решение 2), в карточке объекта и отборах скрыты по умолчанию.
  Объекты: добавить `objects.guid_1c` (TEXT) — привязка к объекту 1С.
- **`headcount_object_map`** — не нужна отдельно: привязка 1С-объект → наш объект хранится в `objects.guid_1c`;
  при импорте несопоставленные GUID со своими названиями показываются списком, пользователь сопоставляет вручную
  (решение 1) — и это запоминается.

## 5. Правила

1. **Ключ и перезапись.** Повторный ввод по тому же ключу не создаёт вторую строку, а заменяет значение;
   прежнее уходит в историю. В форме дубликат строки в той же карточке блокируется до сохранения (как в SharePoint).
2. **Просрочка.** Вносить задним числом можно без ограничений. Срок: рабочий день — до 11:00 этого дня; суббота и
   воскресенье — до 11:00 понедельника. Запись, внесённая позже срока, получает `late = 1` и подсвечивается в
   форме, истории и отчётах («внесено с опозданием на N ч/дн.»). Правка уже внесённого числа после срока
   также фиксируется в истории, но признак `late` ставится только на первое внесение.
3. **Число** — целое, 1–100 000 (как в боте); 0 не вносится — отсутствие записи означает «не было».
4. **Импорт истории** — по строкам выгрузки: сопоставление объекта по GUID 1С (вручную при первой привязке),
   подрядчика по ИНН/названию в рамках объекта (создаётся при отсутствии), работы по коду. Совпадающие ключи
   сворачиваются: последняя по `mcyDateOrig` — актуальна, остальные — в историю. Источник `import`, `late` не ставится.
   Повторная загрузка идемпотентна. Обработка — через `app/release_tasks.py`, если нужна при обновлении, иначе
   по кнопке админа в разделе обмена данными.
5. **Права.** Новый раздел доступа `headcount` (просмотр / правка), правка — на объектах гранта; в проектной команде
   объекта вносят «Нач. участка» и руководитель проекта (роль «менеджер проекта» в `TEAM_ROLES` пока отсутствует —
   уточнить, §9). Журнал: события в `app/activity_actions.py` (внесение, правка, импорт, привязка).

## 6. Экраны (V1 и V2 одновременно)

- **Ввод численности** (на объект): дата → список подрядчиков объекта → строки «подрядчик / вид работ / кол-во»,
  кнопки «добавить», «скопировать строку», «удалить»; рядом — признак просрочки и история значения. Выбор вида работ —
  дерево кодификатора с поиском по коду и названию. Сохранение — шлюзом записи V2 (`write-gate.js`).
- **Подрядчики объекта**: пул, привязка к контрагенту по ИНН, правка ИНН (его добавит пользователь).
- **Отчёты факта**: срезы «по объектам», «по подрядчикам», «по работам», «Факт»; столбцы — факт за вчера, среднее за
  неделю, среднее за текущий месяц, сумма за период; иерархия «СМУ → объект → раздел кодификатора → работа»,
  помесячная диаграмма; отбор по объекту, СМУ, работе, периоду, подрядчику. Excel-экспорт текущего среза.
  Подпись подрядчика — «Название (ИНН …)».
- **Справочник кодификатора**: просмотр, загрузка xlsx.
- **Привязка 1С**: экран сопоставления GUID → объект при импорте.

## 7. Второй этап: Telegram-бот (задел)

У существующего бота (@sbormsu_bot, SQLite на ПК, файл «Список ПО.xlsx») уже та же модель: объект → ответственный →
подрядчики; рассылка 10:30, напоминание 11:30, сводка админу 12:30. Для нашей системы нужен приём числа по API с
токеном (источник `bot`, ключ тот же), а справочник бота берётся из «Подрядчиков объекта» и проектной команды, а не
из отдельного xlsx. Решения о размещении бота (сервер или чей-то ПК) — отдельно.

## 9. Решения пользователя (2026-10-09) и открытое

Решено: 1) объекты 1С привязываются вручную при первой привязке; 2) кодификатор — отдельный справочник; 3) бот —
второй этап; 4) вносят менеджер проекта и начальник участка; 5) дубль запрещён, из истории берём всё, актуально
последнее, предыдущие видны; 6) подрядчиков грузим как есть, ИНН добавит пользователь; 7) план в первом этапе не
делаем; 8) «Дивизион» → в справочник СМУ как архивные подразделения; 9) просрочка разрешена, фиксируется и
подсвечивается.

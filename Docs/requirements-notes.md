# Рабочие заметки по требованиям

Короткие, но важные уточнения к системе, накопленные по ходу разбора реальных
DXF от заказчика. Полное ТЗ — отдельным файлом в этой же папке, когда придёт;
это — то, что не следует из ТЗ буквально, но подтверждено на данных.

## Загрузка DXF полностью из UI, без терминала

`POST /import-dxf` (кнопка "Загрузить чертёж" в тулбаре) — пользователь выбирает
`.dxf` со своего компьютера прямо в браузере, дальше всё (парсинг марок, сетка
осей, запись в БД) происходит на сервере синхронно за один запрос. Это тот же
код, что и в CLI-скриптах (`scripts/parse_zhbi.py`/`assign_axes.py`/
`import_elements.py`) — не отдельная реализация, отрефакторено так, чтобы обе
точки входа (CSV-путь для CLI и in-memory путь для загрузки) шли через одни и
те же `build_row()`/`upsert_elements()`/`save_axis_grid()`. DXF читается один
раз (не трижды, как раньше при последовательном запуске трёх скриптов) — на
~45МБ файле это ускорило обработку с ~19 сек (CLI) до ~8 сек (эндпоинт).

CLI-скрипты остались рабочими как были — это просто ещё один способ попасть в
ту же БД, для тех, кто предпочитает терминал или хочет заскриптовать импорт.

Повторная загрузка файла с тем же именем — как и раньше, upsert по
`(source_file, dxf_handle)`, статусы/история не сбрасываются (проверено сквозным
тестом: статус `installed`, выставленный вручную, пережил повторную загрузку
через `/import-dxf`).

## Два разных "статуса" у элемента — не путать

С появлением интерактивного инструмента (app/) у элемента стало ДВА
независимых поля со словом "статус", и они про разное:

- `axis_status` (`on_axis`/`offset`/`outside_axis_grid`/`no_axis_grid`) —
  результат геометрической адресации по осям (см. выше — offset это норма).
  На схеме отражается пунктирной обводкой, если сетки осей для элемента нет.
- `current_status` (`planned`/`in_production`/`shipped`/`delivered`/
  `installed`/`accepted`) — бизнес-статус поставки/монтажа, меняется
  вручную через контекстное меню на схеме. На схеме — это ЦВЕТ заливки,
  настраиваемый пользователем (`/status-colors`).

Оба сигнала показаны на схеме одновременно и независимо (цвет = бизнес-
статус, пунктир = геометрическая проблема с адресом) — специально не
объединял в одну систему цветов, чтобы не терять ни один из сигналов.

## Смещение колонны от пересечения осей — норма, не ошибка

Часть колонн на схеме закономерно НЕ сидит точно на пересечении
координационных осей (эксцентриситет/привязка — обычная практика в
строительных чертежах, колонна может быть смещена на десятки и сотни мм,
иногда больше метра). Это не повод считать элемент "неразобранным" или
подсвечивать как проблему наравне с реальными ошибками (unresolved-марка,
outside_axis_grid).

Подтверждено на файле `260713_Чертежи для WEB.dxf`: 332 колонны 300×600мм
из 332 имеют смещение от ближайшего пересечения осей (медиана ~320мм по X,
~560мм по Y, максимум до 5.4м) — геометрически это простые прямоугольники
без искажений, то есть смещение реальное, а не артефакт вычисления
центроида.

**Как это отражено в пайплайне:**
- `assign_axes.py` возвращает статус `on_axis` (точно на пересечении, admis
  ≤10мм) ИЛИ `offset` (привязка) — оба считаются штатным, успешным
  результатом адресации, отличается только наличие `offset_x_mm`/`offset_y_mm`.
- `render_plan.py` красит `on_axis`/`offset` ОДИНАКОВО (чёрно-белый контур,
  "в проекте") — красным (диагностический цвет) помечены только элементы,
  для которых сетки осей вообще нет в данной области чертежа
  (`outside_axis_grid`/`no_axis_grid`), это разные по смыслу ситуации и
  путать их нельзя.

## Формат адреса для колонны со смещением — "между осями", не "ближайшая ось"

Если колонна не сидит точно на пересечении (см. пункт выше — это норма),
адрес по этому измерению — не ближайшая ось, а **обе оси, между которыми
элемент находится**, по шаблону `"1-2"` (числовые) / `"А-Б"` (буквенные).
Полный адрес — комбинация по обоим измерениям, например `"3-5/Б-В"`.
Если по конкретному измерению колонна всё же сидит точно на оси (в
пределах допуска `ON_AXIS_TOLERANCE`) — используется одна метка без
дефиса, как раньше (например `"3/Б"`, если точно на пересечении осей 3 и Б,
или `"3/Б-В"`, если точно на оси 3, но между Б и В по Y).

**Реализация:** `assign_axes.py::bracket_label()` — сортирует оси по
координате, ищет соседей слева/справа от значения элемента. На самом краю
сетки (за последней осью, но ещё в пределах `AXIS_GRID_MARGIN`) соседа с
одной стороны нет — тогда просто одна ближайшая метка, без дефиса.

Поля `axis_number`/`axis_letter` в CSV теперь хранят именно эту метку
(возможно, с дефисом), а не ближайшую ось — если нужна именно ближайшая
ось (например, для вычисления смещения), она отдельно лежит в
`nearest_axis_number`/`nearest_axis_letter`.

## Формат входного DXF варьируется между файлами одного заказчика

На трёх присланных файлах встретились два разных способа хранения одних и
тех же данных:

1. **Через блоки** (`Чертежи для WEB.dxf`, `Чертежи для WEB-1.dxf`) —
   элемент = `INSERT`, марка — в атрибуте блока или во вложенном блоке
   сетки осей.
2. **"Распакованная" геометрия** (`260713_Чертежи для WEB.dxf`) — ни одного
   `INSERT` во всём файле (похоже на результат `EXPLODE` в AutoCAD перед
   экспортом). Элемент = замкнутый `LWPOLYLINE` на целевом слое (точка
   привязки — центроид контура, марка только через выноску, т.к. атрибута
   у голого контура нет). Сетка осей — не вложенный блок, а голые `CIRCLE`
   + `ATTDEF` прямо в пространстве модели; метка оси лежит в **теге**
   ATTDEF (`entity.dxf.tag`), а не в его тексте.

`parse_zhbi.py` и `assign_axes.py` теперь поддерживают оба варианта
автоматически (сначала пробуют блочный, если пусто — сырую геометрию),
без ручного переключения. При получении нового файла стоит первым делом
проверить `msp.query("INSERT")` — пусто или нет — чтобы понять, с каким из
двух форматов имеем дело, если пайплайн вдруг вернёт 0 элементов.

## Аутентификация — обязательный вход для всех действий (с 2026-07-14)

По итогам тестирования (см. `Docs/backlog.md` п.8, 12) в системе появилась
полноценная модель пользователей с ролями и вход по логину/паролю —
**обязателен для любого действия**, включая просмотр схемы, не только для
смены статусов/настроек. Это осознанный выбор (подтверждён явно, не
предположение): раньше `changed_by` был свободным текстом без проверки,
что не годится для реального объекта с несколькими бригадами/подрядчиками.

Три роли: `admin` (всё), `user` (схема + смена статусов, без доступа к
настройкам вообще — не только скрыто в UI, но и 403 на бэкенде при прямом
обращении к API), `view` (только чтение, включая экспорт — но не смену
статусов и не настройки). Дефолтный пользователь `admin`/пустой пароль
создаётся автоматически при первой инициализации БД — с него начинается
настройка любого нового развёртывания.

Экспорт настроек (`GET /settings/export`) намеренно включает хэш+соль
пароля пользователей — предназначен для переноса между серверами без
необходимости всем заново задавать пароли. Обращаться с файлом экспорта
нужно так же осторожно, как с резервной копией БД.

# Проект: объединение «Калькулятор ЖБИ» (CalcZhBI) с ЖБИ-трекером

Статус: **проект, не реализовано** (2026-10-03). Решения, помеченные «Вопрос», ждут ответа пользователя.
Исходные данные для проекта: `/Users/max/projects/CalcZhBI` (документы `README.md`, `AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/database.md`,
`DEPLOY.md`), обезличенная копия `data/zhbi.anon.db`. Содержимое рабочей базы калькулятора, цен и чертежей не читалось.

## 1. Цель

1. Калькулятор становится **частью ЖБИ**: один вход, один сервер, одна база, общие пользователи и права, один деплой и одна резервная копия.
2. Из элемента конструктива в ЖБИ (по **марке**) можно перейти на страницу **одноимённого изделия** в калькуляторе; обратно — от изделия калькулятора
   к местам применения в ЖБИ.

То, что хорошо для слияния: стек почти одинаков; калькулятор ещё не опубликован, поэтому второго боевого сервиса поднимать не нужно; в ЖБИ уже есть
справочник марок `marks` и привязка `elements.mark_id`.

## 3. Ключевой риск: совпадение марок (замерено на обезличенной копии)

Сопоставление выполнено нормализацией: верхний регистр, латиница→кириллица (`H→Н`, `K→К`, …), `З→3`, убраны пробелы и разделители `-./,`,
`КВ`/`К8` перед цифрой считаются одним (OCR каталога читает «В» как «8»).

| Показатель | Значение |
|---|---|
| Различных марок в ЖБИ | 925 |
| Нашли изделие в калькуляторе | **877 (95 %)** без нормализации — 806, «Кв»/«К8» добавили 71 |
| Не нашли | 48 (почти все — плиты `1П-1`…`4П-14`, отдельные `Км…`, `РМ…`, `3Р14.5м`) |
| Элементов ЖБИ с найденным изделием | **6 627 из 14 502 (46 %)** |
| По типам | ригели 3782/3791, колонны 1872/1900, панели шахт 158/158, **плиты перекрытия 815/8653** |
| Изделий калькулятора, найденных среди марок ЖБИ | 877 из 1008 |
| Неоднозначные `alias` в каталоге калькулятора | 8 (например `КС11` → две разные колонны) |
| В каталоге повторы | 1008 записей, 943 уникальных полных марок |

Выводы:
* По **числу марок** связь автоматически строится почти полностью, по **числу элементов** покрыто меньше половины: основной объём ЖБИ — плиты, а в
  каталоге калькулятора плит всего 78. Это вопрос **полноты каталога**, а не кода: для плит нужен отдельный источник (расширить каталог либо принять,
  что для них перехода нет).
* Автоматике нельзя доверять слепо: OCR-искажения (`З/3`, `В/8`, `H/Н`) и 8 неоднозначных `alias`. Нужны статусы связи и ручное подтверждение.

## 4. Варианты архитектуры

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Модуль внутри ЖБИ (рекомендую)** | Код калькулятора переносится в `app/calc/`, таблицы с префиксом `calc_` в той же БД, общий вход и права | один сервис, целостность связей (внешние ключи), общие резервные копии | перенос данных и кода, нужна дисциплина с чужими правками |
| B. Отдельный сервис + ссылка | калькулятор остаётся, из ЖБИ ссылка и общий вход (SSO) | минимум правок | не «часть проекта», два деплоя, связь без внешних ключей, два набора пользователей |
| C. Модуль, но **отдельный файл БД** | `data/calc.db`, ЖБИ ссылается по `uid` | калькулятор не рискует боевой БД ЖБИ | нет внешних ключей между БД, транзакции раздельные |

Рекомендую **A** поэтапно (раздел 8). **Вопрос 1:** принимаете ли общую БД (A) или нужна изоляция файла (C).

## 5. Модель данных (вариант A)

Таблицы калькулятора переезжают в БД ЖБИ с префиксом `calc_`; целочисленные ключи, **исходный UUID сохраняется в `uid`** (для идемпотентного импорта и внешних ссылок).

* `calc_projects` (связь с проектом ЖБИ: `project_id` → `projects.id`; каталог принадлежит проекту, а не объекту).
* `calc_products`, `calc_extra_lines`, `calc_line_overrides`, `calc_versions` (снимки расчётов копируются **дословно**, с контрольной суммой), `calc_profiles`,
  `calc_norms`, `calc_resource_baselines`, `calc_files` (+ SHA-256), `calc_discrepancies`, `calc_discrepancy_versions`, `calc_catalog` (метаданные моделей и листов).
* Не переносятся: `users`, `sessions`, `login_attempts`, `audit_log`, `browser_imports`, `mutations` (последняя нужна только идемпотентности внутри
  калькулятора и пересоздаётся). Авторов старых снимков хранить **снимком имени** (`author_name`), без внешнего ключа на пользователя.
* **Связь по марке — отдельная таблица**, а не поле в `marks`:

```
calc_mark_links
  object_id        → objects.id          (каталог один на проект, но связь строится по объекту)
  element_type     TEXT                  (как в marks)
  mark_norm        TEXT                  (нормализованный ключ, см. ниже)
  mark_name        TEXT                  (как в ЖБИ, для показа)
  calc_product_id  → calc_products.id
  status           'auto' | 'confirmed' | 'rejected'
  rule             какое правило сопоставило ('exact','lookalike','kv8',…)
  confirmed_by, confirmed_at
  UNIQUE (object_id, element_type, mark_norm)
```
Почему отдельно: отказ человека («это не то изделие») и ручное подтверждение должны переживать повторный импорт, а у `marks` нет места для статуса
и правила. Переход от элемента: `elements.mark_id → marks → calc_mark_links → calc_products`. Скорость: индекс по `(object_id, element_type, mark_norm)`.

### Правила нормализации и сопоставления (одна функция на сервер и тесты)
1. Верхний регистр, пробелы и разделители убрать, латиницу похожих букв заменить кириллицей, `З→3`.
2. `К[В8]` перед цифрой → `К8`.
3. Совпадение сначала по `alias`, затем по «хвосту» полной марки без слова-типа.
4. **Неоднозначно (>1 изделия) — статус не `auto`**, попадает в очередь ручного подтверждения. Автосвязь только при единственном кандидате.
5. Таблица ручных исключений (`rule='manual'`) приоритетнее правил; нормализация не меняет подтверждённые связи.

## 6. Интерфейс

* **В ЖБИ (V1 и V2), карточка элемента**: строка «Калькуляция изделия» с кнопкой «Открыть в калькуляторе», если связь есть (`auto` или `confirmed`).
  Без связи — подпись «Изделия нет в калькуляторе» и (для права редактирования) «Привязать вручную…». Тот же переход — пункт контекстного меню
  элемента и ссылка в справочнике марок.
* **Раздел «Калькулятор»** в навигации V2 (и пункт меню V1): список по альбомам и типам, 3D, технология, исходные листы, калькуляция, нормы, выгрузка XLSX.
  Адрес-ориентир: `#/calc` и глубокая ссылка `#/calc/product/<id>`; V1 — `/calc#product=<id>`. Возврат «назад к элементу» использует уже существующий
  механизм перехода с сохранением выделения (`locate-handoff`).
* **Обратная ссылка на странице изделия**: «Где применяется в ЖБИ» — объекты, число элементов и статусы; кнопка «Показать на схеме» открывает рабочее
  место «Модель» с фильтром по марке.
* **Экран «Сопоставление марок»** (администратор): очередь неоднозначных и ненайденных, массовое подтверждение, фильтр по объекту и типу; счётчик покрытия
  («877 из 925 марок, 46 % элементов»).
* Этап 1 интерфейса — **встраивание существующего фронтенда калькулятора** (как сделана сцена `embed-bridge.js`: тот же origin, протокол сообщений),
  чтобы не переписывать 3D, вкладки и XLSX сразу. Этап 3 — перенос на ES-модули V2 по экранам.

## 7. Доступ, безопасность, данные

* **Права**: новые разделы в `app/features.py`: `calc_view` (чтение), `calc_edit` (изменение расчётов), `calc_norms`, `calc_prices`
  (видеть цены и суммы — коммерческие данные МСУ-1, **отдельно от просмотра изделия**), `calc_files`, `calc_links` (подтверждать связи). Роли калькулятора
  отображаются на права: `admin→admin`, `editor→calc_edit`, `viewer→calc_view`. Каталог принадлежит проекту: доступ — к любому объекту проекта.
* Единая аутентификация ЖБИ (cookie-сессии, ограничение попыток); собственные сессии, CSRF-токены и `login_attempts` калькулятора **не переносятся** —
  применяется защита ЖБИ. Серверный Decimal-расчёт, `expectedVersion`, неизменяемые версии расчётов — сохраняются как есть.
* Журнал: события калькулятора пишутся в `activity_log` через реестр `app/activity_actions.py` (`calc_product_save`, `calc_norms_save`, `calc_link_confirm`…).
* **Реквизиты заказчика**: PDF-альбомы, OCR, Excel-калькуляции МСУ-1 и каталог **не коммитятся в репозиторий ЖБИ** (он зеркалируется на GitHub, правило из
  `CLAUDE.md`). Они живут в `data/calc/` (источники, вложения, кэш превью), попадают в Docker-том, резервные копии и **не попадают в обезличенную копию**;
  `scripts/anonymize_db.py` расширяется на `calc_*` (цены, названия, авторы), `.claude/settings.json` получает `deny` на `data/calc/` и `CalcZhBI/data`.
* Резервные копии ЖБИ (`app/backups.py`) учитывают `data/calc/uploads`; восстановление проверяется вместе.

Импорт данных повторяем по правилам ЖБИ: резервная копия → миграция на копии → холостой прогон на копии именно того сервера, куда выкатываем → автоматическая
обработка при старте; обработки идемпотентны, повтор — кнопкой в «Что нового». Откат — восстановление копии.

## 9. Риски и ответные меры

| Риск | Мера |
|---|---|
| Калькулятор активно меняется (параллельные исполнители, `delegation/`) во время переноса | заморозка по тегу, перенос одним коммитом; позднее правки — отдельными порциями; `HANDOFF.md` калькулятора остаётся источником статуса моделей |
| Охват связи по элементам 46 % (плиты) | показывать покрытие в «Сопоставлении марок»; для плит решить отдельно (вопрос 4), в карточке явно «нет изделия» |
| OCR-ключи и неоднозначные `alias` | статусы связи, очередь подтверждения, автосвязь только при единственном кандидате |
| Коммерческие цены видны не тем | отдельное право `calc_prices`; цены не уходят в отчёты и выгрузки ЖБИ без него |
| Рост размера образа/копий (~280 МБ PDF) | `data/calc/` в томе, не в образе; кэш превью исключён из копий |
| Миграция боевой БД | порядок ЖБИ: копия → холостой прогон → бэкап; push в `develop` содержит боевые данные, миграции перед ним проверять на копии |
| Совпадение кодов миграций и версий схем | миграции калькулятора **не** переносятся как есть: итоговая схема `calc_*` создаётся одним шагом ЖБИ, история контрольных сумм CalcZhBI сохраняется как справка |

# Бэклог замечаний по тестированию

Замечания от заказчика по итогам тестирования интерактивного инструмента.
Пункты 1–12 реализованы 2026-07-14. Нумерация — как в исходном списке
замечаний.

## 1. Хранение истории статусов: дата, статус, кто установил — ✅ реализовано

Карточка элемента при клике подгружает `GET /elements/{id}` и показывает
таблицу "История статусов" (дата, статус, кто изменил), сначала новые.
`status_history.changed_by_user_id` теперь ссылается на аккаунт (п.8), а
`changed_by` хранит текстовый снимок ФИО на момент изменения (переживёт
переименование пользователя).

## 2. В XLS-экспорт истории добавить дату изменения — ✅ уже было реализовано

Подтверждено при повторной проверке — колонка "Изменено" в листе "История
статусов" (`app/export.py`) на месте.

## 3. Импорт истории статусов из XLS — перенос прогресса на другой сервер — ✅ реализовано

`POST /import-history-xlsx` (`app/history_import.py`, только admin).
Сопоставление элементов — по `(source_file, dxf_handle)`, как и договорились.
Перед импортом пользователь выбирает режим (диалог в UI, меню "Настройки →
Импорт истории из XLS"):
- **Дополнить** — история добавляется, дубли (тот же статус в ту же дату у
  того же элемента) пропускаются.
- **Заменить** — история сопоставленных элементов удаляется перед импортом.

После импорта `current_status` элемента пересчитывается по последней записи
истории. Несопоставленные `dxf_handle` (элемента с таким handle нет в целевой
БД) попадают в сводку `unmatched_handles`, ничего не импортируется молча.
Round-trip проверен: экспорт → импорт того же файла (100% дублей, 0 вставок)
→ импорт файла с новой записью (корректно добавилась, `current_status`
пересчитался) → режим "заменить" (старая история вытеснена).

## 4. Подписи элементов накладываются друг на друга — ✅ реализовано

`computeLabelOffsets()` в `app/static/index.html`: для каждого элемента при
загрузке схемы перебираются 6 кандидатных направлений подписи (право,
право-верх, право-низ, верх, низ, лево), выбирается первое без пересечения
с уже размещёнными (пространственная сетка бакетов, а не полный перебор —
не тормозит на тысяче+ элементов). На реальных данных (332 колонны) 32
подписи получили нестандартное направление из-за коллизий — проверено
проверкой распределения `state.labelOffsetById`, не просто "выполняется
вхолостую".

Клик по элементу добавляет класс `.selected` (синяя жирная обводка),

## 7. Настройка видимости подписей по типу элемента — ✅ реализовано

Таблица `label_visibility` (ключ — `element_type`) самозаполняется при
каждом импорте DXF новыми типами (`ensure_label_visibility` в

появлении ригелей/плит. Быстрые чекбоксы в сайдбаре + полноценный экран в
"Настройки → Видимость подписей" (`GET/PUT /label-visibility`, запись —
только admin).

## 8. Список пользователей: ФИО, должность, подразделение, доменное имя, роль — ✅ реализовано

Полноценная модель (`app/schema.sql`: таблица `users`) + аутентификация по
логину/паролю с серверной сессией (`app/auth.py`, cookie `zhbi_session`,
30 дней). Уточнено в разговоре и реализовано так:
- **Администратор** — полный доступ.
- **Пользователь** — схема + смена статусов; меню "Настройки" не видно и
  недоступно совсем (403 на бэкенде, не только скрыто в UI).
- **Просмотр** — только чтение, контекстное меню смены статуса не
  открывается.

Роли проверены не только в UI, но и на уровне API (403 при прямом вызове
в обход интерфейса) — см. curl-тесты в истории разработки.

## 9. Меню "Настройки" — ✅ реализовано

Выпадающее меню в тулбаре, видимое только администратору. Подпункты: Цвета
статусов, Видимость подписей, Пользователи, Импорт истории из XLS,
Экспорт/импорт настроек. "Загрузить чертёж"/"Экспорт в XLS" остались
обычными кнопками (доступны admin+user, это не "настройки", а рабочие
действия) — осознанное разграничение, см. п.8.

## 10. Экспорт/импорт настроек проекта — ✅ реализовано

`GET /settings/export` / `POST /settings/import` (JSON, только admin).
Содержит пользователей (включая хэш+соль пароля — осознанно, чтобы не
заставлять всех заново задавать пароли при переносе на другой сервер; файл
нужно беречь как резервную копию БД), цвета статусов, видимость подписей.
Импорт — upsert (по `domain_login` для пользователей), ничего не удаляет
молча. Проверено сквозным сценарием: экспорт с "боевого" состояния →
свежая БД (только дефолтный админ) → импорт → пользователь `ivanov` вошёл
на "новом" сервере **тем же паролем**, что был на старом.

## 11. Ограничить максимальный размер маркеров при масштабировании — ✅ реализовано

Радиус маркера и размер шрифта подписи пересчитываются в `updateSizesForZoom()`
при каждом изменении `viewBox` (колесо мыши/перетаскивание), с верхним
пределом в экранных пикселях: `MAX_MARKER_PX = 9`, `MAX_LABEL_FONT_PX = 12`
(константы в начале `<script>`, легко подправить). Проверено: при сильном
приближении радиус фиксируется ровно на 9px, шрифт — ровно на 12px,
дальнейший zoom их не увеличивает.

## 12. Пользователь-администратор по умолчанию — ✅ реализовано

`app/schema.sql` сеет пользователя "Администратор" (`domain_login=admin`,
роль `admin`, пароль не задан) при первой инициализации БД. Пароль
устанавливается тем же механизмом, что и для остальных пользователей
(`POST /users/{id}/set-password`), плюс self-service смена собственного
пароля доступна любому залогиненному пользователю (кнопка "Пароль" в
тулбаре) без необходимости прав администратора.

### 13. Утечка форматирования MTEXT в марке (найдено 2026-07-14)

При разводке подписей на реальном файле `260713_Чертежи для WEB_2.dxf`
обнаружена марка вида `{\C10;9КН3}` — это код цветового форматирования
MTEXT (color override), который не был вырезан при извлечении текста
марки через выноску (`MULTILEADER.get_mtext_content()` в
`scripts/parse_zhbi.py`). Затрагивает не только отображение на схеме, но
и все выгрузки/экспорты, где используется поле `mark`. Нужно отдельно
разобраться, для скольких элементов в реальных файлах это актуально, и
почему `ezdxf` не стрипает этот конкретный паттерн форматирования
(возможно, нужна ручная постобработка регулярным выражением поверх
`get_mtext_content()`).

# Второй раунд замечаний (2026-07-15)

Нумерация — своя для этого раунда (1–12), не путать с п.1–13 выше.

## 1. Зафиксированные подписи осей: комфортный размер + прореживание при коллизии — ✅ реализовано

`updateAxisLabelSizing()` в `app/static/index.html`: размер шрифта подписи
оси капается в экранных пикселях (`MAX_AXIS_FONT_PX = 13`), как и у марок.
При мелком масштабе, если соседние подписи по минимальному шагу между
осями не помещаются без наложения, включается прореживание — динамически
считается шаг (каждая 2-я/3-я/... подпись) по формуле
`ceil(нужный_px / фактический_шаг_px)`, независимо для числовых и
буквенных осей. Сами линии сетки остаются видимы всегда, прореживаются
только подписи. Проверено визуально на общем виде схемы — вместо всех
39 числовых осей видны только "1, 11, 21, 29, 33/1, 38" при удалении.

## 2. Редизайн — современный UI в духе gosuslugi.ru — ✅ реализовано

Полностью переработан `<style>` в `app/static/index.html`: CSS-переменные
для акцентного синего (`--color-primary: #1353d6`), поверхностей, границ,
теней; скруглённые кнопки (`.btn`/`.btn-primary`/`.btn-secondary`) с
состояниями hover/focus; модалки с мягкой тенью и увеличенными отступами;
таблицы, дропдауны, чекбоксы — везде единая система. Тёмная тема
переведена на те же переменные (отдельный блок значений в
`@media (prefers-color-scheme: dark)`), проверена скриншотом — не менее
контрастна и читаема, чем светлая. Логин-форма и рабочая область
визуально согласованы (единый шрифт, скругления, акцентный цвет).

## 3. Контекстное меню — по правому клику/двойному клику, не по обычному — ✅ реализовано

`svg-root` теперь слушает три события отдельно: `click` — только
`selectElement()` (карточка в сайдбаре, подсветка), без контекстного
меню; `dblclick` и `contextmenu` (с `preventDefault()`, чтобы не всплывало
нативное меню браузера) — открывают контекстное меню смены статуса.
Проверено прямым `dispatchEvent` нативных `dblclick`/`contextmenu`
событий на элементе — оба корректно открывают меню; обычный клик
подтверждённо не открывает.

## 4. Экспорт в XLS/PDF — перенесены в "Настройки → Обмен данными" — ✅ реализовано

Кнопки "Экспорт в XLS" и "Экспорт в PDF" убраны из тулбара и перенесены в
выпадающее меню "Настройки" отдельным подразделом "Обмен данными"
(визуальный разделитель `.dropdown-divider` над ними), вместе с уже
существовавшими "Импорт истории из XLS" и "Экспорт/импорт настроек". В
тулбаре из операционных кнопок остались только "Загрузить чертёж" (частое
действие) и сам "Настройки ▾".

## 5. Закрытие всех форм настроек по Esc — ✅ реализовано

Общий `keydown`-обработчик на `document`: по `Escape` закрываются все
открытые `.modal-backdrop.open`, контекстное меню статуса и выпадающее
меню "Настройки". Проверено на реальном примере (открыт экран
"Контракты" → Esc → закрылся).

## 6. Удвоить максимальный размер маркеров и подписей при zoom — ✅ реализовано

`MAX_MARKER_PX` 9→18, `MAX_LABEL_FONT_PX` 12→24. Проверено численно при
сильном приближении: радиус маркера ровно 18px, шрифт подписи ровно 24px
на экране — предел работает, не просто увеличенное базовое значение.

## 7. Выпадающий список пользователей на форме входа — ✅ реализовано

Новый публичный эндпоинт `GET /login-users` (`app/auth.py`, без
авторизации — так и должно быть, форма входа работает до логина) отдаёт
только ФИО и `domain_login`, без ролей/паролей/прочих полей — сознательно
урезанная версия полного `/users` (тот admin-only). `#login-domain` стал
`<select>`, заполняется этим списком при показе экрана входа.

**Компромисс, о котором стоит знать**: список валидных логинов теперь
виден без аутентификации — приемлемо для внутреннего инструмента, но
станет проблемой, если сервис когда-нибудь будет доступен из интернета
широкому кругу (упрощает подбор пароля по известному логину). Отмечено
в коде.

## 8. Рабочая дата в тулбаре — ✅ реализовано

Уточнено и сделано так, как согласовали: дата **и точное время**
(`<input type="datetime-local">`), значение запоминается в
`localStorage` между заходами (не сбрасывается на "сегодня" каждый раз).
Кнопка "Сейчас" сбрасывает на текущий момент. Пока рабочая дата
установлена, поле подсвечивается акцентным цветом — чтобы не забыть, что
работаешь задним числом. При смене статуса элемента (и только тогда —
привязка контракта к элементу временем не датируется) выбранное значение
передаётся как `changed_at` в `PATCH /elements/{id}/status`.

**Важный смежный баг, найденный и исправленный по ходу**: `current_status`
элемента раньше слепо выставлялся в значение только что отправленного
статуса. Если рабочая дата — в прошлом, раньше уже существующей более
поздней записи в истории, это было НЕВЕРНО (задний статус "откатывал"
текущий). Исправлено: `current_status` теперь всегда пересчитывается по
самой поздней по `changed_at` записи в истории, та же логика, что уже
использовалась при импорте истории из XLS (`app/history_import.py`).
Проверено сценарием: элемент переведён в "Смонтирован" сегодня, затем
задним числом (2020 год) отправлен статус "Отгружен" — `current_status`
корректно остался "Смонтирован".

## 9. Контроль контрактов — ✅ реализовано

Обсуждено и реализовано согласно ответам:
- **Точка учёта "факта"**: любой статус элемента, кроме "Запланирован".
- **Привязка элемента к контракту**: контракт по умолчанию задаётся на
  раздел "Настройки → Контракты" (по типу элемента), подставляется
  автоматически при первом уходе элемента со статуса "Запланирован", если
  у элемента ещё нет контракта. Всегда можно переназначить вручную —
  выпадающий список прямо в карточке элемента (раздел "Контракт"),
  отфильтрованный по совпадающему типу.
- **Предупреждение**: и отдельный экран "Контракты" (`Настройки →
  Контракты`) с таблицей план/факт/остаток, превышение подсвечено красным
  построчно; и неблокирующий тост в правом верхнем углу схемы сразу после
  действия, из-за которого контракт превышен.

Бэкенд — `app/contracts.py` (`GET/POST/PATCH /contracts`, `GET/PUT
/contracts/default-map`), новые таблицы `contracts`/`default_contracts`,
колонка `elements.contract_id` (миграция). Проверено сквозным сценарием:
контракт на 2 шт., статус выставлен 3 элементам одного типа → на третьем
корректно появляется тост "законтрактовано 2, отмечено на схеме 3", в
таблице контрактов `fact=3, remaining=-1, exceeded=true`.

## 10. Изменяемая ширина сайдбара — ✅ реализовано

## 13. Экспорт схемы в PDF как отчёт с легендой цветов — ✅ реализовано (2026-07-15)

Шаблон согласован в обсуждении и реализован в `app/pdf_export.py`
(`GET /export.pdf?source_file=...&date=...`, кнопка "Экспорт в PDF" в
тулбаре):
- **Шапка**: логотип компании (встроен как вектор через `svglib` — не
  растеризован, чёткий на любом масштабе печати) + "Статус по <чертёж>" +
  дата отчёта. Дата — выбираемая в модалке экспорта; если указана,
  статусы элементов считаются актуальными на эту дату (тот же принцип,
  что у режима "снимок на дату" в XLS-экспорте) — элементы, которых на
  эту дату ещё не существовало, показаны нейтральным серым, а не текущим
  статусом задним числом.
- **Подпись/футер**: автоподпись системы ("Сформировано автоматически
  системой ЖБИ — контроль поставки и монтажа, <дата/время> (<кто
  сформировал>)") и блок для ручной подписи (Составил/Проверил/Утвердил,
  пустые строки под ФИО и дату).
- **Содержимое схемы**: весь чертёж целиком, авто-fit по осям и
  элементам, не зависит от масштаба на экране пользователя на момент
  экспорта.
- **Формат**: альбомная A3, подписи марок показаны, легенда цветов
  статусов отдельной строкой над футером.

**Важный технический момент, найденный при тестировании**: стандартные
PDF-шрифты (Helvetica и т.п.) не содержат кириллицу — без явного
шрифта весь русский текст в отчёте отображался чёрными прямоугольниками.
Исправлено регистрацией DejaVu Sans (свободная лицензия, полная
поддержка кириллицы, зашита в репозиторий — `app/fonts/`, ~2МБ) через
`reportlab.pdfbase.ttfonts`. Это гарантирует одинаковый результат
независимо от того, какие шрифты установлены на сервере развёртывания —
раньше эта проблема могла остаться незамеченной на macOS/Windows (там
обычно есть системный Arial с кириллицей), но проявилась бы на "голом"
Linux-сервере без такого шрифта.

## 5. Подписи осей не зафиксированы при скроллинге/масштабировании — ✅ реализовано

Уточнено: в предыдущем раунде (see раунд 2, п.1) был реализован только
предел размера шрифта + прореживание при коллизии, но не само закрепление
подписей на границах видимой области, как изначально просили ("зафиксировать
наименование осей на границах рабочей области"). Заказчик подтвердил: нужны
подписи, всегда видимые у края экрана, как замороженные заголовки
строки/столбца в таблице, независимо от прокрутки.

Реализовано в `updateAxisLabelSizing()`: на каждый вызов `setView()`
(колесо мыши/перетаскивание) видимая в мировых координатах область
вычисляется из `state.view`, подписи числовых осей закрепляются на
постоянном отступе в пикселях от верхней/нижней границы видимой области
(верхняя и нижняя копия), подписи буквенных осей — от левой границы;
отступ считается в мировых единицах динамически из текущего масштаба
(`px / pxPerUnit`), поэтому визуально остаётся постоянным при любом zoom.
Видимость подписи (нужно ли её вообще показывать) и прореживание при
коллизии теперь считаются только по подмножеству осей, реально видимых в
текущем видовом окне — раньше это считалось по всем осям чертежа сразу.
Линии сетки по-прежнему рисуются на всю длину, закрепление касается только
текстовых подписей. Проверено численно через CDP: при zoom+pan в середину
чертежа и последующей прокрутке ещё дальше подписи остаются на одном и том
же экранном Y (≈85.6px от верха рабочей области) и X (≈15px от левого края)
во всех трёх проверенных положениях просмотра, при этом сам набор видимых
подписей (какие именно оси показаны) корректно меняется под текущую
прокрутку.

## 6. Схема "подпрыгивает" при клике по элементу — ✅ исправлено (найдена настоящая причина)

При диагностике найдены и исправлены **две независимые причины**:

1. **Отсутствие порога перед перетаскиванием**: реальный клик мышью почти
   всегда сопровождается микро-дрожанием на 1-2px между `mousedown` и
   `mouseup`, а обработчик перетаскивания схемы трактовал любое движение
   мыши как намеренный pan. Добавлен порог `DRAG_THRESHOLD_PX = 4` — schema
   не двигается, пока движение мыши не превысит порог; клик с обычным
   дрожанием больше не приводит к микро-панорамированию. Дополнительно клик
   на `svg-root`, случившийся сразу после настоящего перетаскивания (движение
   ≥ порога), больше не выбирает элемент под финальной точкой курсора.

2. **Более существенная причина**: `#app-root` не был полноценным
   flex-контейнером — CSS содержал только `#app-root.hidden { display: none; }`,
   без базового `display: flex`. Из-за этого `#body { flex: 1 }` не имел
   эффекта (родитель не flex), и высота `#stage`/`#sidebar` фактически
   определялась содержимым сайдбара, а не вьюпортом: при выборе элемента
   карточка в сайдбаре становилась выше (доп. поля, история статусов,
   выпадающий список контракта) — и **вся рабочая область реально меняла
   размер**, а `<svg preserveAspectRatio="xMidYMid meet">` пересчитывал
   позицию содержимого под новый размер бокса — отсюда ощущение "подпрыгивает
   и возвращается обратно" даже при клике без единого пикселя перетаскивания.

   Исправлено добавлением `#app-root { display: flex; flex-direction: column; height: 100vh; overflow: hidden; }`.
   Проверено численно: до исправления `getBoundingClientRect()` у `#svg-root`
   менял высоту с 811px до 1098px при обычном клике по элементу (без
   единого пикселя движения мыши); после исправления bounding rect
   `#svg-root` остаётся идентичным на всех этапах — выбор элемента,
   открытие контекстного меню, диалог контракта, подтверждение статуса.

## 7. Поле "Контракт" у элемента — только для чтения — ✅ реализовано

Выпадающий список в карточке элемента убран, вместо него — обычный текст

способ поменять контракт элемента теперь — диалог подтверждения при смене
статуса (п.1-2).

## 8. Новая структура хранения контрактов: контракт + строки по типам — ✅ реализовано

Согласовано: `Контракт (название, поставщик)` → несколько строк
`(тип элемента, количество)` внутри него. Новые таблицы `contracts` (id,
name, supplier) + `contract_lines` (id, contract_id, element_type,
quantity, `UNIQUE(contract_id, element_type)`), взамен единственной таблицы
на строку "контракт=тип+кол-во" из второго раунда. "Факт"/"остаток"/
"превышение" теперь считаются по СТРОКЕ (пара contract_id+element_type), а
не по контракту целиком. Экран "Настройки → Контракты" перерисован
блоками — заголовок контракта (название+поставщик) с кнопкой "Изменить",
под ним таблица его строк (план/факт/остаток, превышение подсвечено).
Форма редактирования — динамический список строк (кнопка "+ строка",
удаление строки крестиком).

**Миграция существующих данных** (`app/db.py:_migrate_contracts_structure`):
старые строки группируются в новые контракты по `(name, supplier)`, ссылки
из `elements.contract_id` и `default_contracts.contract_id` переносятся на
новые id. **Найден и исправлен реальный баг при разработке миграции**:
`ALTER TABLE contracts RENAME TO contracts_old` в SQLite молча переписывает
FK-констрейнты в ДРУГИХ таблицах (`elements.contract_id`,
`default_contracts.contract_id`), которые ссылались на `contracts`, — они
начинают ссылаться на `contracts_old`. Без отключения `PRAGMA foreign_keys`
на время миграции последующий `DROP TABLE contracts_old` запускает
`ON DELETE SET NULL` по этим констрейнтам и обнуляет то, что миграция
только что аккуратно перенесла на новые id — воспроизведено и подтверждено
эмпирически в изолированном тесте до исправления, после исправления
`PRAGMA foreign_key_check` не находит нарушений, а перенесённые ссылки
сохраняют правильные значения.

## 9. Формат дат ДД.ММ.ГГГГ во всех формах — ✅ подтверждено, изменений не потребовалось

## 10. Полосы прокрутки рабочей области — ✅ реализовано

## Отображение ригелей на схеме реальной формой (вытянутый прямоугольник) — ✅ реализовано (2026-07-15)

Запрошено сразу после появления поддержки ригелей: показывать их на схеме
не условным маркером фиксированного размера, а настоящим контуром — так же,
как они выглядят в исходном DXF.

Реализовано как расширение уже существующей настройки "Форма маркеров"

- При парсинге (`scripts/parse_zhbi.py`) элементы, извлечённые из

- На схеме: если элементу назначена форма "outline" и контур есть —
  рисуется `<polygon>` напрямую по мировым координатам, без привязки к
  условному радиусу маркера — масштабируется вместе со всей схемой через

вытянутыми прямоугольниками точно по сетке осей (визуально соответствует

## Исправления по безопасности (найдено при подготовке `Docs/ARCHITECTURE.md`, 2026-07-15)

Найдено при документировании архитектуры для анализа безопасности —
полный разбор см. `Docs/ARCHITECTURE.md`, раздел 9. Ниже — то, что
предложено исправить, зафиксировано как план, **пока не исправлено**.

### 1. Сохранённый XSS через `innerHTML` без экранирования

Марка элемента (текст, извлечённый из содержимого DXF-файла — то есть
контролируется тем, кто загружает чертёж, роль `user` или `admin`) и
ряд других полей (ФИО пользователя, название/поставщик контракта)
вставляются в DOM через `innerHTML` с шаблонными литералами без
экранирования (`app/static/index.html`, начиная с `fieldRowsHtml()` —
затрагивает порядка 13 мест использования `innerHTML`). Сама схема
(SVG) рендерится безопасно, через `textContent` — уязвима только
сайдбар-часть интерфейса (карточка элемента, таблица пользователей,
список контрактов, история статусов).

**Риск**: пользователь с правом загрузки DXF может внедрить payload в
марку элемента; при открытии карточки этого элемента другим
пользователем (включая `admin`) скрипт выполнится в его браузере и
сможет выполнять действия от его имени через `fetch()` к тому же origin
(cookie сессии `httponly`, поэтому прямая кража токена невозможна, но
эскалация действий — возможна).

**План исправления**: один хелпер экранирования (`escapeHtml`, замена
`& < > " '` на HTML-сущности), применить ко всем интерполяциям в
`innerHTML`-шаблонах, где значение приходит не от кода приложения, а
из БД/пользовательского ввода. Там, где вставляется единственное
текстовое значение внутрь уже готовой разметки — предпочесть замену на
`textContent` вместо экранирования (меньше риск регрессии).

### 2. Нет ограничения частоты попыток входа

`POST /login` не ограничен по частоте — ничего не мешает автоматическому
перебору паролей, кроме затрат на PBKDF2 (260к итераций замедляют
каждую попытку, но не останавливают целенаправленный перебор). Усугубляется
тем, что список валидных логинов публично доступен через
`GET /login-users` (уже осознанный компромисс ради удобства входа, см.
`app/auth.py`).

**План исправления**: простой лимит по IP и/или по `domain_login`
(например, экспоненциальная задержка или блокировка на N минут после K
неудачных попыток подряд) — без внешних зависимостей, счётчик можно
хранить в самой SQLite или в памяти процесса.

### 3. Cookie сессии без флага `secure`

`response.set_cookie(...)` в `app/auth.py` не выставляет `secure=True` —
cookie передаётся и по обычному HTTP, не только HTTPS. Приемлемо при
развёртывании за HTTPS-терминирующим прокси в закрытой сети, реальный
риск — при прямой публикации сервиса по HTTP на незащищённой сети.

**План исправления**: выставлять `secure=True` при определении, что
сервис работает через HTTPS (например, по переменной окружения/настройке
развёртывания), не ломая локальную разработку по HTTP.

**Статус всех трёх пунктов**: обсуждено, приоритет и порядок исправления —
по решению заказчика, не реализовано.

## Разбор структурированных имён слоёв DWG/DXF + привязка элементов к захваткам/кранам/стоянкам (поставлено 2026-07-15)

Новый стандарт именования слоёв зафиксирован заказчиком (см. текст задачи
целиком — ниже приведён в исходном виде для точности формулировок, детали
согласования см. в обсуждении после этой записи):

### Стандарт именования

**Слои ЖБИ:**
```
WEB_<Тип>[_<Подтип>][_ОТМ<знак><высота_мм_5цифр>]_<Роль>
```
- Тип: `Колонна` | `Ригель` | `Плита` | `Панель`
- Подтип: опционален (ярус для колонн; "Периметральный" для ригелей;
  Цоколь/ЛифтоваяШахта/ШахтаПодъемника для панелей) — справочник
  допустимых подтипов должен быть конфигурируемым списком, не зашитым в
  логику разбора (полный перечень ярусов ещё уточняется у заказчика).
- ОТМ: буква `П` (плюс) или `М` (минус) перед числом, без буквы — ноль;
  число — высота в мм, дополненная нулями слева до 5 знаков (примеры:
  `ОТМ00000`, `ОТМП15800`, `ОТММ02500`).
- Роль: `Элемент` | `Марка` (последний токен имени).

**Вспомогательные слои (зоны):**
```
WEB_доп_<Категория>[_ОТМ<знак><высота_мм_5цифр>]_<Роль>
```
- Категория: `Захватка` | `Кран` | `Стоянка`
- Захватка и Кран — без отметки (сквозные, на всю высоту здания)
- Стоянка — обязательно с отметкой (свой набор стоянок крана на каждом уровне)
- Роль: `Зона` | `Наименование`

### Требуемая логика

1. **Разбор имени слоя** — функция, принимающая имя слоя, возвращающая
   структуру: группа (`zhbi`/`zone`), тип, подтип (или отсутствует),
   отметка в мм со знаком (или отсутствует), роль. Строгая валидация:
   слой, начинающийся на `WEB_` и не подходящий ни под один из двух
   паттернов — не пропускать молча, явно сообщать об ошибке с именем
   проблемного слоя (чтобы сразу ловить отклонения от стандарта, когда
   проектировщики начнут переименовывать слои).

2. **Реестр зон** — прочитать геометрию (полигоны) из каждого слоя-"Зона",
   прочитать текстовые объекты из парного слоя-"Наименование",
   сопоставить название с полигоном по принципу "точка вставки текста
   лежит внутри полигона". Если текст не попал ни в один полигон или
   попал сразу в несколько — не гадать, помечать как требующее ручной
   проверки, выводить отдельным списком. Реестр зоны: идентификатор,
   категория, отметка (для стоянок), название, геометрия/границы полигона.

3. **Привязка элементов к зонам** — для каждого элемента ЖБИ определить
   захватку, кран, стоянку:
   - точечные элементы (колонна) — точка вставки внутри полигона зоны;
   - протяжённые/площадные элементы (ригель, плита, панель) — доля
     площади/длины элемента, попадающей в полигон зоны; присваивается
     зона с максимальным перекрытием; если максимальное перекрытие
     меньше ~50% или несколько зон дают близкий результат — статус
     "требует проверки", зона не присваивается автоматически;
   - для стоянок — дополнительно фильтровать по совпадению отметки
     элемента с отметкой слоя стоянки (элемент сравнивается только со
     стоянками своего уровня).
   - Результат на элемент (в дополнение к уже существующим марке/адресу
     по осям): тип, подтип, отметка (из имени слоя), захватка+статус,
     кран+статус, стоянка+статус.

4. **Тестовые данные** — сначала синтетические DXF (несколько
   зон-полигонов разной формы + несколько элементов: полностью внутри
   зоны, на границе между двумя зонами, в зоне без сопоставленного
   названия), проверить логику на них, и только потом пробовать на
   реальном чертеже — файла от заказчика, переименованного по новому
   стандарту, пока нет.

**Статус**: ✅ реализовано полностью (ядро логики + интеграция в
БД/пайплайн импорта/API/интерфейс), проверено на синтетических данных и
регрессией на всех реальных файлах старого стандарта.

### Согласованные решения по итогам обсуждения

1. Старый `LAYER_CONFIG` и новый строгий парсер сосуществуют параллельно —
   новый парсер применяется только к слоям с префиксом `WEB_`, реально
   подходящим под новую грамматику; старые файлы продолжают работать как
   работали.
2. Справочник допустимых подтипов — таблица в БД + экран настроек для
   `admin` (как цвета статусов/форма маркеров), не хардкод.
3. Метрика перекрытия для ригелей/плит/панелей — единая по площади
   (`intersection.area / element.area` через `shapely`), не отдельная
   метрика по длине для ригелей — используется уже сохранённый контур
   элемента (см. запись про ригели выше в этом же раунде).
4. Реализовывать сразу оба слоя — бэкенд-логику и отображение в
   интерфейсе (границы зон на схеме, захватка/кран/стоянка в карточке
   элемента) — не только бэкенд.

### Что уже сделано (ядро логики, до интеграции)

- **`scripts/layer_naming.py`** — разбор имени слоя по обеим грамматикам
  (`parse_layer_name`), строгая валидация (`LayerNameError` с именем
  слоя и причиной на любом `WEB_`-слое вне стандарта). Справочник
  подтипов принимается параметром — источник (БД/настройки) появится на
  шаге интеграции.
- **`scripts/zone_parser.py`** — построение реестра зон
  (`build_zone_registry`): группировка слоёв по (категория, отметка),
  геометрия зон из замкнутых `LWPOLYLINE` (переиспользует

  в список `review`, не выбираются "на удачу".
- **`scripts/zone_binding.py`** — привязка элемента к зонам
  (`bind_element_to_zones`): точка для колонн, доля площади пересечения
  для протяжённых/площадных типов; порог 50% на минимальное перекрытие
  и 10 п.п. на "близкий результат" (`OVERLAP_MIN_FRACTION`/
  `OVERLAP_CLOSE_MARGIN`, оба — константы, легко перекалибровать);
  стоянка дополнительно фильтруется по совпадению отметки элемента и
  зоны, элемент без известной отметки получает статус `not_applicable`
  (не `unmatched` — это разные по смыслу ситуации: "нельзя определить"
  vs "определили и не попал").
- **`scripts/generate_test_zones_dxf.py`** — синтетический тестовый DXF
  (`test_data/synthetic_zones.dxf`): 3 захватки (включая одну без

  что элемент не цепляется к стоянке чужого уровня), 3 элемента (колонна
  полностью внутри зоны; ригель ровно на границе двух захваток 50/50;
  колонна внутри зоны без названия).
- **`scripts/verify_zone_pipeline.py`** — прогоняет весь конвейер на
  этом файле, 16 явных проверок (`assert`-подобных), все проходят.
  Ключевые проверенные сценарии: строгая валидация ловит некорректное

### Ревизия стандарта имён слоёв по боевому чертежу (2026-07-15)

После поставки первого реального чертежа, переименованного по новому
стандарту (`260715_Чертежи для WEB.dxf`), выяснилось, что фактическая
грамматика отличается от исходной спецификации выше — заказчик поменял
формат ещё раз до того, как прислал первый файл. Перед реализацией
чертёж и приложенный скриншот диспетчера слоёв были сверены напрямую
через `ezdxf` (полный список реальных имён слоёв — см. историю
разработки), затем заданы 2 уточняющих вопроса, оба отвечены:

1. Сравнение токенов имени слоя — без учёта регистра (не точное
   совпадение написания).
2. Старый словарь зон (`доп`, `Захватка`/`Стоянка` без уточнения) отменён
   окончательно, обратная совместимость под него не нужна.

**Что изменилось в грамматике** (актуальная версия — см. `Docs/TZ.md`,
раздел 3.7):
- У слоёв ЖБИ появился обязательный второй токен `констр`:
  `WEB_констр_<Тип>[_<Подтип>][_ОТМ...]_<Роль>` (было без него).
- У служебных слоёв (зон) `доп` заменён на `тех`:
  `WEB_тех_<Категория>[_ОТМ...]_<Роль>`.
- Словарь категорий зон: `Захватки`/`Стоянки крана`/`Кран` в имени слоя
  (внутреннее каноническое имя в БД/коде осталось прежним — `Захватка`/
  `Стоянка`/`Кран`, меняется только распознавание, не хранимое значение —
  так не пришлось трогать схему БД/CSS/фронтенд).
- Роль зоны: `область` (было `Зона`), `наименование` (было
  `Наименование`, только регистр).
- Слой сетки осей: `WEB_Оси` → `WEB_тех_Оси`. Система теперь пробует оба
  варианта по очереди (`assign_axes.build_axis_grid_auto`,
  `AXIS_LAYER_CANDIDATES`) — старые файлы с `WEB_Оси` продолжают работать.
- Cправочник `allowed_subtypes` пополнен реальными значениями: Колонна —
  `нижняя`, `средняя нижний ярус`; Ригель — `на отм. +15.800`,
  `периметральный`.

**Два бага найдены и исправлены при регрессии на реальном файле**
(не были видны на синтетических данных, т.к. синтетический генератор
использовал `TEXT` и точную геометрию):

1. **Название зоны — `MULTILEADER`, не `TEXT`/`MTEXT`.** На реальном
   чертеже подписи "Захватка 1", "Стоянка 12" и т.п. — это выноски
   (`MULTILEADER`), которые `zone_parser.py` раньше не читал вовсе (искал
   только `TEXT MTEXT`), из-за чего ни одна зона не находила названия.
   Исправлено: `zone_parser._multileader_name()` разворачивает
   `MULTILEADER` так же, как это уже делает `parse_zhbi.collect_annotations`
   для марок элементов, и берёт **остриё выноски** как точку для
   сопоставления с полигоном (не место текстового блока — оно обычно
   вынесено за пределы зоны).
2. **Точная геометрия (`contains`/`covers`) не срабатывала на точках,
   геометрически совпадающих с границей полигона.** Координаты остриёв
   выносок и вершин полигонов в DXF независимо округляются CAD-системой —
   расстояние между геометрически "одной и той же" точкой и границей
   полигона получается порядка 1e-11, а не 0, и точный shapely-предикат
   такую точку не засчитывает. Заменено на проверку расстояния с допуском
   1 мм (`zone_parser.NAME_MATCH_TOLERANCE_MM`,
   `zone_binding.POINT_MATCH_TOLERANCE_MM` — второй допуск применён и к
   привязке точечных элементов/колонн к зоне по той же причине, хотя на
   имеющихся данных проблема проявилась только для названий зон).

**Проверено**: `scripts/verify_zone_pipeline.py` (переведён на новую
грамматику, синтетический DXF перегенерирован) — 18/18 проверок; регрессия
на всех 6 ранее проверенных файлах старого стандарта
(`260713_2`, `260713`, `260714`, `Чертежи для WEB.dxf`, `Чертежи для WEB-1`,
`sample`) — те же числа элементов, что и раньше, `zones: null`; целевой
файл `260715_Чертежи для WEB.dxf` — 1401 элемент, 34 зоны (Захватка: 4,
Кран: 3, Стоянка: 27), **0 зон и 0 привязок элементов требуют проверки**.

**Найдено, но не исправлено (отдельная проблема, вне рамок этой задачи)**:
файл `260714_Чертежи для WEB_2.dxf` (не входил в ранее проверенный набор
регрессии) содержит слой `WEB_Колонна_Средняя нижний ярус_отм 15.800`
(996 сущностей) — не подходит ни под `LAYER_CONFIG` старого способа

осознанно не угадывалось, куда его отнести, нужно уточнение у заказчика.

## Правки схемы: масштаб, выбор слоёв, форма по умолчанию, подложка зон (2026-07-15)

Пакет из 7 связанных правок интерактивной схемы, все проверены статически
(код + юнит-вызов `plan_data()` напрямую в Python — живого браузера в
этой сессии не было, см. примечание в конце).

1. **Масштаб/пан больше не сбрасывается** при изменении состава слоёв —
   `loadPlan()` получил параметр `preserveView` (по умолчанию `true`):
   сбрасывает вид на "вся схема целиком" только при самой первой загрузке
   приложения и сразу после загрузки нового чертежа; все остальные
   перезагрузки данных (переключение слоёв/файлов, сохранение настроек,
   импорт истории) масштаб не трогают.
2. **Список слоёв в выпадающей панели** (`#file-select-menu`) визуально
   не был списком "друг под другом" — **найден реальный CSS-баг**:
   `.layer-list label.checkbox` не задавал `display`, а `<label>` по
   умолчанию `inline`, и правило `.modal label.checkbox { display:flex }`
   не применялось (панель — `.dropdown-menu`, не `.modal`) — чекбоксы
   слоёв рендерились в строку, обтекая друг друга как текст, а не
   списком. Исправлено (`display:flex` + `flex-direction:column` на
   контейнере), плюс разделители между файлами для ясности иерархии.
3. **Форма отображения элемента по умолчанию — «как в оригинале»
   (контур)**, было `circle`. Изменено в двух местах (должны совпадать):
   `shapeNameFor()` на фронтенде и дефолт в `GET /layer-type-combinations`
   на бэкенде (экран настроек показывал `circle` как текущее значение для
   ещё не настроенных пар, теперь тоже `outline`). Переопределение по
   (слой, тип элемента) — в «Настройки → Форма маркеров», уже сохранялось
   на сервере (`element_shapes`) и продолжает.
4. **Реальный баг в `POST /plan-data`**: `if item.layers:` — пустой
   список (`[]`, т.е. "сняты все галочки слоёв") ложный в Python, поэтому
   неотличим от `None` ("все слои") — при снятии всех галочек сервер
   возвращал ВСЕ элементы файла вместо нуля. Исправлено на явную проверку
   `is not None` c отдельной веткой для пустого списка (ноль элементов).

## Каталог Input/, очистка при пустом выборе, масштаб при смене файлов (2026-07-15)

Продолжение предыдущего пакета правок схемы, по итогам дальнейшей
проверки. Уточняющий вопрос был задан и отвечен: каталог `Input/` должен
не только фильтровать список доступных файлов, но и **автоматически
импортировать** новые DXF из него на каждом старте сервера (выбран
рекомендованный вариант).

1. **`INPUT_DIR` (`Input/` в корне проекта) — теперь источник истины для
   списка доступных чертежей.** На старте сервера (`@app.on_event
   ("startup")`) все `.dxf` из `Input/` (пере)обрабатываются через
   `process_upload()` — тот же путь, что и ручная загрузка через UI,
   идемпотентно (повторный прогон того же файла не плодит дубли, не
   сбрасывает статусы — сопоставление по `dxf_handle`). Ошибка одного

   остальных файлов. `GET /source-files` дополнительно фильтрует
   результат живым сканированием `Input/*.dxf` на каждый запрос — файл,
   убранный из папки без перезапуска сервера, тоже сразу перестаёт
   предлагаться (данные из БД при этом не удаляются, только скрываются
   из списка выбора). Кнопка «Загрузить чертёж» (сохраняет в `uploads/`)
   осталась как есть — но если её файл не совпадает по имени ни с чем в
   `Input/`, его данные обработаются, а в списке выбора не появятся, пока
   файл не окажется в `Input/`.
2. **Снятие всех галочек файлов теперь по-настоящему очищает экран** —
   раньше `loadPlan()` при пустом `state.selection` просто молча

   последний отрисованный чертёж висеть на экране. Добавлена
   `clearWorkspace()`: очищает все три SVG-слоя, легенду, тумблеры
   подписей/зон, карточку элемента (плейсхолдер), сбрасывает

   не должен трогать масштаб, см. предыдущую запись). Чекбокс файла в
   `renderFileSelectMenu` — `loadPlan(false)` (рефит) и при включении, и

4. **Найдена и объяснена причина смещения подписей осей к центру при
   переключении файлов**: `updateAxisLabelSizing()` пинит подписи осей к
   границам ТЕКУЩЕГО `state.view` (а не к границам данных). Предыдущая
   правка ("не менять масштаб при смене состава слоёв") по ошибке
   применялась и к переключению ФАЙЛОВ целиком — у каждого файла своя

   набора файлов, `state.view` переставал соответствовать реальному
   охвату новых данных, и подписи осей, честно пинуясь к краям СТАРОГО
   вида, визуально оказывались смещены от истинного края к центру
   относительно НОВОГО содержимого. П.3 выше — прямое исправление: при
   любом изменении состава файлов вид принудительно пересчитывается по
   текущему выбору, поэтому `state.view` всегда актуален и подписи осей

## Доработки фильтров, зон, статусов и справочников (запрошено 2026-07-15)

Список из 10 пунктов, зафиксирован для будущей итерации. **Ничего из
этого не реализовано** — заказчик явно попросил сначала записать в

### 1. Каскадные фильтры (сужение значений по уже применённым)

Сейчас (см. предыдущую запись) `distinctPlacementValues()` в
`app/static/index.html` строит список доступных значений каждой группы
фильтра (Захватка/Кран/Стоянка/Отметка/Тип элемента) по **всем**
`state.elements`, не учитывая, что уже отфильтровано в ДРУГИХ группах.
Нужно: при построении списка значений группы X учитывать только элементы,
прошедшие фильтры ВСЕХ ОСТАЛЬНЫХ групп (не X — иначе группа может скрыть
сама себя). Пример: если в фильтре "Кран" выбран только "Кран 2", то в
фильтре "Стоянка крана" должны остаться только стоянки, реально
относящиеся к "Кран 2" (см. п.2/п.3 ниже). Отдельный вопрос на
реализацию: что делать с уже снятой галочкой значения, которое временно
пропадает из списка при таком сужении — вероятно, не терять её (просто не
показывать чекбокс, но не забывать состояние в `excludedSet`), чтобы при
возврате других фильтров назад выбор не "терялся".

### 2. Связь "стоянка → кран" при разборе файла

Сейчас в `zones` (таблица БД, см. `app/schema.sql`) у категории
"Стоянка" нет связи с "Кран" — они просто два независимых списка зон.
Нужно на этапе `scripts/zone_parser.py`/`new_standard_pipeline.py`
после построения обоих реестров вычислять для каждой зоны-стоянки, в
зоне работы какого крана она физически находится (скорее всего —
point-in-polygon по центроиду стоянки относительно полигонов "Кран", тем
же приёмом, что уже используется для привязки элементов к зонам, см.
`scripts/zone_binding.py`), и сохранять эту связь — потребуется новая
колонка в `zones` (например `parent_zone_id INTEGER REFERENCES
zones(id)`, заполняется только для `category='Стоянка'`). Нужно решить,
как показывать стоянку, не попавшую ни в одну зону крана или попавшую в
несколько сразу — по аналогии с уже существующим `match_status`
зон/`needs_review` у привязки элементов, не молчать.

### 3. Иерархия "Стоянка" внутри "Кран" в фильтре

Зависит от п.2. В `renderPlacementFilters()` объединить группы "Кран" и
"Стоянка крана" в одну иерархическую группу: чекбокс крана + под ним, с
отступом, чекбоксы его стоянок (используя связь из п.2). Клик по
чекбоксу крана — ставит/снимает галочки со всех его стоянок разом (и,
видимо, сам считается отдельным значением фильтра по кранам — элемент,
геометрически относящийся к стоянке крана, но не факт что относится к
самой зоне крана один-в-один, нужно уточнить семантику на реализации).
Стоянки без известного крана (см. "не попала ни в одну зону" в п.2) —
отдельным пунктом вне иерархии ("не определено").

### 4. Фильтр по статусам + переименование статуса

Добавить 6-ю группу в фильтр по размещению — по `current_status`, той же
логикой чекбокс-группы, что и остальные (набор доступных статусов — из
факта присутствия у текущей выборки элементов, как и другие фильтры).
Отдельно, не связано с фильтром напрямую: переименовать статус
`Status.DELIVERED` в `app/models.py` (`STATUS_LABELS_RU`) — сейчас

### 5. Названия зон — обратно внутрь контура

**Разворот предыдущего решения**: в записи "Легенда по типам, вкладки
сайдбара, фильтр по размещению..." (она же — предыдущий раунд, п.5 того
списка) название зоны было намеренно вынесено ЗА контур (над верхним
краем полигона), чтобы не перекрываться с подписями элементов внутри
зоны. Сейчас запрошено обратное — вернуть подпись внутрь контура.
Причина смены решения не указана; вероятно, связана с п.7 (свой цвет на
каждый кран) — с различимой заливкой по кранам название внутри зоны,

не возвращается ли проблема перекрытия с марками элементов внутри

возвращается, обсудить с заказчиком, а не молча делать полумеру.

### 6. Единый (русский) словарь типов элементов

Сейчас два источника `element_type` дают РАЗНЫЕ языковые словари для
одних и тех же по сути типов — старый стандарт слоёв (`LAYER_CONFIG` в
`scripts/parse_zhbi.py`) отдаёт `"column"`/`"beam"` (английские
строки), новый стандарт (`scripts/layer_naming.py`, `ZHBI_TYPES`) —
`"Колонна"`/`"Ригель"`/`"Плита"`/`"Панель"` (русские). Отсюда и
"лишние" английские строки, которые заказчик увидел в "Настройки →
Контракты → контракт по умолчанию" и "Настройки → Видимость подписей"
— эти экраны просто показывают все `element_type`, когда-либо
встретившиеся в данных, не различая язык.

Решение — конвертировать в русский **на этапе разбора файла**: заменить
`LAYER_CONFIG`, чтобы он отдавал `"Колонна"`/`"Ригель"` напрямую, а не
`"column"`/`"beam"` (простая правка словаря в `parse_zhbi.py`).

**Важный нюанс для реализации** — этого НЕДОСТАТОЧНО само по себе:
1. У элементов (`elements.element_type`), уже загруженных со старым
   значением, "column"/"beam" сами по себе не станут "Колонна"/"Ригель"
   задним числом — но т.к. `upsert_elements` обновляет существующую
   строку по `(source_file, dxf_handle)`, при следующей переобработке
   того же файла (а `Input/` теперь переобрабатывается на каждом старте
   сервера, см. соответствующую запись) значение обновится само —
   если файл всё ещё лежит в `Input/`. Для файлов НЕ в `Input/` (старые
   архивные источники) значение останется "как было" без ручной миграции.
2. А вот `label_visibility`, `default_contracts`, `contract_lines`,
   `element_shapes` — это ОТДЕЛЬНЫЕ таблицы, ключ в них — сама строка
   `element_type` (`PRIMARY KEY`/`UNIQUE`), они НЕ выводятся заново из
   `elements` при каждом запросе, а хранят свои строки постоянно. Просто
   исправить парсер эти таблицы не почистит — старые строки с "column"/
   "beam" останутся там висеть осиротевшими (ключ, на который больше
   ничего не ссылается) и по-прежнему будут отображаться в
   соответствующих экранах настроек. Нужна явная разовая миграция
   (переименовать или удалить строки с английским ключом в этих 4
   таблицах) как часть этой доработки, а не только правка парсера.

После этого исправления "Настройки → Контракты по умолчанию" и
"Настройки → Видимость подписей" должны сами показывать только 2 строки
(Колонна/Ригель) вместо 4 — отдельно ничего чинить в этих экранах не
нужно, они уже строятся динамически по факту встретившихся типов.

### 7. Свой цвет зоны на каждый кран

Сейчас цвет зоны — общий на всю категорию (`#zones-layer polygon.zone-
Кран { fill: #c0392b }` и т.п. — фиксированная CSS-подстановка по
категории, см. `app/static/index.html`), а не персональный на
конкретную зону. Нужно: свой цвет на каждую ИНДИВИДУАЛЬНУЮ зону-кран, с
наследованием тем же цветом у её стоянок (см. связь из п.2) — то есть
"Кран 1" и все его стоянки — один цвет, "Кран 2" — другой.

**Важный нюанс** — `upsert_zones` (см. `scripts/import_elements.py`)
делает `DELETE FROM zones WHERE source_file = ?` + заново `INSERT` при
каждой обработке файла (как и сетка осей) — `zones.id` НЕ стабилен
между перезагрузками одного и того же файла (новый `AUTOINCREMENT` id
каждый раз). Значит, привязывать цвет к `zones.id` — ошибка, при
следующей переобработке (а Input/ переобрабатывается на каждом старте
сервера) все настроенные цвета слетят. Ключ для хранения цвета должен
быть стабильным — вероятно `(source_file, category, name)` (имя зоны,
"Кран 1" и т.п.) или просто `name`, если имена кранов в рамках проекта
считаются достаточно уникальными.

При первой загрузке — автоназначение цветов "на усмотрение" (соседние,
визуально различимые цвета из фиксированной палитры, циклически по
порядку кранов). В настройках — новый экран (по аналогии с "Цвета
статусов") для ручного переназначения цвета на кран.

### 8. Фильтр по подтипам внутри фильтра по типам

По аналогии с иерархией "Кран → Стоянка" (п.3) — сделать "Тип элемента"
в фильтре по размещению иерархическим: под каждым типом (Колонна/Ригель/
...) — вложенные чекбоксы его подтипов (`subtype`, справочник которых
уже есть — "Настройки → Справочник подтипов", см. раздел 3.7 ТЗ).
Клик по типу — ставит/снимает все его подтипы разом, аналогично п.3.
Разумно реализовывать п.3 и п.8 через один переиспользуемый компонент
"иерархическая группа фильтра", а не дублировать логику дважды.

### 9. Кнопка сброса всех фильтров

Одна кнопка на вкладке "Фильтры" — очищает все `excludedSet` всех групп
фильтра по размещению (включая новую группу статусов из п.4) разом,
без необходимости жать "все" в каждой группе по отдельности.

### 10. Легенда статусов — по текущим фильтрам

**Разворот предыдущего решения**: в предыдущей записи явно
зафиксировано, что легенда "Статусы" **сознательно** не учитывает
фильтр по размещению — показывает сводку по всей текущей выборке
файлов/слоёв, а не по тому, что видно на схеме сейчас (см. ТЗ, раздел
6.5). Теперь запрошено обратное: легенда должна пересчитываться по
элементам, реально прошедшим текущие фильтры (`passesPlacementFilters`),
а не по полной выборке. Раздел 6.5 ТЗ придётся поправить в этой части
при реализации.

## Реализация 10 пунктов доработок фильтров/зон/статусов/справочников (2026-07-15)

Все 10 пунктов из предыдущей записи реализованы в одной сессии, по
согласованному в переписке решению двух неоднозначностей (без отдельного
уточняющего вопроса — оба вывода обоснованы ниже):

- **Иерархия Кран→Стоянка и Тип→Подтип (п.3, п.8)**: реализована КАК ДВЕ
  независимые категории фильтра (свой `excludedSet` у каждой), а не
  слияние в одну булеву группу — клик по родителю просто программно
  ставит/снимает чекбоксы потомков. Проверено рассуждением, что это даёт
  тот же результат, что и настоящее слияние (элемент, привязанный к
  стоянке крана, но не к самому крану напрямую, всё равно корректно
  скрывается при снятии крана, потому что снимается и чекбокс его
  стоянки) — при этом не требует переписывать булеву семантику
  "И между категориями".

### 1. Единый русский словарь `element_type` (было п.6)

`scripts/parse_zhbi.py` `LAYER_CONFIG` теперь отдаёт `"Колонна"`/
`"Ригель"` вместо `"column"`/`"beam"`. Добавлена идемпотентная миграция
`app/db._normalize_element_type_vocabulary()` (вызывается на каждом
старте, как и `_apply_migrations`) — приводит уже загруженные данные
к тому же словарю: `elements.element_type` — простой `UPDATE`;
`label_visibility`/`default_contracts`/`element_shapes`/`contract_lines`
(element_type — часть уникального ключа) — переименование с проверкой
коллизии: если строка под русским именем уже есть, английская просто
удаляется, иначе переименовывается на месте. Проверено на боевой БД:
`label_visibility` был `{column, beam, Колонна, Ригель}` (4 строки) →
стал `{Колонна, Ригель}` (2), `element_shapes` — 7 строк с английскими
element_type корректно переименованы (коллизий по `(layer, element_type)`
не оказалось — старый и новый стандарт используют разные имена слоёв),
`elements.element_type`: было 3988+634 (column/beam) + 664+737
(Колонна/Ригель) → стало 4652 (Колонна) + 1371 (Ригель), числа сошлись
день-в-день. Повторный запуск миграции — no-op (проверено).

### 2. Связь "стоянка → кран" при разборе файла (было п.2)

`scripts/zone_parser._link_stances_to_cranes()` — после построения
полного реестра зон вычисляет для каждой "Стоянки" её кран
(point-in-polygon центроида стоянки относительно полигонов "Кран", с тем
же допуском по расстоянию, что и у сопоставления названий зон). Новые
колонки `zones.parent_zone_id`/`parent_match_status`. `upsert_zones()` в
`scripts/import_elements.py` пишет `parent_zone_id` вторым проходом
(`UPDATE` после того, как все зоны файла уже вставлены и получили id) —
не нужно гарантировать порядок вставки кран-раньше-стоянки. Проверено на
`260715_Чертежи для WEB.dxf`: все 27 стоянок сопоставились однозначно
(0 needs_review), распределение по кранам — Кран 1: 21, Кран 2: 3,
Кран 3: 3.

### 3-4. Фильтр по статусам + переименование + иерархия Кран/Стоянка (было п.3, п.4)

Добавлена 6-я группа фильтра по размещению — "Статус" (значения — из
факта присутствия в текущей выборке, та же логика, что у остальных
групп). `STATUS_LABELS_RU[DELIVERED]` в `app/models.py`: "Доставлен на
площадку" → "Доставлен" (единственное место хранения подписи, все экраны
берут её оттуда). "Кран"/"Стоянка крана" в фильтре объединены в одну
иерархическую группу (`buildHierarchicalFilterGroup` в
`app/static/index.html`) — заголовки-краны, под каждым вложенные
чекбоксы его стоянок (используя связь из п.2, найденную через
`craneNameForStanceValue()`), клик по крану синхронизирует чекбоксы всех
его стоянок.

### 5. Названия зон — обратно внутрь контура (было п.5, разворот решения)

`renderZones()` — подпись снова по центроиду полигона, как было
изначально (до правки, вынесшей её над верхним краем специально против
перекрытия с марками элементов внутри зоны). Причина разворота — как и
предполагалось в предыдущей записи, появление индивидуального цвета на
каждый кран (п.7) сделало чтение подписи внутри зоны приемлемым.

### 6. Иерархия Тип/Подтип в фильтре (было п.8)

Тем же компонентом `buildHierarchicalFilterGroup`, что и Кран/Стоянка —
под каждым типом элемента вложены чекбоксы его подтипов (группировка —
по факту встречающихся у элементов `subtype`, через
`typesForSubtypeValue()`, не по справочнику `allowed_subtypes` напрямую —
показываются только реально присутствующие в текущей выборке значения).

### 7. Каскадное сужение значений фильтров (было п.1)

`distinctValuesFor(key)` — список значений категории теперь считается по
элементам, прошедшим фильтры **всех остальных** категорий
(`elementPassesExcept`), а не по всей выборке. После любого изменения
любого чекбокса (`onPlacementFilterChange()`) весь блок фильтров
перерисовывается заново (`renderPlacementFilters()`) — состояние
(`excludedSet`) хранится в `state.placementFilters`, а не в DOM, поэтому
перерисовка ничего не теряет, только отражает новый каскад. Значение,
временно пропавшее из видимой выборки из-за фильтра в другой категории,
не сбрасывает свою галочку — просто не рендерится, пока не станет
актуальным снова.

### 8. Свой цвет зоны на каждый кран (было п.7)

Новая таблица `zone_colors` (`source_file`, `category`, `name`, `color`)
— ключ сознательно НЕ включает `zones.id` (не стабилен между
переимпортами файла, `upsert_zones` делает `DELETE`+`INSERT` заново
каждый раз). `_ensure_zone_colors()` в `scripts/import_elements.py`
автоназначает цвет каждому новому крану из фиксированной палитры (10
цветов, дальше циклически), `INSERT OR IGNORE` — уже настроенный цвет
при повторном импорте не трогается (проверено). `plan_data()` в
`app/main.py` резолвит цвет в ответе: у зон категории "Кран" — напрямую,
у "Стоянка" — через `parent_zone_id` из п.2 (наследует цвет своего
крана), у "Захватка" — `null` (остаётся общая раскраска по категории).
Новый экран "Настройки → Цвета зон" (`GET`/`PUT /zone-colors`, только
admin) — список кранов по всем файлам с `<input type="color">`, собран

из текста на чертеже (MULTILEADER), как и в остальных местах, где на
схему могло бы попасть что угодно из DXF, здесь сознательно не
допускается инъекция через шаблонную строку. Проверено на реальном
файле: 3 крана получили 3 разных цвета автоматически, стоянки корректно
унаследовали цвет родителя, повторный импорт не изменил уже назначенные
цвета.

### 9. Кнопка сброса всех фильтров (было п.9)

## Баг: каскад фильтров сужал список значений вместо disabled (2026-07-15)

Заказчик сообщил два симптома сразу после предыдущей записи: (1) у Крана 2
не было стоянок в иерархии фильтра, хотя на схеме они отмечены; (2) при
снятии галочки с "Колонна" в фильтре сам пункт "Колонна" исчезает из
формы, и вернуть его нельзя без полного сброса всех фильтров. Плюс явно
запрошено изменить сам принцип: не убирать из формы фильтры, ставшие
неактуальными при выборе других фильтров, а делать их недоступными
(disabled), не трогая список. Отдельно попросили: сортировать стоянки по
числовому номеру ("Стоянка 2" перед "Стоянка 10"), а не лексикографически.

**Диагностика (2)**: подтверждена прямым запросом к БД — у стоянок Крана 2
реально привязаны элементы (20+4+4), это не проблема данных. Причина —
в архитектуре предыдущей версии `distinctValuesFor(key)`: список значений
категории считался по элементам, прошедшим фильтры ВСЕХ ОСТАЛЬНЫХ
категорий. Клик по родителю в иерархической группе (Кран→Стоянка,
Тип→Подтип) каскадом исключал ВСЕХ потомков через `childExcludedSet`
(например, снятие "Колонна" исключало все подтипы колонны из
`state.placementFilters.subtype`). При следующем пересчёте
`distinctValuesFor("elementType")` — список значений категории "Тип
элемента" — учитывал, среди прочего, фильтр "Подтип" как "остальной", и
раз все подтипы колонны только что оказались исключены, ни один элемент
с типом "Колонна" больше не проходил проверку "остальных фильтров" →
"Колонна" переставала попадать в список значений СВОЕЙ ЖЕ категории —
самоблокирующийся цикл, разорвать который можно было только сбросом всех
фильтров разом. Тот же механизм работал и для Кран→Стоянка: снятие "Кран
2" каскадом исключало все его стоянки из фильтра "Стоянка", а список
значений "Стоянка" (в свою очередь) при расчёте учитывал фильтр "Кран" —
и, что важнее в данном случае, все элементы, привязанные к стоянкам Крана
2, переставали проходить проверку по категории "Кран" (она ведь тоже
исключена) → стоянки Крана 2 пропадали из списка значений категории
"Стоянка" целиком, хотя сам заголовок "Кран 2" оставался виден (доступность
категории "Кран" не проверяет саму себя, поэтому Кран 2 не исчезал — но
дочерние стоянки исчезали из СВОЕЙ категории).

**Исправление — смена принципа**, как и попросил заказчик:
- `allValuesFor(key)` — новая функция, список значений категории теперь
  считается БЕЗ учёта каких-либо текущих фильтров вообще (ни своего, ни
  чужих) — просто полный перечень значений, встречающихся у элементов
  текущей выборки. Для зон (Захватка/Кран/Стоянка) список ещё и
  объединяется с именами зон из `state.zones` — иначе зона без единого
  привязанного элемента (пустая стоянка) не попала бы в список вовсе,
  хотя видна на схеме. Список, возвращаемый этой функцией, никогда не
  меняется от кликов по чекбоксам — только от смены выбора файлов/слоёв.
- `isValueEnabled(key, value)` — используется ТОЛЬКО для визуального
  disabled-состояния чекбокса (серый + не кликается), не для состава
  списка. Считается по элементам, проходящим "остальные" фильтры — но с
  важной поправкой: для категорий, связанных иерархическим каскадом
  (`PLACEMENT_CASCADE_GROUPS = [["elementType","subtype"], ["crane",
  "stance"]]`), при расчёте доступности ОДНОЙ категории игнорируется
  фильтр ОБЕИХ категорий пары — это и разрывает порочный круг: снятие
  "Колонна" по-прежнему каскадом исключает её подтипы, но при проверке
  доступности самой "Колонна" фильтр подтипов больше не учитывается,
  поэтому "Колонна" остаётся ENABLED и кликабельной для возврата.
- `buildFilterGroup`/`buildHierarchicalFilterGroup` — рендерят ВСЕ
  значения из `allValuesFor` всегда, `input.disabled`+CSS-класс

  `isValueEnabled`, состав списка никогда не меняется.
- Сортировка (`placementComparator`) — добавлен `{ numeric: true }` в
  `localeCompare` (родная возможность Intl-сравнения строк в JS) —
  "Стоянка 2" теперь сортируется перед "Стоянка 10".

**Проверено**: логика вынесена в изолированный Node-скрипт с точной

## Баги от заказчика по скриншотам: цвет зон, дублирующиеся имена стоянок (2026-07-16)

Заказчик прислал 3 скриншота (сохранены в `test_data/`) и словами описал три
симптома: (1) у всех зон кранов на схеме один и тот же цвет, хотя в
«Настройки → Цвета зон» видно, что каждому крану назначен свой; (2) в
иерархии фильтра у Крана 2 и Крана 3 нет ни одной стоянки, хотя на схеме
они отмечены, и на скриншоте схемы видно, что у всех трёх кранов есть
СВОЯ "Стоянка 1"; (3) отбор Кран/Стоянка = "не определено" не показывает
ни одного элемента. Попросили сначала объяснить причину и план
исправления, потом делать правки — так и было сделано.

### 1. Цвет зон

`renderZones()` красил полигон через `poly.setAttribute("fill", zone.color)`
— SVG-атрибут `fill="..."` **всегда проигрывает** CSS-правилу класса
(`.zone-Кран { fill: #c0392b }`), независимо от того, что подставлено
через JS и в каком порядке идёт DOM — это общее свойство каскада: обычный
презентационный атрибут имеет более низкий приоритет, чем любое реальное
правило в таблице стилей. Поэтому все краны красились в общий цвет из
CSS, а индивидуальные цвета из БД просто игнорировались на отрисовке.
**Исправлено**: `poly.style.fill`/`poly.style.stroke` (инлайн-стиль,
который, наоборот, побеждает правило класса) вместо `setAttribute`.

### 2-3. Одинаковые имена стоянок у разных кранов + путаница "нет крана"/"без стоянки"

Проверено прямым запросом к БД: "Стоянка 1"/"2"/"3" физически существуют
**трижды** — у каждого крана своя нумерация с единицы (id 620/641/644 —
три разные зоны с именем "Стоянка 1", каждая под своим краном). Фильтр
использовал **имя** зоны как значение/идентификатор — из-за этого
одноимённые зоны разных кранов схлопывались в один пункт списка, а
группировка "какой стоянке какой кран" (`.find()` по имени) всегда
находила первую совпавшую по имени зону — почти всегда одну из зон
Крана 1. В итоге Крану 2 и Крану 3 не доставалось ни одной стоянки в
дереве, хотя данные были верны (см. предыдущую запись, где привязка
стоянок к кранам уже была проверена и работала правильно на уровне БД).

**Исправлено**: значением фильтра для зональных категорий (Захватка/
Кран/Стоянка) теперь служит **id зоны**, а не имя — у элемента он уже
есть готовым (`zone_crane_id`/`zone_stance_id`/`zone_zakhvatka_id`),
резолвить зону для получения значения фильтра не нужно вовсе. Имя
используется только для подписи чекбокса, резолвится отдельной функцией
`zoneNameById()` — поэтому "Стоянка 1" теперь корректно появляется трижды,
по разу под каждым настоящим краном, как одноимённые файлы в разных
папках. Заодно поправлена сортировка (раньше "числовое" сравнение
включалось для любых числовых значений, включая id зон — для id это
бессмысленно, id не несёт порядка; теперь "сырое" числовое сравнение
применяется только к Отметке, остальное сортируется по подписи).

Заодно найдена и устранена путаница ДВУХ разных смыслов "не определено" у
стоянок, из-за чего отбор из п.3 (жалоба заказчика) давал пустой
результат: (а) элемент вообще не привязан ни к одной стоянке (обычный
случай — 1236 из 1401 элементов в целевом файле, большинство элементов
не стоят точно на месте парковки) — раньше ошибочно попадал в дерево ПОД
несуществующим заголовком "Кран: не определено"; (б) зона-стоянка не
сопоставилась ни с одним краном при разборе файла (для этого файла таких
нет — все 27 стоянок сопоставились, см. предыдущую запись). Проверка в БД
подтвердила: `zone_crane_status` — `'matched'` у 100% элементов, то есть

баг; настоящая проблема была именно в том, что (а) визуально пряталось
под ложным заголовком крана. **Исправлено**: (а) вынесено отдельным
плоским пунктом «Стоянка крана — без привязки» вне иерархии кранов;
заголовок «Кран: не определено» теперь появляется только если в файле

ловушка с нулевым результатом без объяснения.

**Проверено**: логика вынесена в изолированный Node-скрипт с моделью
данных, ТОЧНО повторяющей реальный случай (21 стоянка у Крана 1, по 3

## Уточнение: «без стоянки» — дочерний пункт под своим краном, не общий (2026-07-16)

Заказчик поправил моё понимание предметной области: «Стоянка крана» — не
точка, а рабочая зона крана в конкретной позиции (кран, стоя на стоянке
N, монтирует ЖБК в пределах этой зоны). Элементы без привязки к
конкретной стоянке (в целевом файле — 88% элементов, обычный случай) всё
равно физически находятся в рабочей зоне какого-то ОДНОГО, известного
крана. Предыдущая реализация показывала такие элементы одним общим
пунктом «Стоянка крана — без привязки» ВНЕ иерархии — по сути отрывая их
от крана, к которому они на самом деле относятся, хотя эта связь была
прекрасно известна (`zone_crane_status`).

**Исправлено**: элемент без конкретной стоянки, но с известным краном,
теперь получает не общий `PLACEMENT_NONE`, а псевдо-значение вида
`no-stance:<id крана>` (`stanceFilterValue()`), которое корректно ложится
ДОЧЕРНИМ пунктом «— без конкретной стоянки —» под СВОЙ кран в дереве
фильтра — рядом с обычными пронумерованными стоянками этого крана.
Настоящий `PLACEMENT_NONE` (общий пункт вне иерархии) остался только для
случая «и кран, и стоянка не определены одновременно» — для целевого
файла таких элементов нет вовсе, пункт не показывается.

**Проверено**: на реальных данных файла — у каждого из 3 кранов теперь
есть свой дочерний пункт «без конкретной стоянки» (Кран 1: 21 обычная
стоянка + 1 такой пункт = 22 элемента в списке; Кран 2/3: по 3 + 1 = 4);
общий `PLACEMENT_NONE` для категории "stance" в этом файле больше не
встречается вовсе (у всех элементов известен хотя бы кран). Сценарий
«показать элементы Крана 1 без конкретной стоянки» (выключить остальные
краны + все конкретные стоянки Крана 1, оставив только новый дочерний
пункт) корректно даёт 365 элементов, все — из Крана 1 и без стоянки.
Все проверенные функции сверены построчным diff'ом с реальным кодом.
Живой браузерной проверки не было.

## 3D-режим схемы (2026-07-16)

Запрошено заказчиком: возможность покрутить схему в 3D, с той же
функциональностью по клику на элемент, что и в 2D. Уточнения от
заказчика, определившие реализацию: колонна — высота от своей отметки до
следующего уровня; ригель — квадратное сечение (высота = ширина); старый
стандарт входных данных больше не будет использоваться (можно не
поддерживать в 3D).

**Библиотека**: Three.js 0.160.0 — единственный реалистичный вариант для
WebGL 3D в браузере без написания слоя проекции/освещения/raycasting с
нуля. Подключение подтверждено пользователем отдельно (сработала защита
на внесение стороннего кода без явного согласия — правильно сработала,
пользователь подтвердил после объяснения). Файлы (`three.module.min.js`,
`OrbitControls.js`) скачаны через `npm install three@0.160.0` и
скопированы локально в `app/static/vendor/three/` — **не CDN**, чтобы
инструмент не зависел от интернета в рабочем режиме. Подключение — через
`<script type="importmap">` в `<head>` (резолвит bare-специфайер `three`
внутри `OrbitControls.js`) и ленивый динамический `import()` при первом
включении кнопкой «3D» — библиотека (~700 КБ) не грузится, пока
пользователь ни разу не открыл 3D.

**Архитектурное решение**: весь новый код — в существующем классическом
(не `type="module"`) `<script>`, используя `import()` как ВЫРАЖЕНИЕ (не
отдельный `<script type="module">`) — это позволило 3D-коду напрямую
использовать `state`/`selectElement`/`colorFor`/`passesPlacementFilters`
и т.п. без переноса в отдельный модуль и без "мостика" через `window` —
классический и модульный скрипт на одной странице НЕ делят lexical-
scope, а `let state = {...}` не становится свойством `window`
автоматически (в отличие от объявлений `function`), так что раздельный
`<script type="module">` потребовал бы это исправлять.

**Расчёт высоты — найдена и исправлена реальная ошибка в процессе
проверки**: изначально список "ярусов" для колонны считался по отметкам
ВСЕХ элементов (включая ригели). На реальном файле это давало неверный
результат: колонна с отметки 0 "видела" ближайшую отметку — не следующий
этаж колонн (+15800), а отметку периметрального ригеля-парапета на
промежуточной высоте (+5000) — и получала высоту всего 5000мм вместо
верных 15800мм. Исправлено — список ярусов теперь строится только по
отметкам, встречающимся у КОЛОНН (`computeColumnLevels()`), не у всех
элементов. Ширина сечения ригеля считается не по габаритному
прямоугольнику (bounding box — на повёрнутых элементах завышает обе
стороны), а из площади и периметра контура по формуле шнурков в
предположении прямоугольной формы — устойчиво к повороту (проверено на
синтетическом прямоугольнике 5000×400мм, повёрнутом на 37°: формула дала
точные 400мм, bounding-box ошибочно дал бы 3328мм).

**Интерактивность**: клик/двойной клик/правый клик по 3D-мешу —
raycasting → та же `selectElement()`/`openCtxMenu()`, что у 2D, без
дублирования логики карточки/контекстного меню. Фильтр по размещению
(`applyPlacementFilters`) и смена цвета при смене статуса/выборе
(`styleShape`) — расширены на пять строк каждая, чтобы синхронно
обновлять и 2D-фигуру, и 3D-меш (если сцена уже построена). При загрузке
новых данных (`loadPlan`) 3D-сцена пересобирается, только если 3D уже
была включена в этом сеансе — иначе просто ничего не делается, сцена
соберётся с нуля при первом включении.

**Проверено** (без браузера — нет инструмента автоматизации в этой
сессии): вычисления высот и ширин сечений — изолированным Node-тестом на
реальных данных целевого файла (уровни колонн — точно [0, 15800], высота
колонны нижнего яруса — 15800мм, ширина сечения реального ригеля —
450мм, что физически разумно) плюс синтетическая проверка устойчивости
формулы ширины к повороту контура. Все проверенные функции сверены
построчным diff'ом с реальным кодом. JS-синтаксис всего файла проверен
(`node --check`). Раздача новых статических файлов (`/static/vendor/
three/...`) проверена напрямую через сервер (200 OK). **Не проверено**:
собственно рендер в браузере (сцена/камера/свет/raycasting/OrbitControls
— вся часть, требующая реального WebGL-контекста) — стоит открыть
приложение и почовать: вращение камеры, клик по элементу в 3D (карточка
должна открыться так же, как в 2D), смену статуса через контекстное меню
в 3D, визуальную вменяемость высот колонн/ригелей.

**Файлы**: созданы `app/static/vendor/three/three.module.min.js`,
`app/static/vendor/three/OrbitControls.js`; изменены
`app/static/index.html`, `Docs/TZ.md` (новый раздел 6.7).

## 3D: зоны (захватка/кран/стоянка) (2026-07-16)

Продолжение предыдущей записи — заказчик уточнил, что в 3D не хватает зон.
Правило от заказчика: захватка — объём на всю высоту здания (подсветить
так, чтобы элементы внутри остались видны); кран и стоянка — плоские
полигоны на уровне 0 (не объём).

**Реализовано**: `build3DZoneMesh()` — захватка строится экструзией
контура зоны от нижнего яруса колонн до верха здания
(`computeBuildingHeightRange()` — верх считается тем же запасным
приёмом, что и высота самой верхней колонны: последний ярус + высота
последнего пролёта), материал полупрозрачный (7% непрозрачности — то же
значение, что у подложки зон в 2D, `fill-opacity:.07`). Кран/Стоянка —
плоский `ShapeGeometry` на Y≈0 (небольшой отступ 10мм от нуля — чтобы не
мерцало от наложения с полом/сеткой при рендере), непрозрачность 35%.
Цвет — свой у каждого крана и унаследованный его стоянками (та же связь
"стоянка → кран" и та же палитра, что уже резолвится на бэкенде для 2D,
см. `zone.color` в ответе `/plan-data`), у захватки своего цвета нет —
фолбэк на тот же оттенок, что и в 2D CSS (`#1353d6`). И захватка, и
кран/стоянка — `depthWrite:false`, чтобы несколько наложенных
полупрозрачных зон не давали артефактов сортировки глубины. Видимость
зон синхронизирована с существующими тумблерами "Зоны" (сайдбар →
Фильтры) — `apply3DZoneVisibility()` вызывается из того же обработчика,
что и 2D `renderZones()`, без пересборки геометрии. Зоны не входят в
список объектов для raycasting (там участвуют только меши элементов) —
клик всегда выбирает элемент, а не зону, даже если зона визуально сверху.

**Проверено**: расчёт диапазона высоты здания и парсинг цвета — Node-
тестом на реальных данных целевого файла (диапазон 0-31600мм: нижний
ярус колонн 0, верх = 15800 + (15800-0) = 31600; цвет захватки —
фолбэк `#1353d6`, цвет крана — собственный `#c0392b` из БД, корректно
распарсен в число для `THREE.Color`); все 34 зоны файла имеют валидный
контур (≥3 точки). Функции сверены построчным diff'ом с реальным кодом,
JS-синтаксис проверен. Живой браузерной проверки рендера по-прежнему не
было (нет инструмента автоматизации браузера в этой сессии).

**Файлы**: изменены `app/static/index.html`, `Docs/TZ.md` (раздел 6.7).

## Баг: зеркальность 3D-плана (2026-07-16)

Заказчик прислал скриншоты 2D и 3D одного и того же чертежа — по
ощущению 3D выглядела зеркальной. Проверка подтвердила: реальный баг в
переносе координат.

**Причина**: контур элемента/зоны переносился в 3D через
`shapeY = -y` (инверсия) ПЕРЕД `geometry.rotateX(-90°)`. Раскладка
матрицы поворота на -90° вокруг X сама по себе даёт `мировая Z = -shapeY`
— то есть с уже применённой инверсией `shapeY=-y` итоговое `мировая
Z = -(-y) = +y` — прямое (без инверсии) соответствие мировой Z и
исходного Y чертежа. Формально это похоже на "ничего не сломано" (просто
перенос осей), но у право-ориентированной системы координат с осью Y
вверх (как в WebGL/Three.js, так и вообще везде в 3D-графике) перенос
плоского 2D-плана (X вправо, Y вверх на бумаге) в горизонтальную
плоскость X-Z **математически не может** одновременно сохранить И
"право" (X), И "верх" (Y→Z) без инверсии одной из осей — иначе при
взгляде на сцену сверху (или под углом, как в скриншотах) картинка
неизбежно получается ЛИБО зеркальной по одной оси, ЛИБО перевёрнутой по
другой. Прежний код (без нужной инверсии) давал именно зеркальность.

Численно проверено на асимметричном тестовом контуре (прямоугольник со
срезанным углом — форма, аналогичная реальному зданию на скриншотах,
которое имеет срез в правом верхнем углу плана): полный цикл
"dxf-координаты → построение shape → поворот геометрии → мировые
координаты → проекция через базис камеры (метод lookAt, идентичный
внутреннему устройству Three.js)" — с исходным кодом срезанный угол
проецировался на ЛЕВУЮ сторону экрана вместо правой (зеркальность
подтверждена эмпирически, не только теоретическим выводом); после
исправления — корректно на правую сторону.

**Исправлено**: убрана лишняя инверсия при построении контура (`shapeY
= y` вместо `-y`) — у элементов и у зон. Побочный эффект — меняется
порядок обхода контура (winding), а с ним направление нормалей граней
после экструзии; чтобы это не привело к отбраковке "невидимых" граней
(`MeshStandardMaterial` по умолчанию рисует только лицевые грани),
материал элементов дополнительно переведён на `side: THREE.DoubleSide`
(у материала зон это уже было сделано раньше, по другой причине —
прозрачность). Также поправлен расчёт центра камеры
(`fit3DCameraToData`) — цель по Z теперь берётся с тем же знаком, что и
новое соответствие осей, иначе камера целилась бы не в центр модели, а в
его зеркальное отражение.

**Проверено**: изолированным Node-скриптом, реализующим ТОЧНО ту же
математику (матрица поворота -90° вокруг X + базис камеры lookAt) на
синтетическом асимметричном контуре — до фикса срез оказывался слева
(неверно), после — справа (верно, совпадает с положением в исходных
dxf-координатах). Само число проверок формально невелико, но проверка —
не на правдоподобие, а на прямое сравнение "было/стало" с одинаковой
методикой, что даёт высокую уверенность в правильности причины и фикса.
JS-синтаксис всего файла проверен. Живой браузерной проверки по-прежнему
не было.

### 9. Медленный зум в 3D — ✅ найдена причина, исправлено

**Причина**: `OrbitControls.getZoomScale()` нормализует шаг колеса через
`event.deltaY / (100 * devicePixelRatio)`. Трекпад Mac при плавной
инерциальной прокрутке шлёт много событий с очень маленьким `deltaY` —
с библиотечным дефолтом `zoomSpeed=1` каждое такое событие меняло
масштаб на доли процента, из-за чего заметное приближение/отдаление
требовало очень долгой прокрутки. Не связано с масштабом самой сцены
(мм) — чувствительность к вводу, а не к единицам мира.

**Исправлено**: `controls.zoomSpeed = 4` в `init3DScene()` — без правки
самой библиотеки.

**Общая проверка раунда**: JS-синтаксис всего файла (`node --check`) —
чисто, `python3 -m py_compile` бэкенда — чисто, сервер перезапущен и
отвечает `200` на `/health` и на статику 3D-библиотеки. Живой браузерной
проверки по-прежнему не было (нет инструмента автоматизации браузера в
этой сессии) — все проверки выполнены методом изолированного
воспроизведения логики на реальных данных из БД плюс построчная сверка
кода, как и в предыдущих раундах этой сессии.

**Файлы**: изменены `app/static/index.html`, `Docs/TZ.md` (разделы 6.5,
6.7).

## Лесенка сужения зоны стоянки крана с высотой (2026-07-16)

Заказчик указал на пробел: элементы на отметках выше 0 практически никогда
не попадали ни в одну стоянку крана (`zone_stance_status` был либо
`not_applicable`, либо `unmatched` почти у всех — 88% элементов файла), хотя
кран физически монтирует их именно со своей стоянки. Причина —
`zone_binding._candidates_for_category` требовала точного совпадения
отметки элемента с отметкой полигона стоянки, а полигоны стоянок в реальном
файле нарисованы только на отметке 0 (земля) — выше нигде совпадать было
не с чем.

Заказчик описал реальную физику: кран стоит у одного (ближнего к себе) края
своей стоянки и наклоняет стрелу к началу ряда стоянок (см. фото крана в
`test_data/package-lock.jpeg` — стрела резко задрана от крана вверх-в
сторону). Стрела — прямая линия от низкого основания (у крана) до высокой
точки (у дальнего от крана края), поэтому с каждым этажом именно ближний к
крану участок первым выходит из зоны охвата, а дальний остаётся доступен
дольше — "лесенка": на каждом следующем ярусе колонн ближний к крану край
зоны стоянки отступает на 1 реальный пролёт сетки осей, а освободившееся
место подхватывает следующая по номеру стоянка того же крана. Первая
стоянка — дальний край (начало ряда) никогда не отступает; последняя —
ближний к крану край никогда не отступает (забирает всё, что осталось).
Перпендикулярная ряду сторона не меняется ни на одном ярусе.

Согласование заняло несколько раундов уточнений (числовые примеры от
заказчика проверялись на реальных осях/координатах Крана 1 из БД — оси
файла в этом ряду скачут через 2, 1/3/5/7/9/…, что и дало несовпадение
первого черновика формулы с примером, пока не подтвердилось: "отступить на
один реальный пролёт сетки, номера осей могут быть пропущены" + на каком
крае лесенка отступает — "это не дальний, а ближний к крану" край, крану
у своей стоянки).

**Реализовано**:
- `scripts/zone_binding.compute_column_tier_elevations` — ярусы здания
  (уникальные отметки элементов "Колонна", по возрастанию — тот же приём,
  что и `computeColumnLevels()` в 3D, см. `Docs/TZ.md` §6.7).
- `scripts/zone_binding.build_stance_level_polygons` — для каждой стоянки
  крана готовит список shapely-полигонов по ярусам: ярус 0 — исходный
  полигон стоянки без изменений (подрезка по сетке на нулевом ярусе срезала
  бы небольшой технологический зазор между контуром и осью без всякой
  причины); ярус k>0 — окно вдоль оси, вдоль которой физически расположен
  ряд стоянок этого крана (числовая или буквенная, определяется автоматически
  по тому, вдоль какой координаты стоянки одного крана расходятся сильнее),
  подрезанное полигоном ЦЕЛОЙ рабочей зоны крана (не отдельной стоянки — не
  из чего иначе подхватывать уступленное соседом). Стоянки без однозначного
  крана или без номера в названии — исключение, лесенка не применяется.
- `bind_element_to_zones` — новые опциональные параметры
  `stance_level_polys`/`tier_elevations`; если оба переданы, категория
  "Стоянка" использует лесенку по ярусу отметки элемента (зажимается к
  крайнему известному ярусу, чтобы ни один элемент не остался без
  возможности отнесения из-за отметки чуть вне диапазона), иначе (для
  старых вызовов — `scripts/verify_zone_pipeline.py`) — прежнее поведение
  без изменений.
- `app/dxf_import.py` — сетка осей теперь строится ДО привязки элементов
  к зонам (раньше — после; лесенке нужны реальные оси заранее),
  `new_standard_pipeline.process()` получает её новым параметром
  `axis_grid`.

**Проверено**: изолированным Python-скриптом на реальных зонах/сетке осей
Крана 1 из БД — числовой пример заказчика (Стоянка 1 = оси 1–9, Стоянка 2 =
оси 9–11, этаж 2: Стоянка 1 → 1–7, Стоянка 2 → 7–9) воспроизведён точно;
проверена непрерывность окон на этаже 2 по всем 21 стоянкам Крана 1 (ни
разрывов, ни наложений); перпендикулярная сторона окна не меняется между
ярусами. `scripts/verify_zone_pipeline.py` (старый синтетический тест на
точное совпадение отметки) — все проверки пройдены без изменений, обратная
совместимость подтверждена. После переобработки реального файла через
перезапуск сервера (тот же путь, что и загрузка через UI) — доля
`zone_stance_status='matched'` на отметке 15800 выросла с 0% до 100%
(966 из 966 элементов), сводка по всем 1401 элементам файла: 1194
matched / 207 unmatched (без единого `needs_review` — окна стоянок не
пересекаются по построению), `needs_review` не выросло. Оставшиеся
unmatched — все на отметках 0 и 5000, у всех при этом кран определён
корректно, стоянка не найдена из-за небольших зазоров между нарисованными
контурами стоянок на плане (тот же класс проблемы, что и раньше, не
регрессия от этого раунда) — заказчик подтвердил, что исходный файл пока
не наполнен всеми данными.

**Файлы**: изменены `scripts/zone_binding.py`,
`scripts/new_standard_pipeline.py`, `app/dxf_import.py`, `Docs/TZ.md`
(раздел 3.7).

## Установка/обновление на Windows 11 — документация и скрипты (2026-07-16)

Заказчик попросил расписать, что нужно для установки на компьютер с
Windows 11 и как дальше обновлять, не затирая внесённые данные. Не
функциональное изменение приложения — операционная документация +
несколько вспомогательных `.bat`/`.ps1`-скриптов.

**Ключевой факт, определивший подход**: у проекта пока нет git-репозитория
(`git log` — "no commits yet", `git remote -v` — пусто), поэтому
документ описывает ДВА пути обновления: (А) через git, если позже
заведут приватный репозиторий (рекомендуется, безопаснее), и (Б) через
копирование файлов вручную (то, что реально доступно прямо сейчас) — с
явным списком "что копировать / что НИКОГДА не копировать", т.к. самый
опасный сценарий — случайно распаковать новый архив поверх рабочей
папки и затереть `data\zhbi.db`/`Input\`/`uploads\`.

**Добавлено**:
- `Docs/DEPLOYMENT_WINDOWS.md` — установка (Python, venv, зависимости,
  первый запуск, смена пароля admin, доступ по LAN, брандмауэр,
  автозапуск), резервное копирование, оба варианта обновления,
  диагностика типичных проблем.
- `scripts/windows/install.bat` — создаёт `.venv`, ставит
  `requirements.txt`.
- `scripts/windows/run.bat` — запуск `uvicorn --host 0.0.0.0` (LAN-доступ
  из коробки).
- `scripts/windows/backup.bat` + `backup.ps1` — копия `data\zhbi.db` с
  меткой даты/времени в `data\backups\` (дата — через PowerShell
  `Get-Date`, не через batch `%date%`/`%time%`, т.к. их формат зависит от
  региональных настроек Windows и ненадёжен для скриптов).
- `scripts/windows/update-git.bat` — `git pull` + переустановка
  зависимостей, с резервной копией перед обновлением.
- `.gitignore` — добавлены `Input/` (исходные DXF конкретного
  развёртывания) и `output/` (черновой вывод CLI-скриптов) — были
  открытием при подготовке этого раунда: не мешали работе сейчас (в БД
  до сих пор не было ни одного коммита), но были бы западнёй при
  первом же `git init`/`git add .` без этих исключений.
- Все `.bat`-файлы — `chcp 65001` сразу после `@echo off`, иначе
  кириллица в выводе рискует превратиться в "кракозябры" в стандартной
  кодовой странице `cmd.exe`.

**Проверено**: `python3 -m py_compile`/структура файлов — да, но
**реального запуска на Windows в этой сессии не было** (среда
разработки — macOS, нет `pwsh`/`cmd.exe` для проверки синтаксиса
`.bat`/`.ps1` вживую) — весь контент выверен построчно вручную по
описанной логике `cmd.exe`/PowerShell, но не исполнен. Документ явно
предупреждает об этом отдельным разделом ("Не проверялось вживую") —
перед боевым использованием нужен один сквозной прогон на тестовом
компьютере с Windows 11.

**Файлы**: новые `Docs/DEPLOYMENT_WINDOWS.md`, `scripts/windows/
install.bat`, `run.bat`, `backup.bat`, `backup.ps1`, `update-git.bat`;
изменены `.gitignore`, `CLAUDE.md`.

(есть аккаунт GitHub, VS Code) — попросил расписать, как обновлять через

установками.

  не глобально) — `Max Medvedev` / `max.v.medvedev@gmail.com`, взято из
  контекста сессии; поправить одной командой (`git config user.name
  "..."`), если нужно другое имя для авторства коммитов.
- Первый коммит на ветке `main` — весь код (`app/`, `scripts/`,
  `Docs/`, `requirements.txt`, `CLAUDE.md`, `.gitignore`) — 44 файла.

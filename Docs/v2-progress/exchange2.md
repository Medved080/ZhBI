# Перенос V1 → V2: область «exchange2» (продолжение exchange — обязательный перенос)

Ветка `feature/v2-exchange2` (worktree `/Users/max/zhbi-w-exchange2`, от `feature/v2-next`, после слияния
`feature/v2-exchange`). Задача — то, что в `Docs/v2-progress/exchange.md` осталось «не сделано»: экспорт/импорт
настроек, загрузка из PDF (детально и «только фасады»), панели облицовки шахты, внешние 3D-модели (FBX), остальные
операции обмена (образцы файлов, список чертежей, пользователи «Моей работы», справка отчёта, разбор ячейки
«Графика поставки», отладочная очистка), плюс два известных дефекта V1 (`zone_sync` IntegrityError→500, DXF/Revit
несколькими транзакциями).

Проверки — на НАСТОЯЩЕМ backend (`scripts/real_auth_server.py`, временная копия обезличенной БД, порт 8200, входы
`admin`/`user2`/`user3`/`user4`). Боевые данные, `test_data/`, `Input/`, `uploads/` не читались: PDF и DXF —
синтетические комплекты, построенные ПОД разбор V1 (см. ниже), а не образцы заказчика.

## Что сделано (по операциям)

| Операция | Что в V2 | Статус |
| --- | --- | --- |
| `settings-io` | Сверка → явное подтверждение «файл = копия учётных записей» → применение по digest; перечитывание сверки перед применением | 5 |
| `shaft-panels` | Разбор DXF (профиль ГП1/ГП2) → сводка (панели, замечания флажками) → применение по токену; отмена незавершённого анализа | 5 |

### Экспорт/импорт настроек (`settings-io`)

Backend: `app/settings_import.py` — общая логика (`parse_payload`, `analyze` — сверка без записи и без раскрытия
хэшей/солей, `_digest` — хэш файла и состояния БД (пользователи, цвета, видимость подписей), `apply_payload` —
применение). Использует ОБА входа: одношаговый V1 `POST /settings/import` (поведение не изменилось; добавлена
только блокировка записи первым действием — раньше запись шла без неё, сбой посреди цикла оставлял частично
закоммиченные строки из-за неявной транзакции SQLite) и новый двухфазный V2 `POST /settings/import/analyze` →
`POST /settings/import/apply` (`digest` тела форм — sha256, сверяется заново на apply; несовпадение — 409 «сверка
устарела», ничего не применяется). Права — `require_service_feature("settings_io", "write"/"read")`, как в V1
(только администратор сервиса).

Экран V2 — `app/static/v2/exchange-settings.js`: предупреждение о содержимом файла, кнопка выгрузки (переиспользует
существующий allowlist `api.fetchFile`), форма сверки, таблица расхождений (пользователи create/update — БЕЗ
хэшей/солей, только факт «пароль будет заменён»; цвета статусов; счётчик правок видимости подписей; пропущенные
объекты), обязательный чекбокс подтверждения (блокирует кнопку «Применить», пока не отмечен — независимо от
наличия расхождений), диалог подтверждения перед отправкой, обработка устаревшей сверки/сетевого сбоя/потерянного
ответа по общим правилам области `exchange` (`exchange-common.js`).

Шлюз записи: `settings.analyze` (multipart `.json`, без лишних полей) и `settings.apply` (multipart `.json` +
поле `digest`, проверка формы sha256).

### Панели облицовки шахты (`shaft-panels`)

Backend НЕ менялся: `app/shaft_panels_host.py` (роутер `app/shaft_panels/api.py`, `build_router`) уже был подключён в
`app/main.py` для V1, права те же (`assert_object_feature(conn, user, object_id, 'drawings', 'write')`, как у
загрузки DXF). Экран V2 — `app/static/v2/exchange-shaft-panels.js`: объект (список сужен до `kind='zhbi'` — профиль
работает только с ЖБИ, `storage.analyze` иначе отказывает), файл DXF, необязательная толщина панели, разбор →
таблица панелей (марка, шахта/сторона, габарит, расположение) → замечания к чертежу (каждое — отдельный флажок,
без отметки применение недоступно) → (если указана толщина) сводка для применения (новые/обновлённые/без
изменений/отсутствующие, конфликты блокируют кнопку) → диалог подтверждения → применение. Токен разбора явно
отменяется (`DELETE /shaft-panels/pending/{token}`) при смене файла/объекта/толщины и при уходе с экрана —
сервер держит общий лимит в 8 одновременных разборов на всех пользователей, токен принадлежит только своему
пользователю (чужой/отменённый/потраченный — отклоняется).

Синтетика: `scripts/gen_synthetic_shaft_dxf.py` (варианты `ok`/`no_axes`/`missing_mark`/`overlap`/`bad_level`) —
минимальный DXF, проходящий строгий профиль `app/shaft_panels/parser.py` (две развёртки ГП1/ГП2, восемь сторон,
план шахт, атрибуты осей 5/7/Е/Ж, обязательные отметки 0/+15,000/+25,800/+31,300). Целевая сетка осей — объект 1
тестовой копии (обезличенная копия несёт настоящую геометрию, у объекта уже зарегистрированы оси 5/7/Е/Ж из
реального импорта — ничего в БД дозаписывать не потребовалось).

## Найденное и исправленное

* `POST /settings/import` (V1, одношаговый): запись шла без `begin_write` — сбой ПОСРЕДИ цикла (например,
  невалидный цвет статуса не на первой строке) оставлял ранее выполненные INSERT/UPDATE в БД (неявная транзакция
  SQLite не гарантирует «всё или ничего» без явного `BEGIN`). Теперь — блокировка записи первым действием,
  коммит один раз в конце; поведение успешного пути не изменилось (проверено сравнением ответа и по журналу).

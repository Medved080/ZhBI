### 1.2 «Учитывать текущий фильтр схемы» (задание, п.2)

Перенесено для «Статуса монтажа», «Динамики», «Статуса комплектации» (включена по умолчанию, как в V1) и
«Графика поставки» — тех же четырёх отчётов, что показывают галочку в V1 (`REPORTS[key]` без `noFilter`/
`needsWorkPeriod`). Общий механизм — `read-screen.js`: `reportBody()` подмешивает `element_ids` из снимка, если
галочка включена; сама галочка + текст «чей это отбор» — в `paintReport()`.

**Устройство снимка** (новое, не живая синхронизация — архитектурная граница, не техническая недоработка):
рабочее место со схемой («Модель»/«Прораб») при КАЖДОМ изменении модели фильтра (`m.evt === "filters"`, только
когда группы непустые — ждём настоящей загрузки, не преждевременного пустого ответа) просит у кадра со схемой
актуальный список id (новая команда моста `getFilteredIds`, `app/static/embed-bridge.js`, белый список протокола
`zhbi-scene/1` — та же логика, что `state.elements.filter(passesPlacementFilters)` в V1) и кладёт снимок в
`sessionStorage` (`app/static/v2/scheme-filter-snapshot.js`, новый модуль): объект, id, счётчики
(показано/всего/снято), время. Пишется ТОЛЬКО когда сцена реально загружена (`sc.loaded`) — иначе ранний
служебный ответ моста (getFilters уходит сразу по «ready», раньше самой загрузки DXF) лёг бы нулевым снимком
раньше настоящего (найдено и исправлено живой проверкой, см. §3).

Отчёт ЧИТАЕТ снимок ЗАНОВО при каждой сборке запроса (`filterSnapshotFor(objectId)` в `reportBody()`, не
кэшируется в состоянии секции) и СВЕРЯЕТ его объект с объектом отчёта — снимок другого объекта НИКОГДА не
попадает в запрос (задание: «не смешивай данные разных объектов»); рядом с галочкой всегда написано, чей это
отбор, на какой объект и во сколько сделан (задание: «не скрытое протекание состояния»); если снимка нет или он
для другого объекта — галочка снята и НЕДОСТУПНА (disabled), с объяснением текстом (задание: «не применяй
скрытый устаревший фильтр»).

**Найдена особенность V1** (не исправлялась — вне переноса, не моя задача чинить V1): у «Графика контрактации и
поставки» галочка «Учитывать текущий фильтр схемы» ЕСТЬ в V1, но результата не меняет — `build_contracting_schedule`
(`app/report_contracting.py`) не принимает параметр `element_ids` вовсе, backend его отбрасывает молча. В V2
галочку для `report-contracting` НЕ добавляли — показывать переключатель, который ничего не делает, хуже, чем
не показывать вовсе.

**Проверено и чем**: `scripts/charts_verify/chk_filter.mjs` — 14/14 (настоящий backend, объект 1, реальный клик
по чекбоксу фильтра «Статус» в рабочем месте «Модель»): снимок появляется в `sessionStorage` после снятия
значения (7110 из 9580), «Статус комплектации» показывает галочку включённой по умолчанию с текстом «показано

## 2. Найденные дефекты (исправлены)

1. **Преждевременный пустой снимок фильтра.** Первая версия `workspace.js` запрашивала `getFilteredIds` на
   КАЖДОЕ событие `evt:"filters"`, включая самое первое — мост шлёт `getFilters()` сразу по `ready`, РАНЬШЕ, чем
   кадр закончил загружать DXF-элементы (`state.elements.length === 0` в этот момент), и такой ранний ответ
   (`{groups: []}`) уводил снимок в `sessionStorage` с `total:0` — отчёт затем ошибочно показывал «фильтр не
   сужен, показаны все 0 элементов». Исправлено двумя независимыми условиями: запрос `getFilteredIds` уходит,
   только если `m.model.groups.length` непусто; запись снимка — только если `sc?.loaded`. Найдено живым
   прогоном `chk_filter.mjs` (снимок с `total:0` вместо ожидаемого `9580`), не умозрительно.
2. **Чекбокс мог выглядеть отмеченным, но недоступным.** После переключения объекта на другой (без подходящего
   снимка) галочка рендерилась `disabled`, но всё ещё `checked` (из памяти `s.filterOn` этого же объекта отчёта
   на предыдущем объекте) — читалось как «фильтр применён, просто нельзя менять», хотя фактически не
   применяется НИКОГДА (см. `reportBody`). Исправлено: видимое состояние — `s.filterOn && desc.available`
   (сама память выбора не сбрасывается, чтобы вернуться сама на своём объекте). Найдено той же проверкой.

## 5. О номерах `status` в screens.json

Не менял `status` ни у одного из пяти затронутых экранов (`report-status`/`dynamics`/`completion` — остались
`3`; `report-delivery`/`schedule` — остались `5`, уже были). Причина: `status: 5` в реестре трактуется
неоднородно по прежним веткам (у `report-mywork`, судя по тексту его `checks`/`limits`, тоже, похоже, всё
сделано, но он тоже `3`), а у «Статуса комплектации» остаётся нерешённый пробел вне моего задания (вид «сводная
таблица» из V1 не перенесён — по-прежнему только «перечень позиций»), у «Динамики» — ключевые события/задачи
(см. §3). Поднимать номер статуса «по аналогии» без ясного критерия означало бы заявлять больше, чем проверено;
решение о точном критерии — за пользователем при следующей ревизии реестра.

## 6. Вопросы пользователю

1. **«График контрактации и поставки»**: подтверждаю находку — галочка «Учитывать текущий фильтр схемы» в V1
   показывается, но backend её не учитывает (`build_contracting_schedule` без `element_ids`). Чинить ли ЭТО в
   V1 (добавить фильтрацию по маркам на сервере) — отдельное решение вне моей задачи; в V2 галочку по этой
   причине не добавлял.
2. **Ключевые события/задачи/открытые вопросы в отчёте «Динамика»**: не переносил инлайн-блоки с кнопкой правки
   (см. §3) — тот же смысл уже есть в карточке объекта V2. Если ожидалось буквальное визуальное соответствие
   V1 (блоки прямо в отчёте) — отдельная маленькая доработка, независимая от графика.
3. **Статус экранов в screens.json**: см. §5 — сознательно не поднимал номер статуса вслепую; критерий «когда
   READ-отчёт можно звать статусом 5» стоит проговорить один раз для всего реестра (сейчас он расходится между
   старыми ветками), а не решать заново в каждой области.

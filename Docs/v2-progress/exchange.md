## Изменения backend (совместимые, минимальные)

Найдены и исправлены реальными проверками:

1. `POST /import-history-xlsx`: копия базы снималась ДО проверки прав и разбора файла (на битый файл — копия и блокировки нет смысла), не было
   блокировки записи, а поэлементные события журнала писались до отката стража покрытия контрактов (в журнале оставались события несостоявшегося
   импорта). Теперь: права → разбор → копия → `begin_write` → импорт → события уходят после commit (`activity.defer_*`).
2. `POST /import-schedule-xlsx`: то же (+ 404 на несуществующий объект, 422 на неизвестный вид).
3. `POST /import-contracting-xlsx`: разбор файла перед копией.
4. `POST /objects-import/apply`: в INSERT нового объекта имена колонок брались из клиентского JSON без белого списка (подстановка SQL / запись любой
   колонки) — добавлена проверка; плюс блокировка записи и события после commit.
5. `POST /elements/bulk-edit/apply`: события журнала после commit (откат стража не оставляет событий). `analyze` на пустом / битом / не-xlsx файле отвечал
   500 — теперь 400 с понятным текстом. Выгрузка `export` принимает необязательный `object_id` (только изделия объекта).
6. `app/backups.py`: два одновременных импорта ротировали одни и те же копии, второй получал 404 «Резервная копия не найдена» до начала работы — ротация
   теперь пропускает уже удалённую копию.
7. DXF: токен разбора применяется один раз и не параллельно (второй запрос → 409, повтор → 410); события этапа изделий уходят в журнал после его
   commit; при разборе имя чертежа, уже загруженного в ДРУГОЙ объект, даёт 409 (раньше — ошибка сервера `UNIQUE(source_file, dxf_handle)` на применении).
8. Revit: тот же запрет параллельного применения одного токена. Загрузка из папки Input: одна загрузка за раз (409).

Схема БД не менялась.

## Найденное, но НЕ исправленное (дефекты V1 / решения пользователя)

* Применение DXF и Revit идёт несколькими транзакциями (подтипы → изделия → сетка осей → зоны; справочники → элементы → секции): сбой посреди загрузки
  оставляет записанными завершённые этапы. Это исходная семантика V1; в подтверждении V2 об этом сказано, повтор с тем же токеном догружает
  (проверено сбоем на этапе осей). Сделать атомарным — отдельная задача (внутри этапов свои `commit`).
* Синхронизация зон: если полигон зоны при повторной загрузке того же чертежа теряет подпись (название зоны оказывается вне допуска), сервер пытается
  вставить новую запись зоны с тем же `dxf_handle` → `IntegrityError` → 500, при этом этап изделий уже записан. Воспроизведено синтетикой; правка —
  в `app/zone_sync.py` (решение по смыслу зон — за вами).
* Массовая правка `apply` не сверяет `was` с текущим значением (перезаписывает); в V2 это закрыто перечитыванием сверки из файла перед применением.
* Отчёты и выгрузки читаются всеми ролями, у которых есть доступ к объекту (у `user2`/`user4` доступ к обоим объектам с чертежами через проект);
  запрет «чужого» объекта на данных копии проверить нельзя (нет второго проекта с чертежом).

## Что НЕ сделано и почему

* `pdf-import` — двухшаговая загрузка с фоновой задачей и «жёстко под один комплект чертежей»; синтетического PDF для успешного пути нет,
  показывать функцию, проверенную только на отказе, нельзя.
* `shaft-panels` — разбор по «профилю семейства чертежей» (слой, оси 5–7 / Е–Ж, шаблон марки); фикстуры лежат в закрытых каталогах, синтетический
  чертёж этого семейства без реальных данных заказчика не собран.
* `external-models` (FBX) — интерфейс размещения и калибровки в 3D (3 тыс. строк JS), не форма загрузки; перенос — отдельная работа.
* `settings-io` — файл экспорта содержит хэши и соли паролей всех пользователей, импорт перезаписывает пользователей и их роли. Это противоречит
  отключённым строкам шлюза `users.*` («пароли — только человеком в V1»). **Вопрос пользователю:** переносить ли (с явным подтверждением «файл = резервная
  копия учётных записей») или оставить в V1 навсегда.
* `blk-bulk` (массовая правка ЗР через Excel, МФР) — объектный контур «учёт по блокам / work_progress» (область mfr); эндпоинты симметричны
  `bulk-edit` и переносятся тем же модулем — по согласованию.
* «Документы контрактации» (`supplier-change`: создание / проведение / отмена) — область picker (замена поставщика), не трогал.
* Не реализованы в отчётах: отбор «Учитывать текущий фильтр схемы» и печать (нет схемы / печати в V2), порядок группировки «Графика поставки»,
  разбор ячейки по маркам при наведении (`/reports/delivery-schedule/cell` не входит в список чтения `api.readPost`), вид «сводная» у «Статуса комплектации»,
  период «весь срок» и график «Динамики», выбор пользователей в «Моей работе».

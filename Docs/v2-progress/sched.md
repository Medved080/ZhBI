## 1. Что сделано (по операциям задания)

### 1.1 График СМР (`app/static/v2/schedule.js`, экран `schedule`)

Экран был «только просмотр версий» (`impl: "read"`) — переведён в полноценный модуль с четырьмя вкладками, как в V1.

| Операция | Строка шлюза | Backend | Итог |
| --- | --- | --- | --- |
| Версии: просмотр, удаление (базовую — только администратор сервиса) | `schedule.version.delete` | `app/schedule_versions.py` (`begin_write` добавлен) | проверено |
| Исходные данные расчёта: просмотр, правка, сохранение ЦЕЛИКОМ | `schedule.inputs.save` | `app/schedule_calc.py` (`PUT /schedule-calc/inputs`) | проверено |
| Разбор файла обработки заказчика (в форму, не пишет) | `schedule.inputs.parse` | `app/schedule_calc.py` (`POST /schedule-calc/inputs/parse`, без изменений) | проверено |
| «Заполнить поток по модели» | (клиентское, без запроса) | `schedule.js` | проверено |
| Расчёт: предпросмотр (не пишет) → подтверждение (атомарно, с отпечатком исходных данных) | `schedule.calc` | `app/schedule_calc.py` (`POST /schedule-calc`, оба режима — одна строка шлюза) | проверено |
| Диаграмма Ганта: дерево, уровни, версия прогноза, выгрузка XLSX/PDF | (чтение, `schedule.version.delete`-соседняя область читает без строки шлюза; выгрузки GET) | `app/schedule_versions.py`, `app/schedule_gantt_export.py` (без изменений) | проверено |

**Новое в backend (совместимо, схема БД не менялась):**
* `app/schedule_calc.py`: `inputs_version()` — отпечаток исходных данных (виды работ + поток), тот же приём, что `app.record_version`.
  `GET /schedule-calc/inputs` отдаёт `version`; `PUT /schedule-calc/inputs` принимает необязательный `expected_version`, берёт
  `begin_write` первым действием, сверяет под блокировкой — 409 без изменений при расхождении. `POST /schedule-calc` (`CalcIn`) —
  новое необязательное поле `expected_inputs_version`; при `save:true` запрос идёт под `begin_write`, отпечаток сверяется ДО
  расчёта; при `save:false` (предпросмотр) блокировка не берётся вовсе — чтение, не пишет. Ответ всегда несёт `inputs_version`
  (предпросмотр отдаёт его для следующего подтверждения). V1 ни одно из новых полей не шлёт — старое поведение (посчитать и
  сохранить одним движением, без сверки) не изменилось.
* `app/schedule_versions.py`: `DELETE /schedule-versions/{id}` берёт `begin_write` первым действием (было — без блокировки).

### 1.2 Контракт по умолчанию по типу изделия (`app/static/v2/contracts-list.js`, экран `contracts`)

Секция «Контракт по умолчанию по типу изделия» добавлена под список контрактов — как и в V1 (та же форма «Контракты»), объект —
из шапки. `PUT /contracts/default-map` получил необязательный query-параметр `expected_version`: если он есть — карта заменяется
ЦЕЛИКОМ (типа нет среди присланных — его строка удаляется; присланный с `null` — контракт снимается, строка остаётся), сверка
версии — под `begin_write`, отпечаток совпадает с `app.record_version.digest`, посчитан на клиенте (GET не менялся, поле
`version` в ответ не добавлено — полная совместимость с V1). Без параметра (V1) — прежний точечный upsert. Добавлена проверка:
контракт должен принадлежать ТОМУ ЖЕ объекту (иначе 400 вместо 500 от FK).

Строка шлюза: `default-contracts.set` (`picker-gate.js`: `defaultContractsMapBodyProblem` требует `expected_version` в адресе —
V2 никогда не уходит в точечный режим).

### 1.3 Свёртка дублей справочника (режим `mode: "merge"`)

Backend не менялся — режим уже существовал (`app/dict_delete.py`), был отключён шлюзом. `picker-gate.js`:
`contractingDeleteBodyProblem` теперь принимает `mode: "merge"` (ровно одна замена — для самой записи). `delete-plan.js`:
диалог получил выбор режима (радиокнопка «Перенести… / Заменить по отдельности», по умолчанию — перенос, когда возможен, как в
V1); в режиме `merge` дерево показывает ТОЛЬКО корень. Действует для контрагента, договора, спецификации (не для контракта — у
него нет `adopt` в реестре `dict_delete.py`, как и в V1).

### 1.4 Проверено, но не потребовало изменений
* **Привязка контракта к одному изделию** (`PATCH /elements/{id}/contract`): в V2 уже покрыта областью `model`
  (`POST /element-ops/contract`). Строка `counterparties.write` (общий отказ) больше НЕ упоминает контракт по умолчанию и
  свёртку дублей в описании (обе теперь разрешены отдельными строками), но саму строку/регэксп не сузил и не удалил — она
  по-прежнему нужна: блокирует групповую плановую дату (`PATCH /elements/bulk-planned-delivery-date`) и прежние (до V2)
  маршруты правки изделий, которые вне моей задачи.
* **`report-contracting`, `report-delivery`**: НЕ блокер. Обе отчётные формы уже перенесены на `feature/v2-next` ДО этой ветки
  (см. `app/static/v2/reports-exchange.js`, `screens.json`) — читают реальные данные (`app/report_contracting.py`,
  `app/report_delivery.py`, оба содержат полноценную бизнес-логику, не заглушки). Пометка «в разработке» в V1 (см.
  `app/static/index.html`, класс `.in-dev-mark`) означает незавершённую доработку ПРЕДСТАВЛЕНИЯ (нет группировки по маркам при
  наведении, печати), а не отсутствие функции; у «контрактации» файловой выгрузки нет и в V1 — сервер её не строит (это НЕ
  блокер, а задокументированный факт, см. `Docs/TZ.md`).

## 3. Найденные дефекты (исправлены)

1. **Шлюз слепо отклонял предпросмотр расчёта.** `scheduleCalcBodyProblem` проверял `expected_inputs_version` через
   `optVersion({ expected_version: b.expected_inputs_version })` — обёртка создаёт ключ `expected_version` ДАЖЕ когда исходное
   поле отсутствует (значение `undefined`, но `"expected_version" in {...}` — истина), из-за чего КАЖДЫЙ клик «Рассчитать» (без
   `expected_inputs_version` — предпросмотр всегда без него) получал отказ шлюза «Запрос не отправлен» и превращался в
   зависшую кнопку без единого сетевого запроса — backend был исправен и работал верно (проверено прямым curl), поломка была
   только в проверке формы тела на клиенте. Исправлено прямой проверкой `"expected_inputs_version" in b`. Найдено живым
   воспроизведением в браузере (`scripts/cdp.mjs`) — обычный прогон теста показывал только «истекло время ожидания» без причины.
2. Сообщение о конфликте расчёта («Пересчитываю по текущим исходным данным…») стиралось СИНХРОННО раньше, чем успевало
   отрисоваться: `confirmCalc` сразу вызывал `runPreview()`, который первым делом чистит `S.calc.error`. Добавлена пауза (700
   мс) с промежуточной отрисовкой между показом сообщения и автоматическим новым предпросмотром.

## 4. НЕ сделано и почему

Ничего из заданного объёма не осталось несделанным. Сознательные упрощения диаграммы Ганта против V1 (см. `Docs/TZ.md`
§5.7): без перетаскивания границы колонки названий мышью и без кнопки «Во весь экран» — сама диаграмма, две полосы,
отклонение, уровни группировки, переключение версии и выгрузка файлов перенесены полностью.

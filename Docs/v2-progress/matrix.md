# Исполнитель «matrix»: единая матрица операций V1 → V2

Ветка `feature/v2-matrix` (от `feature/v2-next`), рабочая копия `/Users/max/zhbi-w-matrix`. Серверы и браузер не использовались: задача — анализ кода;
на 8000 ничего не публиковалось, общие файлы (`write-gate.js`, `screens.json`, `main.js`, `workspace.js`, backend) не менялись.

## Что сделано

Скрипт `scripts/gen_v2_operations.py` строит по исходникам два файла (генерируются, руками не правятся):

* `Docs/v2-operations-matrix.md` — для людей: сводка, самопроверки, первые отсутствующие операции по областям, таблица экранов V2, матрица по областям
  (в каждой области — «К выполнению» и «Уже в V2 и прочее»);
* `Docs/v2-operations-matrix.json` — для машинной обработки (одна операция на строку; поля `area`, `section`, `v1`, `v2`, `gate`, `checks`, `published`, `action`).

Запуск (из корня рабочей копии; перезапускать после каждого слияния других исполнителей):

```
.venv/bin/python scripts/gen_v2_operations.py                        # --ref HEAD --published-ref main → Docs/v2-operations-matrix.{md,json}
.venv/bin/python scripts/gen_v2_operations.py --ref WORKTREE         # файлы рабочего дерева, с незакоммиченным
.venv/bin/python scripts/gen_v2_operations.py --ref feature/v2-admin # любая ветка (чужая ветка читается через git show, дерево не трогается)
.venv/bin/python scripts/gen_v2_operations.py --check                # только сводка и самопроверки, файлы не пишет
.venv/bin/python scripts/gen_v2_operations.py --out <каталог>        # писать не в Docs/
.venv/bin/python scripts/gen_v2_operations.py --strict               # код 1, если самопроверки нашли проблемы
```

Работает около 8 секунд; нужен `node` (POLICY шлюза вычисляется настоящим node, а не разбирается). Проверено на `HEAD`, `WORKTREE`, `main`, `feature/v2-next`,
`feature/v2-admin` (новые маршруты и модули подхватились, состояние «в ветке, не опубликована» считается) и `feature/v2-exchange`.

## Как считается

Строка матрицы — один маршрут backend (метод + путь; `/dictionaries/{kind}/…` развёрнут по 12 видам справочника из `KINDS` в `app/dict_delete.py`) плюс
клиентские операции без API (печать отчёта, печать бланка шахматки, копирование в буфер, сводная строка про `localStorage`).

* **backend** — `ast` по всем `app/**/*.py`: декораторы `@app/@router`, `include_router` (с префиксами), фабрика роутера `build_router` шахтных панелей;
  права — `assert_*`/`has_*`/`require_*`, `Depends(...)`, готовые зависимости (`require_contracting`), локальные обёртки-проверки (`_guard_elements`, `_guard_report`),
  словари и кортежи ключей (`KIND_FEATURES`, `DOC_FEATURES`), прямая проверка `user["role"] == "admin"`; названия разделов — из `app/features.py`.
* **V1** — токенизатор `scripts/inventory_v1_ui.py`: все строки-адреса `app.js` и соседних скриптов с методом по охватывающему вызову (`api`, `fetch`, `objectUrl`,
  `sendBeacon`, обёртки), таблица отчётов, шаблоны вида `${cond ? "/a" : "/b"}/x`; граф вызовов функций → обработчики пунктов меню «Действия», кнопок панели и
  окон (инвентаризация V1) → точка входа операции («приближённо»: по достижимости в графе; если ни одна точка не принадлежит экрану операции, а кандидатов много —
  «общий код V1»).
* **V2** — тот же токенизатор по `app/static/v2/*.js`: `api.get/post/patch/put/delete/upload/readPost/download`, `fetch`; пути через переменные и `spec.endpoint`
  раскрываются по `screens.json`; `read-screen.js` строится целиком по `screens.json` (`read.sections`, `exports`, `ack`); адресный виджет и карта (модули V1,
  подключаемые V2) считаются вызовами `projects-objects.js`.
* **Шлюз** — `POLICY` через node; для каждой изменяющей операции: разрешающие строки (id, `onlyKeys`, `check`, `proof`) и отключённые строки (id, причина).
* **Опубликовано на 8000** — то же вычисление на `main` (`git show main:…`): в `main` шлюз разрешает И V2 вызывает И маршрут есть в backend.
* **Состояния**: реализована и опубликована; в V2 в ветке (не опубликована); в V2, но отключена шлюзом; только переход в V1 (экран V2 есть, операции в нём нет);
  нет в V2 (нет и экрана); не вызывается интерфейсами (нет ни в V1, ни в V2). Служебные маршруты (вход, `/me`, версия сборки, телеметрия) в счёт не входят.
  Ссылка в V1, заглушка и отключённая кнопка реализованной функцией не считаются.

## Что нужно знать при чтении

* Точки входа V1 и «экран операции» выводятся из графа вызовов и правил пути — это подсказка, а не факт; при расхождении верить коду (в колонке V1 есть `app.js:строка функция`).
* Область (`model/mfr/picker/admin/exchange`), раздел и экран заданы таблицей `RULES` в скрипте (по пути), для маршрутов вне правил — запасное отнесение по разделу
  прав, и такой маршрут попадает в самопроверку. Отчёты, выгрузки и импорты отнесены к `exchange`, шахматка и её выгрузка — к `mfr`, вложения — к `admin`
  (реализованы в модуле проектов и объектов), график СМР — к `picker`.
* Чтения сцены рабочих мест (`/plan-data`, `/revit-plan/*` и т. п.) считаются реализованными через сцену V1 в кадре — по пересечению графа от `bootApp` и перечня
  `SCENE_DATA_RE` (Docs/v2-workspaces.md §1–2). Ресурсы, адрес которых выдаёт сервер (`plan-images/*.png`, плитки карты), помечены в `INDIRECT_USE`.
* Список «Первые отсутствующие операции» — эвристика (вес раздела, запись важнее чтения, наличие точки входа V1, редкие служебные вниз, надбавки `DAILY_BOOST` за
  повседневные сценарии). Это подсказка очерёдности, не решение.
* Права: «условно» — ветвление по праву (например, показ чужих действий), «уровень по условию» — уровень передан переменной. Проверки в теле вспомогательных
  функций других модулей ищутся не глубже трёх звеньев.
* Правки схемы БД, шлюза и интерфейса в этом задании не делались.

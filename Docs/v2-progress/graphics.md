## 1. МФР — привязка секции к осям выпадающим списком

**Было** (V1-подобное текстовое поле убрали ещё раньше, до этой ветки, — в V2 привязка вообще не
редактировалась). **Стало**: два независимых `<select>` «ось от»/«ось до»
(`app/static/v2/mfr-structure.js`) с метками из `GET /revit-plan/filters` (`grids`); выбор в любом
из них шлёт тот же `PATCH /objects/{id}/sections/{id}`, что и подпись секции (сервер
`_set_section_axes` требует обе оси разом или ни одной — как и раньше). Значения обоих select'ов при
отправке читаются ЖИВЬЁМ из DOM (а не из закэшированного объекта секции), поэтому независимые
`change`-обработчики не затирают друг друга. У объекта без осей (PDF-only, либо выгрузка без
сохранённых осей) колонки не показываются вовсе — как в V1.

## 2. МФР — геометрия блока мышью

SVG-редактор поверх существующего представления: угол прямоугольника двигает две смежные границы,
перекладина на ребре — только эту границу, тело — сдвиг целиком; числовые поля x0/x1/y0/y1 остались
вторым синхронным способом (правят тот же массив `g.boxes`). Во время жеста и при вводе числа граница
клампится о соседний блок того же этажа (перенос `blkGeoClampEdgeValue`/`blkGeoClampMove` из V1
`app.js`) с живой текстовой подсказкой прямо в SVG. Соседние блоки рисуются для сверки, но не
перетаскиваются. Слушатели `pointermove`/`pointerup` — на `window` (курсор уходит за пределы SVG),
навешаны один раз при монтировании, снимаются в `destroy()`.

## 3. Документы контрактации — подбор изделий обмена мышью на мини-схеме

Самостоятельный упрощённый SVG (не общая сцена рабочего места) в `supplier-docs.js`: контур и
координаты — готовые с сервера (`GET /supplier-changes/swap-elements`), цвет маркера — по статусу
(`GET /status-colors`). Клик — ближайшее изделие (переключатель), протяжка рамкой — добавляет всё
внутри к уже отмеченному, Shift+перетаскивание — панорама, колесо — масштаб. Список-чекбоксы рядом
остался ДОПОЛНИТЕЛЬНЫМ способом (не убран) и читает/пишет тот же `Set` выбранных id, что и схема —
синхронизация в обе стороны получается «бесплатно», без отдельного моста состояния.

## 4. Найденные и исправленные дефекты

### 4.1 Реальный дефект продукта: `load()` тянула тяжёлый эндпоинт на КАЖДОЕ сохранение

`GET /revit-plan/filters` (`app/revit_plan.py::filters`) — тяжёлый: несколько агрегатов
(`COUNT DISTINCT`/`GROUP BY`) по ВСЕЙ модели объекта, а не только оси. Добавленный код тянул его
внутри `load()`, а `load()` вызывается через `afterWrite()` **после каждой записи** (переименование
секции, правка этажа, сохранение геометрии блока — не только при открытии вкладки). При нескольких
быстрых сохранениях подряд запросы к этому эндпоинту начинали отставать друг от друга, и пока
последний из них не завершался, `st.busy` не сбрасывался — кнопка «Сохранить» и числовые поля
оставались задизейблены. Живой симптом (пойман браузерной проверкой): правка числового поля после
двух подряд сохранений геометрии — клик по «Сохранить» находил кнопку (она существовала в DOM), но
клик по задизейбленной кнопке браузер тихо игнорирует, новый PUT не уходил, а текст статуса
«Геометрия сохранена.» оставался от ПРЕДЫДУЩЕГО сохранения — с виду «всё хорошо», а по факту правка
терялась.

**Исправление**: метки осей не меняются от правки секций/блоков (меняются только загрузкой новой
выгрузки Revit) — эндпоинт грузится один раз за монтирование вкладки (`st.gridsLoaded`), не на каждый
`afterWrite`. Дополнительно `load()` получила параметр `silent` — фоновая перезагрузка после записи
больше не показывает плашку «Загрузка…» на весь блок (раньше это на секунду стирало ВЕСЬ бланк,
включая открытую геометрию и кнопку «Сохранить» — реального разрыва данных не было, но клик/жест,
начатый в этот момент, попадал в пустоту).

### 4.2 Инфраструктурный дефект: `scripts/cdp.mjs` не имел таймаута на отдельный DevTools-вызов

Если конкретный `Runtime.evaluate`/`Page.navigate` не получал ответа НИКОГДА (например,
`beforeunload`-диалог, который никто не подтверждает под CDP), `await send(...)` висел вечно —
внешние таймауты `waitFor` не помогали, потому что они ждут ответа именно от этого зависшего вызова.
Поймано на 9+ минутах реального повисания. Добавлен таймаут 20 с на отдельный вызов (с очисткой из
`pending`), после которого он падает понятной ошибкой вместо вечного зависания. Правка — только в
копии этого worktree, общий `scripts/cdp.mjs` используется несколькими параллельными областями,
каждая со своей рабочей копией.

### 4.3 Тестовая гонка (не дефект продукта): перезагрузка сразу после «сохранено»

Текст статуса «сохранена» показывается ДО `await afterWrite()` (см. `saveSection`), поэтому сразу
после появления текста ещё может быть в полёте `api.hasPendingWrites()` — реальный пользователь тоже
не перезагружает страницу в ту же миллисекунду. Под CDP это иногда попадало на диалог `beforeunload`
и вешало `Page.navigate` (см. 4.2). Добавлена пауза 500 мс перед проверками «переживает reload» —
реалистичная имитация поведения человека, а не ослабление проверки.

### 4.4 Тестовые дефекты в подготовке (не дефекты продукта)

- Роль-проверки МФР использовали `objectId: 4`, но `user2`/`user4` (`real_auth_server.py`) по
  умолчанию имеют доступ только к объекту 1 — переключатель объекта не находил объект 4, хэш
  `#/blocks` никогда не проставлялся. Исправление — подготовка SQL в КОПИИ БД (регламент задания:
  «неполные роли готовь SQL в копии»): `INSERT OR IGNORE INTO user_access` даёт `user2`/`user4`
  доступ к объекту 4 (роли `user`/`view` соответственно) только во временной копии.
- Роль-проверка «Документов контрактации» ожидала, что `user2`/`user4` увидят экран `#/supplier-change`
  read-only. По факту `screen-structure.json` («supplier-change».`menu_features`) требует `write` на
  `doc_supplier_change` ИЛИ `doc_link_swap` просто чтобы ОТКРЫТЬ экран (перенос гейта пункта меню
  V1, не относится к диффу этой области и не менялось) — у `user2`/`user4` обе фичи максимум `read`,
  поэтому экран целиком недостижим, хэш откатывается на `#/`. Это ожидаемое, дизайнерское поведение,
  не баг. Проверка исправлена на то, что происходит по факту: редирект + прямой `POST` всё равно 403.

## 6. Что осталось непроверенным / открытые вопросы

- **Вопрос пользователю, не блокер**: `screen-structure.json` требует `write` на
  `doc_supplier_change`/`doc_link_swap`, чтобы вообще открыть экран «Документы контрактации» — роль
  `view`/`user` с `read` на эти фичи не может даже ПОСМОТРЕТЬ список документов в V2 (в матрице прав
  `read` для этого экрана как уровень существует, но недостижим маршрутизацией). Это унаследовано от
  V1-гейта пункта меню и НЕ менялось этой веткой — не трогал, только зафиксировал в проверке то, что
  есть по факту (п. 4.4). Если это нежелательно — отдельная, не относящаяся к «graphics» задача
  (правка `screen-structure.json`/меню V1).
- Перетаскивание СОСЕДНИХ блоков того же этажа сознательно не реализовано (по заданию) — они рисуются
  только для сверки, правятся через свою же карточку. Это НЕ дефект, а осознанное ограничение.
- Не проверялась геометрия для блока с соседями по ВСЕМ четырём сторонам одновременно (только пары
  восток/запад на одном тестовом блоке) — клампинг по коду симметричен для всех рёбер
  (`geoClampEdgeValue` не различает направление), отдельной проверки на большее число соседей не
  делал ввиду отсутствия такого блока в тестовых данных объекта 4.
- 1366×768 отдельно не проверял (общие компоненты `v2-*` не менялись, риск минимален, но живого
  прогона на этом разрешении для новых элементов — угловых/рёберных ручек SVG — не было).

### Семантика групповой смены статуса (безопасный режим)

* Клиент не присылает контракты «для записи»: у каждого изделия только ожидаемое состояние (`expected_status`, `expected_contract_id`). `PATCH /elements/bulk-status` из V2 не используется (шлюз его не пропускает).
* Контракт СОХРАНЯЕТСЯ. Меняется только по правилам V1: возврат на «Запланирован» снимает контракт и очищает фактическую дату поставки (`sync_element_contract`, `recompute_status_and_actual_date`), либо при явном
  `assign_contract_id` для изделий, у которых контракта нет (страж остатка `contract_guard`; в интерфейсе — только при выходе одного изделия из «Запланирован», окно выбора контракта).
* Режим `preview` выполняет ту же операцию и откатывает: сервер отдаёт последствия (сколько контрактов и с каких снимется, у скольких очистится фактическая дата, сколько изделий уйдёт с «Запланирован» без
  контракта, что найдёт страж); интерфейс показывает их (панель и диалог подтверждения). `apply` требует подтверждения увиденных чисел (`expect`), иначе 409 `consequences_changed`.
* Расхождение состояния — 409 с перечнем причин, без частичных изменений; повтор (потерянный ответ) — 200 `already_applied`; частичный повтор — 409. Всё под `begin_write`, права — на всю пачку, журнал —
  `defer_*` (только после commit). Лимит 2000 изделий. Формат даты/времени проверяется строго (мусор — 400).

## 4. Найденные дефекты и решения

* Исходная семантика `PATCH /elements/bulk-status` (явная перезапись контракта из тела) не годится для V2 — заменена специализированным маршрутом (раздел 1).
* `PATCH /elements/bulk-planned-delivery-date` не проверяет формат даты, не сверяет прежнее значение и не берёт блокировку — в V2 не используется, вместо него `planned-date-batch`.
* Ctrl + щелчок на macOS — системный жест контекстного меню: настоящим щелчком его создать нельзя (в Windows, где работают пользователи, это обычный щелчок). Поэтому ⌘ + щелчок проверен настоящим жестом,
  Ctrl + щелчок — событием `click` с `ctrlKey` (в проверке помечено). Ошибка «Ctrl + щелчок открывает меню статуса вместо добавления» была замечена именно так и относится только к macOS.
* После сохранения реквизитов (тип/марка/адрес) схема перечитывается целиком и выбор V1 сбрасывается — интерфейс возвращает выбор на то же изделие.
* Итог групповой операции при расхождении показывался в форме, исчезавшей вместе со сбросом выделения после перечитывания схемы — вынесен в баннер вверху панели.
* Фантомная проверка «показатели обновились» в первой версии проверки заменена настоящей (вкладка «Статус» и полоса показателей прораба).

## 5. Ограничения и вопросы к пользователю

1. **Не перенесено**: вложения изделия (карточка/форма V1), построчные (разные) плановые даты в таблице «массовая плановая дата» V1 (в V2 одна дата на выбранные изделия, флажок «только у изделий без даты»),
   назначение контрактов ПО СТРОКАМ при групповой смене статуса (в V2 контракты сохраняются; назначить их можно распределением на АРМ комплектовщика или в карточке изделия), групповое выделение в 3D
   (в V1 его тоже нет). Вопрос: нужны ли построчные даты и контракты при групповой смене статуса — это потребует отдельного интерфейса таблицы; сервер `assign_contract_id` уже умеет один контракт на все изделия без контракта.
2. **`fill-scope`** («Заполнить пустые Объект и Проект», временная): в V2 подключено только чтение (что не заполнено). Само заполнение — необратимая массовая административная обработка, которая
   по документации самого модуля подлежит удалению, сервер не сверяет ожидаемое состояние. Не переносил без решения пользователя.
3. **`chess-flat`** (плоская шахматка) — это шахматка работ по блокам МФР (Docs/TZ.md §3в.1), не ЖБИ: не моя область, не трогал.
4. Групповые операции ограничены 2000 изделий за раз (3000 — предел состава выделения в кадре); при большем выборе интерфейс просит уменьшить выбор.
5. Групповые формы отключены на рабочем месте комплектовщика (там выбор нужен распределению; его вкладки и `allocSubmit` не трогал).
6. В шлюзе и на сервере остались прежние V1-маршруты для комментария, реквизитов и истории (без сверки ожидаемого состояния): это последовательность V1, права проверяет сервер. Если нужна такая же защита от устаревших
   данных для правки записи истории — отдельная задача.

# V2 «Документы контрактации» — режим «только просмотр» (область docsview, 2026-09-22)

Ветка `feature/v2-docsview` (от `main` = `5e1c013`), worktree `/Users/max/zhbi-w-docsview`. Решение пользователя: «нужен просмотр».

## Что выяснено до правки

1. **Модель прав.** Разделы `doc_supplier_change` и `doc_link_swap` (`app/features.py`) — обычные объектные разделы с уровнями
   «Нет / Чтение / Изменение»; значения хранятся в БД (`role_features`), реестр — в коде. Заводская раскладка `_от(CONTRACT, WRITE)`
   уже даёт ролям **view** и **user** уровень **«Чтение»** (в обезличенной копии так и есть). Значит, **менять сохранённые данные прав,
   делать миграцию или новую сущность НЕ понадобилось** — читатели уже есть, их просто не пускал интерфейс.
2. **Где гейтился экран.** V2: у записи `supplier-change` в `screens.json` не было `feature`, поэтому `screenAllowed()`
   (`registry.js`) брал `menu_features` из `screen-structure.json` — перенос пункта меню V1 `menu-supplier-change`
   (`data-feature-kind="write"`). V1: тот же атрибут в `app/static/index.html`, видимость ставит `app.js` (`can(k, "write")`).
3. **Сервер (`app/supplier_change.py`).** Просмотру нужны `GET /supplier-changes?object_id` (уже `read`, любой из двух разделов) и
   `GET /supplier-changes/{id}` (уже `read` раздела вида документа). Справочные запросы формы правки — `/refs`, `/candidates`,
   `/swap-elements`, `/contract-marks`, `/mark-contracts` — требуют `write`; просмотру они не нужны (названия контрактов есть в шапке
   документа, состав с адресами и статусами — в `items`), поэтому **сервер не менялся**. Изменяющие маршруты — прежние (`write`).

## Что сделано

* `app/static/v2/screens.json`, запись `supplier-change`: `feature: [[["doc_supplier_change","doc_link_swap"],"read"]]` — экран
  открывается при «Чтении» хотя бы одного вида (поле складывается с `menu_features` по «ИЛИ»); `ops`/`checks`/`limits` обновлены,
  `status` не тронут.
* `app/static/v2/supplier-docs.js`:
  - `canRead(kind)` и `readOnly(x)` = «проведён» ИЛИ «нет Изменения на этот вид»; документ такого вида открывается как проведённый:
    поля заблокированы, контракты и марка — одной строкой из шапки документа, состав «Замены поставщика» — таблица «Изделия документа (N)»
    (тип, марка, адрес, статус сейчас), «Обмен привязками» — стороны по парам и «Пар к обмену: N»; метка «Только просмотр», в подвале —
    «Только просмотр: нет права изменять документы этого вида на объекте»; мини-схема подбора не открывается (кнопки «Подбор…» нет,
    `openPicker` и `onAction` закрыты для вида без «Изменения»);
  - список: пояснение «Только просмотр…», если нет «Изменения» ни на один вид; кнопки создания — как было, по «Изменению» вида; строки —
    только видов, которые человеку дано смотреть (сервер отдаёт список при «Чтении» хотя бы одного вида, а документ открывает по
    разделу ЕГО вида — без отбора строка чужого вида вела бы в 403);
  - читателю не отправляются `/refs` и `/status-colors` при открытии экрана и документа, `loadFormData` (кандидаты/марки) не зовётся;
  - `isDirty`/`saveDraft`/`deleteDraft`/`postOrUnpost` дополнительно проверяют право вида (кнопок в разметке и так нет).
  - Пишущему поведение прежнее. Одно видимое отличие: у ПРОВЕДЁННОГО обмена пишущему больше не показывается подсказка «Марка … больше
    нигде на объекте к контрактам не привязана» — она выводилась всегда (у проведённого документа марки/контракты не загружаются) и была
    ложной.
* `write-gate.js` не менялся: изменяющие операции по-прежнему под шлюзом, а читатель их не отправляет.
* Проверки, чья посылка изменилась решением пользователя: `scripts/verify_graphics_picker.mjs` §4 (раньше ожидал РЕДИРЕКТ user2/user4 —
  теперь экран открыт в режиме просмотра, подбора и мини-схемы нет, прямой POST — 403) и `scripts/picker_verify/docs.mjs` D11.1 (роль
  view: раздел теперь открыт только для просмотра). `scripts/picker_verify/lib.mjs` — переопределение каталога/базы-источника
  (`PV_SP`, `PV_BASE_DB`), `docs.mjs` — порта (`PV_PORT`); по умолчанию всё как было.

## V1

Не менялся. Окно V1 режима просмотра не имеет: `scdOpenDoc` всегда берёт контракты объекта (`/refs`), для обмена — марки и контракты
стороны 2 (`/contract-marks`, `/mark-contracts`), для черновика замены — кандидатов (`/candidates`, рисует состав отметками в таблице
остатков), все — `write`; `scdApplyMode` различает только «проведён/черновик». Выравнивание потребовало бы: пункт меню на `read`, скрытие
«Новая замена/Новый обмен», ветку «читатель» в `scdApplyMode` (все поля, «Подбор», «Сохранить/ОК/Провести/Удалить/Отменить»), в
`scdOpenDoc` — показ без справочных запросов (или их открытие на `read`) и отдельную таблицу состава черновика замены. Это заметная
переделка V1 — оставлено как есть: пункт «Смена поставщика» по-прежнему виден только при «Изменении».

## Открытые вопросы (решение пользователя)

1. **Список на сервере отдаёт документы ОБОИХ видов** при «Чтении» хотя бы одного (`require_any_feature(DOC_FEATURES, "read")`):
   человек с доступом только к «Замене поставщика» получает через API номера, контракты и марки документов «Обмена привязками», которые
   открыть не может. V2 такие строки не показывает; серверный отбор по виду — правка кода (без данных), но меняет ответ и для V1.
   Делать ли?
2. **Черновик «Замены поставщика» читатель видит СОСТАВОМ** (таблица изделий), а не таблицей остатков нового контракта, как пишущий:
   `/candidates` остаётся `write`. Нужно ли читателю видеть «Не поставлено / Свободно в новом контракте» — тогда открыть `/candidates`
   (и для обмена `/contract-marks`) на `read`.
3. **После слияния раздел увидят все роли view/user на объектах ЖБИ** (заводская матрица) — это и есть решение «нужен просмотр», но
   если кому-то просмотр не положен, администратор снимает «Чтение» в матрице ролей (данные, в этой задаче не трогались).
4. V1 — см. выше: переносить ли режим просмотра в V1.

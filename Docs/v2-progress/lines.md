### Семантика построчной плановой даты (`POST /element-ops/planned-date-rows`)

Перенос таблицы `bulk-planned-date-backdrop` V1 (`app/static/app.js:9301-9393`, `index.html:9850-9867`): у каждой выбранной
строки — своя новая дата (или снятие, `planned_date: null`), «Заполнить пустые» заполняет только незаполненные поля.
Отличия от V1-маршрута `PATCH /elements/bulk-planned-delivery-date` (в V2 не используется — не сверяет прежнее значение,
не проверяет формат даты, не берёт блокировку записи): каждая строка несёт `expected_planned_date` (что видел клиент);
`mode: preview` считает последствия (сколько дат будет задано / заменено / снято) БЕЗ записи; `mode: apply` требует
подтверждения этих чисел (`expect`), иначе 409 `consequences_changed`; расхождение хотя бы одной строки — 409 с перечнем
причин и БЕЗ частичных изменений; повтор того же запроса (потерянный ответ) — `already_applied`, без повторной записи и
задвоения журнала. Строка, где новое значение равно прежнему («менять нечего»), в тело не попадает — отфильтровывается на
клиенте до отправки (сервер тоже отклоняет такую строку как `same_value`, если она всё же придёт).

### Семантика построчной смены статуса с контрактом (`POST /element-ops/status-rows`)

Перенос таблицы `bulk-status-backdrop` V1 (`app/static/app.js:8928-9295`, `index.html:9723-9756`): статус — ОДИН на всю
пачку (как в самой форме V1, поле выбора статуса общее), контракт — СВОЙ у КАЖДОЙ строки, указывается ЯВНО (число —
назначить/сохранить/заменить; `null` — «без контракта»; выбор — тем же окном с числами «всего / разнесено / доступно» по
позиции строки, что у одного изделия и у обычной групповой формы, `pickContract`). В отличие от `PATCH /elements/bulk-status`
(в V2 по-прежнему не используется — устаревший контракт в теле молча перезаписывает чужую правку, снимает контракт значением
`null` без предупреждения, принимает архивный и чужой объект контракта; подробности — `Docs/v2-workspaces.md` §9б):

* каждая строка несёт `expected_status` и `expected_contract_id` (что видел клиент) — расхождение с сервером даёт 409
  `state_changed` для ВСЕЙ пачки, а не молчаливую подгонку под чужую правку;
* контракты, которые строки НАЗНАЧАЮТ или ЗАМЕНЯЮТ, проверяются ДО применения пачки (существование, не архивный, тот же
  объект, что у изделий) — отказ до записи, без частичных изменений; контракт, который строка ПРОСТО СОХРАНЯЕТ (не
  указан к замене), повторно не проверяется — он уже стоит у изделия;
* режим `preview` выполняет операцию тем же кодом и откатывает, отдавая последствия по фактическому результату: сколько
  контрактов СНЯТО (с разбивкой по контракту), сколько ЗАМЕНЕНО (с разбивкой «откуда → куда»), сколько НАЗНАЧЕНО (с
  разбивкой по контракту), сколько изделий останутся без контракта, предупреждения стража о превышении; режим `apply`
  требует подтверждения увиденных чисел (`expect`), иначе 409;
* строки, освобождающие контракт (снятие или замена), применяются ПЕРВЫМИ внутри пачки — страж остатка видит
  освободившееся место раньше строк, которые на этот контракт назначаются (тот же приём, что не даёт ложных отказов при
  «обмене местами» внутри одной пачки);
* для статуса «Запланирован» контракт строки ЗАПРЕЩЁН телом (400 до записи, без похода в базу) — снимается у ВСЕХ строк,
  как и в обычной групповой форме (`element.status.batch`);
* отказ стража остатка хотя бы у одной строки — 409 `contract_guard`, ОТКАТ ВСЕЙ пачки (проверено конкуренцией за
  последнее место позиции: из двух одновременных заявок проходит ровно одна, вторая — 409, без частичного захвата).

Построчный режим НЕ заменяет и не дублирует распределение (`POST /contracts/{id}/allocations`, АРМ комплектовщика,
`Docs/v2-workspaces.md` §9): распределение — для запланированных изделий позиции БЕЗ контракта (перевод в «Контрактация»
пачкой не больше остатка); построчный режим — для изделий, УЖЕ имеющих статус и контракт (или без него), когда нужно
изменить контракт КАЖДОГО по отдельности при смене статуса (в т. ч. переоформление, разные контракты в одной пачке).

## 2. Что НЕ перенесено (зафиксировано, не изобреталось)

1. **«Контракт для МАРКИ» / «Распределить»** (V1: шапка формы `bulk-status-backdrop`, `app/static/app.js:9053-9253`,
   функции `renderBulkFillMarks`/`distributeBulkMark`/`openBulkMarkPicker`) — удобство поверх построчного выбора: один
   контракт выбирается для ВСЕЙ марки и одним нажатием проставляется незаполненным строкам этой марки в пределах остатка.
   В V2 НЕ перенесено — каждая строка выбирается по отдельности через свою кнопку контракта. Функционально то же самое
   достижимо (построчно, за N кликов вместо одного «Распределить»), но без ускорения на больших пачках одной марки.
2. **«Контракт по умолчанию» по типу изделия** (`default_contracts`, `app/contracts.py:754-783`, читается V1 в
   `state.defaultContracts` и предзаполняет кнопку контракта строки/диалога, `app/static/app.js:8560,8959`) — в V2 не
   подключено вовсе (сам раздел `default_contracts` отключён в шлюзе записи, блок «временно отключено», строка
   `counterparties.write`, `write-gate.js`). Построчный выбор в V2 по умолчанию показывает «— выбрать —» (если у изделия
   нет текущего контракта) без подсказки «обычно этот», а не «— выбрать —» с предзаполненным дефолтом, как в V1.
3. **«Убрать из выборки»** (кнопка ✕ у каждой строки в обеих V1-таблицах, `removeBtn` в `renderBulkStatusTable`/
   `renderBulkPlannedDateTable`) — убирает ОДНО изделие из пачки, не закрывая форму. В V2 такой команды для рабочего
   места «Модель»/«АРМ прораба» у моста кадра нет (`embed-bridge.js`: `pickerSelectIds` существует только для
   комплектовщика) — построчные окна V2 показывают состав, зафиксированный на момент открытия; убрать одну строку можно
   только закрытием окна и новым выбором на схеме (Ctrl/⌘-щелчком по лишнему изделию перед открытием окна).
4. Разъяснение по формулировке задания («назначение контрактов группе изделий по строкам»): в V1 это НЕ отдельная
   операция — тот же механизм, что и построчный контракт при смене статуса (`.bulk-row-contract` в ОДНОЙ форме
   `bulk-status-backdrop`; выбор контракта строки без смены статуса единственным изделием — `PATCH /elements/{id}/contract`,
   уже перенесён в V2 как `element.contract.set`, `Docs/v2-progress/model.md`). Отдельной формы «назначить контракты N
   изделиям без смены статуса» в V1 нет — не изобреталась.

## 4. Найденные дефекты (в собственном коде, исправлены до сдачи)

* Первая версия построчной плановой даты использовала жёстко заданные тестовые даты — повторный прогон проверки на той
  же копии БД спотыкался о «менять нечего» (даты уже стоят с прошлого прогона). Собственная проверка, не дефект приложения;
  исправлено вычислением дат ЗАВЕДОМО отличных от текущего значения каждого изделия.
* В сценарии «потеря ответа» первая версия проверки выбирала ОДНО изделие — панель группового выделения (и, значит,
  построчные режимы) показывается только при ДВУХ и более выбранных элементах (`sc.multi.count > 1` в `propsInner`,
  `element-ops.js`); это свойство самого интерфейса, не дефект — исправлено выбором пары изделий.
* При проверке контракта строки (кнопка `.eo-crow[data-c="none"]` — «— без контракта —») первая версия проверки искала
  кнопку ПО ТЕКСТУ «без контракта» через общий `document.querySelectorAll('.v2-dialog button')`: при ДВУХ одновременно
  открытых `.v2-dialog` (окно построчного статуса ПОД окном выбора контракта строки — оба используют один и тот же CSS-класс)
  `document.querySelector('.v2-dialog')` берёт ПЕРВЫЙ по порядку в DOM, то есть НИЖНИЙ, а не видимый верхний. Это
  особенность вёрстки диалогов (оба — `.v2-dialog`, стек через `z-index`), не дефект приложения — собственная проверка
  исправлена: клики по кнопкам диалога подтверждения (`showConfirmDialog`) целятся по `role="alertdialog"`, выбор
  «без контракта» — прямым селектором `data-c="none"`, а не текстовым поиском по всем `.v2-dialog` разом.

## 5. Ограничения и вопросы к пользователю

1. Пункты 1–3 раздела 2 («Что НЕ перенесено») — решение пользователя не запрашивалось (задание явно требует перенос
   безопасно, без переспрашивания «нужно ли»), но эти удобства V1 в построчных окнах V2 отсутствуют: «Распределить» по
   марке, предзаполнение «контракта по умолчанию», построчное «убрать из выборки». Если для повседневной работы это
   окажется неудобным на больших пачках одной марки — отдельная небольшая задача (UI поверх уже готового
   `POST /element-ops/status-rows`, серверных изменений не потребует).
2. Групповые построчные формы ограничены тем же порогом прав и тем же лимитом 2000 изделий за пачку, что и обычные
   групповые формы (`element.status.batch`/`element.planned.batch`); при выборе > 3000 на схеме (предел состава
   выделения в кадре, `embed-bridge.js`) построчные кнопки не показываются вовсе (как и обычные групповые).
3. Вложения изделия используют существующие серверные маршруты и строки шлюза `attachments.add`/`attachments.delete`
   (область `admin`) — при интеграции с областью `admin` возможен смысловой (не файловый) конфликт: если admin
   параллельно сузит/уберёт эти строки, карточка изделия молча потеряет вложения. Стоит свериться при слиянии веток.

## 6. Точка продолжения

* Пользователь принимает результат на 8000 после интеграции лидером. При интеграции проверить конфликты: `app/main.py`
  (одна добавленная строка импорта/подключения роутера `element_rows_router`, СРАЗУ после `element_ops_router` — не
  перед `@app.on_event("startup")`, см. стоячую инструкцию CLAUDE.md про порядок вставки функций), `write-gate.js` (блок
  `область: model`, 2 новые строки `element.planned.rows`/`element.status.rows`, импорт `plannedRowsBodyProblem`/
  `statusRowsBodyProblem` из `element-ops-rules.js`), `element-ops.js` (импорт `element-attachments.js`, блок «Вложения»
  в `cardHtml`, привязка в `bind()`, две новые функции `openPlannedRowsModal`/`openStatusRowsModal`, две кнопки в
  `groupHtml()`), `element-ops-rules.js` (новые экспортируемые функции добавлены, СТАРЫЕ не менялись), `element-ops.css`
  (2 новых правила), `screens.json` (3 строки: `ws-model`, `element-ops`, `ws-foreman`), `Docs/TZ.md`, `Docs/v2-workspaces.md` §9б.
* Файл `app/element_rows.py` — новый роутер, импортирует приватные помощники из `app/element_ops.py`
  (`_element_out`, `_norm_date`, `_norm_datetime`, `_contract_name`, `_problem`, `MAX_ITEMS`) — если `feature/v2-model`
  переименует/уберёт эти имена при слиянии, `element_rows.py` перестанет импортироваться; проверить `py_compile`
  обоих файлов вместе после слияния.
* Если решено переносить «Распределить по марке» или «контракт по умолчанию» в построчный режим — отдельная задача
  поверх уже готового backend (`POST /element-ops/status-rows` принимает contract_id любой строки независимо, менять
  сервер не потребуется, только интерфейс модального окна).

# Техническое задание — веб-сервис контроля поставки и монтажа ЖБИ

**Статус документа:** живой, поддерживается в актуальном состоянии.
Каждое функциональное изменение системы отражается здесь — либо правкой
существующего раздела (если изменилось поведение уже описанной функции),
либо новым разделом (если добавилась функция). Историю "как дошли до
текущего состояния" и мотивацию конкретных решений см. в
`Docs/backlog.md` (хронологический журнал по раундам тестирования) и
`Docs/requirements-notes.md` (точечные уточнения по данным). Этот файл —
про то, **что система делает сейчас**, а не про то, в каком порядке это
появлялось.

Последнее обновление: 2026-07-19 (раздел 5.1 «Партии», 6.7 «3D-режим схемы»).

---

## 1. Назначение

Веб-сервис для контроля поставки и монтажа сборных железобетонных
конструкций (ЖБИ — колонны, ригели и т.д.) на стройке. Источник данных —
чертежи в формате DXF: сервис извлекает из чертежа элементы конструкции
(с маркой и координатами), строит по ним интерактивную схему в браузере,
и позволяет прослеживать статус каждого элемента по всему циклу —
от планирования до приёмки на площадке.

## 2. Технологический стек

- **Бэкенд:** Python, FastAPI, SQLite (файл `data/zhbi.db`), без внешних
  сервисов (очередей, отдельной БД, кэшей).
- **Фронтенд:** один статический HTML-файл (`app/static/index.html`) —
  ванильный JavaScript без сборки/фреймворков, SVG для отрисовки схемы.
- **Парсинг DXF:** библиотека `ezdxf`.
- **Экспорт:** `openpyxl` (XLS), `reportlab`+`svglib` (PDF).
- Полный список зависимостей — `requirements.txt`.

Работа с системой возможна полностью из браузера, без обращения к
терминалу — включая загрузку новых чертежей. Терминал/CLI-скрипты
(`scripts/*.py`) остаются рабочим альтернативным путём для тех, кто хочет
импортировать данные вручную или заскриптовать процесс, но не обязательны
для повседневного использования.

## 3. Импорт DXF-чертежей

### 3.1 Способ загрузки

Два независимых способа попасть в БД, оба ведут к одной и той же
обработке (`process_upload`) и одинаково безопасны для повторного запуска
— сопоставление элементов по паре `(source_file, dxf_handle)`, повторная
обработка файла с тем же именем обновляет геометрию/адресацию, но **не
сбрасывает** `current_status` и историю статусов уже отслеживаемых
элементов:

1. **Каталог `Input/`** (в корне проекта) — основной способ. Все `.dxf`
   прямо в этой папке (без подпапок) перечитываются и (пере)обрабатываются
   **на каждом старте сервера**, автоматически, без участия пользователя.
   Ошибка одного файла (например, не подходит под грамматику имён слоёв —
   см. 3.7) логируется в консоль сервера и не мешает обработке остальных
   файлов и запуску сервера. **Список файлов, доступных для выбора в
   интерфейсе** (`GET /source-files`, поле выбора чертежа в тулбаре) —
   ограничен тем, что реально лежит в `Input/` прямо сейчас: данные ранее
   обработанного файла, чьё имя пропало из `Input/`, не удаляются из БД,
   но перестают предлагаться к выбору (проверяется на каждый запрос
   списка, без необходимости перезапускать сервер).
2. **Кнопка «Загрузить чертёж»** в тулбаре → выбор `.dxf`-файла на
   компьютере пользователя → обработка синхронно за один запрос
   (`POST /import-dxf`), файл сохраняется в `uploads/`. Остаётся как
   вспомогательный способ (например, разово проверить файл, который ещё
   не решили класть в `Input/`) — но если его имя не совпадает ни с одним
   файлом в `Input/`, обработанные данные не попадут в список выбора,
   пока файл также не окажется в `Input/`.

### 3.2 Поддерживаемые форматы геометрии внутри DXF

Один и тот же чертёж от одного и того же заказчика на практике встречается
в двух разных внутренних представлениях, оба поддерживаются автоматически
(без ручного переключения):

1. **Через блоки** — элемент представлен как `INSERT` (вставка блока),
   марка — в атрибуте блока либо определяется через ближайшую выноску.
2. **«Распакованная» геометрия** (после `EXPLODE` в AutoCAD) — блоков нет
   вообще, элемент — замкнутый `LWPOLYLINE` на целевом слое; точка
   привязки — центроид контура; марка всегда определяется через выноску
   или ближайший текст (атрибута у голого контура нет).

«Замкнутость» контура определяется либо явным DXF-флагом `closed`, либо
геометрически — когда первая и последняя точки контура совпадают, а флаг
почему-то не выставлен (встречается на реальных файлах, например у
ригелей).

### 3.3 Слои и типы элементов

Два независимых, параллельно работающих способа распознать слой —
старый и новый (см. 3.7), в зависимости от того, как чертёж назвал свои
слои.

**Старый способ** — список распознаваемых слоёв и их типов зашит в коде
(`LAYER_CONFIG` в `scripts/parse_zhbi.py`) — соответствие «имя слоя DXF →
тип элемента» задаётся вручную при появлении нового слоя в присланных
файлах. Слои, отсутствующие в этом списке И не подходящие под новый
стандарт имён (3.7), **молча игнорируются** — не попадают ни в базу, ни
в список слоёв для выбора в интерфейсе. Распознаются на сегодня:
`Колонны`/`WEB_Колонна_нижняя` → тип `Колонна`; `WEB_Ригель_на отм.
+15.800` → тип `Ригель`. Тип элемента — единый русский словарь для
старого и нового способа (`Колонна`/`Ригель`/`Плита`/`Панель`/`Плита
перекрытия`, см. 3.7) — раньше старый способ отдавал английские
`column`/`beam`, из-за чего один и тот же по сути тип элемента давал две
разные строки в экранах, завязанных на `element_type` (видимость
подписей, контракт по умолчанию), см. Docs/backlog.md.

**Запланировано, не реализовано:** экран при загрузке DXF, показывающий
ВСЕ слои файла с геометрией (включая нераспознанные ни одним из двух
способов), с возможностью включить незнакомый слой в импорт из
интерфейса одним кликом (тип элемента по умолчанию — имя самого слоя),
без правки кода на каждый новый слой. Подробности плана — в
`Docs/backlog.md`, раздел «Запланировано».

### 3.4 Определение марки элемента

Для слоя марок группы (тип/подтип/отметка, новый стандарт имён слоёв —
см. 3.7) сначала определяется, есть ли на нём хотя бы одна настоящая
выноска (`LEADER`/`MULTILEADER`):

**Если выноски есть** (обычный случай — Колонна, Ригель) — марка
определяется в следующем порядке приоритета:
1. Атрибут блока (`INSERT` с тегом `MARK`/`MARKA`/`МАРКА`/`TAG`, без учёта
   регистра).
2. Ближайшая выноска (`LEADER` старого образца или `MULTILEADER`) —
   геометрическое сопоставление «элемент ↔ выноска» решается глобально
   (жадный алгоритм по возрастанию расстояния, чтобы выноска не досталась
   не своему элементу, если рядом есть более далёкий претендент).
3. Ближайший «голый» текст (`TEXT`/`MTEXT`) без выноски вообще — нужно
   для элементов, у которых марка на чертеже подписана просто рядом, без
   линии-указателя (например, ригели).

Максимальное расстояние для сопоставления по выноске/тексту —
константа `MAX_LEADER_MATCH_DISTANCE`, подобрана так, чтобы покрывать и
компактные элементы (колонны, дистанция ~50мм), и вытянутые (ригели,
дистанция до ~1500мм), не путая при этом соседние элементы.

Из марки, извлечённой через `MULTILEADER`, автоматически вырезаются
служебные коды форматирования MTEXT (например, `{\C10;...}` — переопределение
цвета), которые иначе попадали в марку как мусорный текст.

**Если выносок на слое нет вообще** (найдено на плитах перекрытия —
марка нарисована не одной надписью и не выноской, а несколькими
отдельными `TEXT`, положенными прямо на элемент, например "4П" + "-" +
"1" вместо одной строки "4П-1") — марка собирается из всех текстовых
фрагментов, чья точка вставки физически лежит внутри контура элемента:
фрагменты сортируются по направлению чтения (проекция координаты на
поворот текста — работает и для горизонтальных, и для повёрнутых
надписей) и склеиваются без разделителя. Один фрагмент внутри контура
(обычная надпись целиком на элементе) обрабатывается тем же кодом без
особого случая. Пограничные фрагменты, чья точка вставки лежит ровно на
общей стороне двух соседних элементов (равное расстояние 0 до обоих —
подтверждено на реальных данных), достаются только одному — тому, чей
центроид ближе (тот же принцип глобального жадного сопоставления, что и
у выносок выше, только по фрагментам текста, а не по выноскам).
`element.mark_source` в этом случае — `grouped_text` (в дополнение к
`attribute`/`leader`/`unresolved`).

### 3.5 Адресация по осям

Каждому элементу вычисляется адрес относительно сетки координационных
осей чертежа:
- **Точно на пересечении осей** — адрес вида `"3/Б"`.
- **Со смещением от пересечения** (обычная практика в строительных
  чертежах, эксцентриситет привязки) — адрес вида `"3-5/Б-В"`, то есть обе
  оси, между которыми находится элемент, по каждому измерению отдельно
  (если по одному из измерений элемент точно на оси — для него используется
  одна метка без дефиса).
- **Вне сетки осей** / **сетки осей нет для этого чертежа** — отдельные
  статусы адресации (`outside_axis_grid`/`no_axis_grid`), на схеме
  отображаются пунктирной обводкой элемента. Это диагностический сигнал,
  не связанный со статусом поставки/монтажа.

Поле `axis_status` (геометрическая адресация) и поле `current_status`
(бизнес-статус поставки/монтажа) — независимые друг от друга и не
смешиваются в одну систему цветов на схеме.

### 3.6 Геометрия элемента (контур)

Для элементов, извлечённых из `LWPOLYLINE` (не из блока), дополнительно
сохраняется полный контур — список вершин в мировых координатах чертежа.
Используется для отображения элемента на схеме его настоящей формой (см.
раздел 6.1), а не только точкой. У элементов из `INSERT`-блоков контур не
извлекается (`None`).

### 3.7 Новый стандарт имён слоёв + привязка к захваткам/кранам/стоянкам

Второй, независимый от `LAYER_CONFIG` способ распознать слои — по
структурированному имени. Работает **параллельно** со старым способом
(3.3): применяется только к слоям с префиксом `WEB_`, которые старый
способ не распознал; слои, уже занятые старым конвейером (например,
слой сетки осей `WEB_Оси` в старых файлах), в новую грамматику не
попадают, чтобы не ломать уже присланные файлы.

Стандарт менялся у заказчика дважды; текущая (вторая) редакция
подтверждена реальным чертежом. Сравнение всех токенов имени (тип,
категория, роль, подтип, буква знака отметки) — **без учёта регистра**;
возвращается всегда каноническое написание, не то, что было в файле.
Словарь старой редакции (`доп` вместо `тех`, `Захватка`/`Стоянка` без
уточнения «крана» и т.п.) заказчиком отменён окончательно и заново не
появится — обратной совместимости под него нет.

**Формат имени слоя ЖБИ:**
```
WEB_констр_<Тип>[_<Подтип>][_ОТМ<знак><высота_мм_5цифр>]_<Роль>
```
- Второй токен `констр` — обязательный признак слоя ЖБИ (отличает его от
  служебного слоя ниже).
- Тип: `Колонна` | `Ригель` | `Плита` | `Панель` | `Плита перекрытия`
  (два последних — раздельные типы, не тип+подтип, несмотря на общее
  слово «Плита»; «Плита перекрытия» — отдельный, самостоятельный тип
  словаря, ровно как остальные, просто в имени слоя записан как одно
  словосочетание через пробел, не через `_`).
- Подтип — опционален, из справочника допустимых подтипов по типу
  элемента (настраивается в «Настройки → Справочник подтипов», не зашит
  в код). Заполнен по реальным чертежам: Колонна — `нижняя`,
  `средняя нижний ярус`, `средняя верхний ярус`, `верхняя`; Ригель —
  `на отм. +15.800`, `на отм. +25.800`, `на отм. +34.700`,
  `периметральный`; Плита перекрытия — `на отм. +25.800`; Панель (из
  исходной спецификации, подтверждающих чертежей пока не было) —
  `Цоколь`/`ЛифтоваяШахта`/`ШахтаПодъемника`.
- Отметка (`ОТМ...`) — опциональна, буква `П`/`М` (плюс/минус) перед
  5-значным числом (высота в мм), без буквы — ноль.
- Роль — `Элемент` (геометрия, замкнутый `LWPOLYLINE`) или `Марка`
  (аннотация с текстом марки — выноска `MULTILEADER`/`LEADER` или голый
  текст, парная геометрическому слою той же комбинации тип/подтип/отметка).

**Формат имени служебного слоя (зоны):**
```
WEB_тех_<Категория>[_ОТМ<знак><высота_мм_5цифр>]_<Роль>
```
- Категория (в имени слоя может быть написана по-разному, но внутренне
  всегда приводится к одному из трёх канонических значений — БД, CSS,
  фронтенд везде используют только их): `Захватки`→`Захватка`,
  `Кран`→`Кран`, `Стоянки крана`→`Стоянка`. Захватка и кран — сквозные
  зоны на всю высоту здания, без отметки; стоянка (крана) — обязательно
  с отметкой, свой набор стоянок на каждом уровне (номера стоянок могут
  повторяться между разными кранами — это нормально, зоны различаются по
  геометрии/отметке, а не по уникальности имени).
- Роль: `область`→`Зона` (полигон-контур) или `наименование`→`Наименование`
  (текст с названием зоны — на реальных чертежах это `MULTILEADER`, точка
  привязки для сопоставления с полигоном — остриё выноски, а не место
  текстового блока, см. ниже).

**Слой сетки осей** — тоже сменил имя (`WEB_Оси` → `WEB_тех_Оси`), но не
подпадает под грамматику зон (нет категории/роли) — система пробует оба
варианта имени при поиске сетки осей и использует тот, что реально
присутствует в файле (см. `assign_axes.build_axis_grid_auto`).

**Строгая валидация**: любой слой с префиксом `WEB_`, не распознанный
старым способом и не подходящий ни под одну из двух грамматик выше,
**прерывает импорт файла** с сообщением, называющим проблемный слой и
причину — это намеренно жёстче, чем молчаливый пропуск у старого
способа: цель — сразу ловить отклонения от стандарта, когда
структурированные имена слоёв станут основным способом.

**Реестр зон**: геометрия зоны (полигон) сопоставляется с текстом её
названия по принципу «точка привязки текста внутри полигона (или на
расстоянии не более 1 мм от его границы — компенсация независимого
округления координат текста/полигона в DXF, см. `zone_parser.
NAME_MATCH_TOLERANCE_MM`)». Зона без найденного названия или с
несколькими текстами внутри — не выбирается «наугад», получает
соответствующий статус (`unmatched`/`ambiguous`) и показывается как
требующая проверки, но продолжает участвовать в привязке элементов (у
зоны просто нет названия, это не мешает определить, что элемент
физически в ней находится).

**Привязка элемента к зоне** — метод зависит от типа элемента:
- Колонна — точка вставки внутри полигона зоны (тот же допуск 1 мм по
  расстоянию до границы, что и при сопоставлении названий зон, —
  `zone_binding.POINT_MATCH_TOLERANCE_MM`).
- Ригель/Плита/Панель — доля площади пересечения контура элемента с
  полигоном зоны (не длина — единая метрика площади для всех типов,
  используется уже сохранённый контур, см. 3.6). Присваивается зона с
  максимальным перекрытием; если максимум меньше 50% или разница с
  ближайшим конкурентом меньше 10 процентных пунктов — статус
  `needs_review`, зона не присваивается автоматически.
- Стоянка — не просто совпадение отметки элемента с отметкой полигона, а
  «лесенка» сужения зоны стоянки с высотой (см. ниже); элемент без
  известной отметки получает статус `not_applicable` (в отличие от
  `unmatched` — «нельзя определить», а не «определили и не попал»).

Результат хранится у элемента: `subtype`, `elevation_mm`, и по каждой из
трёх категорий — id зоны (может быть пустым) и статус
(`matched`/`unmatched`/`needs_review`/`not_applicable`).

**Лесенка сужения зоны стоянки крана с высотой.** Стоянка крана — не
точка и не «этаж», а рабочая зона крана в конкретной позиции (см. 6.5):
кран стоит у одного (ближнего к себе) края своей стоянки и наклоняет
стрелу в сторону начала ряда стоянок, к месту разгрузки. Стрела — прямая
линия от основания (низко, у самого крана) до верхней точки (высоко, у
дальнего от крана края) — поэтому чем выше этаж, тем меньше остаётся
доступным именно **ближний к крану** участок (стрела там ещё физически
не поднялась до нужной высоты), а дальний остаётся в зоне охвата дольше.
На каждом следующем ярусе колонн (см. 6.7 — те же ярусы, что и для высоты
элемента в 3D) ближний к крану край зоны стоянки отступает на 1 реальный
пролёт сетки осей (номера осей допустимо пропускать — считается по факту
существующим соседним осям сетки, а не по разнице номеров). Освободившееся
место подхватывает следующая по номеру стоянка того же крана — на этом
ярусе её ближний край «уезжает» назад ровно настолько же — так по всей
высоте здания не остаётся непокрытых мест. У первой стоянки крана дальний
(от крана) край — начало всего ряда — никогда не отступает. У последней
стоянки крана ближний к крану край никогда не отступает — она забирает
всё, что осталось выше по этому ярусу. Перпендикулярная ряду сторона зоны
не меняется ни на одном ярусе. Ярус земли (нижний) — исходный полигон
стоянки как нарисован, без каких-либо изменений.

Направление ряда (вдоль числовой или вдоль буквенной оси сетки) и порядок
стоянок определяются автоматически — по номеру в названии стоянки
(«Стоянка N») и по тому, вдоль какой координаты стоянки одного крана
физически расходятся сильнее. Материал для «подрезки» окна на ярусах
выше земли — полигон всей рабочей зоны **крана** целиком (она физически
охватывает весь ряд его стоянок), а не полигон отдельной стоянки — иначе
не из чего было бы «подхватывать» уступленное соседней стоянкой. Стоянки,
для которых кран не определён однозначно или номер не удалось извлечь из
названия, — исключение, лесенка к ним не применяется, на всех ярусах
используется их полигон без изменений.

Реализация: `scripts/zone_binding.build_stance_level_polygons` +
`compute_column_tier_elevations`, вызывается из
`scripts/new_standard_pipeline.process` (только когда передана сетка осей
— `app/dxf_import.py` теперь строит её ДО привязки элементов к зонам, а
не после, как раньше). Старое поведение (точное совпадение отметки
элемента с отметкой полигона стоянки) сохранено как запасной путь для
вызовов без сетки осей (тесты).

## 4. Статусы поставки и монтажа

Статус элемента (`current_status`) — по этому статусу элемент ведётся по
всему производственному циклу:

| Статус | Код | Смысл |
|---|---|---|
| Запланирован | `planned` | Начальное состояние, присваивается при импорте |
| Контрактация | `contracting` | Идёт процесс заключения/уточнения поставки по контракту |
| В производстве | `in_production` | Изготавливается |
| Отгружен | `shipped` | Отгружен поставщиком |
| Доставлен | `delivered` | Прибыл на стройплощадку |
| Смонтирован | `installed` | Установлен |
| Принят | `accepted` | Принят по факту монтажа |

Смена статуса — через контекстное меню на схеме (двойной клик или клик
правой кнопкой мыши по элементу; обычный клик — просто выбор/подсветка) —
для ОДНОГО элемента, либо массово для выделенной группы (см. 4.2).
Переходы между статусами **не валидируются по порядку** — можно
пропустить промежуточный статус (например, сразу с «Запланирован» в
«В производстве», минуя «Контрактация») или откатить назад.

Клик по любому статусу в контекстном меню открывает **диалог
подтверждения** (2026-07-17) — не применяется мгновенно. Диалог всегда
показывает и даёт поменять **дату и время**, на которые фиксируется
переход (по умолчанию — рабочая дата, если она сейчас активна в
тулбаре, иначе текущий момент; правка в диалоге не меняет сам тулбар,
это одноразовое значение для этого действия). Если переход уходит со
статуса «Запланирован» — дополнительно показываются выбор **контракта**
и, если контракт уже выбран в этом же диалоге, **партии** (см. 5, 5.1)
— оба можно указать сразу одним действием, не заходя в контекстное меню
повторно.

Каждая смена статуса фиксируется в истории (`status_history`): статус,
момент времени, кто изменил (текстовый снимок ФИО + ссылка на аккаунт),
опциональный комментарий, привязанный контракт (см. раздел 5). Историю
можно посмотреть в карточке элемента; отдельную запись можно удалить
(кроме последней оставшейся — история никогда не становится пустой). При
удалении/добавлении записи `current_status` элемента всегда пересчитывается
заново как статус самой поздней по времени оставшейся записи — не
обязательно только что добавленной/удалённой.

### 4.1 Рабочая дата (backdating)

В тулбаре — поле «Рабочая дата»: если задано, служит **дефолтом** для
диалога смены статуса (см. выше) и напрямую используется массовой сменой
статуса (4.2 — там своего поля даты нет, только общий тулбар). Пока
рабочая дата активна, поле подсвечивается, чтобы не забыть, что работа
идёт задним числом. Две кнопки:
- **«Сейчас»** — ЗАПОЛНЯЕТ поле текущими датой/временем (не очищает —
  поле остаётся активным/подсвеченным).
- **«✕» (2026-07-17)** — ОЧИЩАЕТ поле полностью. Пустое поле — рабочая
  дата неактивна, сервер на запись всегда подставляет собственный
  текущий момент (`datetime('now')`), а не значение, зафиксированное
  клиентом заранее. Добавлена по прямой жалобе: «Сейчас» не убирает
  подсветку/активность поля, из-за чего рабочая дата могла незаметно
  остаться активной с прошлой сессии (сохраняется в `localStorage`) и
  подставляться в новые действия без ведома пользователя — новая
  смена статуса с более РАННИМ временем, чем уже существующая запись
  истории элемента, корректно "проигрывала" по хронологии (текущий
  статус — всегда самая поздняя по времени запись), что выглядело как
  "смена статуса не сработала".

### 4.2 Массовая смена статуса

Для большого количества элементов сразу — выделение рамкой в 2D-режиме:
**Shift+перетаскивание** мышью по рабочей области (обычное перетаскивание
без Shift, как и раньше, панорамирует схему). В рамку попадают элементы,
которые СЕЙЧАС проходят фильтры (6.5) и видны на схеме — центр элемента
внутри прямоугольника рамки. После отпускания кнопки мыши появляется
плавающая панель «Выделено: N» с кнопками «Изменить статус…» и «✕»
(снять выделение). Групповое выделение подсвечивается на схеме отдельным
цветом (оранжевый пунктир), отличным от обычной подсветки одиночного
выбора (карточка в сайдбаре) — оба вида подсветки независимы и могут
быть на разных элементах одновременно.

Кнопка «Изменить статус…» открывает форму со **списком выделенных
элементов в виде таблицы**: ID, марка, тип, текущий статус (подсвечен
цветом этого статуса), и отдельная колонка — выпадающий список контракта
для каждой строки. Возможности формы:
- **Убрать лишнюю строку** — если рамка захватила элемент по ошибке,
  крестик у строки убирает её из выборки без переоткрытия формы.
- **Контракт обязателен для КАЖДОЙ строки** — заполненным считается любой
  явный выбор, включая «без контракта»; кнопка «Применить» заблокирована,
  пока хоть одна строка не заполнена.
- **Массовое заполнение** — в шапке формы выбирается контракт и по кнопке
  «Заполнить пустые» проставляется всем пока незаполненным строкам, ЧЬЕМУ
  типу элемента этот контракт подходит (остальные пустые строки
  пропускаются — не перезаписываются наугад).
- В шапке же выбирается **новый статус** — единый для всех строк формы.
  По кнопке «Применить» статус меняется одним запросом ко всем элементам
  сразу (единая транзакция на бэкенде — либо применяется целиком, либо
  ни к одному).

## 5. Контракты

Контракт — это договор поставки: **название + поставщик**, с одной или
несколькими строками **«тип элемента → законтрактованное количество»**
внутри (один контракт может покрывать несколько типов элементов сразу,
каждый со своим количеством). Также хранит (2026-07-17, см.
Docs/backlog.md, "Партия — учёт по маркам") **дату контракта**
(бизнес-дата подписания, не `created_at` — служебная метка БД) и
**короткий код контрагента** — оба используются только для формулы
метки партии и допстроки подписи на схеме (см. 5.1, 6.1), оба
необязательны, у контрактов, созданных раньше, остаются пустыми.

- **Привязка элемента к контракту** хранится не у самого элемента
  напрямую, а в каждой записи истории статусов — `elements.contract_id`
  является денормализованным кэшем, всегда равным контракту самой
  последней по времени записи истории, и **недоступен для прямого
  редактирования** через интерфейс (показывается в карточке элемента
  только для чтения).
- **Диалог выбора контракта** появляется при переходе элемента СО статуса
  «Запланирован» на любой другой (включая переход с пропуском
  «Контрактации») — предзаполнен последним известным для этого элемента
  контрактом либо контрактом по умолчанию для его типа, можно изменить
  или явно указать «без контракта».
- **Наследование**: все последующие смены статуса (без повторного показа
  диалога) автоматически сохраняют тот же контракт, что был установлен на
  предыдущем шаге — контракт «тянется» по истории вперёд, пока не будет
  переопределён явно.
- **Контракт по умолчанию** по типу элемента — настраивается в разделе
  «Настройки → Контракты», подставляется в диалог как значение по
  умолчанию, если у элемента ещё нет своего контракта.
- **Факт/план/повреждено/остаток** считаются по строке контракта (пара
  контракт+тип элемента): факт — количество элементов этого типа с этим
  контрактом, находящихся в любом статусе кроме «Запланирован»;
  повреждено — сумма количества по всем инцидентам этого контракта на
  этот тип (см. ниже); `остаток = план − факт − повреждено`. Превышение
  (факт + повреждено) над планом не блокирует смену статуса — только
  показывает неблокирующее предупреждение (тост на схеме, с указанием
  повреждённого количества, если оно есть) и подсвечивается красным в
  таблице контрактов.
- **Инциденты повреждений на стройке** — у контракта отдельная таблица
  записей: дата, тип элемента, количество, описание. Инцидент — это
  ТОЛЬКО количество, без привязки к конкретным элементам схемы (не нужно
  указывать, какие именно экземпляры пострадали). Записи без отдельного
  статуса подтверждения — любая внесённая запись сразу учитывается в
  остатке; правка/удаление — как правка строк плана поставки. Форма
  редактирования контракта («Настройки → Контракты → Изменить») — две
  табличные части: строки плана поставки (тип + количество) и таблица
  инцидентов (дата + тип + количество + описание), обе сохраняются одним
  запросом при нажатии «Сохранить» (полная замена списка, как и раньше у
  строк плана — не частичный патч по отдельной записи).
- Проверка остатка при **массовой (групповой) смене статуса** (см. 4.2)
  тоже учитывает повреждённое количество — тот же денормализованный
  остаток из `GET /contracts`, что используется везде.

### 5.1 Партии (2026-07-17)

Учёт контракта — на уровне ТИПА элемента (см. выше). **Партия** —
дочерняя сущность контракта, детализирующая план до уровня **марки**:
плановая дата поставки на площадку + таблица строк «тип + подтип + марка
→ плановое количество». Управляется из «Настройки → Контракты → Партии»
(кнопка рядом с «Изменить» у каждого контракта) — список партий
контракта, добавление/изменение/удаление, у каждой партии — своя
таблица строк с планом/фактом/остатком по марке (`GET /batches?
contract_id=...`, `POST/PATCH/DELETE /batches/{id}`, только admin).
Партии, в отличие от контрактов, **удаляемы** — более "расходный"
объект, план поставок часто корректируется.

**Идентификация партии** — без ручного названия/номера, метка
собирается автоматически по маске «Контрагент. Номер и дата контракта.
Дата»: `<поставщик>. <название контракта> от <дата контракта>. <плановая
дата партии>` (часть «от …» опускается, если у контракта дата не
заполнена) — считается на сервере (`compose_batch_label`,
`app/batches.py`), единственный источник форматирования.

**Назначение элемента на партию** — независимое действие, НЕ привязанное
к смене статуса (в отличие от контракта, см. выше). Два входа:
- **Контекстное меню** (правый клик/меню на схеме) — пункт «Партия»
  **ВСЕГДА присутствует** (2026-07-17, тот же принцип, что у фильтров —
  "полный список действий всегда виден + недоступен (disabled), не
  сужается"), недоступен только пока у элемента правда нет контракта, с
  подсказкой почему; текст меняется на «Изменить партию…», если партия
  уже назначена — работает и для первичной установки, и для повторного
  изменения.
- **Диалог смены статуса** (см. 4) — если контракт указывается ПРЯМО В
  НЁМ (уход со статуса «Запланирован»), там же можно сразу выбрать и
  партию, без отдельного захода в контекстное меню (список партий
  зависит от контракта, выбранного в том же диалоге).

Партия — простое живое поле (`elements.batch_id`), БЕЗ версионирования
по истории статусов (в отличие от `contract_id`) — переназначение не
оставляет следа "кто/когда поменял". Поддерживается и одиночное
назначение, и массовое (кнопка «Назначить партию…» в панели
множественного выбора — рамка в 2D, та же механика, что у массовой
смены статуса).

**Жёсткое ограничение** — назначить элемент на партию можно, ТОЛЬКО если
в её строках есть точное совпадение (тип, подтип, марка) — иначе выбор
недоступен в интерфейсе, а прямой запрос к API вернёт 400. Сравнение
NULL-safe (элемент без подтипа/марки корректно совпадает со строкой без
подтипа/марки).

**Овербукинг** — мягкое, неблокирующее предупреждение (тост), как и у
остатка контракта: если элементов данной марки на партию назначено
больше, чем запланировано в её строке, назначение всё равно проходит.

**Смена контракта у уже назначенного на партию элемента** — партия
принадлежит конкретному контракту; если контракт элемента меняется
(явно в диалоге при смене статуса) на другой (или снимается), партия
автоматически сбрасывается в «не назначена» — иначе элемент остался бы
привязан к партии чужого контракта.

**В карточке элемента** партия показывается строкой внутри блока
«Контракт» (не отдельным блоком) — для admin кликабельна, открывает ту
же форму редактирования партии.

## 6. Интерактивная схема

### 6.1 Отображение элементов

Каждый элемент рисуется на схеме маркером, форма которого настраивается
по паре (слой, тип элемента) в разделе «Настройки → Форма маркеров»,
настройка сохраняется на сервере (таблица `element_shapes`) — общая для
всех пользователей, переживает перезагрузку страницы:
- **«Как в оригинале» (контур)** — форма по умолчанию для любой пары
  (слой, тип элемента), пока админ явно не назначил другую. Настоящий
  контур элемента из чертежа (см. раздел 3.6), масштабируется вместе со
  всей схемой как обычная геометрия, а не как условный маркер экранного
  размера. Если контур для элемента не сохранён (например, элемент из
  `INSERT`-блока, а не замкнутого `LWPOLYLINE`) — тихий откат на круг.
- **Условные маркеры фиксированного экранного размера** — круг, квадрат,
  треугольник, ромб, шестиугольник. Размер ограничен максимумом в
  экранных пикселях при увеличении масштаба (не раздуваются до
  неудобного размера). Назначаются вручную там, где условный маркер
  читается понятнее контура (например, для компактных элементов).

Базовый радиус маркера (и производный от него размер шрифта подписи
марки) сервер оценивает автоматически по медианному расстоянию до
ближайшего РАЗЛИЧНОГО соседа среди всех элементов текущей выборки
(`estimate_marker_radius`, `app/main.py`) — так маркеры/подписи не
разрастаются на разреженных чертежах и не наезжают друг на друга на
плотных. При этом элементы одного следа на плане, но на разных ярусах
(колонна/ригель, продолжающиеся через несколько отметок с той же
координатой X,Y) в этот расчёт не считаются "соседями" — иначе на
многоярусных зданиях медиана обрушивается почти до нуля и маркеры/
подписи становятся невидимыми на любом масштабе (см. Docs/backlog.md,
"Подписи марок пропали на плотных многоярусных файлах", 2026-07-17).

Цвет заливки маркера — по текущему статусу поставки/монтажа,
настраивается в «Настройки → Цвета статусов». Пунктирная обводка —
диагностический сигнал проблемы адресации по осям (см. 3.5), не связан с
цветом.

Подпись марки рядом с элементом:
- Направление подписи выбирается один раз при загрузке схемы так, чтобы
  минимизировать пересечения с соседними подписями (перебор 6 кандидатных
  направлений).
- Подписи, которые всё равно пересекаются при текущем масштабе (плотная
  застройка), динамически скрываются и появляются обратно по мере
  приближения.
- Видимость подписей по типу элемента отдельно переключается (сайдбар →
  вкладка «Фильтры», см. 6.5) — сеансовый переключатель, не сохраняется
  на сервере.
- **Цвет текста подписи** — персональная настройка на пользователя
  («Настройки → Цвет подписей марок», доступно всем ролям), хранится в
  `users.label_color` (2026-07-17). По умолчанию `#222222` — единый
  дефолт для 2D и 3D (раньше были два разных несогласованных значения).
  Вокруг букв — белый контур (`stroke`+`paint-order: stroke` в CSS, не
  отдельная подложка-прямоугольник — в SVG со уже применённым
  контрфлипом текста отдельный `<rect>` позади было рискованно проверить
  без браузера) — читаемость на любом фоне/цвете элемента.
- **Допстрока (партия)** — вторая, более мелкая строка под маркой, если
  элемент в процессе поставки (Контрактация/В производстве/Отгружен, см.
  раздел 4) уже назначен на партию (см. 5.1): «‹код контрагента›.
  ‹плановая дата поставки партии›» (код опускается, если у контракта не
  заполнен). Пропадает, когда элемент физически на площадке (Доставлен и
  далее) — плановая дата там уже неактуальна, либо когда партия снята.
  Не участвует в отдельном расчёте коллизий — видимость наследуется от
  основной строки (упрощение первой итерации, тот же принцип, что уже
  применялся к постоянным 3D-подписям).

Сетка координационных осей рисуется линиями на весь охват чертежа;
подписи осей закреплены на границах видимой области экрана (как
замороженные заголовки строки/столбца в таблице) — всегда видны
независимо от прокрутки, с прореживанием при коллизии на мелком
масштабе.

Зоны (захватка/кран/стоянка, см. 3.7, только для файлов нового стандарта
имён слоёв) рисуются полигонами под элементами, но над сеткой осей —
раскраска по категории (у каждой ИНДИВИДУАЛЬНОЙ зоны категории «Кран» и
её стоянок — свой цвет, не общий на категорию, см. 6.6), полупрозрачная
заливка и полупрозрачная обводка (подложка, не спорит визуально с
маркерами элементов поверх неё), пунктирная обводка для зон без
сопоставленного названия или с несколькими кандидатами. Подпись названия
(или причины отсутствия) — по центроиду полигона, внутри контура. Размер
шрифта подписи зоны ограничен тем же приёмом, что у подписей марок и осей
(предел в экранных пикселях, не растёт бесконечно при увеличении
масштаба). Видимость по категории переключается отдельно (сайдбар →
вкладка «Фильтры», раздел «Зоны», см. 6.5).

### 6.2 Навигация по схеме

- Колесо мыши — масштабирование к точке под курсором.
- Перетаскивание — панорамирование (с порогом в несколько пикселей,
  чтобы обычное дрожание руки при клике не воспринималось как
  перетаскивание).
- **Shift+перетаскивание** — рамка группового выделения для массовой
  смены статуса (см. 4.2), не панорамирование.
- Функциональные полосы прокрутки (вертикальная и горизонтальная) —
  перетаскивание ползунка или клик по треку панорамирует схему;
  скрываются, если весь охват уже помещается в видимую область.
- Индикатор текущего масштаба в правом нижнем углу (100% — «вся схема
  целиком», как при первом открытии чертежа) с кнопкой сброса.

Текущий масштаб/панорама **не сбрасываются** при изменении состава
отображаемых **слоёв внутри уже выбранного файла** (чекбоксы слоёв, 6.3)
и при сохранении настроек/подобных перезагрузках данных схемы —
переключение слоя не должно "дёргать" вид.

Изменение состава **файлов** (отметить/снять галочку файла целиком в 6.3)
— наоборот, **всегда пересчитывает вид** заново по текущему набору
выбранных файлов, при включении файла и при выключении, независимо от
порядка кликов. Это осознанное отличие от слоёв: у каждого файла своя
сетка осей, а подписи осей закреплены на границах ТЕКУЩЕЙ видимой
области (см. выше) — если оставлять старый вид от предыдущего набора
файлов, подписи осей оказываются привязаны к границам уже неактуального
охвата и визуально "уплывают" от истинного края к центру. Пересчёт вида
на каждое изменение состава файлов — единственный способ гарантировать,
что подписи осей всегда ровно по краю видимой области.

Если сняты галочки со **всех** файлов — рабочая область и карточка
элемента полностью очищаются (не остаётся последний отрисованный
чертёж).

### 6.3 Выбор источника: файлы и слои

Поле выбора чертежа в тулбаре — выпадающая панель с чекбоксами: сначала
файлы (см. 3.1 — только те, что сейчас лежат в `Input/`), при отметке
файла — раскрывается список его слоёв (тоже чекбоксами, друг под другом,
с отступом под своим файлом). Можно:
- выбрать произвольный набор слоёв внутри одного файла, вплоть до нуля —
  тогда на схеме от этого файла остаются только сетка осей и зоны (если
  есть), элементов нет;
- **совместить элементы из нескольких разных файлов** одновременно
  (по общим координатам чертежа) — сетки осей и элементы всех выбранных
  файлов рисуются на одной схеме.

Выбор — **сеансовый**, не сохраняется ни на сервере, ни в браузере между
перезагрузками страницы (сбрасывается на дефолт — последний загруженный
файл, все его слои).

### 6.4 Карточка элемента

При выборе элемента (клик) в сайдбаре показывается карточка со всеми
полями, сгруппированными по темам: идентификатор, тип и марка (включая
подтип, если есть), адрес по осям, статус, контракт (только для чтения),
координаты (включая отметку, если есть) — и история статусов с
возможностью удалить отдельную запись. У элементов нового стандарта имён
слоёв (см. 3.7) дополнительно показывается блок «Зоны» — захватка/кран/
стоянка, каждая либо название зоны, либо статус («не определено»/
«требует проверки»/«неприменимо»); у элементов старого стандарта блок не
показывается вовсе. Клик по элементу автоматически переключает сайдбар на
вкладку «Свойства» (см. 6.5), если в этот момент была открыта «Фильтры».

### 6.5 Сайдбар: вкладки «Свойства» и «Фильтры»

Сайдбар разбит на две вкладки:

- **«Свойства»** — раздел «Статусы» (см. ниже) и карточка выбранного
  элемента (6.4).
- **«Фильтры»** — блок «Настройка отображения» (две колонки рядом:
  переключатели видимости зон «Отображение зон» и видимости подписей
  марок по типу элемента «Подписи» — сгруппированы визуально в один
  блок, но остаются независимыми наборами тумблеров) и ниже блок
  «Фильтры» — отбор отображаемых на схеме элементов по характеристикам
  размещения.

**Раздел «Статусы»** — таблица: строки — статусы поставки/монтажа (см.
раздел 4), столбцы — типы элементов, определённые динамически по факту
(`element_type` из загруженных данных — единый русский словарь для
старого и нового стандарта имён слоёв, см. 3.3: `Колонна`/`Ригель`/
`Плита`/`Панель` — какие типы реально встретились в текущей выборке
файлов/слоёв, такие столбцы и показаны), плюс итоговый столбец и итоговая
строка. Считается по элементам, **прошедшим текущий фильтр по
размещению** (ниже) — легенда обновляется при каждом изменении фильтра,
показывает сводку по тому, что видно на схеме прямо сейчас, а не по всей
исходной выборке файлов/слоёв.

**Раздел «Фильтры»** — группы чекбоксов: Захватка,
Кран/Стоянка крана (иерархически — см. ниже), «Отметка (высота)» (высота
от уровня земли, мм), Тип элемента/Подтип/Марка (иерархически, 3
уровня — см. ниже), Статус,
Поставщик/Контракт (иерархически, тем же приёмом, что Кран/Стоянка —
источник значений не элементы схемы, а справочник контрактов, см.
раздел 5; контракт резолвится у элемента через `contract_id`).
Значения в каждой
группе — не зашиты в код, а собраны из полного набора того, что
встречается у элементов и зон текущей выборки, **и всегда показываются
целиком, независимо от состояния других фильтров** (в т.ч. специальное
значение «— не определено —» / «— без отметки —» / «— без подтипа —» —
для элементов без привязки к этой категории, например у старого
стандарта имён слоёв, где зон/отметок/подтипов не бывает вовсе). По
умолчанию в каждой группе отмечены все значения — группа тогда ничего не
отсеивает; снятие галочки с конкретного значения исключает элементы с
этим значением из отображения на схеме. Кнопки «все»/«ничего» у каждой
группы — быстрый сброс/полное исключение; отдельная кнопка «Сбросить все
фильтры» в верхней части раздела — то же самое разом по всем группам.
Итоговое правило — элемент показывается на схеме, только если по
**каждой** группе он не попал под исключённое значение (И между
группами; ИЛИ между отмеченными значениями внутри одной группы — обычная
семантика мультивыбора). Действует поверх выбора файлов/слоёв (тулбар) и
не требует обращения к серверу — все нужные данные уже есть в браузере,
скрытие/показ элементов на схеме мгновенное. Значения внутри группы
отсортированы «по-человечески» — числа внутри названия учитываются как
числа («Стоянка 2» раньше «Стоянка 10»), а не лексикографически.

**Недоступные (disabled), а не скрытые значения** — если при текущей
комбинации фильтров какое-то значение не соответствует ни одному видимому
элементу, его чекбокс не исчезает из формы, а становится серым/
неактивным (клик по нему не действует), но остаётся на месте и снова
становится активным, как только условия изменятся. Раньше список значений
каждой группы физически сужался под текущий каскад — это приводило к
двум реальным багам: (1) снятие галочки с «Колонна» убирало саму
«Колонна» из списка без возможности вернуть без полного сброса фильтров;
(2) стоянки крана целиком пропадали из иерархии, если сам кран оказывался
исключён. При расчёте доступности категории, связанной иерархией с другой
(Кран↔Стоянка крана, Тип элемента↔Подтип), фильтр СВЯЗАННОЙ категории
игнорируется — иначе доступность родителя зависела бы от состояния его
же потомков (тот же порочный круг, что и в багах выше).

**Иерархия «Кран → Стоянка крана», «Тип элемента → Подтип → Марка» и
«Поставщик → Контракт»** — стоянки показываются вложенными под своим
краном (связь между зонами, вычисленная при разборе файла — см. 3.7, «в
свойствах стоянки крана — связь с краном»), подтипы — вложенными под
своим типом элемента, марки — вложенными под своим подтипом (3-й
уровень, без строки поиска — обычный список чекбоксов, как у подтипов;
число уникальных марок сильно разнится по подтипу, от единиц до
нескольких сотен — длинные списки у некоторых подтипов ожидаемы),
контракты — вложенными под своим поставщиком (справочник контрактов,
раздел 5), **всегда полностью, независимо от фильтров** (см. выше). Клик
по чекбоксу родителя (крана, типа или поставщика) ставит/снимает галочки
со всех его потомков разом — у группы Тип/Подтип/Марка каскад с типа
идёт сразу на оба нижних уровня (все подтипы И все их марки), с подтипа —
на его марки. Технически каждый уровень остаётся своей независимой
группой фильтра (см. выше про И/ИЛИ) — вложенность и каскадный клик по
родителю только удобство ввода, на итоговую логику фильтрации не влияют.
Обратное направление тоже работает: включение галочки у ОДНОГО потомка
(например, одной стоянки или одной марки), если его родитель (а для
марки — оба предка, подтип и тип) сейчас выключен, автоматически
включает предка(ов) — но не трогает остальных потомков того же уровня
(иначе включить один дочерний пункт при выключенном родителе было бы
невозможно, не сбросив фильтр вручную).

Список потомков каждого родителя по умолчанию **свёрнут** — видна только
строка родителя (по факту это и есть выбор «всей группы крана» целиком,
как и раньше), рядом стрелка-разворот, если у родителя вообще есть
потомки. Разворот открывает список для выбора конкретных стоянок/
подтипов/контрактов; состояние (какие родители сейчас развёрнуты)
хранится в состоянии интерфейса на время сеанса и переживает
перестроение списка при каждом изменении фильтра, но сбрасывается
кнопкой «Сбросить все фильтры» и при смене чертежа.

Значение фильтра в категориях Захватка/Кран/Стоянка — **id зоны, не её
имя**: имена зон не уникальны глобально (у каждого крана своя нумерация
стоянок — «Стоянка 1» физически существует у каждого крана как отдельная
зона), поэтому сравнение по имени схлопывало бы разные зоны в один пункт
фильтра. Одинаковое имя может корректно встречаться несколько раз в
списке — по разу под каждым краном, которому принадлежит; это не
дубликат, а разные физические зоны с одинаковой подписью.

«Стоянка крана» — не точка, а рабочая зона крана в конкретной позиции:
кран, встав на стоянку N, монтирует ЖБК в пределах этой зоны. Элемент
вполне может физически находиться в рабочей зоне какого-то крана, но не
в контуре ни одной конкретной стоянки внутри неё — это обычный, массовый
случай (для целевого файла — 88% элементов), а не редкое исключение. Для
такого элемента кран, как правило, прекрасно известен — неизвестна
только КОНКРЕТНАЯ стоянка. Поэтому «вне стоянок» — это
**дочерний пункт под своим краном** в той же иерархии, что и обычные
стоянки (а не общий пункт вне иерархии — так было раньше, и это
визуально отрывало такие элементы от их крана).

Единственный случай, когда пункт показывается ВНЕ иерархии, отдельно —
«Кран и стоянка — не определены»: и кран, и стоянка неизвестны
одновременно (редкость, для большинства файлов список пуст и пункт не
показывается вовсе). Отдельно от этого, зона-стоянка, которая при
разборе файла не сопоставилась ни с одним краном (недочёт в самом
чертеже) — попадает под настоящий заголовок «Кран: не определено».

### 6.6 Цвета зон (по крану)

У каждой ИНДИВИДУАЛЬНОЙ зоны категории «Кран» — свой цвет заливки и
обводки на схеме (не общий цвет на всю категорию, как раньше) — её
стоянки окрашиваются тем же цветом (наследуют цвет через связь
«стоянка → кран», см. 6.5/3.7). При первой обработке файла цвет каждому
новому крану назначается автоматически из фиксированной палитры
(циклически, если кранов в файле больше, чем цветов в палитре) — при
повторной обработке того же файла уже назначенный цвет не сбрасывается.
Изменить вручную — «Настройки → Цвета зон» (список кранов по всем
загруженным файлам, `<input type="color">` на каждый). Захватка цвет по
кранам не имеет — раскрашивается по-прежнему одним цветом на категорию.

### 6.7 3D-режим схемы

Переключатель «2D / 3D» в тулбаре — сегментированный контрол с обеими
подписями видимыми одновременно (не залипающая кнопка-тумблер), активный
режим подсвечен. Переключает рабочую область между 2D-схемой (6.1) и
объёмным видом с вращением камеры (Three.js, WebGL) — библиотека
подключена локально (`app/static/vendor/three/`, не CDN) через import
map и подгружается лениво (динамический `import()`) только при первом
включении 3D, а не на каждой загрузке страницы. Второе и последующие
включения — мгновенные (сцена уже построена, просто показывается заново).

Масштабирование колесом мыши/трекпадом — ускоренное относительно
библиотечного значения по умолчанию (`OrbitControls.zoomSpeed = 4`
вместо `1`): сцена оперирует мировыми координатами в мм (десятки-сотни
тысяч единиц), а трекпад Mac шлёт события с очень маленьким `deltaY`
(плавная инерциальная прокрутка) — с дефолтной чувствительностью один
«тик» менял масштаб на доли процента, и приблизить/отдалить модель
требовало очень долгой прокрутки.

**Высота элемента в 3D** — вычисляется, у элемента нет в данных реальной
геометрической высоты (DXF плоский):
- **Колонна** — от своей отметки (`elevation_mm`) до **следующего яруса
  КОЛОНН** (не любого элемента — иначе колонна на нижнем ярусе могла бы
  "увидеть" отметку случайного ригеля-парапета между этажами и вылезти
  заниженной). Список ярусов — уникальные отметки, встречающиеся именно
  у колонн текущей выборки, по возрастанию. Для самой верхней колонны
  (яруса выше нет) — запасной вариант: высота предыдущего пролёта
  (или 3000 мм, если ярус всего один).
- **Плита перекрытия** — фиксированная толщина 300 мм (допущение,
  подтверждено заказчиком) — не зависит от контура, применяется ко
  всему типу целиком, любой подтип/отметка.
- **Ригель/Плита/Панель** — квадратное сечение (допущение, подтверждено
  заказчиком): высота = ширина контура элемента. Ширина считается не по
  габаритному прямоугольнику (bounding box — завышает обе стороны на
  повёрнутых элементах), а из площади и периметра контура по формуле
  шнурков, в предположении, что контур прямоугольный: `S=a·b`,
  `P=2(a+b)` → обе стороны как корни квадратного уравнения, возвращается
  меньшая. Устойчиво к повороту элемента на плане. «Плита перекрытия» —
  отдельный тип от «Плита» (см. 3.7) и под это допущение не подпадает —
  своё правило выше.

Старый стандарт имён слоёв для 3D не поддерживается (в нём нет отметки
и не у всех элементов есть контур) — предполагается, что входные файлы
теперь только нового стандарта (см. 3.7).

**Ориентация плана** — контур элемента/зоны переносится в 3D БЕЗ
инверсии оси Y перед поворотом геометрии в горизонтальную плоскость
(`geometry.rotateX(-90°)` уже даёт нужный перенос "мировая Z = минус
мировая Y элемента" сам по себе). Это не декоративная деталь: у
право-ориентированной (как и весь WebGL/Three.js) системы координат с
осью Y вверх перенос 2D-плана (X вправо, Y вверх на бумаге) в
горизонтальную плоскость X-Z принципиально требует инверсии ОДНОЙ из
осей плана — иначе при взгляде на сцену сверху картинка неизбежно
получается либо зеркальной по одной оси, либо перевёрнутой по другой
(математически недостижимо избежать обоих сразу без инверсии). Была
допущена именно такая ошибка в первой версии (лишний минус на этапе
построения контура вместо использования того, что даёт сам поворот) —
из-за неё план в 3D зеркалился относительно 2D-плана.

**Взаимодействие** — полностью переиспользует функциональность 2D, не
дублирует её: клик по элементу (raycasting) вызывает ту же
`selectElement()` (карточка в сайдбаре, вкладка «Свойства»), двойной
клик/правый клик — то же контекстное меню смены статуса. Фильтр по
размещению (6.5) и подсветка выбранного элемента одинаково действуют в
обоих режимах — переключение 2D/3D не сбрасывает ни выбор, ни фильтры.
При смене чертежа/слоёв (тулбар) 3D-сцена, если она уже была открыта,
пересобирается вместе с 2D; если 3D ни разу не открывали в текущем
сеансе — библиотека не грузится вовсе.

Камера при первом построении сцены автоматически вписывается в охват
текущих данных (аналог «вся схема целиком» у 2D); дальше — свободное
вращение/панорамирование/зум мышью (OrbitControls).

**Зоны (захватка/кран/стоянка) в 3D** — рисуются вместе с элементами,
видимость управляется теми же тумблерами «Зоны» (6.5), что и у 2D:
- **Захватка** — объём НА ВСЮ ВЫСОТУ здания (от нижнего яруса колонн до
  верха верхнего яруса), сильно полупрозрачный (7% непрозрачности, как у
  2D-подложки) — элементы внутри объёма остаются хорошо видны.
- **Кран и Стоянка** — плоские полигоны на уровне земли (не объём —
  привязаны к отметке на плане, а не к высоте здания), собственный цвет
  каждого крана (6.6) и унаследованный его стоянками, как и в 2D.

Зоны не участвуют в raycasting (клик всегда «сквозь» них, реагируют
только элементы) — не мешают выбору элементов, даже если визуально
перекрывают их сверху.

**Граница элемента** (2026-07-17, трижды переделано) — без этого
однотипные примыкающие элементы одного статуса (одинаковая заливка)
визуально сливались в одно пятно без видимой границы между соседями.
Первая версия (`THREE.EdgesGeometry`+`THREE.LineSegments`) оказалась на
практике почти невидима — `THREE.LineBasicMaterial.linewidth` не
работает в большинстве браузеров (WebGL1/ANGLE клэмпит толщину GL-линии
к 1px независимо от заданного значения — известное ограничение, не баг
конкретной реализации), тонкая 1px линия на масштабе всего чертежа
(десятки-сотни метров) визуально теряется. Настоящий "толстый line" в
Three.js требует `Line2`/`LineMaterial` из `examples/jsm/lines/` —
новый сторонний код, нужно отдельное подтверждение по правилу проекта
(см. CLAUDE.md), поэтому выбран путь без нового вендоринга — граница
ОТДЕЛЬНЫЙ МЕШ (`build3DOutlineMesh`), не GL-линия.

Вторая версия (меш границы ШИРЕ основного на 8% от центроида,
`OUTLINE_MARGIN_SCALE`, и НИЖЕ на фиксированные 25мм) провалилась на
реальных данных для примыкающих впритык элементов (плиты перекрытия):
расширенная граница одного элемента заходила на территорию соседа, где
её закрывал уже ЕГО собственный (не уже, а полноразмерный) основной
меш — граница между плитами не появлялась вообще. Плюс оба меша делили
одну и ту же нижнюю Y-координату — мерцание (z-fighting) при взгляде
снизу.

**Текущая (2026-07-19) версия — ролями наоборот**: граница строится по
ИСТИННОМУ контуру и истинной высоте элемента (`build3DOutlineMesh`, без
масштабирования), а ЦВЕТНОЙ (статусный) меш — уже, чем истинный контур,
на `OUTLINE_INNER_SCALE = 0.94` (6% меньше от центроида,
`scaledOutline`), и выше/ниже своей истинной высоты на
`OUTLINE_VERTICAL_MARGIN_MM = 15` мм С ОБЕИХ сторон (не только сверху).
Граница — дочерний объект цветного меша, смещён на `+15мм` по Y
относительно родителя, чтобы совпасть по вертикали с истинным
положением элемента. Эффект: контуры границ соседних элементов сходятся
ровно по истинной общей грани без захода на территорию друг друга (у
любых элементов, включая впритык примыкающие) — граница всегда видна.
Диапазон Y цветного меша охватывает диапазон Y границы на 15мм с ОБЕИХ
сторон при любом ракурсе (включая снизу) — исключает z-fighting.
Цвет границы — затемнённая версия ТОГО ЖЕ статусного цвета
(`darkerColor`, множитель 0.55 на канал, не фиксированный чёрный —
граница читается при любом цвете статуса, включая уже тёмные),
пересчитывается вместе с цветом заливки при каждой смене
статуса/выбора (`update3DElementAppearance`, обновляет
`mesh.userData.outline.material.color`). При очистке сцены геометрия/
материал меша границы освобождаются явно (дочерние объекты не
диспозятся автоматически при диспозе родителя).

Проверено изолированным Node-тестом с мок-стабом THREE.js (8/8
утверждений: охват Y цветным мешом с обеих сторон, истинность размера
контура границы, уменьшенный на 6% размер цветного меша) — живой
браузерной проверки в этой сессии не было (инструмент автоматизации
браузера недоступен), это открытый пробел на момент записи.

**Подсказка при наведении** — если курсор задерживается на одном и том
же элементе дольше 1 секунды (без вращения/панорамирования камеры),
рядом с курсором появляется всплывающая подсказка: тип элемента,
подтип, марка, ID, адрес по осям, отметка. Таймер сбрасывается при
переходе на другой элемент или уход с элемента вовсе — заново отсчитывает
секунду; подсказка сразу скрывается при начале вращения камеры, клике,
открытии контекстного меню или переключении обратно в 2D.

**Постоянные подписи марок** (2026-07-17) — помимо подсказки при
наведении, марка каждого элемента (если она есть) отображается
ПОСТОЯННО прямо над его верхней гранью — `THREE.Sprite` с
canvas-текстурой (билборд, всегда развёрнут к камере автоматически,
ничего не нужно обновлять на каждый кадр). Реализовано без нового
вендоринга стороннего кода — используется только уже провендоренное
ядро Three.js (`Sprite`/`SpriteMaterial`/`CanvasTexture` — его часть);
`CSS2DRenderer`/`TextGeometry` НЕ провендорены и не использовались.
Масштаб подписи — в мировых единицах, опирается на тот же
`baseMarkerRadius`, что задаёт размер 2D-маркеров/подписей (единая
логика между режимами). Видимость управляется ТЕМ ЖЕ переключателем
«Подписи» по типу элемента (6.5), что и в 2D (`state.labelVisibility`,
без отдельного 3D-состояния), и тем же фильтром по размещению (6.5) —
элемент, скрытый фильтром, не показывает подпись и в 3D. Рисуются для
ВСЕХ элементов сразу, без логики скрытия пересечений, которая есть у
2D (заказчик выбрал самый простой вариант для первой итерации) — риск
визуального наложения ниже, чем в 2D: элементы одного следа на разных
ярусах (см. `estimate_marker_radius`, 3.7) физически разнесены по
высоте в 3D, поэтому не совпадают так плотно, как на плоской
2D-проекции.

**Контраст и вторая строка** (2026-07-17) — на canvas-текстуре спрайта,
перед текстом, рисуется полупрозрачная белая подложка (`rgba(255,255,255,
0.72)`, весь холст) — контраст читается на любом цвете элемента под
спрайтом; в 3D, в отличие от 2D SVG, это простая безопасная canvas-
операция, поэтому здесь реализована буквальная подложка, а не только
контур. Цвет текста марки — персональная настройка пользователя (см.
6.1) — canvas "запекается" один раз при создании, поэтому смена цвета в
настройках требует пересборки 3D-сцены (`build3DScene()`, уже дёшево
вызывать по факту), чтобы применилось немедленно. Если у элемента
активна допстрока (партия, см. 5.1, 6.1) — рисуется второй, более
мелкой строкой на том же холсте под маркой; холст и мировой размер
спрайта пропорционально увеличиваются, чтобы сама марка не меняла
видимый размер от наличия/отсутствия второй строки.

## 7. Пользователи и роли

Вход в систему обязателен для любого действия, включая просмотр схемы —
по логину/паролю с серверной сессией (cookie, 30 дней). Три роли:

| Роль | Права |
|---|---|
| `admin` | Полный доступ, включая все настройки |
| `user` | Схема, смена статусов, загрузка чертежей — без доступа к настройкам |
| `view` | Только чтение (включая экспорт), без смены статусов |

Права проверяются не только в интерфейсе (скрытие элементов управления),
но и на уровне API (403 при прямом обращении в обход интерфейса).

**Защита входа** (2026-07-17): `POST /login` ограничен по IP-адресу
клиента — 5 неудачных попыток за 5 минут блокируют дальнейшие попытки с
этого IP (429), счётчик сбрасывается при успешном входе; лимит
in-memory (один процесс `uvicorn`, без внешнего кэша). Блокировка
именно по IP, а не по логину — логины и так публично видны через
`GET /login-users` (см. ниже), блокировка по логину позволила бы
намеренно запереть чужого пользователя, зная только его логин. Cookie
сессии — `httponly` и `samesite=lax` всегда; флаг `secure` — по
переменной окружения `ZHBI_SECURE_COOKIES` (по умолчанию выключен,
деплой сейчас на обычном HTTP внутри локальной сети — см.
`Docs/DEPLOYMENT_WINDOWS.md`, §1.5).

При первой инициализации БД автоматически создаётся пользователь
«Администратор» (`admin`/пустой пароль) — с него начинается настройка
любого нового развёртывания. Смена собственного пароля доступна всем
ролям через меню «Настройки → Сменить пароль» (само меню видно всем
ролям, admin-специфичные пункты внутри скрыты адресно). Тем же
самообслуживанием (`current["role"] != "admin" and current["id"] !=
user_id` → 403) реализован «Настройки → Цвет подписей марок»
(2026-07-17, см. 6.1) — `PATCH /users/{id}/label-color`.

## 8. Настройки (раздел «Настройки», доступен админу)

- **Цвета статусов** — свой цвет заливки маркера на каждый статус.
- **Форма маркеров** — по паре (слой, тип элемента), см. 6.1.
- **Цвета зон** — свой цвет на каждый кран (наследуется его стоянками), см. 6.6.
- **Справочник подтипов** — допустимые подтипы по типу элемента для
  нового стандарта имён слоёв (см. 3.7), список тегов на тип,
  добавление/удаление применяется сразу.
- **Пользователи** — список, создание/редактирование, роль, пароль.
- **Контракты** — список (сгруппированы по контракту, с расшифровкой по
  строкам план/факт/остаток), контракт по умолчанию по типу элемента.
- **Экспорт/импорт настроек проекта** (JSON) — пользователи (включая
  хэш+соль пароля — для переноса на другой сервер без пересоздания
  паролей), цвета статусов, видимость подписей. Импорт — upsert, ничего
  не удаляет молча.
- **Импорт истории статусов из XLS** — перенос истории поставки/монтажа с
  другого сервера/из резервной копии, режимы «дополнить» (пропускать
  дубли) и «заменить» (перезаписать историю сопоставленных элементов).

## 9. Экспорт данных

- **XLS** — два режима: история изменений за период (все записи истории
  с датами) или снимок актуального статуса на выбранную дату. Оба режима
  включают полный набор текущих свойств элемента — идентификаторы, тип и
  подтип, координаты и отметку, адрес по осям, привязку к зонам (Захватка/
  Кран/Стоянка — название зоны или статус «не определено»/«требует
  проверки»/«неприменимо», та же логика резолвинга, что в карточке
  элемента, 6.4) и контракт. В снимке контракт — текущий (`elements.
  contract_id`); в истории — контракт **на момент конкретного события**
  (`status_history.contract_id`), а не текущий, чтобы отчёт корректно
  отражал, что было на самом деле в тот момент.
- **PDF-отчёт** — вся схема целиком (авто-масштаб, альбомная ориентация),
  подписи марок, легенда цветов статусов, шапка с логотипом и названием
  чертежа, дата отчёта (можно указать любую — статусы посчитаются
  актуальными на неё), футер с автоподписью системы и местом для ручной
  подписи (Составил/Проверил/Утвердил).

## 10. Известные ограничения

- Список распознаваемых слоёв DXF старого стандарта (`LAYER_CONFIG`)
  зашит в коде — см. раздел 3.3 и план автоматизации в
  `Docs/backlog.md`. Новый стандарт имён слоёв (3.7) этого ограничения
  не имеет (тип/подтип/отметка разбираются из самого имени слоя), но
  требует, чтобы имя строго следовало формату — при отклонении импорт
  всего файла прерывается, а не пропускает проблемный слой молча.
- Сопоставление элементов между повторными импортами — по
  `(source_file, dxf_handle)`; если DXF пересобран так, что handle у тех
  же физических элементов изменился, вместо обновления создастся новый
  элемент.
- Формат дат в полях `<input type="date">`/`<input type="datetime-local">`
  — по локали браузера/ОС, не принудительно ДД.ММ.ГГГГ (решение
  зафиксировано осознанно, см. `Docs/backlog.md`, четвёртый раунд, п.9).
- Контур (раздел 3.6/6.1) сохраняется только для элементов из
  `LWPOLYLINE`; для элементов из `INSERT`-блоков «настоящая форма» на
  схеме недоступна.

## 11. Порядок ведения документа

Этот файл поддерживается в актуальном состоянии при каждом функциональном
изменении системы — как часть обычного рабочего процесса, без отдельного
запроса. Прошлые решения и мотивация «почему сделано именно так» не
переносятся сюда целиком — для этого есть `Docs/backlog.md`; здесь
остаётся только актуальное описание того, как система работает сейчас.

Принципы проектирования

Данные и код живут отдельно

Код — внутри Docker-образа и заменяется при обновлении; данные — обычные папки тома, пересборка образа их не касается.

Загрузка в два шага

Любой импорт сначала анализирует файл и показывает сводку расхождений, и только после подтверждения применяется. Перед записью делается копия.

Релиз только добавляет

Обработки данных новой версии — записи реестра: идемпотентны, выполняются сами при старте после копии базы, упавшая не роняет запуск и повторяется кнопкой.

Права — данные, а не код

Разрешения ролей хранятся в базе, перечень разделов — в одном реестре. Интерфейс прав не выводит, а спрашивает сервер.

Тип учёта — применимость, не право

Объект ЖБИ или МФР определяет, какие разделы вообще имеют смысл; это действует и на администратора.

Одно место для каждого определения

Реестр разделов прав, реестр событий журнала, описание схемы БД — единые; экран, выгрузка и генератор читают один источник.

Офлайн по умолчанию

Все сторонние библиотеки вендорены; карта работает на локальной подложке; облачные подключения — только по отдельному решению.

Разработка на обезличенных данных

Для отладки используется обезличенная копия базы; боевые данные не покидают корпоративный контур.

Безопасность

  • Вход обязателен для любого действия, включая просмотр; сессия хранится на сервере (httponly-cookie).
  • Пароли хранятся только как солёные хэши PBKDF2; доменный вход проверяется контроллером домена.
  • Права проверяются на сервере по разделу и объекту; роли независимы, разрешения складываются.
  • Все значимые действия и ошибки (сервера и браузера) пишутся в журнал с категориями.
  • Политика безопасности контента (CSP), лимиты размера загрузок, обработчик ошибок без раскрытия внутренностей.
  • ИИ-помощник читает только разрешённый снимок данных в памяти; SQL модели — только чтение под авторизатором.
  • Резервные копии снимаются автоматически перед обновлением, импортом, заменой базы и уборкой.

Развёртывание и обновление

  • Код попадает на серверы только пушем в ветки репозитория: пайплайн собирает образ, кладёт в реестр и перезапускает контейнер.
  • Два контура: тестовый и рабочий; перенос данных между ними — обменом выбранными разделами или переносом базы целиком.
  • Перед выкладкой миграции прогоняются «вхолостую» на копии базы того сервера, куда выкатывается версия.
  • Откат — возврат на предыдущий образ и восстановление базы из копии; порядок описан в руководстве по развёртыванию.

Два интерфейса

Рядом существуют интерфейс V1 (рабочий, весь функционал) и V2 (полный интерфейс нового поколения со всеми экранами сервиса). Пользователь переключается между ними в настройках, при необходимости есть аварийный возврат на V1. Каждое изменение интерфейса вносится в оба, схема в V2 встроена как режим «только сцена» движка V1 — отрисовка одна, оболочка своя.

Задача: реализовать в zhbi-tool сущность «Запланированная работа по блоку»
(ЗР) для объектов МФР по заданию `Docs/block-works-schedule-task.md`. Это
единственный источник требований; ниже — решения пользователя (уже внесены
в задание, здесь для акцента), порядок работы и жёсткие ограничения.

## 1. Решения пользователя (не пересматривать, не переспрашивать)

- **План блока явный.** У ненастроенного блока перечень ЗР ПУСТОЙ, никакой
  материализации «всех операций». Всюду, где сейчас действует правило
  «`blocks.work_types_configured_at IS NULL` ⇒ все операции BLOCK_UNITS»
  (`work_fact.block_settings`, `_op_included_percents`,
  `board_block_values`, `used_planning_tracks`, панель блока, «Шахматка»),
  его убрать: источник состава — только `block_works`. Явные пары
  `block_work_types` переносятся 1:1. Для строк `work_fact_items`, чьей пары
  нет (факт зафиксирован, операцию явно не выбирали), ЗР создаётся
  обработкой релиза с `note = 'восстановлена по факту'` — историю не терять.
- **Сроки только у ЗР** (блок × операция `эт/сек`/`кв.эт/сек`). Секция,
  объект и вид работ целиком — АГРЕГАТЫ по ЗР: план = min(`plan_start`) /
  max(`plan_end`), прогноз = min/max `forecast_*`, факт = среднее процентов,
  статус — по порогам от среднего; ЗР без дат в min/max не участвуют.
  Операции `сек`/`компл` и таблицу `work_progress` НЕ трогать.
- **Версии актуализации накапливаются**, как у ЖБИ (`schedule_versions`):
  таблица `block_work_forecasts`, текущие `forecast_start`/`forecast_end`
  денормализованы на `block_works`. Источник — ТОЛЬКО ручной ввод (карточка
  ЗР, групповая форма «Сроки»). Пересчёт по факту и импорт из xlsx НЕ
  делать — вне области, появятся отдельной задачей.
- **Ответственный за факт — учётная запись** (`created_by`/`updated_by`
  документа и строки). Поля `responsible_id` нет, справочник физлиц не
  подключать.
- **Один промпт на всё**: этапы ниже идут подряд; после каждого — коммит и
  короткий отчёт пользователю в чате (что сделано, чем проверено, что
  осталось).

## 2. Вопросы, которые НАДО задать пользователю перед этапом 4

Через AskUserQuestion, с вариантами и рекомендацией, не решать самому:

1. Хранить ли построчную историю правок документа факта
   (`work_fact_item_history`), и разрешать ли удаление документа — кому.
2. Снятие операции с блока при наличии факта или дат — запрет с текстом или
   мягкая пометка `retired_at` с сохранением истории.

Любое другое разночтение в требованиях — тоже вопрос пользователю (стоячая
инструкция `CLAUDE.md`), а не молчаливое допущение.

## 3. Этапы

Границы и проверка — §10 задания.

**Этап 1 — модель.** `block_works` (`id, object_id, block_id, work_type_id,
plan_start, plan_end, forecast_start, forecast_end, forecast_at,
forecast_by, note, created_at/by, updated_at/by`, UNIQUE(block_id,
work_type_id)), `block_work_forecasts`, `work_fact_items.block_work_id`.
Миграция в `app/db.py` (SQLite не добавляет PK — пересоздание таблицы с
переносом строк), две идемпотентные обработки в `app/release_tasks.py`
(перенос пар + восстановление по факту; заполнение `block_work_id`),
описания полей в `app/db_schema_doc.py`, перегенерировать
`Docs/db-schema.drawio` (`scripts/gen_db_schema_drawio.py`),
`app/import_reset.py` чистит новые таблицы, `app/work_fact.py` переведён на
`block_works`, «Настройки» блока = состав работ (создаёт/удаляет ЗР).
Проверка: `scripts/dry_run_migration.py` на копии; скриптом в scratchpad
снять `board_block_values` и текущие проценты ДО и ПОСЛЕ — для явно
настроенных блоков должны совпасть; блоки без настройки после миграции
пусты (это ожидаемо, сказать пользователю явно).

**Этап 2 — сроки.** Новый `app/block_works.py`: CRUD, версии прогноза,
производные §4 задания в одной функции `derive(...)`, агрегаты по
секции/объекту/узлу дерева. Эндпоинты §5 задания (без import/recalc).
Карточка ЗР (модалка), правка обеих пар дат, групповая форма «Сроки»
(сдвиг на N дней / значение / «прогноз = план» для не начатых). Строка
операции в карточке блока — план/прогноз/отклонение второй строкой; шапка
карточки блока и узлы дерева — агрегаты. Коды журнала в
`app/activity_actions.py`: `block_work_add`, `block_work_remove`,
`block_work_plan_set`, `block_work_forecast_set`, `block_work_bulk_edit`
(без подписи и категории pre-commit не пустит).

**Этап 3 — фильтры и «Шахматка».** Вкладка «Фильтры»: группы «Сроки»
(в графике / отстаёт / просрочена / не начата в срок / без сроков) и
«Период по плану / по прогнозу»; «Сбросить все фильтры» их чистит. Вкладка
«Вид»: режим раскраски доски «по выполнению» / «по срокам» (худший признак
среди ЗР доски у блока), «±N дн» в подписи на грани — 2D и 3D одной
раскладкой (`mfrChessLabelLayout`, `buildMfrChessLabelMesh`), вторая
палитра `MFR_CHESS_COLORS_3D`, легенда по режиму; `board_block_values`
отдаёт обе сводки одним запросом.

**Этап 4 — документы факта** (после ответов п.2). `updated_at`/`updated_by`
на строке `work_fact_items`, «кто менял строку» в подсказке истории
(`op_fact_history`, `#bp-history-tooltip`), история правок и/или удаление —
как решит пользователь. Документы факта в общий журнал действий по-прежнему
НЕ пишут (решение 2026-09-02).

**Этап 5 — отчёты, права, обучение.** «Учёт по блокам: статусы» —
переключатель показа процент / план / прогноз / отклонение (правка только в
режиме «процент») и подсказка «есть N %, по плану должно быть M %». Новый
отчёт «График работ по блокам» (`app/report_block_schedule.py`,
`POST /reports/block-schedule` + `.xlsx`/`.pdf`): группировка через
`createGroupChooser`, итоги по группе, вид «Гант» по образцу
`app/schedule_gantt_export.py` (дерево своё, сетку недель переиспользовать).
Разделы `report_block_schedule` и `report_block_status` в `app/features.py`
(в `_ТОЛЬКО_МФР`), справка в `app/report_help.py` (для `block_status` её
тоже нет), учебные блоки в `app/training_content.py`; блок `work_progress`
там переписать — он описывает клик-цикл и закладку «Статусы», которых нет.

**Этап 6 — документация.** `Docs/TZ.md` §3в (подраздел о проценте по
блоку — под ЗР), `Docs/block-accounting.md` новый §13, `Docs/DECISIONS.md`
(три инварианта из §9 задания), `Docs/MAP.md`, `CLAUDE.md` одной строкой,
`Docs/OPEN.md` — снять пункт о задании. Запись в `app/changelog.py` — ТОЛЬКО
после согласования текста с пользователем.

## 4. Ограничения проекта

- Комментарии, докстринги, ответы пользователю — по-русски.
- Никакого нового стороннего кода без явного подтверждения.
- Обработка данных для новой версии — в `app/release_tasks.py`, не скриптом.
- Новое действие журнала = строка в `app/activity_actions.py`.
- Вставляя функции в `app/main.py` перед `on_startup`, не отобрать
  `@app.on_event("startup")` (страж при импорте).
- Проверка UI — живой браузер на копии; в 3D навигация через
  `javascript_tool`. Перед коммитом: `scripts/check_undefined_names.py`,
  `scripts/check_activity_actions.py`, `scripts/check_training_coverage.py`,
  `scripts/audit_endpoints.py`.
- После обкатки миграции на копии напомнить пользователю порядок для
  боевой базы с командами: `scripts/dry_run_migration.py` на боевом файле →
  бэкап → старт `zhbi-server` → `.venv/bin/python scripts/anonymize_db.py`.

# Чтение векторных листов КЖИ без нейросети: прототип и выводы (2026-10-04)

Код — `scripts/prototypes/vector_ocr/` (README там же). Прототип не меняет `app/calc/*` и не подключён к приложению. Все цифры ниже
получены на реальных альбомах `data/calc/assets/sources/doc01…doc20.pdf` (только чтение), воспроизводятся командами из последнего раздела.

## 1. Кратко

- Листы чертежей во всех открывающихся альбомах — **вектор без текстового слоя** (растровых нет): буквы и цифры — наборы штрихов.
  Шрифт один (курсив CAD, наклон ≈10°), но цифры в размерах набраны **двумя гарнитурами** (основная — doc01…; вторая — весь doc14,
  часть doc12). Реальные текстовые слои есть только у пояснительных и титульных страниц (doc16/17 целиком, первые страницы нескольких альбомов).
- **Числа размеров** код читает надёжно там, где они набраны основной гарнитурой, и проверяет каждое по геометрии (засечки × масштаб вида).
  На 59 случайных листах 17 альбомов: по геометрии видно 2679 размеров, прочитано 2376 (**89%**), согласовано с геометрией 2057 (**87% от
  прочитанных**; случайное совпадение, по нулевой модели, ≈17%, т. е. «чистая» доля ≈84%).
- **Спецификация** (поз., обозначение, наименование, кол., масса) разбирается по линиям рамки: заголовок «Поз.» найден на 48 из 59 листов,
  строки разобраны на 45; на трёх листах, проверенных по картинке, позиция, количество и масса — **23 из 23 строк**, наименование — 22 из 23
  (ошибка в марке с цифрами).
- Сверка с готовыми моделями поставщика (26 листов, 13 альбомов): класс бетона **26/26**, объём бетона **23/26**, состав изделия
  (позиции спецификации ↔ `components` каталога) **96/113 = 85%**.
- Код **не строит** геометрию. Он снимает с Qwen самую дорогую и хуже всего контролируемую часть — чтение цифр и спецификации — и может
  проверять цитаты Qwen. Для подписей, связей «размер ↔ элемент», форм гибов и других гарнитур нужна гибридная схема (раздел 7).

## 2. Что за листы (опрос 76 страниц, по 4 из каждого альбома)

- PDF: 19 альбомов, doc18 не открывается (pdfium). Страницы A4–A0 (595×842 … 4209×1191 pt); почти во всех альбомах (19 из 19 открывающихся) страницы с `/Rotate` 90/270 —
  без приведения штрихов к экранным координатам текст оказывается «повёрнутым» (в прототипе это сделано в `segments()`).
- Чертёжный лист: от 1,5 до 72 тыс. объектов-путей, 0 изображений, 1–5 «текстовых» объектов (штамп/формат). Текстовый слой
  (≥200 символов) — у 15 из 76 страниц (doc16 и doc17 целиком, титулы и пояснительные страницы doc05/07/08/10/11/14).
- Лист может быть напечатан с уменьшением: A2→A3 с коэффициентом **0,70** (doc04 стр. 100: 72 размера согласуются при k=0,70 и только 10
  при k=1), 0,705 (doc19 стр. 106: 17 против 3). Калибровка k — в `analyze.calibrate` (кандидаты вокруг форматов ISO, k≠1 принимается
  только при выигрыше ≥5 размеров и ≥15%: свободная подгонка k давала ложные «улучшения»).
- Масштабы видов на одном листе разные (1:10, 1:20, 1:50 на doc01 стр. 270) — определяются сами по кластерам «значение / интервал»;
  на doc06 стр. 109 справа 1:10, а слева отношение «значение / интервал» разбросано 11,5–13,7 (нестандартный масштаб или не те интервалы — не разобрано).

## 3. Что реализовано

1. **Символы и цифры** (`vector_ocr.py`): связные штрихи → символ; цифры 0–9 по растровым эталонам (повороты 0/90/270; «1» в любом повороте);
   слова-числа; проверка по засечкам (штрихи ≈45°, 3–10 pt) слева и справа от числа и по стандартному масштабу, допуск ±0,8 pt (1 pt = 0,3528 мм).
2. **Текст** (`glyphs.py`, `textcells.py`): строки текста по цепочке символов; расшатка курсива (сдвиг x на 0,176·y) — после неё стойки букв
   вертикальны, а фрагменты одной буквы («к», «н», «й», «ы» = «ь» + «|») склеиваются по перекрытию по x; растр ячейки в системе строки (база и
   высота прописной = 1). Высота строки определяется по общему верху ≥2 символов; для строк из одних строчных пробуются две гипотезы.
   Мелкие знаки («.», «,») присоединяются к строке отдельно, иначе склеиваются с соседней цифрой.
3. **Эталоны букв** (`train_font.py`, `font_protos.json`: 302 экземпляра, 69 меток): самообучение по словарю типовых строк — строка листа принимается,
   если число ячеек равно числу символов и распознавание ≥0,6 похоже на словарную строку; принятые экземпляры пополняют эталоны. Метрика
   сходства — мягкий Жаккар по размытым растрам (средняя абсолютная разность тонких линий не отличала «а», «о», «с», «е»).
4. **Слова и обозначения** (`lexicon.py`): привязка слов к словарю с дешёвой заменой похожих начертаний (Б/В, а/з, К/Ж…), шифр «77/113/114-Р-КЖ…».
5. **Таблицы** (`tables.py`): рамка символа = ближайшие линии слева/справа/сверху/снизу, перекрывающие его центр (работает и с объединёнными ячейками);
   спецификация — по ролям столбцов (по тексту заголовка: «Поз.», «Обозначение», «Наименование», «Кол.», «Масса ед.»…); лишние столбцы (рамка листа) пропускаются.
6. **Оценка** (`evaluate.py`, `analyze.py`): по каждому листу — размеры по геометрии (независимо от чтения), прочитанные, согласованные, нулевая
   модель (числа перемешаны между теми же интервалами), причины сбоев, внутренняя согласованность спецификации.
7. **Сверка с моделями** (`models_ref.py`, `compare_models.py`): лист ↔ модель по `source.id` + `source.productPage`; сравниваются класс и объём бетона,
   состав (`components`), габариты (`solidModel.bounds`).

## 4. Результаты

### 4.1. Символы и текст (шаг 1)

Эталоны есть для 78 символов (408 экземпляров): все строчные кириллицы, кроме «ё» (и «ы» собирается из «ь» и «|»); заглавные кроме «Е», «Ё», «Ш», «Щ», «Ъ», «Ы», «Ь», «Ю»;
цифры, «. , - / = ( ) Ø №», латинская «L». Недостающие заглавные в выборке из 192 листов не встречаются вообще (искались по шаблонам слов), собрать их не из чего. Для 21 символа экземпляров меньше трёх.
Добор шёл по кластерам нераспознанных ячеек (`unknown_cells.py`: 29 587 ячеек со 192 листов, 5321 из них внутри слов; кластеры размечены по контексту читаемых соседних букв, фрагменты вроде «\», «/» отброшены).
Проверка на **28 листах вне сборки эталонов** (по 2 на альбом): нераспознанных букв внутри слов было 372 из 15 850 (2,3%), стало 127 из 16 159 (**0,8%**).
Проверка на **неучаствовавшем в обучении листе** (doc06 стр. 59, надписи и штамп): «Данный лист смотреть совместно с листом 46.», «Вид А», «Разраб.»,
«Масштаб», «Масса», дата «14.01.26», «Вид А, сечения 2-2, 3-3 к ригелю 2Р17.2» — без единой ошибки; ошибки: буква без эталона («Я» в «Яргеева» → «Н») и текст вне таблицы
«ГОСТ 14098-2014-С23-Мэ», прочитанный как «ГОсТ 14798-3014-С23-Мз» (цифры вне таблицы читает буквенный классификатор: 0→7, 2→3; «э»→«з», регистр «С/с»). Читается и свободный текст технических требований («Лестничные балки изготовить в соответствии с требованиями
технических условий по рабочим чертежам»), но с ошибками на цифрах (2→3, 6→8, 0→7): в таблицах цифры поэтому читаются классификатором цифр, а не буквенным; для текста вне таблиц это остаётся резервом.

Спецификация (три листа, проверено по картинке): doc01 стр. 270 — 10 из 10 строк (поз., кол., масса, наименование; «Труба 50х5 ГОСТ 32678-2014 L=900»,
«Закладная деталь ЗД17»…), doc04 стр. 100 — 6 из 6 по поз./кол./массе, наименование 5 из 6 («8КП84» прочиталось как «8КПв4»: в/8 в середине марки),
doc14 стр. 7 — 7 из 7 по всем полям. Столбец «Обозначение» (шифр и лист сборки): 15 из 17; типичная ошибка — «0» внутри «л.206» как «й», «КЖ» как «·».
Общая внутренняя согласованность на 45 разобранных спецификациях (285 строк): количество — целое в 237 строках (83%), масса вида «12,34» — в 207 (73%),
позиции идут подряд на 31 из 45 листов. Это формат, не правильность; пропуски — в основном мелкие цифры массы и разорванные «,».

## 5. Где ломается (причины с числами)

По 319 несогласованным размерам (из 2376 прочитанных):

| Причина | Доля | Что это |
| --- | ---: | --- |
| `span` — интервал не тот | 55% (176) | число стоит вне засечек (малые размеры с выносом), цепочка из нескольких размеров на одной линии, интервал взят по соседней паре засечек, вид с разрывом (зигзаг) — размер не в масштабе (doc14: 3040, 5360) |
| `read` — цифры прочитаны неверно | 25% (79) | мелкий шрифт, слипание цифр, непрочитанная «1» (2310 → 230) |
| `chain` — слитое число | 20% (64) | «200х3=600», «100х21=2100» читаются как одно число «2003600»: «х» и «=» не попадают в слово |

Помимо размеров: слэш «/» и «×» в шифрах (читается точкой-заглушкой, шифр восстанавливается регулярным выражением); регистр у букв с одинаковой формой
(с/С, о/О, х/Х, ж/Ж) — решается высотой относительно строки, но на строках из одних строчных ошибается; марки со смешанными цифрами и буквами
(«8КП84», «ЗД1»/«3Д1»); буквы без эталонов.

## 6. Правила сборки геометрии по видам, которые нужны дальше

Эти правила — то, чего в прототипе нет и без чего «код вместо Qwen» невозможен:

1. **Вид как объект.** Найти вид (рамка/кластер штрихов + подпись «Вид А», «1-1», «2-2»), определить его масштаб по кластеру отношений «значение / интервал»
   и перевести штрихи вида в миллиметры. Это ключевое: после калибровки масштаба вида **любой штрих — уже миллиметровая геометрия**, а прочитанные числа
   работают как проверка, а не как источник координат.
2. **Контур бетона**: внешняя замкнутая ломаная вида (по толщине линии и цвету; код сейчас их не использует — pdfium отдаёт ширину и цвет штриха),
   габариты — сверка с размерными цепочками по краям.
3. **Размерные цепочки**: «200х3=600» (читать «х» и «=»), последовательные интервалы между засечками, общий итог цепочки = сумме; размеры вне засечек
   (выносные линии) и размеры на разорванных видах — помечать как не проверяемые по масштабу.
4. **Закладные, трубы, петли**: стандартные символы (прямоугольник с диагональю, круг с крестом, дуга петли); их положение — из пересечения выносных/осевых.
5. **Выноски позиций**: номер в кружке/на полке на линии-выноске → геометрический объект; связывает строки спецификации с объектами вида.
6. **Арматура**: стержни — толстые линии/цвет (на doc06 стр. 59 арматура синяя и пурпурная), сетки/каркасы — повторения с шагом «100х21»; формы гибов — по
   размерным цепям; число и шаг — из спецификации и «ш. 300мм».
7. **Сечения**: ссылка вида «1—1» ↔ сечение на листе; привязка сечения к виду по стрелкам и осям.
8. **Классификация листа**: чертёж / таблица / оглавление / пояснительная записка (в выборке 5 листов без размеров, оглавление — doc14 стр. 5).

## 7. Код против Qwen, гибридная схема

Что делает нейросетевой конвейер (`app/calc/recovery.py`, `recovery_schema.py`; состояние `main` на 2026-10-04, коммит 9ffab06): стадия чтения — несколько запросов
к Qwen на лист: «общий вид» (штамп, спецификация и ведомости, габариты, марки; до 60 фактов) и фрагменты листа (числа на размерных линиях, позиции, марки; до 80 фактов
на фрагмент); результат — `PageReading` (`Fact`: `subject`, `property`, `value`, `unit`, цитата `quote`, `bbox` в долях полного листа); оборванные ответы (лимит токенов,
зацикливание) обрабатываются спасением фактов из частичного ответа. Стадия сборки — Qwen строит `GeometryDraft` (компоненты, объёмы с профилем в базисе u/v/direction,
стержни); `compile_draft` (`recovery_geometry.py`) проверяет только то, что можно проверить кодом: факт с таким id существует и `value` не пусто, ортонормированность
базиса, невырожденность контура, отверстия внутри контура, длина стержня против спецификации, количество против `expectedCount`, покрытие. Достоверность самой цитаты и
значения относительно листа **не проверяется** — именно её может проверять код. Запросы «числа на размерных линиях» и «спецификация и ведомости» — это ровно то, что
прототип делает без нейросети для векторных листов; обрывы и зацикливание ответа — класс сбоев, которого у кода нет.

| Часть конвейера | Может ли код | Замечание |
| --- | --- | --- |
| Числа размеров с bbox | да, основной гарнитурой надёжно | прочитано 89% размеров, видимых по геометрии, из них 87% согласованы; остальное — дообучение гарнитур, правила цепочек и выносов; в формате `Fact` (value, bbox, quote = «как написано») |
| Спецификация (поз., обозначение, наименование, кол., масса) | да | структура по рамке надёжна; наименования — со словарём; марки со смешанными символами — с проверкой по каталогу |
| Проверка цитат Qwen | да, **это самое ценное** | сравнить `value` Qwen с числом, прочитанным кодом в его `bbox`; расхождение → предупреждение в QA вместо слепого доверия |
| Метрическая геометрия (контур, положение элементов) | потенциально, после раздела 6 | не сделано; даёт геометрию без галлюцинаций, но дорога |
| Подписи видов/сечений, названия деталей, ссылки на другие листы | нет (пока) | один шрифт, но много слов; словарь без нейросети покроет типовые, нетиповые — Qwen |
| Связи «размер ↔ элемент», смысл размеров, формы гибов | нет | нужны семантика и знания о конструкции |
| Листы с другой гарнитурой/сканы | с оговорками | каждая гарнитура — 1–2 часа разметки или самообучение; для растров код бесполезен |
| Неоднозначности и «неразборчиво» | нет | остаются Qwen и человеку |

**Предлагаемая схема.** (1) код читает лист и отдаёт список фактов-чисел (с bbox, интервалом, масштабом вида, флагом «согласовано с геометрией») и таблицу
спецификации; (2) Qwen получает их в промпте и читает только подписи, связи и неоднозначности — это сокращает вход и объём фактов в `PageReading` (мелкие цифры при 1400 px — вероятный источник ошибок чтения Qwen; точность Qwen здесь не измерялась,
для неё есть `scripts/compare_candidate.py`); (3) QA сверяет значения Qwen с кодом, а не только с самим собой; (4) `compile_draft`
получает независимое основание для `expectedCount` и `lengthMm` — из спецификации, прочитанной кодом. Сделанная часть даёт данные для (3) и (4), но интерфейс (перевод pt в доли листа, формат `Fact`) не написан; (2) требует
правки промпта и схемы (`app/calc` в этой работе не менялся).

## 8. Трудоёмкость (грубая, человеко-дни одного разработчика)

| Работа | Оценка | Условие |
| --- | ---: | --- |
| Довести чтение чисел и спецификации до модуля с интерфейсом `Fact`/`PageReading`, bbox в координатах листа, ускорение классификатора, тесты на 100+ листах | 8–12 | основная и вторая гарнитуры |
| Цепочки, выносы, разорванные виды, «х» и «=»; поднять согласие размеров с 87% до 92–95% | 5–8 | на тех же альбомах |
| Дообучение гарнитур/букв по всем альбомам (сделано для doc12, doc14 и ≈30 букв; остаются «7» во второй гарнитуре и проверка остальных альбомов), словарь по реальной лексике | 3–5 | автоматизируемо, постоянная поддержка |
| Проверка цитат Qwen в QA (раздел 7, п. 3) | 3–4 | после первого пункта |
| Правила видов (раздел 6, п. 1–5, 8): вид, масштаб вида, контур бетона, закладные/трубы/петли, выноски | 25–40 | высокий риск: форма символов по альбомам |
| Арматура по цвету/толщине, шаги, гибы по цепям (п. 6–7) | 30–50 | риск высокий; полная замена Qwen в сборке — не цель |

Оценка — нижняя граница: опыт показывает, что каждая новая гарнитура/альбом открывает новый класс исключений (разрывы, нестандартные k, листы
с несколькими масштабами).

## 9. Оговорки

- «Согласовано с геометрией» — самосогласованность, не эталон: число и интервал совпали в допуске ±0,8 pt при стандартном масштабе; случайные совпадения ≈17%.
  Эталонов «человека» немного: три спецификации и надписи одного листа, проверенные по картинке.
- Часть эталонов цифр и букв размечена вручную по контактным листам (порядка 1–2 часов); словарь строк для самообучения составлен по этим же листам.
  Обобщение проверено на неучаствовавших листах (doc06 стр. 59, спецификация doc14 стр. 7), но малой выборкой.
- Свойства листов и модели каталога (`source.productPage`) считаются верными; расхождений каталога с листом специально не искали.
- Данные заказчика в git не добавлялись: в репозитории только растры символов и код; файлы результатов `*_last.json` игнорируются.

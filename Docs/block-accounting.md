# Учёт работ по блокам «этаж + секция»

Статус: **первая версия реализована** (2026-08-25, `Docs/TZ.md` §3в) —
модель данных, ручной ввод секций/этажей, блоки, загрузчик справочника
видов работ, экран простановки статусов. Источник требований — два
документа заказчика: «WBS МФР типовой» (типовая структура работ) и
«Концепция автоматизации календарного планирования v3.1» (MS Project + VBA).

**Что реализовано.** Секции/этажи объекта — ручной ввод (`app/blocks.py`,
`POST/PATCH/DELETE /objects/{id}/sections`, `/levels`), пишет в те же
`object_sections`/`object_levels`, что и Revit-импорт (§7 ниже уточнён:
источник — «выгрузка Revit ИЛИ ручной ввод», оба пишут в одни таблицы и
сливаются по коду секции/номеру этажа). Блоки — явные пары, не декартово
произведение (`blocks`, `app/blocks.py`). Справочник видов работ —
двухфазный xlsx-загрузчик (`app/work_types_import.py`), ключ записи путь
по дереву, ловушки формата из §4 ниже обработаны (последняя — оба
обозначения глубины узла — найдена и закрыта 2026-09-02 на реальном файле
«WBS МФР типовой», раньше проверялась синтетикой, где ловушка не
воспроизводилась). Статусы — `work_progress`
(`app/work_progress.py`), экран «Действия → Документы → Учёт по блокам».
Для операций «эт/сек» этот 3-статусный клик-цикл заменён процентом
(2026-09-02, живой запрос пользователя) — см. §8: отбор операций для
блока и отчёты о фактическом выполнении, `app/work_fact.py`, панель блока
в «Модели МФР». Колонка «Трек планирования» в файле справочника и
переосмысление «Шахматки» досками-по-треку, а также добавление «кв.эт/сек»
в те же BLOCK_UNITS, что «эт/сек» (2026-09-04, живой запрос пользователя)
— см. §4 и конец §8.

**Что НЕ реализовано, сознательно.** Квартиры (`object_flats`, единица
`кв.эт/сек`) — таблица в схеме есть, но заполняется только выгрузкой Revit
Rooms; ручного ввода нет, и у объекта без модели заводить квартиры не из
чего. Статус операций «кв.эт/сек» это НЕ блокирует (2026-09-04) — их
процент вводится на БЛОК целиком, тем же механизмом, что «эт/сек», без
разбивки по отдельным квартирам (задел на будущее — своей геометрии у
квартиры в БД тоже нет, дробить её сейчас не на чем); `object_flats`
самостоятельно при этом по-прежнему не используется. Единицы вне
блочного контура (`шт`, `м2`, `м3`, `т`, `пог.м`, `опора`) в дереве
показываются, статус на них не ставится — это исходное
решение §2, не пробел реализации.

## 1. Что это и чем отличается от учёта сборного ЖБИ

**Отдельная ветка варианта учёта.** Существующий контур — поштучный учёт
сборных ЖБИ-изделий: марка, контракт, поставка, монтаж, история статусов.
Новый контур — учёт ВИДОВ РАБОТ на блоках здания:

> вид работ × блок (этаж + секция) → **План / В работе / Выполнено**

Контуры сосуществуют и **не влияют друг на друга**. Это инвариант, а не
временное упрощение:

* контур блоков не пишет в `elements`, `element_status_history`, контракты
  и график поставки — и не читает их как источник статуса;
* статус блока **ставит человек**, он не выводится из состояния элементов;
  «Выполнено» — это приёмка, а не арифметика по изделиям;
* общий у двух контуров только Объект.

Инструменты простановки статуса разрабатываются позже — сейчас
проектируется модель данных и загрузка входных справочников.

## 2. Откуда взялась гранулярность

Колонка «Единицы измерения» в WBS — это объявление гранулярности учёта.
По 134 операциям и 17 вехам:

| Единица | Операций | К чему привязан статус |
|---|---|---|
| `эт/сек` | 61 | блок: секция + этаж |
| `компл` | 23 | объект целиком |
| `шт` | 16 | вне блочного контура |
| `сек` | 10 | секция целиком |
| `м2`, `м3`, `т`, `пог.м`, `опора` | 16 | вне блочного контура |
| `кв.эт/сек` | 8 | квартира |
| нет единицы | 10 | вехи «Готовность к ПНИ» |

Разделы, живущие в блоках: внутренние инженерные системы (28 операций в
`эт/сек`), фасады (9), каменная кладка (7), отделочные работы (7 + 8 в
`кв.эт/сек`), заполнение дверных проёмов (4), монолитные и сборные Ж/Б
конструкции выше нуля (3), светопрозрачные конструкции (2),
металлоконструкции (1).

Важное следствие: **монолит выше нуля меряется в `эт/сек`, а не в
кубометрах** (операции 160-02-01…03). Поэтому отдельные статусные цепочки
монолита (опалубка → армирование → бетонирование → распалубка) не нужны —
достаточно трёх статусов на блоке.

## 3. Сущности

| Сущность | Содержание | Источник |
|---|---|---|
| `sections` | секция объекта: имя, порядок | выгрузка Revit (общий параметр `MCY_Секция`), правка вручную |
| `levels` | уровень: имя, отметка, порядок | выгрузка Revit (Levels) |
| `blocks` | пара (секция, этаж) | порождается из встреченного в модели |
| (геометрия блока) | параллелепипед: оси здания × отметки этажа, опционально | только у объектов с осями из Revit — `Docs/TZ.md`, «Геометрия блока» |
| `apartments` | квартира: номер, секция, этаж, площадь | выгрузка Revit (помещения, Rooms) |
| `work_types` | справочник видов работ | внешний xlsx, перезагружаемый |
| `work_progress` | статус вида работ на привязке | ставит человек |

**Секция — новая сущность.** Сейчас у элемента есть Захватка, Кран,
Стоянка, Этаж; секции нет ни у нас, ни в карте полей MS Project заказчика
(Text1 = Захватка, Text2 = Кран, Text3 = Стоянка, Text4 = Этаж). Захватка
секцией не является и её не заменяет.

**Но в модели Revit она уже есть.** Вычитано из файла КР 2026-08-10: у
заказчика заведено семейство общих параметров `MCY_*`, и среди них
`MCY_Секция`, `MCY_Этаж`, `MCY_Корпус`, `MCY_Тип этажа` (Автостоянка,
1 этаж, Типовой этаж, Кровля), `MCY_Часть здания` — они используются как
единый адресный набор. Договариваться о том, чем задавать секцию, не
нужно; проверить надо заполненность у элементов.

`MCY_Тип этажа` пригодится сразу: в WBS есть виды работ, различающиеся
именно типом этажа («кладка стен 1 этажа», «типового этажа»,
«технического этажа»), и этот параметр позволяет не спрашивать у человека,
какой из них применим к блоку.

**Уровни становятся справочником.** Сейчас `elements.floor` — свободный
текст. Для блоков нужен перечень уровней объекта с отметками и порядком.

**Блоки — не декартово произведение** секций и этажей: у секции может не
быть верхних этажей. Перечень порождается из того, что реально встретилось
в модели, плюс ручное добавление.

### Привязка статуса

Единица измерения вида работ — **единственный** источник правды о том, чем
должна быть заполнена привязка. Отдельно гранулярность не задаётся:

| Единица | `section_id` | `level_id` | `apartment_id` |
|---|---|---|---|
| `эт/сек` | обязателен | обязателен | — |
| `сек` | обязателен | — | — |
| `кв.эт/сек` | — | — | обязателен |
| `компл` | — | — | — |
| прочие | вне контура | | |

**Отсутствие записи означает «План».** Записи `work_progress` появляются
только при первом переходе в «В работе». Иначе пришлось бы держать
десятки тысяч строк со значением по умолчанию (151 вид работ × этажи ×
секции), которые ничего не сообщают.

## 4. Загрузка справочника видов работ

Грузится снаружи, тем же xlsx, и может меняться. Не зависит от выгрузки
Revit — этот шаг делается первым и самостоятельно.

Формат листа `WBS` (или первого листа книги, если листа с таким именем нет
— старые однолистовые файлы вроде «WBS МФР типовой»): `Уровень WBS |
Идентификатор операции | Название операции | Единицы измерения |
Кодификатор`, плюс необязательная «Примечание» — не во всех файлах есть, и
не у всех строк заполнена (в «WBS МФР типовой» — 5 из 224), но несёт
содержательные пояснения («выбрать нужную технологию» у узлов с
альтернативными вариантами исполнения) и сохраняется, если колонка в файле
есть (`work_types.note`, `work_types_import.COL_NOTE`).

**«Трек планирования» и лист `PlanningTrack`** (2026-09-04, новый формат
файла заказчика) — тоже необязательная колонка, тем же приёмом: код у
каждой строки-операции/вехи (`work_types.planning_track_code`), а
расшифровка код→название — на отдельном листе `PlanningTrack` той же
книги (`Код | Наименование | Примечание`, `work_types_import.
parse_planning_track`), сохраняется в свою таблицу `planning_tracks`
объекта, переустанавливаемую целиком при каждой загрузке (маленький
справочник без собственной истории — по коду на него никто не ссылается
FK, только сравнением значения). Коды «1»-«20» — доска «Шахматка» с
визуализацией на модели (§8, ниже), «0» — линейный трек (просто
процентная шкала, без раскраски блоков), `компл`/`Веха` — вне области этой
доработки. На реальном файле заказчика (233 строки оп/веха) коды 1-20 —
НЕ чистые группы «эт/сек»: например код «Отделка квартир» — все операции в
нём с единицей `кв.эт/сек`, а не `эт/сек`; в одном из кодов половина
операций «м3»; в нескольких кодах подмешаны операции `компл`. Доска
«Шахматка» строится только из операций с единицей `эт/сек`/`кв.эт/сек` —
остальные единицы того же кода трека в неё не попадают, остаются видны
только в дереве «Виды работ» и в старой матрице статусов (решение
пользователя, живое согласование).

**Ключ записи — полный путь по дереву, а не кодификатор.** Проверено
скриптом на файле:

* путь уникален для всех 151 операции и вехи;
* кодификатор НЕ уникален: `290-13` встречается 7 раз, `190` и `210-02-03`
  по 3 раза, `140-03`, `160-01`, `180-01`, `290-10` — по 2;
* кодификатор отсутствует у 108 строк из 217;
* название операции не уникально: «Вертикальная разводка» — 9 раз, «Пол» и
  «Стены» — по 6.

Ловушки исходного файла, которые импорт обязан учитывать:

* **у узла название лежит в колонке «Идентификатор операции», а у операции
  — в «Название операции»**. Наивный разбор по одной колонке даёт дерево
  без имён;
* `оп` и `веха` в колонке «Уровень WBS» — не уровни, а типы строки; уровень
  наследуется от последнего узла;
* **«Уровень WBS» узла бывает в двух несовместимых обозначениях** — путь по
  дереву («1», «1.2», «2.1.3», глубина по числу точек) или голое число
  абсолютной глубины («1», «2», «3», «4», глубина это само число); файл
  выдерживает только одно из них на весь лист. В «WBS МФР типовой» —
  второе: узел третьего уровня обозначен просто «3». Перепутать — посчитать
  голое число точками — критично: все узлы дерева схлопываются в глубину 1,
  и одноимённые категории из разных веток («Земляные работы»,
  «Металлоконструкции» и т.п. — они и правда повторяются: паркинг ниже
  нуля, типовой корпус/секция, отдельные разделы) склеиваются по пути в
  один узел, затирая бо́льшую часть подчинённых операций (найдено 2026-09-02
  на реальном файле, `app/work_types_import.py:_uses_dotted_levels`
  определяет формат один раз на весь лист по наличию точки хоть где-то в
  колонке);
* 10 вех «Готовность к ПНИ» без единицы измерения;
* одна операция без названия (строка 158, раздел «ВК. Канализация
  хоз-бытовая», единица `эт/сек`) — дефект исходника; показывать в сводке,
  не угадывать.

Раз справочник перезагружаемый, загрузка идёт по той же двухфазной схеме
`analyze → apply`, что и чертежи: совпавшие по пути сохраняют проставленные
статусы, исчезнувшие помечаются, новые добавляются — и всё это видно ДО
применения. Ключ-путь делает такую сверку возможной; ключ-кодификатор не
сделал бы.

## 7. Связь с MS Project

Концепция заказчика, Модуль 2, «будущий режим»: даты поставок подтягиваются
из базы данных прямо в вехи, ручной ввод исключается. Речь про нашу базу.
Ключ сопоставления у них — Text10 (Захватка + Кран + Стоянка + Этаж +
Элемент), все эти поля у нашего элемента есть.

Это относится к контуру ИЗДЕЛИЙ, а не к блочному: отдавать наружу нужно
даты поставки по элементам. Отмечено здесь, чтобы не потерялось.

## 8. Процент выполнения по блоку (2026-09-02)

Живой запрос пользователя: для операций «эт/сек» простого клик-цикла
План/В работе/Выполнено недостаточно — нужен процент, свой отбор операций
на каждом блоке и документ-отчёт с историей правок. Реализовано целиком
в `app/work_fact.py`, экран — панель блока в «Модели МФР» (клик по
параллелепипеду блока: карточка справа получает дерево с процентом и две
кнопки), а с 2026-09-05 (живой запрос пользователя, тот же, что перенёс
вкладку «Статусы» в «Отчёты», см. ниже) — ЕЩЁ и отчёт «Учёт по блокам:
статусы» целиком (вся матрица разом, с выбором даты).

**Область действия — «эт/сек» и «кв.эт/сек» (`work_progress.BLOCK_UNITS`,
вторая добавлена 2026-09-04).** «Сек» и «компл» остаются на старом
`work_progress` без изменений (в отчёте «Учёт по блокам: статусы» —
бывшая вкладка «Статусы», перенесённая туда 2026-09-05 — они по-прежнему
кликаются циклом). Для BLOCK_UNITS старая матрица `work_progress` лишилась
интерактивности насовсем (`ADDRESSABLE_UNITS` в `app/work_progress.py` их
не включает) — правка переехала в процент, две модели статуса на одну и ту
же операцию не сосуществуют. Отчёт «Учёт по блокам: статусы» — ОДНА
таблица на ОБА мира: строит её `work_fact.status_report` поверх дерева
`work_progress.matrix`, подменяя ячейки BLOCK_UNITS на {percent, status}
НА ВЫБРАННУЮ ДАТУ (последний отчёт блока не позже неё —
`work_fact._percents_as_of`), а «сек»/«компл» оставляя как есть (для них
истории по датам не существует вовсе). Правка одной ячейки — новый
`work_fact.set_cell_percent`/`PUT .../work-progress-cell`: собирает полный
слепок операций блока НА ЭТУ ДАТУ (недостающим — 0) и уходит в тот же
`save_report`, что и «Факт» в панели блока, — то есть попадает в ТОТ ЖЕ
отчёт-документ, а не в отдельный след. Отсюда же следствие для журнала
действий: этот эндпоинт НЕ пишет в `activity_actions` — правка «Факт»
из панели блока туда тоже не пишет (см. ниже), а это тот же механизм под
другим экраном, вторая запись была бы задвоением.

**«Настройки» — отбор, а не отдельное состояние.** Не каждая операция
справочника реально идёт на каждом блоке (не на всех этажах, например,
кладка). Список — `block_work_types` (block_id, work_type_id). Пока блок
не настраивали (`blocks.work_types_configured_at IS NULL`), считается
выбранным ВЕСЬ список «эт/сек»-операций объекта — так вело себя старое
поведение до этой доработки, форма «Настройки» открывается с этим же
предзаполнением (все галочки стоят) и только СУЖАЕТ список. Сохранение
делает список ЯВНЫМ, даже если он совпал с «всё».

Список в форме — ИЕРАРХИЧЕСКИЙ (2026-09-05, живой запрос пользователя):
раньше это был плоский перечень, где полный путь операции печатался
приглушённой «хлебной крошкой» в каждой строке — на реальном справочнике
(130+ операций «эт/сек») крошки повторялись десятками строк подряд, а
понять «что уже отмечено внутри Секции 1» было нельзя. Дерево строится на
фронте ИЗ ПУТЕЙ (`blockSettingsTreeHtml`), сервер по-прежнему отдаёт
плоский список с полем «путь» — отдельное дерево ему для этой формы
заводить незачем. У каждого узла свой чекбокс на всю ветку (отметить или
снять раздел целиком) с промежуточным состоянием, когда внутри отмечено не
всё. На сервер уходят строго id операций (`input[value]`), чекбоксы узлов —
только элемент управления и в отбор не попадают. Главная строка в этом
дереве — САМА ОПЕРАЦИЯ (живой запрос там же): её крупнее и жирнее, а
разделы мельче и приглушённо — обратно обычному для деревьев этого
приложения, потому что отмечают галочкой именно операцию, а разделы лишь
говорят, где она лежит. Полоса прокрутки у списка ПОСТОЯННАЯ (класс
`.scroll-always`, живой запрос там же; тем же классом — оба списка формы
«Факт»): дорожка на месте, даже когда содержимое влезло целиком. Внутри — две тонкости: `overflow-y: scroll`
вместо `auto` (иначе список дёргается по ширине, стоит отбору стать
короче) и оформленный `::-webkit-scrollbar` БЕЗ `scrollbar-width` — с
Chrome 121 стандартное свойство отключает вебкитовые правила, и на macOS
полоса снова становится накладной и прячущейся (поймано живой проверкой:
ширина дорожки была 0).

**Группа блоков разом** (2026-09-05, живой запрос «выделить несколько
блоков и задать им одинаковый список операций»). Выделение — Ctrl/Cmd-клик
по блокам в «Модели МФР», и в 2D, и в 3D (обычный клик по-прежнему выбирает
один); подсвечиваются все выделенные, в панели блока появляется плашка «N
блоков» со списком и ссылкой «снять выделение». «Настройки» тогда работают
на всю группу, а «Факт» гаснет: отчёт о выполнении — документ ПО ОДНОМУ
блоку, складывать проценты разных блоков не во что. Клик по ПУСТОМУ месту
плана или сцены снимает выделение целиком (живой запрос там же); клик по
элементу модели его НЕ трогает — карточки элемента и блока намеренно живут
рядом и независимо. Панорамирование за сброс не считается: сдвиг курсора
больше 4 px — это перетаскивание, а не клик (тот же порог, что у выбора в
3D).

Проверяются обе клавиши-модификатора не для красоты: на macOS **Ctrl+клик
системой считается правым кликом** и до обработчика не доходит — там
работает Cmd. Поймано живой проверкой.

Заодно там же вскрылась и починена СТАРАЯ поломка 2D: план забирает
pointer capture на `pointerdown` (панорамирование), и браузер адресует
последующий `click` самому `<svg>`, а не фигуре под курсором — `e.target.
closest()` не находил ничего, и клики по блокам и элементам в 2D не
срабатывали вовсе (в 3D всё работало: там своего pointer capture нет).
Теперь фигура берётся хит-тестом `document.elementFromPoint` по координатам
курсора.

Форма группы показывает ТРИ состояния операции: галочка — есть у всех
выделенных, промежуточное — только у части, пусто — ни у кого
(`work_fact.blocks_settings` возвращает `selected_all`/`selected_some`,
пересечение и разницу объединения). Сохранение ставит ВСЕМ выделенным один
и тот же список: нетронутое промежуточное состояние в `checked` не
попадает и снимается у всех — так и просил пользователь («одинаковый
список»), и об этом прямо сказано в подсказке формы и в её заголовке
(«операции N блоков»). На сервере групповой ветки хранения нет:
`save_blocks_settings` — цикл по тем же `save_block_settings`, «группа»
живёт только в интерфейсе. Эндпоинты — `GET/PUT
/objects/{id}/blocks/work-types-settings` (без `{block_id}`, блоки списком),
журнал действий тот же `block_work_types_settings`.

**«Факт» — документ на дату, не журнал.** `work_fact_reports` +
`work_fact_items`: живой запрос пользователя — аналог бумажного отчёта
ответственного со стройки, к любому из которых можно вернуться и
исправить зафиксированные цифры (не append-only журнал, а редактируемый
документ, как `supplier_change_docs`). Текущий процент операции на блоке —
значение из отчёта с максимальной `report_date` среди тех, что её
касаются; при равенстве дат — из записанного позже (бо́льший id). Новый
отчёт в форме предзаполняется ТЕКУЩИМИ процентами (обычно за день меняется
немногое) — сохраняются только реально задетые пользователем значения по
факту нажатия «Сохранить» (форма шлёт полный слепок всех выбранных
операций, не только изменённые).

**Отдельно от общего журнала действий.** Пользователь явно попросил
отдельный документ-журнал, а не запись в `app/activity_actions.py` (там
уже есть `work_progress_set` для старой модели) — «Факт» в общий журнал не
пишет. «Настройки» — обычное административное действие, пишет
`block_work_types_settings` в общий журнал как остальные настройки.

**Статус по порогам, не отдельным полем.** «План» = 0%, «В работе» =
1-99%, «Выполнено» = 100% (`work_fact._status_from_percent`) — используется
только для цвета полосы прогресса и сводки блока
(`work_fact.block_summary`, тот же формат, что раньше отдавала
`work_progress.block_status_summary`, которая теперь удалена — работала на
старых данных).

**«Шахматка»** (левая панель «Модели МФР», живой запрос пользователя,
переосмыслена 2026-09-04) — выбор ДОСКИ красит СРАЗУ ВСЕ блоки плана; клик
по блоку ведёт себя как раньше (карточка справа, «Настройки»/«Факт» — те
же). Раньше доска была ОДНОЙ операцией «эт/сек» (выбор — иерархическим
деревом всех операций, `work_fact.used_work_types_tree`); с появлением
колонки «Трек планирования» в исходном файле (§4) доска переопределена как
**группа операций одного кода трека** («1»-«20», имена — из листа
`PlanningTrack`), а не одна операция — так это называет и сам заказчик
(«Шахматка с визуализацией на модели» — примечание кода в файле).

**Цвет и подпись блока — по всем операциям доски, применимым к нему
разом**, а не по одной:

* цвет/статус блока — `_status_from_percent` от СРЕДНЕГО арифметического
  процентов его операций доски (решение пользователя — не минимум, не
  доля выполненных, а именно среднее);
* подпись на блоке — БОЛЬШЕ НЕ одно число: по строке на каждую применимую
  операцию, и строка ОДНА на операцию — имя, следом полоса выполнения,
  следом процент (живой запрос 2026-09-05). Полосы всех строк начинаются с
  ОДНОГО x (колонка имени — по самому длинному имени), высота полосы равна
  строке. Раскладка общая на оба вида — `mfrChessLabelLayout` в долях
  опорного кегля: 2D рисует её SVG (`mfrChessOpsLabelSvg`), 3D тем же
  порядком на канвасе (`buildMfrChessLabelMesh`), поэтому план и сцена
  показывают одно и то же.

  **Размер — строго по габариту, а не константа** (живой репорт со
  скриншотами 2026-09-05: в 3D фиксированный мировой размер строки делал
  подпись выше самого этажа — соседние этажи перекрывались внахлёст; в 2D
  подпись, наоборот, раздувалась на крупном блоке в «нечитаемую огромную
  надпись» вместо компактной наклейки). 2D вписывает наклейку в
  прямоугольник блока и вдобавок ограничивает её долей ширины ВСЕГО плана
  (`MFR_CHESS_LABEL_PLAN_SHARE`) — на больших блоках она остаётся
  компактной; 3D вписывает канвас («contain», меньшим из двух отношений)
  в реальные метры грани: ширина — ширина конкретной стены, высота —
  фактическая высота этажа (`b.z1 - b.z0`), обе с небольшим запасом
  (0.92/0.8), чтобы не касаться соседних этажей и рёбер.

* **в 3D наклейка ставится на ВСЕ ЧЕТЫРЕ боковые грани блока**
  (2026-09-05, живой запрос «сделай надписи не на одной, а на всех видимых
  боковых гранях»). До этого выбиралась одна «наружная» грань — и это дважды
  оказалось неверным: сначала нормалью бралось сырое направление от центра
  здания к центру блока, и у углового блока плоскость вставала поперёк угла,
  ровно на ребре («надписи на ребре, а не на грани»); а любая ОДНА грань
  оставляет блок без подписи со всех прочих ракурсов. Теперь нормали строго
  осевые (±X, ±Y), по одной наклейке на стену. Канвас рисуется ОДИН на блок
  и делится всеми четырьмя мешами (содержимое одинаковое), а
  `side: THREE.FrontSide` показывает каждую плашку только со своей стороны —
  иначе сквозь полупрозрачный блок читалась бы зеркальная изнанка
  противоположной стены. Прежней функции выбора грани
  (`mfrChessOutwardOffset`) больше нет.

`board_block_values` (замена `work_type_block_values`) собирает это одним
запросом на доску: операции треку (`unit IN (эт/сек, кв.эт/сек)`,
`planning_track_code = код`), для каждой — те же правила «включена ли в
блок» и «текущий процент», что у одной операции раньше, группирует по
блоку и считает среднее.

Поле в сайдбаре — просто название доски: у доски, в отличие от прежней
одной операции, нет пути по дереву — строку-путь под названием убрали
вместе с этим. Сам выбор — по клику полем открывается ОТДЕЛЬНОЕ крупное
окно (`#mfr-chess-modal-backdrop`), но теперь ПЛОСКИМ списком названий
досок (`.chess-pick`, без `.chess-group` — иерархия внутри доски не нужна,
её операции и так видны построчно на блоке), а не деревом всех операций,
как раньше.

Список ограничен досками, реально применимыми хотя бы к одному блоку
(`work_fact.used_planning_tracks` — коды строго «1»-«20», у которых есть
хотя бы одна операция BLOCK_UNITS с этим кодом; блок без явной настройки
использует ВЕСЬ список, значит при наличии хоть одного неотнастроенного
блока в выборе все такие коды разом). Блок вне отбора для выбранной доски
(ни одной применимой операции) красится тускло-серым БЕЗ подписи — это
«неприменимо», а не «0%», разные вещи.

Работает и в 2D (план по текущему этажу), и в 3D (`buildMfr3D` — цвет
материала блока плюс построчная подпись). Практика важнее плана: 2D
показывает один этаж за раз, а сравнивать блоки между собой (весь смысл
«Шахматки») нужно по всему зданию сразу — то есть в 3D без отбора по
этажам, это и есть основной сценарий (живой запрос пользователя,
2026-09-02 — раскраска работала только в 2D, но проверяли её в 3D, и «все
блоки остались синими»). Смена доски сбрасывает кэш 3D-сцены
(`mfr3d.key = null`) — иначе `buildMfr3D` не перестроил бы уже показанные
блоки. `THREE.Color` не понимает переменные CSS — палитра статуса в 3D
задана отдельными hex-константами (`MFR_CHESS_COLORS_3D`), совпадающими
по смыслу с 2D/CSS.

Подпись процентом в 3D прошла три версии (живой запрос пользователя,
2026-09-02, три уточнения подряд):

1. Билборд-спрайт (`THREE.Sprite`) над крышей блока — сразу же оказалось
   мало: «процент внутри блока, в его центре… должен быть наклейкой на
   внешней ближайшей видимой вертикальной грани».
2. Спрайт остался, но `updateMfrChessLabels` каждый кадр пересчитывал его
   позицию — направление из центра блока к ТЕКУЩЕЙ камере, вытянутое до
   пересечения со стеной по x,y (крыша исключена совсем — при счёте по
   всем трём осям, как в п.1, при взгляде сверху доминировал Z). Ближе,
   но спрайт по определению всегда разворачивается к камере — «наклейка
   не поворачивается в сторону пользователя, чётко на поверхности грани
   параллельно ей — как на ЖБИ» (там марки элементов — не спрайт,
   `collectMarkDecalQuads`/`buildMergedDecals`: плоский меш, развёрнутый
   по нормали грани).
3. Как сейчас: `buildMfrChessLabelMesh` строит `THREE.Mesh` с
   `PlaneGeometry` и базисом (право = верх×нормаль, верх = мировой Z,
   нормаль = сторона стены) — читаемый текст, зафиксированный в
   плоскости конкретной стены НАВСЕГДА, камеру не отслеживает вообще.
   Выбора стены больше нет (2026-09-05): наклейка ставится на ВСЕ ЧЕТЫРЕ
   боковые грани разом, см. выше. Вынос наружу — фиксированные 400 мм (не
   доля полуразмера блока, как раньше): реальное остекление/облицовка на
   плане иногда выступает за 200-мм технологический отступ блока
   (`MFR_BLOCK_MARGIN_MM`), и меньший запас визуально «тонул» в фасаде.
   Своего атласа и общего буфера, в отличие от ЖБИ-марок, нет — наклеек на
   объект сотни, не тысячи меток, склейка не окупается; канвас переиспользуется
   между гранями одного блока.

Подсветка ВЫБРАННОГО блока при активной «Шахматке» — не общий оранжевый
`MFR_HIGHLIGHT_COLOR`: заливка — более насыщенный и тёмный вариант ЕГО ЖЕ
цвета статуса (живой запрос пользователя, 2026-09-02: «должно
соответствовать цвету статуса, но быть насыщеннее, чем у других блоков в
том же статусе»), а грани — БЕЛЫЕ, отдельно от заливки (уточнено там же:
«добавь выбранному блоку более контрастные грани, например белые» — контур
того же тона на цветной заливке читался хуже, особенно у тусклого серого
«план»). `mfrChessBoldColor` — ручной HSL-буст БЕЗ прибавки константы к
насыщенности, только множителем (`s*1.7`, `l*0.68`): у серого «план»
(#9aa0a6) исходная насыщенность и так почти нулевая (6%, чуть голубит), и
первая версия с прибавкой (`s*1.6+0.25`) утраивала её до 35% — серый
превращался в откровенно синий вместо «того же серого, но темнее» (баг
найден живой проверкой в 3D). Множитель безопасен для любой базы: серый
остаётся серым, а насыщенные план/зелёный статусы действительно густеют.
Работает и в 2D (`--mfr-sel-fill`/`--mfr-sel-stroke` на самом элементе,
`.mfr-selected` в разметке ссылается на них с запасными обычными
значениями — оранжевым контуром и светло-оранжевой заливкой), и в 3D
(`highlightColor` в заливку накладки, `highlightEdgeColor` в её рёбра —
разные материалы одной группы).

Свои CSS-классы (`.chess-pick`/`.chess-group`), не переиспользование
`.revit-pick`: тот управляется общим обработчиком клика по
`#mfr-workspace` и `markRevitPicks()` по
`kind∈{level,section,part,category}`, «chess» там не значится —
переиспользование тут же гасило бы подсветку выбора.

## 9. Правая панель «Модели МФР»: вкладки, фильтр дашборда, динамика за период (2026-09-09)

Живой запрос пользователя, три связанные правки разом:

**Вкладки вместо двух панелей по бокам.** Прежняя левая панель фильтров
плана (Этаж/Раздел/Секция/Категория/«Шахматка») переехала целиком на
вкладку «Фильтры» правой панели (`#mfr-panel-tab-filters`); вкладка
«Свойства» (`#mfr-panel-tab-properties`) показывает карточку АКТИВНОЙ
сущности — элемент ИЛИ блок, взаимоисключающе (`showRevitCard`/
`renderBlockCard` теперь прячут чужую карточку; раньше обе оставались
видны разом — расхождение с уже взаимоисключающей подсветкой на схеме).
Переключатель вкладок — `switchMfrPanelTab`, копия `switchTab`/
`switchBlocksTab` со своим селектором (`.tabs`/`.tab-panel` — общие на весь
проект классы, `#sidebar`-специфичный `switchTab` их не годится трогать).
Правая панель регулируется по ширине (`makePanelResizer`, ключ
`zhbi_mfr_card_panel_width`) — для этого ей понадобился СВОЙ CSS
(`flex: 0 0 auto; width: 300px` вместо `flex-basis` у `.mfr-side-right`:
при заданном `flex-basis` браузер игнорирует `width`, которым резайзер
двигает панель).

**Фильтр карточки блока — раздел + статус**, ЛОКАЛЬНЫЙ для дерева операций
одного блока (`blockProgressFilter`, `filterBlockProgressTree`), не путать
с «Шахматкой» на вкладке «Фильтры» — та красит весь план. Выбор раздела
оформлен той же модалкой со списком (`.chess-pick`), что у «Шахматки»
(`#bp-filter-modal-backdrop`, отдельный экземпляр от `#mfr-chess-modal-backdrop`),
данные — тот же уже загруженный `mfrChessTracks`. Дерево, полученное с
сервера, режется на фронте без повторного запроса; «узел» без детей после
фильтрации не рисуется.

**Динамика факта за период** — подсветка блоков, где факт менялся внутри
периода (переключатель+даты на вкладке «Фильтры»). Источника-журнала для
BLOCK_UNITS нет (см. выше — только отчёты на дату), поэтому «изменилось» —
сравнение `_percents_as_of` на двух датах (`work_fact.blocks_fact_changes`).
Область сравнения — операции активной доски «Шахматка», если она выбрана,
иначе все операции, отобранные для блока (решение пользователя: динамика
должна быть про то же, что сейчас красит план). Подсветка НЕ зависит от
текущего выбора и рисуется в `mfrHighlightSelection` при каждой пересборке
плана/сцены — как и обычное выделение, только своим классом
(`.mfr-fact-changed` в 2D — яркий пунктир поверх заливки статуса; в 3D —
отдельная группа `mfr3d.dynamicsHighlight`, только рёбра БЕЗ заливки, чтобы
несколько подсвеченных блоков разом не перекрывали друг другу цвет
статуса). Открытая карточка блока в этом режиме получает от
`work_fact.block_progress_tree` (параметры `date_from`/`date_to`) не
`percent`/`status`, а `percent_from`/`percent_to`/`status_from`/`status_to`
— дерево рисует ОДИН прогресс-бар на операцию (2026-09-10, живой запрос,
было — две отдельные полосы): заливка до `percent_to`, риска-метка
(`.bp-bar-marker`) на позиции `percent_from`, подпись «было% → стало%»;
фильтр по статусу (выше) в этом режиме смотрит на `status_to` — состояние
на конец периода. Подпись «Динамика за период с … по …» — общий для 2D и
3D оверлей (`#mfr-dynamics-caption`, лежит поверх обеих схем в одном
контейнере), чтобы не дублировать разметку на два режима. **Обе даты
необязательны** (2026-09-10, живой запрос — пустая дата не «отбор снят», а
«без границы»): на сервере отсутствие параметра НЕ то же самое, что его
пустое значение — присутствие `date_from`/`date_to` в запросе (хотя бы
одного, пусть даже пустой строкой) само по себе включает режим динамики,
пустая граница внутри него подставляется сентинелом
(`work_fact._DYNAMICS_MIN_DATE = "0001-01-01"`) или сегодняшней датой
(`blocks_fact_changes`, `block_progress_tree`) — то есть «обе даты пустые»
означает «за весь период», а не «динамика выключена»; подпись в этом
случае — «Динамика за весь период».

**История факта по наведению** (2026-09-10, живой запрос) — у ЛЮБОЙ полосы
(и в обычном режиме, и в режиме динамики) наведение показывает всплывающую
карточку `#bp-history-tooltip` (тот же визуальный приём, что у
`#chart-tooltip`, свой независимый экземпляр — другой триггер, mouseenter/
mouseleave, а не mousemove по SVG) со списком «дата — процент —
пользователь» по всем отчётам, что касаются этой операции на этом блоке
(`work_fact.op_fact_history`, эндпоинт
`GET /objects/{id}/blocks/{block_id}/work-types/{work_type_id}/fact-history`,
кэш на фронте `bpHistoryCache`, сбрасывается при сохранении «Факта»).
Уровня точнее — кто именно менял ЭТУ операцию внутри документа, а не
пользователь, зафиксировавший отчёт целиком, — схема не хранит (см. §8,
`work_fact_reports.updated_by` общий на весь документ); показан автор
отчёта, а если его позже редактировали — редактор.

**Вид группировки карточек-фильтров вкладки «Фильтры»** — как у групп

единообразия, «хотя бы» стрелку слева). Разметка — `.filter-group`/

## 10. 3D-сцена МФР: убрана инерция вращения камеры (2026-09-10)

Живой запрос пользователя: после отпускания мыши модель ещё около 3 секунд
«мерцала и переливалась», прежде чем картинка стабилизировалась — тот же
эффект, что чинили в основной 3D-сцене ЖБИ 2026-07-25 (`Docs/backlog.md`),
но фикс тогда перенесли не на все сцены. Причина — включённая инерция
`OrbitControls` (`enableDamping=true`, `dampingFactor=0.12`): после
отпускания кнопки `controls.update()` ещё некоторое время по экспоненте
доворачивает камеру, из-за чего рендер-цикл (безусловный
`requestAnimationFrame`, без early-exit) продолжает рисовать чуть
меняющиеся кадры — блики, видимость рёбер и наклеек «плывут». Исправлено
точечно, как и в основной сцене: `controls.enableDamping = false`
(`buildMfr3D`) — камера останавливается СРАЗУ с последним движением мыши.
Сам безусловный цикл рендера (в отличие от основной сцены, там он давно
переведён на «по требованию») не переписан — устранена причина лишних
кадров, а не сам факт их отрисовки; при необходимости снизить нагрузку в
простое это отдельная, самостоятельная оптимизация.

## 13. Запланированная работа (ЗР) как основной объект управления (2026-09-10)

Согласовано и реализовано по отдельному заданию
`Docs/block-works-schedule-task.md` (полный текст решений и обоснований —
там; здесь только итог, ловушки и куда смотреть в коде). Центр контура
сместился с пары «операция × блок» (`block_work_types`, без id и без
сроков) на **ЗР** — ту же пару, но с id, директивным и актуализированным
сроками, историей. Новый модуль `app/block_works.py` — ЗР как сущность
(CRUD, версии прогноза, производные, агрегаты); `app/work_fact.py` остаётся
про документы факта и состав работ блока, переведён на `block_works`.

**Явность плана (В1) — самая заметная ловушка при живой проверке.** До
2026-09-10 отсутствие настройки у блока читалось как «выбрано всё» — так
матрица статусов вела себя изначально, и это перекочевало в «эт/сек». У
ЗР со сроками неявного «всё» быть не может (срок ставится на конкретную
строку), поэтому план блока стал явным: не настраивали — список ПУСТ.
Живое следствие для проверки боевых данных после миграции: подавляющее
большинство блоков не настраивали НИ РАЗУ (настройка нужна была только
затем, чтобы сузить список от «всё», а по умолчанию и так было «всё») —
после миграции они окажутся с пустым планом, это ожидаемо, а не потеря
данных; история (факт, если он есть) не теряется — см. ниже.

**Мягкое снятие (В7) вместо удаления.** «Настройки» больше не удаляют
строку `block_works` безвозвратно, если на ней уже есть факт или заданные
сроки (`_block_work_has_history`) — вместо DELETE строка помечается
`retired_at` и пропадает из активного плана/отбора/досок/отчётов
(везде читается `retired_at IS NULL`), но остаётся адресуемой по id:
карточка ЗР открывается, версии и факт видны, только формы правки
отключены. Повторное включение той же операции СНИМАЕТ пометку у
существующей строки (реактивация), а не вставляет новую — иначе
конфликт с `UNIQUE(block_id, work_type_id)`. Совсем пустую ЗР (ни фактов,
ни сроков) по-прежнему можно удалить без следа — истории у неё и так нет.

**Перенос данных со старой схемы — обработками релиза, а не миграцией
схемы.** Сама пересборка `block_work_types` → `block_works` (перенос пар
1:1, без бизнес-логики) — структурная миграция в `app/db.py`, выполняется
всегда и не может провалиться частично. А вот факты, зафиксированные на
блоке, который никогда явно не настраивали (неявное «всё» тогда позволяло
это) — их ЗР может не быть вовсе; такую ЗР восстанавливает ОТДЕЛЬНАЯ
идемпотентная обработка релиза (`app/release_tasks.py`,
`_restore_block_works_from_fact`, помечает `note='восстановлена по
факту'`), а не структурная миграция — она вправе не выполниться сразу и
быть повторена кнопкой, не блокируя старт сервера.

**`work_fact_items.block_work_id` — добавочный, не замена ключа
(отклонение от первоначального текста задания).** §2.4 задания просил
заменить `work_type_id` на `block_work_id` целиком; реализовано мягче —
`block_work_id` добавлен РЯДОМ, чтение факта по `work_type_id` продолжает
работать без изменений. Причина: заполнение новой ссылки для накопленных
строк — обработка релиза, а она может не успеть выполниться или упасть,
не блокируя старт; код чтения обязан работать и до её успешного прогона.
Новые и восстановленные строки получают `block_work_id` сразу при
сохранении. Полная замена ключа (со сменой PK) — не в этой доработке,
понадобится отдельным шагом, если/когда встанет вопрос.

**Три инварианта** (вынесены в `Docs/DECISIONS.md`, раздел «Данные и
доступ»): план ЗР — явный список, неявного «всё» не существует; базовый
срок меняется только явной правкой с записью старого/нового в журнал;
актуализированный срок — версиями, старые не правятся и не удаляются.

**Разделение с `app/work_fact.py` — импорт в ОДНУ сторону.**
`block_works` читает `work_fact` (за процентом, за построчной историей) —
циклического импорта нет, потому что даты в уже построенное дерево
`work_fact.block_progress_tree`/`work_fact.status_report`/`work_fact.
board_block_values` домешивает САМ `block_works` отдельным проходом
(`merge_dates_into_tree`, `status_report_with_deadlines`,
`board_block_deviation_by_track`) — `work_fact` о существовании сроков не
знает вовсе. Тот же приём для отчёта «График работ по блокам»
(`app/report_block_schedule.py`): источник строк —
`block_works.list_block_works`, группировка и агрегаты — уже в самом
отчёте.

**Построчный аудит факта (В6).** `work_fact_items.updated_at/updated_by` —
кто сохранял строку последним (обновляется при КАЖДОМ сохранении отчёта,
не только при изменении значения — документ каждый раз перезаписывает
полный слепок). `work_fact_item_history` — отдельно, только ЗАДЕТЫЕ строки
(значение реально изменилось между старым и новым слепком), пишется в
`save_report` ДО удаления старых `work_fact_items`. Подсказка истории
факта (`op_fact_history`) с 2026-09-10 показывает автора именно ЭТОЙ
строки (`i.updated_by`), а не отчёта целиком — расхождение возможно, если
один человек создал отчёт, а другой позже поправил в нём одну операцию.
Удаление документа факта разрешено (порог — «Изменение» раздела, тот же,
что у сохранения), логируется отдельно (`block_fact_report_delete`) —
единственное действие контура факта, попадающее в общий журнал.

## 14. Вкладка «Запланированные работы» и интерактивная карточка ЗР (2026-09-10)

Живой запрос пользователя: третий, самостоятельный путь к ЗР — не через
панель блока «Модели МФР» и не через отчёт статусов, а прямо из модалки
«Учёт по блокам» (`Действия → Справочники → Учёт по блокам`). Новая вкладка
`blk-tab-plans`: слева список блоков объекта (`GET .../blocks`), справа —
ЗР выбранного блока (`GET .../block-works?block_ids=`), клик по строке
открывает уже существующую карточку ЗР (`openBlockWorkCard`) — форма не
дублируется, реквизиты/сроки/факт те же, что и из панели блока.

**Карточка ЗР получила интерактивный список документов вместо read-only
истории.** Раньше «История факта» в карточке была только для чтения;
теперь — «Документы факта»: каждая строка (дата, процент ИМЕННО этой
операции в документе, автор последней правки) с кнопками «Править» и
«Удалить». Источник — новая `work_fact.list_reports_with_percent()`:
тот же список, что `list_reports`, плюс `LEFT JOIN work_fact_items` по
`work_type_id` этой ЗР (документ мог не коснуться операции — тогда
`percent IS NULL`, в списке «—»).

Редактирование документа из карточки ЗР **не заводит отдельную форму** —
открывает существующую форму «Факт» на нужном отчёте (`openBlockFactForm`,
вынесена в отдельную функцию из инлайн-обработчика кнопки блока). Причина:
документ — это снимок ВСЕХ операций блока на дату, редактировать одну
операцию в отрыве от прочих бессмысленно и разошлось бы с уже существующей
формой «Факт». Удаление — тот же `DELETE .../fact-reports/{id}`, что и
кнопка «Удалить отчёт» внутри формы «Факт», с тем же `confirm()`.

**Баг стекинга модалок (пойман при живой проверке).** `#block-work-backdrop`
(карточка ЗР) и `#block-fact-backdrop` (форма «Факт») делят один
`z-index: 100`; открытие «Факта» поверх уже открытой карточки ЗР было
технически успешным (класс `open` появлялся), но невидимым — карточка ЗР
оставалась выше по порядку в DOM. Починка: кнопка «Править» в списке
документов закрывает `#block-work-backdrop` ПЕРЕД открытием «Факта» —
карточка ЗР сама обновится по возврату (см. ниже), повторно открывать её не
нужно.

**Синхронизация вкладки при правках извне** — `refreshPlansTabIfOpen(blockId)`,
единая точка: если вкладка «Запланированные работы» открыта и показывает
именно этот блок, перегружает список ЗР. Вызывается из всех мест, где
меняются сроки или документы факта ЗР: сохранение базового/актуализированного
срока и удаление документа в карточке ЗР, сохранение/удаление отчёта «Факт»,
построчная и массовая правка сроков в форме «Сроки». Без этого хука список
во вкладке расходился бы с карточкой сразу после первой же правки оттуда.

## 15. Удаление используемой секции/этажа — с предупреждением, а не запретом (2026-09-10)

Живой отчёт пользователя («не работает добавление и удаление секций, и
этажи проверь») вскрыл два независимых дефекта вкладки «Секции и этажи»:

1. **`delete_level` падал 500 на КАЖДОМ вызове** (`app/blocks.py`) — SQL с
   4 плейсхолдерами `level_id = ?` получал кортеж из 3 значений
   (`sqlite3.ProgrammingError`), баг с самого появления функции. Удаление
   этажа не работало вообще, независимо от того, используется он или нет.
2. **Ошибки «Добавить»/«удалить» у секций и этажей шли через `showToast`** —
   общую строку состояния снизу экрана, физически перекрытую бэкдропом
   этой же модалки (тот же класс бага, что уже был у «Обновить
   принадлежность элементов», см. §8/§9 выше). Отказ («секция
   используется», код не по формату, дубликат этажа) не был виден вовсе —
   с точки зрения пользователя «кнопка не работает». Заменено на
   `blkSetupStatus` — приём, уже используемый для правки полей на месте в
   этой же вкладке.

Заодно, тем же живым запросом («разрешай удалять используемую секцию,
предупреждай о количестве элементов, где ссылка будет очищена»), снят и
сам запрет на удаление используемой секции/этажа. **`PRAGMA foreign_keys =
ON` держится на каждом соединении** (`app/db.py`) — значит обычный
`DELETE FROM object_sections WHERE id = ?` УЖЕ выполняет то, что описано в
`app/schema.sql`: `revit_elements`/`revit_rooms` — `ON DELETE SET NULL`
(просто теряют привязку), а `blocks`/`object_flats`/`work_progress` —
`ON DELETE CASCADE` (удаляются безвозвратно вместе с секцией — а с
блоками каскадом уходят и их ЗР, сроки, факт, история). Разница между
«потеряет привязку» и «удалится» существенная, поэтому:

- `blocks_mod.delete_section`/`delete_level` получили `force: bool = False`
  и новый тип исключения `UsageWarning(BlockError)` — считает точный
  счётчик по каждой затронутой таблице и делит на `clears` (SET NULL) и
  `deletes` (CASCADE), а не просто «используется/не используется»;
- без `force` — сервер отвечает **409** с `UsageWarning.to_dict()`
  (`{message, clears, deletes}`), а не 422 «отказано»;
- фронт (`deleteBlkEntity` в `app.js`) при 409 показывает ВТОРОЙ, уже
  предметный `confirm()` с этим сообщением и, если подтверждено, повторяет
  DELETE с `?force=true`; `api()` для этого прокидывает `res.status` и
  `body.detail` на кидаемый `Error` (`err.status`/`err.detail`) — раньше
  терялось, `describeApiError` сворачивал любой нестроковый `detail` в
  сырой JSON.

У НЕиспользуемой секции/этажа поведение не изменилось — DELETE отрабатывает
с первого захода, без лишнего диалога.

## 16. Код секции вручную — не только формат «С0N» (2026-09-10)

`blocks_mod.create_section` до сих пор всегда проверяла ручной ввод через
`revit_package.normalize_section` и отказывала («Не похоже на секцию»),
если код не приводился к «С0N» — хотя сама функция `normalize_section`
писалась для разбора автоматической Revit-выгрузки (защита от МУСОРА,
случайная метка вроде «Автостоянка» не должна заводить фиктивную секцию),
а не для осмысленного ручного ввода человеком. Исключение для такого
случая уже было — но только в пути PDF-загрузки (`trusted=True`,
2026-08-31, секция «Паркинг»); сама форма «Секции и этажи» под него не
попадала. Живой отчёт пользователя (09-10, секция «Парковка 2», «что за
ограничение») вскрыл это несоответствие.

Починка — не `trusted=True` целиком (это отключило бы и полезную сторону
`normalize_section`, нормализацию типового числового ввода в «С0N»), а
мягкий fallback: `normalize_section(code) or code.strip()` — типовой ввод
(«1», «Секция 5») по-прежнему приводится к «С01»/«С05», а всё, что вне
этого формата («Парковка 2»), используется как есть, а не отклоняется.
`trusted=True` (PDF-импорт) не тронут — там код уже готов, нормализация не
нужна вовсе.

Побочно замечено, не чинилось: голое число БЕЗ буквы/слова-префикса
(«1» само по себе, без «С»/«Секция») `_SECTION_RE` не матчит вовсе —
`normalize_section("1")` возвращает `None` уже давно, хотя подсказка формы
и текст ошибки называют «1» валидным примером. До этой правки ввод «1»
отклонялся с противоречивым сообщением, теперь просто сохраняется как
код «1» (без нормализации в «С01») — реальный баг остаётся, не входил в
объём этого запроса.

# Учёт работ по блокам «этаж + секция»

Статус: **первая версия реализована** (2026-08-25, `Docs/TZ.md` §3в) —
модель данных, ручной ввод секций/этажей, блоки, загрузчик справочника
видов работ, экран простановки статусов. Источник требований — два
документа заказчика: «WBS МФР типовой» (типовая структура работ) и
«Концепция автоматизации календарного планирования v3.1» (MS Project + VBA).

**Что реализовано.** Секции/этажи объекта — ручной ввод (`app/blocks.py`,
`POST/PATCH/DELETE /objects/{id}/sections`, `/levels`), пишет в те же
`object_sections`/`object_levels`, что и Revit-импорт (§7 ниже уточнён:
источник — «выгрузка Revit ИЛИ ручной ввод», оба пишут в одни таблицы и
сливаются по коду секции/номеру этажа). Блоки — явные пары, не декартово
произведение (`blocks`, `app/blocks.py`). Справочник видов работ —
двухфазный xlsx-загрузчик (`app/work_types_import.py`), ключ записи путь
по дереву, ловушки формата из §4 ниже обработаны и проверены синтетическим
файлом, воспроизводящим все четыре. Статусы — `work_progress`
(`app/work_progress.py`), экран «Действия → Документы → Учёт по блокам».

**Что НЕ реализовано, сознательно.** Квартиры (`object_flats`, единица
`кв.эт/сек`) — таблица в схеме есть, но заполняется только выгрузкой Revit
Rooms; ручного ввода нет, и у объекта без модели заводить квартиры не из
чего. Единицы вне блочного контура (`шт`, `м2`, `м3`, `т`, `пог.м`,
`опора`) в дереве показываются, статус на них не ставится — это исходное
решение §2, не пробел реализации.

## 1. Что это и чем отличается от учёта сборного ЖБИ

**Отдельная ветка варианта учёта.** Существующий контур — поштучный учёт
сборных ЖБИ-изделий: марка, контракт, поставка, монтаж, история статусов.
Новый контур — учёт ВИДОВ РАБОТ на блоках здания:

> вид работ × блок (этаж + секция) → **План / В работе / Выполнено**

Контуры сосуществуют и **не влияют друг на друга**. Это инвариант, а не
временное упрощение:

* контур блоков не пишет в `elements`, `element_status_history`, контракты
  и график поставки — и не читает их как источник статуса;
* статус блока **ставит человек**, он не выводится из состояния элементов;
  «Выполнено» — это приёмка, а не арифметика по изделиям;
* общий у двух контуров только Объект.

Инструменты простановки статуса разрабатываются позже — сейчас
проектируется модель данных и загрузка входных справочников.

## 2. Откуда взялась гранулярность

Колонка «Единицы измерения» в WBS — это объявление гранулярности учёта.
По 134 операциям и 17 вехам:

| Единица | Операций | К чему привязан статус |
|---|---|---|
| `эт/сек` | 61 | блок: секция + этаж |
| `компл` | 23 | объект целиком |
| `шт` | 16 | вне блочного контура |
| `сек` | 10 | секция целиком |
| `м2`, `м3`, `т`, `пог.м`, `опора` | 16 | вне блочного контура |
| `кв.эт/сек` | 8 | квартира |
| нет единицы | 10 | вехи «Готовность к ПНИ» |

Разделы, живущие в блоках: внутренние инженерные системы (28 операций в
`эт/сек`), фасады (9), каменная кладка (7), отделочные работы (7 + 8 в
`кв.эт/сек`), заполнение дверных проёмов (4), монолитные и сборные Ж/Б
конструкции выше нуля (3), светопрозрачные конструкции (2),
металлоконструкции (1).

Важное следствие: **монолит выше нуля меряется в `эт/сек`, а не в
кубометрах** (операции 160-02-01…03). Поэтому отдельные статусные цепочки
монолита (опалубка → армирование → бетонирование → распалубка) не нужны —
достаточно трёх статусов на блоке.

## 3. Сущности

| Сущность | Содержание | Источник |
|---|---|---|
| `sections` | секция объекта: имя, порядок | выгрузка Revit (общий параметр `MCY_Секция`), правка вручную |
| `levels` | уровень: имя, отметка, порядок | выгрузка Revit (Levels) |
| `blocks` | пара (секция, этаж) | порождается из встреченного в модели |
| (геометрия блока) | параллелепипед: оси здания × отметки этажа, опционально | только у объектов с осями из Revit — `Docs/TZ.md`, «Геометрия блока» |
| `apartments` | квартира: номер, секция, этаж, площадь | выгрузка Revit (помещения, Rooms) |
| `work_types` | справочник видов работ | внешний xlsx, перезагружаемый |
| `work_progress` | статус вида работ на привязке | ставит человек |

**Секция — новая сущность.** Сейчас у элемента есть Захватка, Кран,
Стоянка, Этаж; секции нет ни у нас, ни в карте полей MS Project заказчика
(Text1 = Захватка, Text2 = Кран, Text3 = Стоянка, Text4 = Этаж). Захватка
секцией не является и её не заменяет.

**Но в модели Revit она уже есть.** Вычитано из файла КР 2026-08-10: у
заказчика заведено семейство общих параметров `MCY_*`, и среди них
`MCY_Секция`, `MCY_Этаж`, `MCY_Корпус`, `MCY_Тип этажа` (Автостоянка,
1 этаж, Типовой этаж, Кровля), `MCY_Часть здания` — они используются как
единый адресный набор. Договариваться о том, чем задавать секцию, не
нужно; проверить надо заполненность у элементов.

`MCY_Тип этажа` пригодится сразу: в WBS есть виды работ, различающиеся
именно типом этажа («кладка стен 1 этажа», «типового этажа»,
«технического этажа»), и этот параметр позволяет не спрашивать у человека,
какой из них применим к блоку.

**Уровни становятся справочником.** Сейчас `elements.floor` — свободный
текст. Для блоков нужен перечень уровней объекта с отметками и порядком.

**Блоки — не декартово произведение** секций и этажей: у секции может не
быть верхних этажей. Перечень порождается из того, что реально встретилось
в модели, плюс ручное добавление.

### Привязка статуса

Единица измерения вида работ — **единственный** источник правды о том, чем
должна быть заполнена привязка. Отдельно гранулярность не задаётся:

| Единица | `section_id` | `level_id` | `apartment_id` |
|---|---|---|---|
| `эт/сек` | обязателен | обязателен | — |
| `сек` | обязателен | — | — |
| `кв.эт/сек` | — | — | обязателен |
| `компл` | — | — | — |
| прочие | вне контура | | |

**Отсутствие записи означает «План».** Записи `work_progress` появляются
только при первом переходе в «В работе». Иначе пришлось бы держать
десятки тысяч строк со значением по умолчанию (151 вид работ × этажи ×
секции), которые ничего не сообщают.

## 4. Загрузка справочника видов работ

Грузится снаружи, тем же xlsx, и может меняться. Не зависит от выгрузки
Revit — этот шаг делается первым и самостоятельно.

Формат листа: `Уровень WBS | Идентификатор операции | Название операции |
Единицы измерения | Кодификатор`.

**Ключ записи — полный путь по дереву, а не кодификатор.** Проверено
скриптом на файле:

* путь уникален для всех 151 операции и вехи;
* кодификатор НЕ уникален: `290-13` встречается 7 раз, `190` и `210-02-03`
  по 3 раза, `140-03`, `160-01`, `180-01`, `290-10` — по 2;
* кодификатор отсутствует у 108 строк из 217;
* название операции не уникально: «Вертикальная разводка» — 9 раз, «Пол» и
  «Стены» — по 6.

Ловушки исходного файла, которые импорт обязан учитывать:

* **у узла название лежит в колонке «Идентификатор операции», а у операции
  — в «Название операции»**. Наивный разбор по одной колонке даёт дерево
  без имён;
* `оп` и `веха` в колонке «Уровень WBS» — не уровни, а типы строки; уровень
  наследуется от последнего узла;
* 10 вех «Готовность к ПНИ» без единицы измерения;
* одна операция без названия (строка 158, раздел «ВК. Канализация
  хоз-бытовая», единица `эт/сек`) — дефект исходника; показывать в сводке,
  не угадывать.

Раз справочник перезагружаемый, загрузка идёт по той же двухфазной схеме
`analyze → apply`, что и чертежи: совпавшие по пути сохраняют проставленные
статусы, исчезнувшие помечаются, новые добавляются — и всё это видно ДО
применения. Ключ-путь делает такую сверку возможной; ключ-кодификатор не
сделал бы.

## 5. Что дополнительно нужно из Revit

К составу пакета выгрузки (см. `Docs/revit-import.md`) добавляется:

* адресные поля элемента из общих параметров заказчика: `MCY_Секция`,
  `MCY_Этаж`, `MCY_Корпус`, `MCY_Тип этажа`, `MCY_Часть здания`;
* секция пакета `помещения` (Rooms): номер, этаж, секция, площадь, контур —
  для квартир.

Уровни в пакете уже предусмотрены.

## 6. Порядок работ

1. Загрузка справочника видов работ из xlsx — самостоятельна, от Revit не
   зависит.
2. Секции, уровни, помещения — из выгрузки Revit.
3. Порождение блоков.
4. Экран статусов и инструменты простановки — позже, отдельно.

## 7. Связь с MS Project

Концепция заказчика, Модуль 2, «будущий режим»: даты поставок подтягиваются
из базы данных прямо в вехи, ручной ввод исключается. Речь про нашу базу.
Ключ сопоставления у них — Text10 (Захватка + Кран + Стоянка + Этаж +
Элемент), все эти поля у нашего элемента есть.

Это относится к контуру ИЗДЕЛИЙ, а не к блочному: отдавать наружу нужно
даты поставки по элементам. Отмечено здесь, чтобы не потерялось.

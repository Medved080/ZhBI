# CLAUDE.md — сводка проекта для быстрого старта сессии

Держать этот файл кратким (100–200 строк) и обновлять при значимых
изменениях архитектуры/статуса — по стоячей инструкции пользователя, без
напоминания. Подробности — в `Docs/TZ.md` (живой тех.спек, обновляется на
каждое функциональное изменение), `Docs/ARCHITECTURE.md` (технический
снимок «как устроено и почему» — компоненты, алгоритмы, инварианты,
техдолг; обновляется по явной просьбе) и `Docs/backlog.md` (датированный
журнал с причиной/фиксом/проверкой каждого раунда работ).
`Docs/requirements-notes.md` — точечные уточнения по реальным данным
заказчика (форматы DXF, адресация по осям), на них ссылается сам
`Docs/TZ.md`. `Docs/DEPLOYMENT_LINUX.md` — установка/обновление сервера
на Ubuntu Server LTS через **Docker** (`Dockerfile`/`docker-compose.yml`
в корне, скрипты в `scripts/linux/`; **не проверено ни на реальном
Ubuntu, ни локальной сборкой** — на Mac разработчика нет ни Docker, ни
Homebrew, см. предупреждение в самом файле и `Docs/backlog.md`).
Клиенты (браузер) — на Windows, никакой установки не требуют, только
сетевой доступ к серверу.

## Что это

ЖБИ-трекер: веб-инструмент для отслеживания статусов поставки/монтажа
сборных железобетонных элементов на стройплощадке. Чертежи — DXF,
загружаются через UI (кнопка «Загрузить чертёж», `POST /import-dxf`)
или кладутся в `Input/` (подхватываются при старте сервера — основной
способ). Данные — марка, тип, координаты, адрес по осям, привязка к
зонам (захватка/кран/стоянка), статус, контракт, партия, история.

## Стек и структура

- **Backend**: FastAPI + Starlette (синхронные `def`-роуты, threadpool),
  SQLite без WAL (`app/db.py`). Сессии — cookie, 30 дней. Три роли
  пользователей (`admin`/`user`/`view`), обязательный вход для всех
  действий, включая просмотр схемы.
- **Frontend**: один файл `app/static/index.html` (~4800+ строк) —
  vanilla JS + SVG для 2D-схемы, Three.js (вендорено локально,
  `app/static/vendor/three/`, НЕ CDN — см. "Ключевые решения" ниже) для
  3D-режима. Никакого сборщика/фреймворка.
- **Импорт DXF** — два параллельных конвейера, старый не трогать при
  правке нового:
  - Старый (`scripts/parse_zhbi.py`, `LAYER_CONFIG`) — плоские слои без
    зон/подтипов/отметок.
  - Новый стандарт имён (`scripts/layer_naming.py`,
    `scripts/new_standard_pipeline.py`) — слои `WEB_констр_...` /
    `WEB_тех_...`, с зонами, подтипами, отметками. Только новый
    конвейер поддерживает зоны и 3D.
  - Адресация по осям — `scripts/assign_axes.py` (общая для обоих).
  - Зоны (захватка/кран/стоянка) — `scripts/zone_parser.py` (реестр,
    сопоставление названий, связь стоянка→кран) +
    `scripts/zone_binding.py` (привязка элемента к зоне).
  - Оркестрация загрузки через UI — `app/dxf_import.py` (сохранить →
    распарсить → адресовать → записать), переиспользует те же функции,
    что и CLI-скрипты `scripts/*.py` — обе точки входа не дублируют
    логику.
- **Тесты/проверка** — нет pytest-сюиты; методология: изолированные
  Python/Node-скрипты в `/tmp`, тестирующие извлечённые функции на
  РЕАЛЬНЫХ данных из `data/zhbi.db` (`plan_data()`/прямые SQL-запросы),
  плюс один сквозной синтетический тест `scripts/verify_zone_pipeline.py`
  (`test_data/synthetic_zones.dxf`, генерится
  `scripts/generate_test_zones_dxf.py`). С 2026-07-22 живой браузер
  доступен и используется как основной способ верификации UI (см.
  предупреждение выше).

## Ключевые решения (коротко, детали — в Docs/backlog.md по дате)

- **Единый русский словарь `element_type`** — Колонна/Ригель/Панель/
  Плита перекрытия (генерик «Плита» убран 2026-07-30: означал то же, что
  «Плита перекрытия», в реальных данных не использовался, а два имени для
  одного типа расщепляли бы элементы по двум ветвям фильтров и контрактов;
  накопленные записи переименовываются той же миграцией), миграция
  идемпотентна
  (`app/db._normalize_element_type_vocabulary`).
- **Фильтры на клиенте** (`app/static/index.html`) — архитектура "полный
  список значений всегда виден + недоступен (disabled), не сужается" —
  фикс двух багов самоблокировки. `PLACEMENT_CASCADE_GROUPS` = группы
  [`elementType`,`subtype`,`mark`] и [`crane`,`stance`], [`supplier`,`contract`]
  — при расчёте доступности одной категории группы фильтр ОСТАЛЬНЫХ
  игнорируется. Иерархические группы (`buildHierarchicalFilterGroup`)
  сворачиваемы (по умолчанию закрыты, кроме родителя); клик по потомку,
  если родитель сейчас выключен, включает и родителя (но не остальных
  потомков) — иначе включить одну стоянку при выключенном кране было
  невозможно. Функция поддерживает опциональный 3-й уровень
  (`grandchildConfig`) — сейчас единственный случай: Марка под Подтипом
  у группы "Тип элемента/Подтип/Марка"; два других вызова (Кран/Стоянка,
  Поставщик/Контракт) параметр не передают и работают как раньше.
  Ключ подтипа (`subtypeFilterValue`) — составной, тип+текст
  (`subtypeLogicalKey`, разделитель `::`, с 2026-07-24), НЕ голый текст —
  текст подтипа намеренно переиспользуется между типами в справочнике
  (например, "на отм. +15.000" одновременно у Ригеля и Плиты перекрытия),
  раньше это давало баг: снятие галочки с одного типа каскадом скрывало
  элементы ДРУГОГО типа с тем же текстом подтипа (живой репорт
  пользователя, см. `Docs/backlog.md`). Тот же приём составного ключа,
  что у стоянок (`stanceLogicalKey`) и уже был в диалоге "Партия"
  (`buildBatchDialogMaps`) — теперь везде единообразно.
  `FLAT_MARK_TYPES = {"Плита перекрытия", "Ригель"}` — у этих типов
  подтип почти всегда буквально отметка (избыточно с отдельным фильтром
  "Отметка (высота)") — `subtypeFilterValue` для них кладёт в "слот
  подтипа" МАРКУ, марки становятся прямыми детьми типа (без
  промежуточного уровня); у Колонны подтип смысловой ("нижняя"/
  "верхняя"), не трогали.
- **Строка состояния под рабочей областью** (2026-07-31, живой запрос) —
  закреплённая полоса внизу `#stage-area` (новая колонка-обёртка вокруг
  `#stage`/`#stage-3d`, сайдбар в неё НЕ входит: полоса относится к схеме).
  В покое — «Показано N из M · Фильтры — …» (`updateStatusBarDefault`
  вызывается из `applyPlacementFilters`, счёт видимых берётся из его же
  цикла; перечень строит `describeActiveFilters` теми же функциями подписей,
  что и форма фильтров — ради этого `zoneLabelFor`/`statusLabelFor`/… и
  `PLACEMENT_CATEGORY_INFO` вынесены из `renderPlacementFilters` на уровень
  модуля). Поверх — служебные сообщения на 7 с, потом полоса возвращается к
  перечню. `showToast` СОХРАНЁН как имя (30 мест вызова), но теперь пишет
  в полосу, а не во всплывающую карточку в углу — `#toast-container` и его
  стили удалены. Каждое сообщение попадает в `statusLog` (лента сеанса,
  только в браузере, до перезагрузки) — кнопка «История» рядом с полосой;
  это НЕ журнал действий (`app/activity.py`, серверный).
- **Фильтр по датам СМР — диапазоном, не чекбоксами** (2026-07-31, живой
  запрос) — ОДНА группа «СМР» в конце раздела «Фильтры», внутри две
  НЕсворачиваемые подгруппы: «Дата начала СМР» (`project_smr_start_date`)
  и «Дата окончания СМР» (`project_delivery_date`). В каждой поля «с»/«по»
  (обе границы включительно и необязательны — это и «больше», и «меньше»,
  и диапазон) плюс три взаимоисключающих варианта для элементов без даты:
  «с датой и без даты» / «только с датой» / «только без даты» (последний
  выключает поля границ — они уже ни на что не влияют). Галочки тут
  недостаточно: «только пустые» — это не включение/выключение одного
  значения рядом с остальными, а выбор, и «остальные значения» здесь
  вообще не список, а непрерывный диапазон.
  Отдельная структура `state.dateFilters` и отдельный предикат
  `elementPassesDateFilters`, а НЕ запись в `PLACEMENT_FILTER_DEFS`: вся
  та машинерия построена на перечислимой категории с набором исключённых
  значений, а у даты значений сотни и отбор по ним — диапазон. Предикат
  зовётся из ДВУХ мест — `passesPlacementFilters` (видимость) и
  `elementPassesExceptKeys` (иначе диапазон дат не влиял бы на посерение
  значений в остальных категориях). Группа свёрнута по умолчанию, поэтому
  заголовок дописывает сводку заданного отбора («СМР · начало: …») —
  иначе диапазон не виден вовсе. `renderPlacementFilters` пересобирает контейнер целиком, из-за
  чего поле ввода теряет фокус (у чекбоксов незаметно) — фокус
  восстанавливается по метке `data-date-filter` (`pendingDateFilterFocus`).
- **Форма элемента показывает ВСЕ поля** (2026-07-31, живой запрос) —
  правимых полей стало девять: к типу/подтипу/марке/отметке/этажу/адресу
  и плановой дате добавлены ОБЕ даты СМР (`project_smr_start_date`,
  `project_delivery_date`). Раньше их заполнял только импорт графика MS
  Project, и элемент, чьего блока «Кран+Стоянка+Этаж+Тип+Подтип» в
  графике нет, оставался без дат навсегда (на реальном файле — 18
  «Ригелей периметральных» из 103). Даты принимаются строго `ГГГГ-ММ-ДД`
  (`_ELEMENT_DATE_FIELDS`, app/main.py): в БД они текст и сравниваются
  как текст. Остальные ~25 колонок — свёрнутый блок «только для чтения»
  из пяти групп, каждая подписана тем, ЧЕМ значение меняется (статус —
  историей, зоны — геометрией, координаты — чертежом). Названия зон/
  объекта и число точек контура даёт `_element_reference_labels` —
  ОТДЕЛЬНАЯ функция, НЕ расширение `enrich_element_row` (та зовётся на
  каждую из 9422 строк `/plan-data`); из `state.zones` брать нельзя —
  справочник открывается и без загруженной схемы. Обязательная обратная
  сторона: `import_schedule` теперь уважает `manual_fields` и обновляет
  две даты ПООТДЕЛЬНОСТИ (общий `UPDATE` двумя колонками затирал бы
  правку соседней), а пропущенные показывает в сводке (`manual_kept`) —
  молча не применить значение так же плохо, как молча затереть.
- **2D-подписи марок — плашка, не контур** (с 2026-07-24) — `<rect
  class="mark-label-bg">` ПЕРЕД `<text class="mark-label">` в DOM
  (рисуется позади), тот же стиль, что уже был в 3D
  (`build3DLabelSprite`, `rgba(255,255,255,0.72)`). Размер бокса — без
  `getBBox()` (форсирует layout, дорого при тысячах элементов на каждый
  тик зума) — оценка по числу символов, та же константа 0.62×fontSize,
  что уже использует `updateLabelCollisionVisibility`. Видимость
  подложки синхронизирована с текстом через `labelBgByText`
  (`WeakMap`) + `setLabelDisplay()` — единая точка вместо правки 6 мест,
  где раньше менялся `label.style.display` напрямую.
- **3D-"наклейка" марки на грани** (`build3DMarkDecal`, с 2026-07-25) —
  для Плиты перекрытия (верх+низ), Ригеля (все 4 длинные грани — сечение
  квадратное, боковые того же размера, что верх/низ) и Колонны (все
  боковые грани, подтверждено явно заказчиком — не торец, вертикальная,
  текст снизу вверх) вместо плавающей таблички (`build3DLabelSprite`),
  если марка помещается по длине элемента (`DECAL_FIT_MARGIN=0.92`,
  оценка ширины той же константой 0.62×fontSize, что и в 2D) — иначе
  прежняя табличка, запасной вариант. Ориентация плоскости — явный
  ортонормированный базис (`orientDecalMesh`, `Matrix4.makeBasis`), не
  подбор углов вручную (тот же класс ошибок, что и у зеркальности всей
  сцены). Текстура — общая на МАРКУ (`decalTextureCache`), не на элемент
  (марки повторяются десятками раз). Наклейка НЕ билборд (лежит плоско
  на грани) — при вращении камеры может читаться вверх ногами;
  `updateDecalOrientation`/`updateAllDecalOrientations` пересчитывают на
  каждое движение `OrbitControls` (дёшево — только смена кватерниона у
  уже существующих мешей): разворот на 180° вокруг нормали, если "верх"
  текста (`cross(normal,right)`) сейчас направлен ОТ камеры.
- **Стоянка крана ≠ точка** — рабочая зона крана в конкретной позиции.
  Элемент без конкретной стоянки, но с известным краном — псевдо-значение
  `no-stance:<craneId>` (метка "вне стоянок"), ложится ДОЧЕРНИМ пунктом
  под свой кран, не в общий "не определено".
- **Лесенка сужения зоны стоянки с высотой** — ТОЛЬКО когда в файле
  физически один ярус стоянок (старые файлы, `WEB_тех_Стоянки
  крана_ОТМ00000`): на каждом ярусе колонн ближний к крану край окна
  стоянки отступает на 1 реальный пролёт сетки осей, следующая по
  номеру стоянка подхватывает уступленное.
  `scripts/zone_binding.build_stance_level_polygons` +
  `compute_column_tier_elevations`. Если заказчик уже нарисовал РЕАЛЬНЫЕ

  стоянки в ряду" с "ярус", см. Docs/backlog.md 260722), привязка идёт
  прямым снэпом элемента на ближайший НИЖЕ реально нарисованный ярус

  стоянке крана — физически венчают ярус снизу (лежат на его колоннах),

- **Колонны верхнего яруса — удлинение до конца ригеля ВЫШЕ базового
  потолка** (`computeColumnEndExtensions`, app.js, 2026-07-25/26) —
  когда есть локальная надстройка (ригели/плиты) ЕЩЁ ВЫШЕ уже учтённого
  потолка (`computeTopColumnCeiling` — ближайшая плита перекрытия над
  верхним ярусом, напр. 34700), нужны конкретные колонны, доходящие

  физически стоят под КОНЦОМ такого ригеля (ригель опирается концами на
  колонны, плита лежит на ригеле — не наоборот). Колонна под СЕРЕДИНОЙ
  пролёта такого ригеля высоту не меняет (живой запрос пользователя).

  контура (не по `x`/`y` марки — это позиция лидера/выноски, а не
  геометрический центр), допуск `COLUMN_BEAM_END_MATCH_TOLERANCE_MM=1000`

  отметке 39200 — все совпали с колонной ближе 1000мм, часть точнее

  наблюдение замера: слитая сцена с рёбрами рисует В СЕМЬ РАЗ БОЛЬШЕ

  равно в 400 раз быстрее — треугольники ничего не стоят, стоило только
  число вызовов. Поэтому рёбрами жертвовать не пришлось, вид прежний.

  не считаются заново; помнит владельца (`highlightElementId`), иначе
  перекраска чужого элемента при массовой смене статуса гасила бы
  выделение; (4) скрытие по фильтрам — пересборкой сцены, как и было.
  **Ловушка, стоившая двух неверных гипотез**: после слияния кадр упал не
  до 0,1, а до 7,9 мс ПРИ 4 ВЫЗОВАХ — время уходило в

  видимости (9420 выключенных наклеек = 35 тыс. объектов). Напрашивающийся

  (проверено подсчётом вызовов: дети всё равно обходятся, 50 из 50) —
  работает только ОТСОЕДИНЕНИЕ контейнера от сцены

  отдельными объектами (1327 колонн → 382 вызова, 4,1 мс на кадр).

- **Доступ и роли на объекте** (2026-08-01, этап C; `app/access.py`).

  снятый доступ возвращался бы сам. **Все 54 `require_admin` разобраны**

  применения чертежа объект берётся ИЗ ТОКЕНА анализа. Данные без объекта
  — только системному админу. Настройки, лежавшие одной записью на всю
  систему, оставались тогда системными и переехали внутрь объекта в этапе
  D (см. следующий пункт); системной осознанно осталась массовая правка
  через Excel (нужен отбор строк по доступным объектам — отдельная
  задача).

- **Настройки и справочники — внутри объекта** (2026-08-02, этап D).
  Пять таблиц (`label_visibility`, `zone_colors`, `report_notes`,
  `default_contracts`, `app_settings`) ключуются объектом, и всё чтение/
  запись это учитывает. `get_setting`/`set_setting` берут `object_id`
  ОБЯЗАТЕЛЬНЫМ позиционным аргументом — со значением по умолчанию забытый
  объект молча читал бы чужую строку. **Цвет крана переехал с файла на
  объект** — это не косметика: новая версия чертежа приходит под новым
  именем, и настроенная раскраска пропадала с каждой выдачей, а форма
  показывала один кран столько раз, сколько версий накопилось (проверено:
  цвет пережил переимпорт под новым именем). `plan-data` берёт объект из
  ПЕРВОГО элемента выборки (схема показывает один объект), но цвета кранов
  читает по объекту КАЖДОГО элемента. Отчёты принимают `object_id` и умеют
  вывести его из `source_file`; БЕЗ объекта карточка ПУСТАЯ, а не
  «какая-нибудь» — числа одной стройки рядом с вехами другой хуже пустой
  шапки. Экспорт настроек разложен по объектам, ключ — ИМЯ объекта (файл
  переносят на другой сервер, id там ничего не значит); неизвестный объект
  пропускается и попадает в сводку. **Индексы объектных таблиц — в
  `_ensure_object_scoped_indexes`, НЕ в `schema.sql`**: тот выполняется до
  миграций, и `CREATE INDEX` по ещё не добавленной колонке роняет старт —
  ровно этим сервер уже один раз лёг. Унаследованный CLI-путь
  (`upsert_elements`/`upsert_zones`) эти строки больше не заводит вовсе:
  его элементы без объекта, выдумывать им объект значило бы дописать
  настройку чужой стройке.

## Требования к загружаемым файлам и образцы (2026-07-30)

`app/import_templates.py` — ОДНО место, где описаны все шесть загрузок

MS Project ушли в «пропущено»). Данные образцов — РЕАЛЬНЫЕ значения
справочников, поэтому рядом с кнопкой стоит предупреждение не грузить
образец в рабочую базу.

## ⚠ Открытый дефект: загрузка DXF падает на боевой БД (2026-07-30)

`POST /import-dxf` → 500, `no such table: main.batches`. Падает ЛЮБАЯ
вставка в `elements`: `get_connection()` включает `PRAGMA foreign_keys =
ON`, а у `elements` остался внешний ключ `batch_id -> batches(id)` при
том, что таблица убрана в «Контрактации 2.0». Схема проходит `init_db()`
молча — SQLite разрешает цель FK только при записи. Тот же ключ значится
в `_KNOWN_HARMLESS_DANGLING_FKS` (`app/main.py`) как «безобидный» — это
неверно, его надо убирать пересборкой таблицы `elements`. НЕ чинить без
подтверждения пользователя: прошлая автоматическая «починка схемы на
старте» стоила всех статусов. Детали и минимальный опыт-доказательство —
`Docs/backlog.md`, запись 2026-07-30.

- **Объект и идентичность элемента** (2026-07-30, этап 1 переработки
  объектов системы) — элементы принадлежат ОБЪЕКТУ (`objects`,
  `object_drawings`), а не файлу чертежа: до этого идентичностью была
  пара `(source_file, dxf_handle)`, и новая версия чертежа (заказчик
  выдаёт их под новым именем) давала 9422 новых строки со статусом
  «Запланирован» — именно из-за этого прогресс однажды восстанавливали из
  выгрузки XLS. Переимпорт теперь ОБНОВЛЯЕТ элементы; статусы, история,
  контракт и даты импортом не затрагиваются. Сверка многоуровневая
  (`app/element_identity.py` — чистый модуль, `app/element_sync.py` — БД):
  handle → точный ключ «тип+отметка+центроид» → ближайший в плане (50 мм),
  причём ОТМЕТКА не входит в ключ (на 260722→260723 у 1771 элемента она
  сменилась при том же handle — как часть ключа она дала бы «1771 исчезло
  + 1771 новых»), но различает колонны в стопке на одной точке плана.
  Импорт двухфазный: `/import-dxf/analyze` (в БД не пишет) → сводка с
  разворотом построчно → `/import-dxf/apply`; смена марки СОГЛАСУЕТСЯ
  (привязана к позиции контракта). `is_current=0` — элемент исчез из
  чертежа: строка/статус/история сохраняются, со схемы уходит; единое
  условие видимости — `visible_elements_clause()` (`app/db.py`), НЕ
  повторять его строками (мест чтения восемь). Выгрузка ИСТОРИИ намеренно
  без этого фильтра — архив. `ZHBI_DB_PATH` — путь к БД через окружение,
  для живой проверки на копии. Подробности, замеры и два унаследованных
  бага, найденных живой проверкой (`layersCache is not defined` после
  каждой успешной загрузки чертежа; загруженный через интерфейс чертёж не
  попадал в список выбора) — `Docs/backlog.md`.
- **`elements.batch_id` снят** (там же) — это был не мусор, а поломка: с
  `PRAGMA foreign_keys = ON` любая вставка в `elements` падала на
  «no such table: main.batches», то есть загрузка любого чертежа была
  невозможна. Снято через `ALTER TABLE ... DROP COLUMN` (проверено: убирает
  и колонку, и висячий FK, таблицу НЕ переименовывает — значит чужие FK на
  `elements` не могут быть молча переписаны, того класса ошибки здесь
  просто нет). `_KNOWN_HARMLESS_DANGLING_FKS` теперь пуст — «безобидный
  висячий FK» надо проверять записью, а не рассуждением.
- **Зоны — справочник уровня Объекта** (2026-07-30, этап 2; решения
  З1–З16 в `Docs/backlog.md`). `zones` больше не ярусная таблица: это
  запись справочника с `number` (целое, разбирается из подписи —
  `parse_zone_number`), `object_id`, `is_current`; геометрия ярусов — в
  новой `zone_levels` (отметка + контур + откуда пришло). «Стоянка 01» на
  четырёх ярусах была ЧЕТЫРЬМЯ зонами с разными id, стала одной записью с
  четырьмя полигонами. У элемента добавился `zone_stance_level_id` — иначе
  ярус потерялся бы при склейке. Ключ опознания при переимпорте —
  категория + номер (+ родительский кран у стоянки), НЕ имя: его формат
  менялся между версиями чертежа («Стоянка 1» → «Стоянка 01»), и сравнение
  строк давало бы «новая зона» на ровном месте; ведущие нули срезаются по
  той же причине. Запись при импорте — `app/zone_sync.py` (опознать и
  обновить), НЕ прежний DELETE+INSERT: на записи справочника ссылаются
  элементы. `plan-data` отдаёт по строке на ЯРУС, но `id` во всех ярусах
  одной зоны ОДИНАКОВ (это id записи справочника) — так подписи, цвет
  крана и склейка стоянок в фильтре работают без переделки фронтенда.
  Зоны устаревших версий чертежа остались строками старой формы, поэтому
  `zones.outline_json` НЕ удалён.
- **Пересчёт привязки к зонам и откат** (там же, `app/zone_recalc.py`) —
  при сохранении зоны привязка элементов пересчитывается автоматически и
  ТЕМИ ЖЕ функциями, что импорт (`zone_binding.bind_element_to_zones`):
  вторая реализация «точка в полигоне» разъехалась бы с правилами про
  ярус строго ниже отметки у Ригеля/Плиты и привязку колонны точкой. Один
  осознанный отказ (`can_recalculate`) — чертёж с ОДНИМ ярусом стоянок:
  там импорт строит ярусы «лесенкой» по сетке осей, и пересчёт без неё дал
  бы другую привязку, поэтому форма просит перезагрузить чертёж, а не
  считает молча. Откат (`zone_edit_undo`) возвращает всю цепочку —
  реквизиты, ярусы И привязки; повтор отклоняется 409. **Две ловушки,
  оплаченные проверкой**: снимок привязок надо снимать ДО правки геометрии
  (DELETE ярусов обнуляет `zone_stance_level_id` каскадом, и снимок
  записывал NULL), а восстанавливать ярус — по ОТМЕТКЕ, а не по id (при
  откате ярусы вставляются заново и получают другие id; сравнение по id
  показывало 443 фантомных «расхождения»).
- **Форма зоны: правка точек + предпросмотр 2D/3D** (там же) —
  координаты приводятся к ЦЕЛЫМ мм (из DXF приходит
  `6718.578588724135`, править такое в поле невозможно); предпросмотр
  перерисовывается на `input`, а не `change`; закреплён `position:sticky`
  (+ обязательный `align-self:flex-start`, растянутый flex-элемент не
  прилипает); номера точек на превью совпадают с таблицей. 3D — СВОЯ
  маленькая сцена (основная держит ~9400 мешей), кадр строго по
  требованию и `enableDamping=false`. Запрещающие проверки: <3 точек,
  самопересечение, дубль отметки яруса, занятый номер, стоянка ЦЕЛИКОМ вне
  своего крана — частичный выход НЕ запрещён (на 260723 так нарисованы 184
  стоянки из 252, это норма чертежа).
- **Иерархия «Проект → Объект» и доступ по объектам** (2026-07-31,
  решения П1–П9 в `Docs/backlog.md`; в коде — только **этап A**, модель
  данных). Проект (`projects`) — группировка и единица выдачи доступа, у
  него НЕТ своих данных, кроме реквизитов: все свойства, справочники и
  контракты живут внутри объекта, сроки проекта сводятся из сроков
  объектов. Схема показывает ОДИН объект за раз (совмещать соседние
  здания нечем — у каждого файла своя сетка осей, общность координат
  непроверяема без второго объекта в данных). **Роль переезжает на
  объект** (`user_access.role`, грант с `object_id IS NULL` = весь проект
  вместе с будущими объектами); `users.role` остаётся СИСТЕМНОЙ ролью.
  Контрагент — сквозной (одно юрлицо на все стройки; дробление сделало бы
  «К-ЖБИ» двумя контрагентами), а договор — объектный
  (`agreements.object_id`), поэтому объект контракта ВЫВОДИТСЯ по цепочке
  и полем не дублируется: «объект контракта = объект элемента» становится
  инвариантом схемы. Дообъектное наследие УДАЛЕНО
  (`_purge_legacy_elements`): 30 123 элемента, 361 зона, 328 линий осей;
  чистка одноразовая, за маркером в `app_settings` — «удалять всё с
  `object_id IS NULL` на каждом старте» выглядит идемпотентным, но молча
  уничтожало бы будущие сбойные строки на каждом деплое. Элементы с
  `is_current=0` при живом `object_id` — НЕ наследие, а результат сверки
  при переимпорте, их чистка не трогает. `visible_elements_clause()`
  схлопнута до `(is_current = 1)`.

## Текущий статус (2026-07-29, релиз v0.21)

Всё перечисленное ниже вошло в **v0.21** (`app/changelog.py`, запись
добавлена по прямой просьбе пользователя). Предыдущий релиз — v0.20.

- **Журнал действий (`app/activity.py`, таблица `activity_log`)** — раньше
  логирования не было вообще. Пишется В ФОНЕ: отдельный поток-писатель со
  своим соединением, события через очередь, пачками до 500 в транзакции
  (SQLite делает fsync на каждый commit — поштучно на 9422 событиях было бы
  видно глазом). НЕ `BackgroundTasks` FastAPI — те занимают поток пула и на
  массовых операциях конкурируют с запросами. Замеры: 3,9 мкс на постановку
  события, смена статуса 300 элементов с журналом — 0,09 мс на элемент.
  Переполнение очереди не блокирует, отброшенные считаются и пишутся
  записью `log_overflow`. Запись — внутри `apply_status_change`, а не в
  эндпоинтах: смену статуса делают ДВА роута, общая точка не даёт пути
  остаться незалогированным. Клиентские тайминги (нажал/открылось/записал)
  копятся в браузере и уходят пачкой раз в 10 с (`POST /activity`),
  длительности — `performance.now()`, НЕ разница часов: часы машин
  расходятся на минуты, а цель журнала — сравнивать машины. `GET /activity`
  — поиск, `POST /activity/cleanup` — очистка за период. Форма «Действия →
  Настройки → Журнал действий». Дашборд статистики — не сделан, отложен.
- **Автообновление при совместной работе** — `GET /changes?source_file=&since=`,
  опрос раз в 15 с + кнопка «⟳» в тулбаре. Опрос, а НЕ SSE/WebSocket:
  в `app/main.py` 45 синхронных роутов против 2 async, открытое соединение
  заняло бы поток пула на каждого пользователя и десяток вкладок подвесил
  бы сервис. Пустой ответ — 54 байта против 1,65 МБ полной перезагрузки.
  Метка времени — ИЗ ОТВЕТА СЕРВЕРА, никогда с часов браузера. Первый
  запрос только запоминает метку, `loadPlan` её сбрасывает (иначе сразу
  после открытия чертежа выскочило бы «обновлено 9422 элемента»).
  Конфликт — побеждает последний + уведомление второму. **Попутно найдена
  и закрыта дыра**: `recompute_element_contract_cache` не двигала
  `elements.updated_at`, смена одного контракта на другой без смены статуса
  опросом не ловилась (отрицательный контроль: было 0, стало 1).
- **Режим слабого компьютера (3D) = профиль «слабая машина или RDP»**
  (расширен 2026-08-01) — переключатель «3D лёгкий»,
  `localStorage` (настройка КОМПЬЮТЕРА, не проекта). Шесть мер: рёбра не
  создаются, `pixelRatio` 1 вместо 1.5, `antialias: false`,
  `logarithmicDepthBuffer: false`, потолок частоты кадров
  (`LOW_SPEC_FPS_CAP=20`, т.е. не чаще кадра в 50 мс) и падение
  разрешения в 0,6 раза на время вращения мышью (`set3DDragging`).
  Обычный режим 3D НЕ затронут ни одной из них. Повод — живой репорт «через
  RDP вращение сильно тормозит, напрямую из браузера нет»; `chrome://gpu`
  с той станции снял гипотезу о программном рендеринге (WebGL аппаратный),
  но показал встроенную Intel UHD 730, дисплей RDP на 32 Гц и флаг драйвера
  `msaa_is_slow` — при том, что мы просили и MSAA, и логарифмический буфер
  глубины (последний вводился РАДИ рёбер, которых в лёгком режиме нет).
  Поверх отрисовки там лежит кодирование картинки протоколом, поэтому
  потолок частоты — не про видеокарту, а про то, чтобы не копить очередь
  кадров, которые RDP не успевает передать (движение при этом не теряется:
  отложенный кадр рисуется по САМОМУ СВЕЖЕМУ положению камеры).
  `antialias`/`logarithmicDepthBuffer` — свойства контекста WebGL, у живого
  рендерера не меняются: создание рендерера вынесено в
  `create3DRendererAndControls`, смена профиля пересоздаёт контекст
  (`rebuild3DRenderer`, с `forceContextLoss()` — у вкладки жёсткий лимит на
  число живых контекстов), сцена/камера/геометрия те же. Заодно
  `updateAllDecalOrientations` и `updateZoomIndicator3D` сняты с события
  `change` у OrbitControls и перенесены ВНУТРЬ `render3DFrame` — события
  приходят чаще, чем рисуется кадр. Подробности и замеры —
  `Docs/backlog.md`, запись 2026-08-01. Перенос рендера на сервер
  рассматривался и отклонён: нужен GPU на сервере и упирается в задержку
  сети; предпосчёт геометрии на сервере ускорил бы ЗАГРУЗКУ, а тормозит
  КАДР. **Смысл режима изменился после слияния геометрии** (см. выше,
  2026-07-30): раньше он убирал половину ВЫЗОВОВ отрисовки — главное
  узкое место тех времён; теперь вызовов и так 4–6 при любом наборе, и
  режим экономит другое — ~730 тыс. треугольников из 860 тыс., память и
  время сборки сцены (313 мс против 536 мс). С 2026-08-01 к режиму
  добавлены ещё четыре меры под удалённый рабочий стол — см. «Ключевые
  решения» выше.
- **Загрузка из Input/ убрана со старта сервера** — теперь только по

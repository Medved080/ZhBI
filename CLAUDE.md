# CLAUDE.md — сводка проекта для быстрого старта сессии

Держать этот файл кратким (100–200 строк) и обновлять при значимых
изменениях архитектуры/статуса — по стоячей инструкции пользователя, без
напоминания. Подробности — в `Docs/TZ.md` (живой тех.спек, обновляется на
каждое функциональное изменение), `Docs/ARCHITECTURE.md` (технический
снимок «как устроено и почему» — компоненты, алгоритмы, инварианты,
техдолг; обновляется по явной просьбе) и `Docs/backlog.md` (датированный
журнал с причиной/фиксом/проверкой каждого раунда работ).
`Docs/requirements-notes.md` — точечные уточнения по реальным данным
заказчика (форматы DXF, адресация по осям), на них ссылается сам
`Docs/TZ.md`. `Docs/DEPLOYMENT_WINDOWS.md` — установка/обновление на
Windows 11, скрипты в `scripts/windows/` (**не проверено на реальной
Windows** — среда разработки — macOS, см. предупреждение в самом файле).

## Как продолжить работу с нуля (новая сессия/новое приложение)

Порядок чтения для полного погружения без потерь контекста: **этот
файл** (текущее состояние и пойнтеры) → `Docs/ARCHITECTURE.md` (как
устроено технически) → `Docs/TZ.md` (что система делает, вся бизнес-
логика) → `Docs/backlog.md` (хронология — зачем сделано именно так,
какие баги уже находили и чинили, чтобы не наступить повторно). Все три
документа поддерживаются в актуальном состоянии как часть обычной
работы, не только «под занавес» — можно доверять их текущему
содержимому, а не только этому файлу.

**Git** (с 2026-07-16): локальный репозиторий инициализирован, ветка
`main`. Публичного/приватного remote на GitHub пока НЕТ — следующий шаг
(руками пользователя, не мной) описан в `Docs/DEPLOYMENT_WINDOWS.md`
§3.1. Модель: `main` = разработка, теги релизов (`vГГГГ.ММ.ДД`) = что
ставится на продакшен (`update-git-test.bat`/`update-git-prod.bat`,
выбор тега вручную). Открытый вопрос: включать ли `test_data/` (147 МБ
реальных чертежей заказчика, пока НЕ в git) в историю репозитория — см.
§3.7 того же файла.

**Инструмент автоматизации браузера недоступен в терминальных сессиях**
(claude-in-chrome/CDP не подключён) — вся верификация UI делалась
изолированными Python/Node-тестами на реальных данных + curl против
живого сервера, БЕЗ визуального подтверждения в браузере. Если новая
сессия открыта в приложении/окружении, где браузерный инструмент
доступен — это открытый пробел, который стоит закрыть в первую очередь
для уже реализованных, но не проверенных вживую раундов (см. «Что
дальше» ниже).

## Что это

ЖБИ-трекер: веб-инструмент для отслеживания статусов поставки/монтажа
сборных железобетонных элементов на стройплощадке. Чертежи — DXF,
загружаются через UI (кнопка «Загрузить чертёж», `POST /import-dxf`)
или кладутся в `Input/` (подхватываются при старте сервера — основной
способ). Данные — марка, тип, координаты, адрес по осям, привязка к
зонам (захватка/кран/стоянка), статус, контракт, партия, история.

## Стек и структура

- **Backend**: FastAPI + Starlette (синхронные `def`-роуты, threadpool),
  SQLite без WAL (`app/db.py`). Сессии — cookie, 30 дней. Три роли
  пользователей (`admin`/`user`/`view`), обязательный вход для всех
  действий, включая просмотр схемы.
- **Frontend**: один файл `app/static/index.html` (~4800+ строк) —
  vanilla JS + SVG для 2D-схемы, Three.js (вендорено локально,
  `app/static/vendor/three/`, НЕ CDN — см. "Ключевые решения" ниже) для
  3D-режима. Никакого сборщика/фреймворка.
- **Импорт DXF** — два параллельных конвейера, старый не трогать при
  правке нового:
  - Старый (`scripts/parse_zhbi.py`, `LAYER_CONFIG`) — плоские слои без
    зон/подтипов/отметок.
  - Новый стандарт имён (`scripts/layer_naming.py`,
    `scripts/new_standard_pipeline.py`) — слои `WEB_констр_...` /
    `WEB_тех_...`, с зонами, подтипами, отметками. Только новый
    конвейер поддерживает зоны и 3D.
  - Адресация по осям — `scripts/assign_axes.py` (общая для обоих).
  - Зоны (захватка/кран/стоянка) — `scripts/zone_parser.py` (реестр,
    сопоставление названий, связь стоянка→кран) +
    `scripts/zone_binding.py` (привязка элемента к зоне).
  - Оркестрация загрузки через UI — `app/dxf_import.py` (сохранить →
    распарсить → адресовать → записать), переиспользует те же функции,
    что и CLI-скрипты `scripts/*.py` — обе точки входа не дублируют
    логику.
- **Тесты/проверка** — нет pytest-сюиты; методология: изолированные
  Python/Node-скрипты в `/tmp`, тестирующие извлечённые функции на
  РЕАЛЬНЫХ данных из `data/zhbi.db` (`plan_data()`/прямые SQL-запросы),
  плюс один сквозной синтетический тест `scripts/verify_zone_pipeline.py`
  (`test_data/synthetic_zones.dxf`, генерится
  `scripts/generate_test_zones_dxf.py`). Живого браузерного тестирования
  нет (см. предупреждение выше) — открытый пробел, проговаривается
  пользователю после каждого раунда UI-правок.

## Ключевые решения (коротко, детали — в Docs/backlog.md по дате)

- **Единый русский словарь `element_type`** — Колонна/Ригель/Плита/
  Панель/Плита перекрытия, миграция идемпотентна
  (`app/db._normalize_element_type_vocabulary`).
- **Фильтры на клиенте** (`app/static/index.html`) — архитектура "полный
  список значений всегда виден + недоступен (disabled), не сужается" —
  фикс двух багов самоблокировки. `PLACEMENT_CASCADE_GROUPS` = группы
  [`elementType`,`subtype`,`mark`] и [`crane`,`stance`], [`supplier`,`contract`]
  — при расчёте доступности одной категории группы фильтр ОСТАЛЬНЫХ
  игнорируется. Иерархические группы (`buildHierarchicalFilterGroup`)
  сворачиваемы (по умолчанию закрыты, кроме родителя); клик по потомку,
  если родитель сейчас выключен, включает и родителя (но не остальных
  потомков) — иначе включить одну стоянку при выключенном кране было
  невозможно. Функция поддерживает опциональный 3-й уровень
  (`grandchildConfig`) — сейчас единственный случай: Марка под Подтипом
  у группы "Тип элемента/Подтип/Марка"; два других вызова (Кран/Стоянка,
  Поставщик/Контракт) параметр не передают и работают как раньше.
- **Стоянка крана ≠ точка** — рабочая зона крана в конкретной позиции.
  Элемент без конкретной стоянки, но с известным краном — псевдо-значение
  `no-stance:<craneId>` (метка "вне стоянок"), ложится ДОЧЕРНИМ пунктом
  под свой кран, не в общий "не определено".
- **Лесенка сужения зоны стоянки с высотой** — на каждом ярусе колонн
  ближний к крану край окна стоянки отступает на 1 реальный пролёт
  сетки осей, следующая по номеру стоянка подхватывает уступленное.
  `scripts/zone_binding.build_stance_level_polygons` +
  `compute_column_tier_elevations`.
- **Цвета зон по крану** — `zone_colors` таблица ключуется
  `(source_file, category, name)`, НЕ `zones.id` (нестабилен между
  переимпортами — `upsert_zones` делает DELETE+INSERT каждый раз).
- **3D-режим** — Three.js 0.160.0, вендорено ЛОКАЛЬНО. Перед вендорингом
  стороннего кода ОБЯЗАТЕЛЬНО явное подтверждение пользователя — уже
  было получено ("подтверждаю"), но при любом НОВОМ стороннем коде
  правило действует снова. Координатное отображение: `world.X=dxf.x`,
  `world.Z=-dxf.y` (внимательно с знаком — уже был баг зеркальности).
  `OrbitControls.zoomSpeed=4` (дефолт 1 слишком медленный для трекпада).
  Граница элемента (не путать с заливкой) — `build3DOutlineMesh`,
  третья по счёту версия после двух неудачных (см. `Docs/TZ.md` §6.7)
  — GL-линии (`LineBasicMaterial.linewidth`) не работают в большинстве
  браузеров, а «шире+ниже» ломалось на впритык примыкающих элементах и
  вызывало z-fighting снизу; текущая версия строит границу по истинному
  контуру, а цветной меш уже (`OUTLINE_INNER_SCALE=0.94`) и с запасом
  по высоте с обеих сторон (`OUTLINE_VERTICAL_MARGIN_MM=15`).
- **Docs/TZ.md обновляется на КАЖДОЕ функциональное изменение** без
  напоминания — стоячая инструкция, отдельно от этого файла.
- **Партия** (`app/batches.py`, свой роутер, как `app/contracts.py`) —
  дочерняя сущность контракта, детализация плана до МАРКИ (не типа),
  назначение элемента на партию — независимое действие от смены
  статуса (доступно из того же контекстного меню, всегда, а не условно).
  `elements.batch_id` — простое живое поле, БЕЗ версионирования по
  `status_history` (в отличие от `contract_id`). Жёсткий отказ при
  несовпадении марки/типа/подтипа со строкой партии, мягкое
  предупреждение (не блокирует) при овербукинге. NULL-safe уникальность
  строк партии — обычный SQLite `UNIQUE` не считает `NULL=NULL`, нужен
  `COALESCE`-индекс, иначе строки без подтипа/марки дублируются молча.
  Self-service паттерн (`current["role"] != "admin" and current["id"]
  != user_id` → 403) переиспользован из `set-password` для
  `PATCH /users/{id}/label-color` — эталон для будущих персональных
  настроек.
- **«Рабочая дата» (backdating)** — `current_status`/`contract_id`
  элемента всегда вычисляются как значение из ПОСЛЕДНЕЙ ПО `changed_at`
  записи `status_history`, не последней по вставке. Кнопка «Сейчас» в
  тулбаре ЗАПОЛНЯЕТ рабочую дату текущим временем, но НЕ деактивирует
  поле — раньше это давало баг «статус не меняется» (застрявшая старая
  рабочая дата делала новую запись хронологически раньше уже
  существующей). Теперь есть отдельная кнопка «✕», которая ОЧИЩАЕТ
  рабочую дату (система переходит на текущее системное время), и диалог
  смены статуса всегда явно показывает и даёт поменять дату/время
  применения на месте.

## Текущий статус (2026-07-19)

Реализовано и проверено изолированными тестами + живым сервером (curl),
без живой браузерной проверки (см. предупреждение выше):

- **Партия** — полный цикл: контракт (поля дата+код) → партия (дата +
  строки тип/подтип/марка→кол-во, метка «Контрагент. Номер и дата
  контракта. Дата» собирается на сервере) → назначение элемента на
  партию → мягкое предупреждение при овербукинге / жёсткий отказ при
  несовпадении марки → допстрока подписи на схеме (2D+3D) «код. дата
  партии» для статусов Контрактация/В производстве/Отгружен → откат.
  Диалог смены статуса — всегда с явной датой/временем применения и
  доступом к назначению партии (не только при первом уходе с
  "Запланирован"). Контекстное меню — пункт «Партия» всегда виден
  (disabled вместо условного скрытия).
- **3D-граница элементов** — видна на любых элементах, включая впритык
  примыкающие (плиты перекрытия), без мерцания при взгляде снизу —
  третья версия геометрии, см. «Ключевые решения» и `Docs/TZ.md` §6.7.
- **Контраст подписей** — белая подложка в 3D (canvas), белый контур
  вокруг букв в 2D (`stroke`+`paint-order`, замена буквальной подложки —
  риск точного позиционирования `<rect>` под контрфлипом `scale(1,-1)`
  без браузера признан неприемлемым).
- **Персональный цвет подписей марок** — настройка на пользователя
  (`users.label_color`), видно всем ролям, как смена пароля.
- Более ранние (2026-07-15…07-17), тоже завершённые раунды: марка как
  3-й уровень фильтра, постоянные подписи марок в 3D, три пункта
  безопасности (`escapeHtml()` в ~17 местах, rate-limit на `/login` по
  IP — 5 попыток/300с, cookie `secure` через `ZHBI_SECURE_COOKIES`),
  новый тип «Плита перекрытия» + 2 новых яруса, лесенка сужения зоны
  стоянки с высотой, групповая смена статуса, иерархический фильтр
  «Поставщик/Контракт», учёт повреждённых элементов у контракта. Полная
  хронология и обоснования каждого — `Docs/backlog.md` по датам.

## Что это

ЖБИ-трекер: веб-инструмент для отслеживания статусов поставки и монтажа
сборных железобетонных элементов на стройплощадке. Чертежи — DXF,
загружаются через UI или из папки `Input/` по команде. Данные — марка, тип,
координаты, адрес по осям, привязка к зонам (захватка/кран/стоянка),
статус, контракт, даты, история. Клиенты — браузер на Windows, установка не
нужна, только сетевой доступ.

Что в системе УЖЕ есть — `Docs/MAP.md` (справочники, три рабочих места,
восемь отчётов, документы контрактации, график СМР, настройка ролей,
обучение, резервные копии, стражи). Заглядывать туда ДО того, как писать
новое: половина «новых» задач там уже закрыта.

## ⚠ Работа ведётся на ОБЕЗЛИЧЕННОЙ копии БД (с 2026-08-03)

Всё, что попадает в контекст ассистента, уходит на сторонние серверы: файлы,
вывод команд, **скриншоты**. Реквизиты заказчика за корпоративный контур
выносить нельзя.

- Отладка и живая браузерная проверка — **только** на `data/zhbi.anon.db`
  (конфигурация `zhbi-server-anon`, порт 8020). Нагрузка боевая (9422
  элемента, геометрия, статусы, история), данные самоочевидно фиктивные.
- Пересобрать копию: `.venv/bin/python scripts/anonymize_db.py` (сам
  проверяет результат на утечки). Пароль в копии задаёт пользователь:
  `ZHBI_DB_PATH=data/zhbi.anon.db .venv/bin/python scripts/reset_password.py admin`.
- **Боевые данные** (`zhbi-server`, порт 8000, `data/zhbi.db`) запускает
  ПОЛЬЗОВАТЕЛЬ; ассистент их не открывает и скриншотов не делает.
- **Реструктуризация БД применяется и к боевому файлу.** Порядок: обкатать
  миграцию на копии → `scripts/dry_run_migration.py` на боевом файле → бэкап →
  боевой файл мигрирует сам при старте `zhbi-server` → **пересобрать
  обезличенную копию**. Ловушка: миграции, решения которых зависят от
  ЗНАЧЕНИЙ (сравнение названий, регистр кириллицы, склейка дублей), на копии
  ведут себя ИНАЧЕ — холостой прогон на боевом файле обязателен.
- Локальный `uvicorn --reload` не должен смотреть на `data/zhbi.db`:
  автоперезагрузка применяет миграцию раньше, чем её проверили (уже дважды
  стоило схемы). Для этого есть `zhbi-server-testcopy` (`data/zhbi.check.db`).
  **Пользователь держит свой сервер на 8000 именно так** (боевая база +
  `--reload`) — знает и принял; перед правкой схемы напоминать про копию.
- **`--reload` требует `watchfiles`** (`requirements-dev.txt`): без него
  uvicorn молча берёт `StatReload`, который тут не срабатывал вовсе — сервер
  три часа отдавал уже исправленную ошибку. Правка «не применилась» — сначала
  проверить время старта процесса
  (`ps -o pid,lstart -p $(lsof -tiTCP:8000 -sTCP:LISTEN)`) и лог
  `logs/uvicorn-8000.log`; детали — `Docs/backlog.md` 08-03.
- `.claude/settings.json` — `deny` на чтение боевой БД, карты соответствий,
  `Input/`, `uploads/`, `test_data/`, `Модели/`, `.env`.
- Принято осознанно: геометрия, отметки, сетка осей, марки и даты в копии
  РЕАЛЬНЫЕ — иначе не отлаживаются привязка к зонам, 3D и наклейки. Если
  тайной является само здание — работать на синтетике
  (`scripts/generate_test_zones_dxf.py`).
- Открыто, кодом не закрывается: реквизиты заказчика лежат в отслеживаемых
  git-файлах (`Docs/*`, образцы в `app/import_templates.py`) и уже в истории
  на GitHub. Детали — `Docs/backlog.md` 08-03.

## Стоячие инструкции

- `Docs/TZ.md` обновляется на КАЖДОЕ функциональное изменение, без
  напоминания. `CLAUDE.md`, `Docs/MAP.md`, `Docs/OPEN.md` — при значимых.
  `Docs/ARCHITECTURE.md` — только по явной просьбе.
- **Всегда задавать уточняющие вопросы**, если в требовании возможны
  разночтения (08-04).
- Если просишь пользователя что-то проверить или сделать — давай команду.
- **Текст новой записи в `app/changelog.py` согласовывается с пользователем**
  до добавления. Не добавлять по своей инициативе.
- **Любой НОВЫЙ сторонний код вендорится только с явного подтверждения**
  (Three.js и `lines/`-примеры подтверждены отдельно, это не индульгенция).
- Живой браузер (Claude Browser pane) — способ верификации UI по умолчанию, а
  не изолированные скрипты. На больших файлах живой zoom/pan подвисает — для
  навигации дёргать `setView(...)`/сцену Three.js через `javascript_tool`.
- Инвентаризация чего-либо по коду — скриптом по AST, НЕ регуляркой и не
  глазами: регулярка находила 11 из 54, глаза пропускали десятки.
- **Обработка данных, нужная новой версии, добавляется в
  `app/release_tasks.py`**, а не отдельным скриптом: она обязана выполниться
  сама при старте после обновления.
- **При изменении текста инлайнового `<script type="importmap">` пересчитать
  sha256 в `_CSP` (`app/main.py`)** — иначе 3D тихо ломается. Хэш считать по
  `el.textContent` из браузера, не regex'ом по исходнику.
- **Вставляешь функцию перед `on_startup` в `app/main.py` — проверь, кому
  достался `@app.on_event("startup")`**: 08-14 его забрала вставленная выше
  функция, и сервер трое суток поднимался БЕЗ миграций. Ловится стражем при
  импорте, снимать его нельзя (`Docs/backlog.md` 08-17).
- **Рабочее дерево бывает НЕ ТОЛЬКО твоё** (08-14): пользователь держит две
  сессии над одним каталогом. Перед задачей — коммит-точка
  (`git add -A && git commit -m "wip: перед <задачей>"`), тогда откат это
  `git revert`, а не возня с деревом. `git checkout -- <файл>`, `git stash`,
  `git restore` — только после сверки `git status` со снимком на начало
  сессии: они не различают, чья строка. Что появилось в дереве не от тебя —
  не трогать, спрашивать (`Docs/backlog.md` 08-14).
- **Параллельная работа — в отдельном worktree.** Просят работать параллельно
  (или видишь чужие правки в дереве) — уходи в worktree сразу, каталог
  `.claude/worktrees/` уже в `.gitignore`. Ответвление от `origin/main`; если
  локальные коммиты не запушены — от текущего HEAD. В worktree нет `.venv`,
  `data/`, `node_modules` (их нет в git) — симлинк на `.venv` основного
  каталога и своя копия `data/zhbi.anon.db`; порт сервера подберётся сам
  (`autoPort` в `.claude/launch.json`). Схему БД в общей копии базы не
  мигрировать — вторая сессия читает тот же файл.

## Git и деплой

Локальный репозиторий, ветка `main`, разработку ведёт ОДИН человек —
пользователь. Три коммита от `@mcy-1.ru` — DevOps-инженеры корпоративного
контура (README, `.gitlab-ci.yml`, `docker-compose.yml` под реестр); за
второго разработчика их не принимать.

Два удалённых репозитория (`Docs/DEPLOYMENT_LINUX.md` §3): `origin` =
приватный GitHub, зеркало для разработки, серверы с ним не взаимодействуют;
`gitlab` = корпоративный, с CI/CD. Ветки на GitLab: `develop` и
`production` — пуш в них разворачивает через пайплайн. **На сервере
`develop` (10.190.15.25) сейчас БОЕВЫЕ данные** (08-19): тестовым он станет
после запуска отдельного боевого под HTTPS, а пока пуш в `develop` применяет
миграции к живым данным. Холостой прогон — на копии базы ИМЕННО того сервера,
куда выкатываем. С Mac
пуш идёт refspec'ом: `git push gitlab main:develop`. Корпоративный GitLab
доступен только через VPN, а под VPN недоступен Claude Code — пуш и SSH
пользователь делает сам, вне сессии. Код уходит на серверы ТОЛЬКО пушем в
`develop`/`production` (вопрос закрыт 08-02); по SSH пользователь заходит для
эксплуатации — откат на предыдущий образ и восстановление базы
(`Docs/DEPLOYMENT_LINUX.md` §4).

**Обновление ничего не требует от человека на сервере** (08-04). Всё, что
новая версия должна сделать с накопленными данными, — запись в реестре
`app/release_tasks.py`, а НЕ скрипт в `scripts/`: скрипт нужно кому-то
запустить, а запускать некому. Порядок первого старта: копия базы → миграции
схемы → обработки → версия базы догоняет версию кода. Копия есть перед ЛЮБОЙ
обработкой данных (08-10). Обработки идемпотентны, упавшая не роняет старт и
повторяется кнопкой в «Что нового» (закладка «Обновление»). Перед деплоем —
`scripts/dry_run_migration.py` на копии боевой базы: он прогоняет и миграции,
и обработки, причём обработки дважды — второй проход проверяет
идемпотентность на реальных данных. Релиз только ДОБАВЛЯЕТ; уборка отжившего
— отдельный вид обработки, только по кнопке админа. Подробности —
`Docs/DECISIONS.md`, «Обновление и обработки данных».

`test_data/` (147 МБ чертежей заказчика) держится ВНЕ git — это данные, а не
код (вопрос закрыт, заново не поднимать).

## Стек и структура

- **Backend**: FastAPI + Starlette (синхронные `def`-роуты, threadpool),
  SQLite в режиме WAL (с 08-14, `app/db.py`; на сетевой ФС перевод может не
  пройти — тогда читатели снова ждут пишущих). Файлы-спутники `*.db-wal` и
  `*.db-shm` в git не уходят. Сессии — cookie, 30 дней.
- **Frontend**: `app/static/index.html` + `app/static/app.js` (~14,5 тыс.
  строк) — vanilla JS, SVG для 2D, Three.js (вендорено локально) для 3D.
  Сборщика и фреймворка нет.
- **Импорт DXF** — два параллельных конвейера, старый не трогать при правке
  нового: старый (`scripts/parse_zhbi.py`, `LAYER_CONFIG`) — плоские слои;
  новый стандарт имён (`scripts/layer_naming.py`,
  `scripts/new_standard_pipeline.py`) — слои `WEB_констр_…`/`WEB_тех_…`, с
  зонами, подтипами, отметками; только он поддерживает зоны и 3D. Оси —
  `scripts/assign_axes.py`, зоны — `scripts/zone_parser.py` +
  `scripts/zone_binding.py`, оркестрация загрузки через UI —
  `app/dxf_import.py` (переиспользует те же функции, что CLI-скрипты).
- **Тесты**: pytest-сюиты нет. Методология — изолированные Python/Node-скрипты
  в scratchpad на РЕАЛЬНЫХ данных (`plan_data()`/прямые SQL), один сквозной
  синтетический тест `scripts/verify_zone_pipeline.py`, живой браузер как
  основной способ проверки UI, плюс стражи из `Docs/MAP.md`.
- **git-хук `pre-commit`** (08-18) гоняет `scripts/check_undefined_names.py` по
  проиндексированным `.py` — не пускает в коммит обращение к имени, которого
  нет (таким четыре дня не открывался справочник контрагентов) — и
  `scripts/check_activity_actions.py` (08-20): новое событие журнала без
  русской подписи и категории в коммит тоже не проходит. Хук в git не
  версионируется, поэтому ставится командой:
  `.venv/bin/python scripts/install_git_hooks.py`. Разовый обход —
  `git commit --no-verify`.
- **Новое событие журнала = строка в `app/activity_actions.py`** (08-20):
  один реестр «код действия → подпись + категория» на журнал и на отчёт
  «Моя работа». Ошибки сервера и браузера пишутся туда же сами
  (`app/error_log.py`), руками их логировать не нужно.

## Ключевые решения

Вынесены в `Docs/DECISIONS.md` (08-04) — инварианты, которые нельзя нарушить,
с причинами: данные и доступ; импорт DXF, зоны, геометрия; статусы, история,
контрактация; Excel-обмен; интерфейс (фильтры, подписи, 2D/3D); отчёты и
журнал; безопасность и вход. **Читать по надобности — перед правкой
соответствующей части**, а не целиком при старте сессии. Обновлять при
значимых изменениях архитектуры, как и этот файл.

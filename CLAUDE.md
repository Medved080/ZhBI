## Что это

ЖБИ-трекер: веб-инструмент для отслеживания статусов поставки и монтажа
сборных железобетонных элементов на стройплощадке. Чертежи — DXF,
загружаются через UI или из папки `Input/` по команде. Данные — марка, тип,
координаты, адрес по осям, привязка к зонам (захватка/кран/стоянка),
статус, контракт, даты, история. Клиенты — браузер на Windows, установка не
нужна, только сетевой доступ.

**Что ещё в системе есть** (чтобы не изобретать заново; подробности —
`Docs/TZ.md`): справочники элементов, зон, контрагентов, контрактов,
подтипов, МАРОК (`app/marks.py`, с 08-05: владелец — тип, область —
объект) и префиксов марок; удаление любой записи справочника с
переводом ссылок на замену (`app/dict_delete.py`, только администратор
сервиса); вложения к проекту/объекту/изделию и
комментарий к изделию (`app/attachments.py`); отчёты «Статус монтажа»,
«Отчёт о динамике поставки и монтажа», «График поставки», «Статус
комплектации», «Моя работа», «График контрактации и поставки»,
«Аналитическая справка» (08-11: что мешает стройке сейчас — контрактация
под ближайшие этапы СМР и критический путь поставки,
`app/report_analytics.py`; сроки считаются очередью завода из его
производительности, `app/capacity.py`) — у отчёта бывает признак
«в разработке» (`IN_DEVELOPMENT`, только пометка, доступ не режет);
второе рабочее место «АРМ комплектовщика» (переключатель в тулбаре
рядом с 2D/3D; дашборд из блоков-срезов и количественных показателей,
свой отбор, отдельный от фильтров «Модели»; пока виден только
администратору сервиса — `Docs/TZ.md` §6.8);
журнал действий с очисткой;
документы контрактации, группа меню «Документы» (`app/supplier_change.py`,
08-11, `Docs/TZ.md` §5.6): «Замена поставщика» и «Обмен привязками»
(подбор рамкой на схеме); оба проводятся, проведение отменяемо;
перенос базы ЦЕЛИКОМ между серверами — четвёртый режим массовой правки,
полная ЗАМЕНА снимком, не дополнение (`app/db_transfer.py`, 08-11);
резервные копии (`app/backups.py`); экран «Состояние БД»
(`app/db_status.py`); памятка администратора с командами обслуживания
(`app/admin_guide.py`); журнал версий сервиса (`app/changelog.py`, кнопка
«?»); цвет подписей марок; массовая смена статуса рамкой; групповая
настройка прав и отчёт «Матрица прав» (`app/rights_matrix.py`);
отладочный режим «Зайти под пользователем» (`app/impersonation.py`);
инвентаризация эндпоинтов (`scripts/audit_endpoints.py`).

## ⚠ Работа ведётся на ОБЕЗЛИЧЕННОЙ копии БД (с 2026-08-03)

Всё, что попадает в контекст ассистента, уходит на сторонние серверы:
файлы, вывод команд, **скриншоты**. Реквизиты заказчика за корпоративный
контур выносить нельзя.

- Отладка и живая браузерная проверка — **только** на `data/zhbi.anon.db`
  (конфигурация `zhbi-server-anon`, порт 8020). Нагрузка боевая (9422
  элемента, геометрия, статусы, история), данные самоочевидно фиктивные.
- Пересобрать копию: `.venv/bin/python scripts/anonymize_db.py` (сам
  проверяет результат на утечки). Пароль в копии задаёт пользователь:
  `ZHBI_DB_PATH=data/zhbi.anon.db .venv/bin/python scripts/reset_password.py admin`.
- **Боевые данные** (`zhbi-server`, порт 8000, `data/zhbi.db`) запускает
  ПОЛЬЗОВАТЕЛЬ; ассистент их не открывает и скриншотов не делает.
- **Реструктуризация БД применяется и к боевому файлу.** Порядок: обкатать
  миграцию на копии → `scripts/dry_run_migration.py` на боевом файле →
  бэкап → боевой файл мигрирует сам при старте `zhbi-server` → **пересобрать
  обезличенную копию**. Ловушка: миграции, решения которых зависят от
  ЗНАЧЕНИЙ (сравнение названий, регистр кириллицы, склейка дублей), на копии
  ведут себя ИНАЧЕ — их холостой прогон на боевом файле обязателен.
- Локальный `uvicorn --reload` не должен смотреть на `data/zhbi.db`:
  автоперезагрузка применяет миграцию раньше, чем её проверили (уже дважды
  стоило схемы). Для этого есть `zhbi-server-testcopy` (`data/zhbi.check.db`).
  **Пользователь держит свой сервер на 8000 именно так** (боевая база +
  `--reload`) — знает и принял; перед правкой схемы напоминать про копию.
- **`--reload` требует `watchfiles`** (`requirements-dev.txt`, в образ не
  входит). Без него uvicorn молча берёт запасной `StatReload`, который на
  этом проекте не срабатывал ВОВСЕ: сервер на 8000 три часа отдавал уже
  исправленную ошибку, потому что крутил старый код. Если правка «не
  применилась» — сначала проверить, когда стартовал рабочий процесс
  (`ps -o pid,lstart -p $(lsof -tiTCP:8000 -sTCP:LISTEN)`), а не искать
  ошибку в коде. Лог — `logs/uvicorn-8000.log`.
- `.claude/settings.json` — `deny` на чтение боевой БД, карты соответствий,
  `Input/`, `uploads/`, `test_data/`, `Модели/`, `.env`.
- Принято осознанно: геометрия, отметки, сетка осей, марки и даты в копии
  РЕАЛЬНЫЕ — иначе не отлаживаются привязка к зонам, 3D и наклейки. Если
  тайной является само здание — работать на синтетике
  (`scripts/generate_test_zones_dxf.py`).
- Открыто, кодом не закрывается: реквизиты заказчика лежат в отслеживаемых
  git-файлах (`Docs/*`, образцы в `app/import_templates.py`) и уже в истории
  на GitHub. Детали — `Docs/backlog.md` 2026-08-03.

- Живой браузер (Claude Browser pane) — способ верификации UI по умолчанию,
  а не изолированные скрипты. На больших файлах живой zoom/pan подвисает —
  для навигации дёргать `setView(...)`/сцену Three.js через `javascript_tool`.
- Инвентаризация чего-либо по коду — скриптом по AST, НЕ регуляркой и не
  глазами: регулярка уже находила 11 из 54, а глаза пропускали десятки.
- Если просишь пользователя что-то проверить или сделать — давай команду.
- **Всегда задавать уточняющие вопросы**, если в требовании возможны
  разночтения (стоячая инструкция пользователя 2026-08-04).
- **Обработка данных, нужная новой версии, добавляется в `app/release_tasks.py`**,
  а не отдельным скриптом: она обязана выполниться сама при старте после
  обновления.

## Git и деплой

Локальный репозиторий, ветка `main`, разработку ведёт ОДИН человек —
пользователь. Три коммита от `@mcy-1.ru` — DevOps-инженеры корпоративного
контура (README, `.gitlab-ci.yml`, `docker-compose.yml` под реестр); за
второго разработчика их не принимать.

Два удалённых репозитория (`Docs/DEPLOYMENT_LINUX.md` §3): `origin` =
приватный GitHub, зеркало для разработки, серверы с ним не взаимодействуют;
`gitlab` = корпоративный, с CI/CD. Ветки на GitLab: `develop` (тестовый
сервер) и `production` (прод) — пуш в них разворачивает через пайплайн. С
Mac пуш идёт refspec'ом: `git push gitlab main:develop`. Корпоративный
GitLab доступен только через VPN, а под VPN недоступен Claude Code — пуш и
SSH пользователь делает сам, вне сессии.

Код уходит на серверы ТОЛЬКО пушем в `develop`/`production` (вопрос закрыт
2026-08-02); по SSH пользователь заходит для эксплуатации — аварийный откат
на предыдущий образ и восстановление базы, `Docs/DEPLOYMENT_LINUX.md` §4.

**Обновление ничего не требует от человека на сервере** (08-04). Всё, что
новая версия должна сделать с накопленными данными, — запись в реестре
`app/release_tasks.py`, а НЕ скрипт в `scripts/`: скрипт нужно кому-то
запустить, а запускать некому. Порядок первого старта: копия базы →
миграции схемы → обработки → версия базы догоняет версию кода. Копия есть
перед ЛЮБОЙ обработкой данных (08-10): при смене версии хватает копии
старта, иначе (обработку дописали в вышедшую версию, повтор кнопкой)
снимается своя. Обработки
идемпотентны, упавшая не роняет старт и повторяется кнопкой в «Что нового»
(закладка «Обновление»). Перед деплоем — `scripts/dry_run_migration.py` на
копии боевой базы: он прогоняет и миграции, и обработки, причём обработки
дважды — второй проход проверяет идемпотентность на реальных данных.
Релиз только ДОБАВЛЯЕТ; уборка отжившего — отдельный вид обработки, только
по кнопке админа. Подробности — `Docs/DECISIONS.md`, «Обновление и обработки
данных», и `Docs/DEPLOYMENT_LINUX.md` §3.3.
`test_data/` (147 МБ чертежей заказчика) держится ВНЕ git — это данные, а не
код (вопрос закрыт, заново не поднимать).

## Стек и структура

- **Backend**: FastAPI + Starlette (синхронные `def`-роуты, threadpool),
  SQLite без WAL (`app/db.py`). Сессии — cookie, 30 дней.
- **Frontend**: `app/static/index.html` + `app/static/app.js` (~14,5 тыс.
  строк) — vanilla JS, SVG для 2D, Three.js (вендорено локально) для 3D.
  Сборщика и фреймворка нет.
- **Импорт DXF** — два параллельных конвейера, старый не трогать при правке
  нового: старый (`scripts/parse_zhbi.py`, `LAYER_CONFIG`) — плоские слои;
  новый стандарт имён (`scripts/layer_naming.py`,
  `scripts/new_standard_pipeline.py`) — слои `WEB_констр_…`/`WEB_тех_…`, с
  зонами, подтипами, отметками; только он поддерживает зоны и 3D. Оси —
  `scripts/assign_axes.py`, зоны — `scripts/zone_parser.py` +
  `scripts/zone_binding.py`, оркестрация загрузки через UI —
  `app/dxf_import.py` (переиспользует те же функции, что CLI-скрипты).
- **Тесты**: pytest-сюиты нет. Методология — изолированные Python/Node-
  скрипты в scratchpad на РЕАЛЬНЫХ данных (`plan_data()`/прямые SQL), один
  сквозной синтетический тест `scripts/verify_zone_pipeline.py`, плюс живой
  браузер как основной способ проверки UI.

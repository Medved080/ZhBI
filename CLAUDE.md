## Что это

ЖБИ-трекер: веб-инструмент для отслеживания статусов поставки/монтажа
сборных железобетонных элементов на стройплощадке. Чертежи — DXF,
загружаются через UI или кладутся в `Input/` (подхватываются при
старте сервера). Данные — марка, тип, координаты, адрес по осям,
привязка к зонам (захватка/кран/стоянка), статус, контракт, история.

## Стек и структура

- **Backend**: FastAPI + Starlette (синхронные `def`-роуты, threadpool),
  SQLite без WAL (`app/db.py`). Сессии — cookie, 30 дней. Три роли
  пользователей.
- **Frontend**: один файл `app/static/index.html` (~4000+ строк) —
  vanilla JS + SVG для 2D-схемы, Three.js (вендорено локально,
  `app/static/vendor/three/`, НЕ CDN — см. "Ключевые решения" ниже) для
  3D-режима. Никакого сборщика/фреймворка.
- **Импорт DXF** — два параллельных конвейера, старый не трогать при
  правке нового:
  - Старый (`scripts/parse_zhbi.py`, `LAYER_CONFIG`) — плоские слои без
    зон/подтипов/отметок.
  - Новый стандарт имён (`scripts/layer_naming.py`,
    `scripts/new_standard_pipeline.py`) — слои `WEB_констр_...` /
    `WEB_тех_...`, с зонами, подтипами, отметками. Только новый
    конвейер поддерживает зоны и 3D.
  - Адресация по осям — `scripts/assign_axes.py` (общая для обоих).
  - Зоны (захватка/кран/стоянка) — `scripts/zone_parser.py` (реестр,
    сопоставление названий, связь стоянка→кран) +
    `scripts/zone_binding.py` (привязка элемента к зоне).
  - Оркестрация загрузки через UI — `app/dxf_import.py` (сохранить →
    распарсить → адресовать → записать), переиспользует те же функции,
    что и CLI-скрипты `scripts/*.py`.
- **Тесты/проверка** — нет pytest-сюиты; методология: изолированные
  Python/Node-скрипты в `/tmp`, тестирующие извлечённые функции на
  РЕАЛЬНЫХ данных из `data/zhbi.db` (`plan_data()`/прямые SQL-запросы),
  плюс один сквозной синтетический тест `scripts/verify_zone_pipeline.py`
  (`test_data/synthetic_zones.dxf`, генерится
  `scripts/generate_test_zones_dxf.py`). Живого браузерного тестирования
  нет (нет инструмента автоматизации браузера в этой среде) — это
  открытый пробел, проговаривается пользователю после каждого раунда UI-
  правок.

## Ключевые решения (коротко, детали — в Docs/backlog.md по дате)

- **Единый русский словарь `element_type`** — Колонна/Ригель/Плита/
  Панель, миграция идемпотентна (`app/db._normalize_element_type_vocabulary`).
- **Фильтры на клиенте** (`app/static/index.html`) — архитектура "полный
  список значений всегда виден + недоступен (disabled), не сужается" —
  фикс двух багов самоблокировки. `PLACEMENT_CASCADE_GROUPS` = группы
  [`elementType`,`subtype`,`mark`] и [`crane`,`stance`], [`supplier`,`contract`]
  — при расчёте доступности одной категории группы фильтр ОСТАЛЬНЫХ
  игнорируется. Иерархические группы (`buildHierarchicalFilterGroup`)
  сворачиваемы (по умолчанию закрыты, кроме родителя); клик по потомку,
  если родитель сейчас выключен, включает и родителя (но не остальных
  потомков) — иначе включить одну стоянку при выключенном кране было
  невозможно. С 2026-07-17 функция поддерживает опциональный 3-й
  уровень (`grandchildConfig`) — сейчас единственный случай: Марка под
  Подтипом у группы "Тип элемента/Подтип/Марка"; два других вызова
  (Кран/Стоянка, Поставщик/Контракт) параметр не передают и работают
  как раньше (регресс-проверено).
- **Стоянка крана ≠ точка** — рабочая зона крана в конкретной позиции.
  Элемент без конкретной стоянки, но с известным краном — псевдо-значение
  `no-stance:<craneId>` (метка "вне стоянок"), ложится ДОЧЕРНИМ пунктом
  под свой кран, не в общий "не определено".
- **Лесенка сужения зоны стоянки с высотой** (главная фича последнего
  раунда, см. ниже) — на каждом ярусе колонн ближний к крану край окна
  стоянки отступает на 1 реальный пролёт сетки осей, следующая по номеру
  стоянка подхватывает уступленное. `scripts/zone_binding.
  build_stance_level_polygons` + `compute_column_tier_elevations`.
- **Цвета зон по крану** — `zone_colors` таблица ключуется
  `(source_file, category, name)`, НЕ `zones.id` (нестабилен между
  переимпортами — `upsert_zones` делает DELETE+INSERT каждый раз).
- **3D-режим** — Three.js 0.160.0, вендорено ЛОКАЛЬНО. Перед вендорингом
  стороннего кода ОБЯЗАТЕЛЬНО явное подтверждение пользователя — уже
  было получено ("подтверждаю"), но при любом НОВОМ стороннем коде
  правило действует снова. Координатное отображение: `world.X=dxf.x`,
  `world.Z=-dxf.y` (внимательно с знаком — уже был баг зеркальности).
  `OrbitControls.zoomSpeed=4` (дефолт 1 слишком медленный для трекпада).
- **Docs/TZ.md обновляется на КАЖДОЕ функциональное изменение** без
  напоминания — стоячая инструкция, отдельно от этого файла.

## Статус на 2026-07-17 (текущий раунд — все 4 пункта завершены)

**Раунд из 3 пунктов + безопасность** (все ✅, детали — `Docs/backlog.md`,
"Раунд из 3 пунктов" и "Исправления по безопасности — реализовано"):
1. **Подписи марок пропадали на плотных многоярусных файлах** —
   причина: `estimate_marker_radius` (`app/main.py`) считал медианное
   расстояние до ближайшего соседа по ВСЕМ элементам выборки, не
   исключая элементы одного следа на разных ярусах (колонна/ригель с
   одинаковой X,Y на разных отметках) — на файле с 4 ярусами (~46%
   элементов имеют такого двойника) медиана рухнула до 0.0013 мм,
   маркеры/подписи стали невидимы. Такие соседи (≤50мм,
   `SAME_FOOTPRINT_TOLERANCE_MM`) больше не считаются; заодно переписано
   на `shapely.strtree.STRtree` (O(n²) ~4.2с → ~0.03с на 5330 эл.).
2. **Марка как 3-й уровень фильтра** (Тип→Подтип→Марка) — заказчик
   выбрал обычный список без поиска. `buildHierarchicalFilterGroup`
   генерализована опциональным `grandchildConfig` (см. "Ключевые
   решения" выше); 22 изолированные Node-проверки на реальных данных
   (каскад в обе стороны + регресс 2-уровневых групп).
3. **Постоянные подписи марок в 3D** — заказчик выбрал: спрайты
   (`THREE.Sprite` + canvas-текстура, БЕЗ нового вендоринга — только уже
   провендоренное ядро Three.js), для всех элементов сразу, тот же
   тумблер видимости, что в 2D (`state.labelVisibility`). Масштаб — от
   `state.baseMarkerRadius` (тот же параметр, что у 2D). **Живой
   проверки в браузере (плавность на 5330 эл.) не было** — нет
   инструмента автоматизации браузера, явно сообщено пользователю.
4. **3 пункта безопасности** (были в бэклоге с 2026-07-15,
   нереализованы) — `escapeHtml()` + обёрнуты все интерполяции
   untrusted-данных в `innerHTML` (~17 мест); rate-limit на
   `POST /login` по IP (5/5мин, 429, in-memory); cookie `secure` через
   `ZHBI_SECURE_COOKIES` (по умолчанию выключено — деплой сейчас на
   HTTP). Все проверены живым сервером (`curl`), не только изолированно.

**Марка плит перекрытия из нескольких TEXT-фрагментов** (та же сессия) —
слой марок плит не имеет выносок вообще, марка "4П-1" нарисована как 3
отдельных TEXT ("4П","-","1"). Новая `scripts/parse_zhbi.
resolve_via_polygon_texts()` — марка = фрагменты ВНУТРИ контура
элемента, склеенные по порядку чтения (проекция на поворот текста),
эксклюзивно (STRtree + глобальный жадный алгоритм по расстоянию до
центроида — тот же принцип, что уже был в `resolve_via_leaders`).
**Важно**: применяется ТОЛЬКО когда на слое марок нет ни одной
LEADER/MULTILEADER — иначе ломает Ригель/Колонну (было поймано именно
так — `git stash` + сравнение с поведением до правки, см.
`Docs/backlog.md`, "Плиты перекрытия — марка из нескольких текстовых
фрагментов"). Урок на будущее: при любой новой логике резолвинга марки
ВСЕГДА сравнивать mark_source-статистику ДО/ПОСЛЕ по ВСЕМ типам
элементов группы, не только по тому типу, для которого делалась правка.

Более раннее (2026-07-16), тоже завершено и проверено (детали —
`Docs/backlog.md` по датированным разделам): пакет из 9 UI/UX-правок

Все изменения проверены: `node --check`, `python3 -m py_compile`,

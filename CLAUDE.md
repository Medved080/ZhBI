# CLAUDE.md — сводка проекта для быстрого старта сессии

Держать этот файл кратким (100–200 строк) и обновлять при значимых
изменениях архитектуры/статуса — по стоячей инструкции пользователя, без
напоминания. Подробности — в `Docs/TZ.md` (живой тех.спек, обновляется на
каждое функциональное изменение), `Docs/ARCHITECTURE.md` (технический
снимок «как устроено и почему» — компоненты, алгоритмы, инварианты,
техдолг; обновляется по явной просьбе) и `Docs/backlog.md` (датированный
журнал с причиной/фиксом/проверкой каждого раунда работ).
`Docs/requirements-notes.md` — точечные уточнения по реальным данным
заказчика (форматы DXF, адресация по осям), на них ссылается сам
`Docs/TZ.md`. `Docs/DEPLOYMENT_LINUX.md` — установка/обновление сервера
на Ubuntu Server LTS через **Docker** (`Dockerfile`/`docker-compose.yml`
в корне, скрипты в `scripts/linux/`; **не проверено ни на реальном
Ubuntu, ни локальной сборкой** — на Mac разработчика нет ни Docker, ни
Homebrew, см. предупреждение в самом файле и `Docs/backlog.md`).
Клиенты (браузер) — на Windows, никакой установки не требуют, только
сетевой доступ к серверу.

## Как продолжить работу с нуля (новая сессия/новое приложение)

Порядок чтения для полного погружения без потерь контекста: **этот
файл** (текущее состояние и пойнтеры) → `Docs/ARCHITECTURE.md` (как
устроено технически) → `Docs/TZ.md` (что система делает, вся бизнес-
логика) → `Docs/backlog.md` (хронология — зачем сделано именно так,
какие баги уже находили и чинили, чтобы не наступить повторно). Все три
документа поддерживаются в актуальном состоянии как часть обычной
работы, не только «под занавес» — можно доверять их текущему
содержимому, а не только этому файлу.

**Git** (с 2026-07-16, схема remote — с 2026-07-24): локальный
репозиторий инициализирован, ветка `main`. **Два** удалённых
репозитория, разные роли (`Docs/DEPLOYMENT_LINUX.md` §3): `origin` =
GitHub, приватный, основной для разработки, просто резервная копия/
зеркало — серверы с ним не взаимодействуют; `gitlab` = корпоративный
GitLab, единственный источник кода для тестового и продуктового
серверов (пуш туда — отдельный явный шаг, не при каждом коммите). Сами
репозитории на GitHub/GitLab и доступ к ним создаёт пользователь
руками, я только добавляю remote и пушу по его подтверждению. Модель
веток без изменений: `main` = разработка, теги релизов (`vГГГГ.ММ.ДД`)
= что ставится на продакшен (`scripts/linux/update-test.sh`/
`update-prod.sh`, выбор тега вручную). Открытый вопрос: включать ли
`test_data/` (147 МБ реальных чертежей заказчика, пока НЕ в git) в
историю репозитория — см. §3.7 `Docs/DEPLOYMENT_LINUX.md`.

**Живой браузер доступен** (Claude Browser pane, с 2026-07-22) — первая
живая сессия сразу нашла 5 багов, которые изолированные Python/Node-
тесты не ловили (см. `Docs/backlog.md`, "Первая живая браузерная сессия").
Использовать его для верификации UI-правок по умолчанию, не только
изолированные скрипты + curl. При крупных файлах (5000+ элементов)
живой zoom/pan через `computer{action:"scroll"}` может подвисать на
десятки секунд — надёжнее дергать `setView(...)`/сцену Three.js напрямую
через `javascript_tool` для навигации и диагностики (см. пример подхода
в свежей записи backlog).

## Что это

ЖБИ-трекер: веб-инструмент для отслеживания статусов поставки/монтажа
сборных железобетонных элементов на стройплощадке. Чертежи — DXF,
загружаются через UI (кнопка «Загрузить чертёж», `POST /import-dxf`)
или кладутся в `Input/` (подхватываются при старте сервера — основной
способ). Данные — марка, тип, координаты, адрес по осям, привязка к
зонам (захватка/кран/стоянка), статус, контракт, партия, история.

## Стек и структура

- **Backend**: FastAPI + Starlette (синхронные `def`-роуты, threadpool),
  SQLite без WAL (`app/db.py`). Сессии — cookie, 30 дней. Три роли
  пользователей (`admin`/`user`/`view`), обязательный вход для всех
  действий, включая просмотр схемы.
- **Frontend**: один файл `app/static/index.html` (~4800+ строк) —
  vanilla JS + SVG для 2D-схемы, Three.js (вендорено локально,
  `app/static/vendor/three/`, НЕ CDN — см. "Ключевые решения" ниже) для
  3D-режима. Никакого сборщика/фреймворка.
- **Импорт DXF** — два параллельных конвейера, старый не трогать при
  правке нового:
  - Старый (`scripts/parse_zhbi.py`, `LAYER_CONFIG`) — плоские слои без
    зон/подтипов/отметок.
  - Новый стандарт имён (`scripts/layer_naming.py`,
    `scripts/new_standard_pipeline.py`) — слои `WEB_констр_...` /
    `WEB_тех_...`, с зонами, подтипами, отметками. Только новый
    конвейер поддерживает зоны и 3D.
  - Адресация по осям — `scripts/assign_axes.py` (общая для обоих).
  - Зоны (захватка/кран/стоянка) — `scripts/zone_parser.py` (реестр,
    сопоставление названий, связь стоянка→кран) +
    `scripts/zone_binding.py` (привязка элемента к зоне).
  - Оркестрация загрузки через UI — `app/dxf_import.py` (сохранить →
    распарсить → адресовать → записать), переиспользует те же функции,
    что и CLI-скрипты `scripts/*.py` — обе точки входа не дублируют
    логику.
- **Тесты/проверка** — нет pytest-сюиты; методология: изолированные
  Python/Node-скрипты в `/tmp`, тестирующие извлечённые функции на
  РЕАЛЬНЫХ данных из `data/zhbi.db` (`plan_data()`/прямые SQL-запросы),
  плюс один сквозной синтетический тест `scripts/verify_zone_pipeline.py`
  (`test_data/synthetic_zones.dxf`, генерится
  `scripts/generate_test_zones_dxf.py`). С 2026-07-22 живой браузер
  доступен и используется как основной способ верификации UI (см.
  предупреждение выше).

## Ключевые решения (коротко, детали — в Docs/backlog.md по дате)

- **Единый русский словарь `element_type`** — Колонна/Ригель/Плита/
  Панель/Плита перекрытия, миграция идемпотентна
  (`app/db._normalize_element_type_vocabulary`).
- **Фильтры на клиенте** (`app/static/index.html`) — архитектура "полный
  список значений всегда виден + недоступен (disabled), не сужается" —
  фикс двух багов самоблокировки. `PLACEMENT_CASCADE_GROUPS` = группы
  [`elementType`,`subtype`,`mark`] и [`crane`,`stance`], [`supplier`,`contract`]
  — при расчёте доступности одной категории группы фильтр ОСТАЛЬНЫХ
  игнорируется. Иерархические группы (`buildHierarchicalFilterGroup`)
  сворачиваемы (по умолчанию закрыты, кроме родителя); клик по потомку,
  если родитель сейчас выключен, включает и родителя (но не остальных
  потомков) — иначе включить одну стоянку при выключенном кране было
  невозможно. Функция поддерживает опциональный 3-й уровень
  (`grandchildConfig`) — сейчас единственный случай: Марка под Подтипом
  у группы "Тип элемента/Подтип/Марка"; два других вызова (Кран/Стоянка,
  Поставщик/Контракт) параметр не передают и работают как раньше.
  Ключ подтипа (`subtypeFilterValue`) — составной, тип+текст
  (`subtypeLogicalKey`, разделитель `::`, с 2026-07-24), НЕ голый текст —
  текст подтипа намеренно переиспользуется между типами в справочнике
  (например, "на отм. +15.000" одновременно у Ригеля и Плиты перекрытия),
  раньше это давало баг: снятие галочки с одного типа каскадом скрывало
  элементы ДРУГОГО типа с тем же текстом подтипа (живой репорт
  пользователя, см. `Docs/backlog.md`). Тот же приём составного ключа,
  что у стоянок (`stanceLogicalKey`) и уже был в диалоге "Партия"
  (`buildBatchDialogMaps`) — теперь везде единообразно.
  `FLAT_MARK_TYPES = {"Плита перекрытия", "Ригель"}` — у этих типов
  подтип почти всегда буквально отметка (избыточно с отдельным фильтром
  "Отметка (высота)") — `subtypeFilterValue` для них кладёт в "слот
  подтипа" МАРКУ, марки становятся прямыми детьми типа (без
  промежуточного уровня); у Колонны подтип смысловой ("нижняя"/
  "верхняя"), не трогали.
- **2D-подписи марок — плашка, не контур** (с 2026-07-24) — `<rect
  class="mark-label-bg">` ПЕРЕД `<text class="mark-label">` в DOM
  (рисуется позади), тот же стиль, что уже был в 3D
  (`build3DLabelSprite`, `rgba(255,255,255,0.72)`). Размер бокса — без
  `getBBox()` (форсирует layout, дорого при тысячах элементов на каждый
  тик зума) — оценка по числу символов, та же константа 0.62×fontSize,
  что уже использует `updateLabelCollisionVisibility`. Видимость
  подложки синхронизирована с текстом через `labelBgByText`
  (`WeakMap`) + `setLabelDisplay()` — единая точка вместо правки 6 мест,
  где раньше менялся `label.style.display` напрямую.
- **3D-"наклейка" марки на грани** (`build3DMarkDecal`, с 2026-07-25) —
  для Плиты перекрытия (верх+низ), Ригеля (все 4 длинные грани — сечение
  квадратное, боковые того же размера, что верх/низ) и Колонны (все
  боковые грани, подтверждено явно заказчиком — не торец, вертикальная,
  текст снизу вверх) вместо плавающей таблички (`build3DLabelSprite`),
  если марка помещается по длине элемента (`DECAL_FIT_MARGIN=0.92`,
  оценка ширины той же константой 0.62×fontSize, что и в 2D) — иначе
  прежняя табличка, запасной вариант. Ориентация плоскости — явный
  ортонормированный базис (`orientDecalMesh`, `Matrix4.makeBasis`), не
  подбор углов вручную (тот же класс ошибок, что и у зеркальности всей
  сцены). Текстура — общая на МАРКУ (`decalTextureCache`), не на элемент
  (марки повторяются десятками раз). Наклейка НЕ билборд (лежит плоско
  на грани) — при вращении камеры может читаться вверх ногами;
  `updateDecalOrientation`/`updateAllDecalOrientations` пересчитывают на
  каждое движение `OrbitControls` (дёшево — только смена кватерниона у
  уже существующих мешей): разворот на 180° вокруг нормали, если "верх"
  текста (`cross(normal,right)`) сейчас направлен ОТ камеры.
- **Стоянка крана ≠ точка** — рабочая зона крана в конкретной позиции.
  Элемент без конкретной стоянки, но с известным краном — псевдо-значение
  `no-stance:<craneId>` (метка "вне стоянок"), ложится ДОЧЕРНИМ пунктом
  под свой кран, не в общий "не определено".
- **Лесенка сужения зоны стоянки с высотой** — ТОЛЬКО когда в файле
  физически один ярус стоянок (старые файлы, `WEB_тех_Стоянки
  крана_ОТМ00000`): на каждом ярусе колонн ближний к крану край окна
  стоянки отступает на 1 реальный пролёт сетки осей, следующая по
  номеру стоянка подхватывает уступленное.
  `scripts/zone_binding.build_stance_level_polygons` +
  `compute_column_tier_elevations`. Если заказчик уже нарисовал РЕАЛЬНЫЕ
  полигоны стоянок на НЕСКОЛЬКИХ ярусах (несколько разных `elevation_mm`
  среди зон категории "Стоянка") — лесенка ВЫКЛЮЧЕНА (путает "номер
  стоянки в ряду" с "ярус", см. Docs/backlog.md 260722), привязка идёт
  прямым снэпом элемента на ближайший НИЖЕ реально нарисованный ярус
  стоянок (`zone_binding._candidates_for_category`).
- **Ригель/Плита перекрытия относятся к ярусу НИЖЕ** для привязки к
  стоянке крана — физически венчают ярус снизу (лежат на его колоннах),
  хотя в имени слоя отметка совпадает с ярусом, который они венчают.
  Колонна по-прежнему относится к своему ярусу.
  `zone_binding.TIER_CAPPING_TYPES` — снэп к ярусу СТРОГО ниже отметки
  элемента (`<`, не `<=`), в обоих механизмах привязки к стоянке
  (лесенка и прямой снэп). Подтверждено на реальных данных: ригель стоит
  точно на отметках колонн (15800/25800/34700), плита перекрытия близко
  (15000 vs 15800). 3D-высоты колонн (`computeColumnLevels`) не
  затронуты — отдельная логика.
- **Цвета зон по крану** — `zone_colors` таблица ключуется
  `(source_file, category, name)`, НЕ `zones.id` (нестабилен между
  переимпортами — `upsert_zones` делает DELETE+INSERT каждый раз).
- **3D-режим** — Three.js 0.160.0, вендорено ЛОКАЛЬНО. Перед вендорингом
  стороннего кода ОБЯЗАТЕЛЬНО явное подтверждение пользователя — уже
  было получено ("подтверждаю"), но при любом НОВОМ стороннем коде
  правило действует снова. Координатное отображение: `world.X=dxf.x`,
  `world.Z=-dxf.y` (внимательно с знаком — уже был баг зеркальности).
  `OrbitControls.zoomSpeed=4` (дефолт 1 слишком медленный для трекпада).
  Граница элемента (не путать с заливкой) — до 2026-07-24 была отдельным
  раздутым/утопленным дублирующим мешом ("инвертированная оболочка",
  4 версии подряд, см. `Docs/backlog.md`) — за один день дала три
  независимых бага (наложение по высоте на стыках, перекошенный офсет на
  вытянутых контурах, непропорциональный отступ на коротких марках).
  Заказчик потребовал убрать приём целиком: "3D объект должен точно
  соответствовать своей геометрии и координатам из входящих данных".
  Сейчас (`build3DMeshForElement`) — ОДИН меш, геометрия строится
  НАПРЯМУЮ из `element.outline`, БЕЗ каких-либо офсетов/отступов ни в
  плане, ни по высоте; рёбра — `THREE.EdgesGeometry` (только для
  вычисления позиций рёбер) → `LineSegments2`/`LineMaterial`/
  `LineSegmentsGeometry` (вендоринг подтверждён пользователем 2026-07-24,
  `app/static/vendor/three/examples/jsm/lines/` — обычный
  `THREE.LineSegments` даёт 1px, реально не видно, `LineBasicMaterial.
  linewidth` не работает в браузерах). `EDGE_LINE_WIDTH_PX=2` — толщина
  в ПИКСЕЛЯХ ЭКРАНА (`worldUnits:false`), не меняется с зумом; требует
  uniform `resolution`. Материал ребра — ОДИН общий на все элементы
  (`state.view3d.edgeMaterial`, создаётся в `init3DScene()`), не свой на
  каждый — раньше (пока цвет ребра зависел от статуса) было по одному
  экземпляру `LineMaterial` НА ЭЛЕМЕНТ (~9400 на реальном файле), что
  ломало сортировку рендера по материалу и заметно тормозило вращение/
  зум (живой репорт пользователя, см. Docs/backlog.md) — перестало быть
  нужным, когда цвет стал фиксированным, но не было убрано сразу.
  `on3DResize()` пересчитывает `resolution` только у этого одного
  материала. Цвет ребра — фиксированный чёрный (`EDGE_COLOR`), НЕ
  зависит от статуса (было — темнее статусного цвета в 3 раза, недостаточно
  контрастно на полутонах серой схемы, живой репорт пользователя, см.
  Docs/backlog.md). Ребро лежит РОВНО на поверхности грани (без зазора,
  по требованию заказчика выше) — без доп. мер это чистый z-fighting,
  грань почти всегда побеждает в тесте глубины; фикс —
  `polygonOffset`/`polygonOffsetFactor=4`/`polygonOffsetUnits=4` на
  материале грани (сдвиг ТОЛЬКО в буфере глубины, не физически) +
  `logarithmicDepthBuffer: true` на `WebGLRenderer` (модель в мм на весь
  масштаб здания — near/far различаются на 4-5 порядков, обычный буфер
  глубины на таком разбросе слишком грубый вдали от камеры). Известный
  непроверенный живьём риск: элементы, стыкующиеся впритык без реального
  зазора, теперь имеют точно совпадающие грани — потенциальный
  z-fighting МЕЖДУ РАЗНЫМИ элементами (раньше от этого защищал отступ
  цветного меша, убран по явному требованию заказчика).
- **3D-быстродействие** — материал ГРАНИ элемента тоже теперь общий НА
  СТАТУС (`getStatusMeshMaterial`, `state.view3d.materialByStatus`), не
  свой на каждый элемент — та же причина/фикс, что и у материала ребра
  выше (~9400 разных материалов на реальном файле ломали сортировку
  рендера, тормозили вращение/зум). Подсветка выбранного элемента —
  раньше меняла `emissive` прямо на своём материале, теперь материал
  общий, так нельзя (перекрасило бы всех с тем же статусом) —
  `getHighlightMeshMaterial()`, один переиспользуемый материал
  (выбранный элемент всегда только один), перекрашиваемый под нужный
  статус при каждом выборе; `mesh.material` при выборе/смене статуса
  ПЕРЕКЛЮЧАЕТСЯ между общими материалами, не перекрашивается на месте.
  Смена цветовой схемы статусов (Настройки) явно обновляет цвета во всех
  закэшированных материалах — иначе 3D отстал бы от 2D до перезагрузки.
  Плюс `renderer.setPixelRatio` ограничен до 1.5 (было — необрезанный
  `devicePixelRatio`, на Retina вчетверо больше пикселей на кадр, чем
  1x). Следующий кандидат, если этого не хватит (не сделано, крупная
  работа): слияние геометрии многих элементов в одну BufferGeometry —
  требует переделать поэлементный клик-выбор и скрытие по фильтрам.
- **2D-подписи в отдельном SVG-слое** (`#labels-layer`, ПОСЛЕ
  `#elements-layer` в разметке) — раньше подпись жила в одной `<g>` с
  фигурой СВОЕГО элемента; у многоярусных конструкций (колонна/ригель
  одной (x,y), разной elevation_mm) фигура более позднего яруса рисуется
  позже = поверх ВСЕГО более раннего, включая его подпись — подпись
  нижнего яруса была скрыта НАВСЕГДА, даже когда включена в настройках
  (см. `Docs/backlog.md`, 2026-07-22). Теперь все фигуры — в
  elements-layer, все подписи (+допстроки партии) — в labels-layer,
  подписи всегда поверх любых фигур; столкновения подписей друг с
  другом по-прежнему решает `updateLabelCollisionVisibility`.
  `.mark-label`/`.mark-sublabel` — обязательно `vector-effect:
  non-scaling-stroke` на белом контуре текста (без него обводка в
  мировых мм при близком зуме становится толще самих букв — та же
  запись backlog).
- **Подписи и зоны (захватка/кран/стоянка) выключены по умолчанию** —
  быстродействие на больших файлах (`updateSizesForZoom`/
  `updateLabelCollisionVisibility` — O(n) без throttle на каждый тик
  зума). `label_visibility` (БД) — новые типы заводятся `visible=0`;
  `state.zoneVisibility` (клиент, не персистится) — дефолт `false`.
  Включаются как раньше, через Фильтры → Подписи/Отображение зон.
- **Docs/TZ.md обновляется на КАЖДОЕ функциональное изменение** без
  напоминания — стоячая инструкция, отдельно от этого файла.
- **Партия** (`app/batches.py`, свой роутер, как `app/contracts.py`) —
  дочерняя сущность контракта, детализация плана до МАРКИ (не типа),
  назначение элемента на партию — независимое действие от смены
  статуса (доступно из того же контекстного меню, всегда, а не условно).
  `elements.batch_id` — простое живое поле, БЕЗ версионирования по
  `status_history` (в отличие от `contract_id`). Жёсткий отказ при
  несовпадении марки/типа/подтипа со строкой партии, мягкое
  предупреждение (не блокирует) при овербукинге. NULL-safe уникальность
  строк партии — обычный SQLite `UNIQUE` не считает `NULL=NULL`, нужен
  `COALESCE`-индекс, иначе строки без подтипа/марки дублируются молча.
  Self-service паттерн (`current["role"] != "admin" and current["id"]
  != user_id` → 403) переиспользован из `set-password` для
  `PATCH /users/{id}/label-color` — эталон для будущих персональных
  настроек.
- **Пароли** (аудит безопасности 2026-07-23, `app/auth.py`) —
  `password_hash IS NULL` = вход ЗАПРЕЩЁН (не "пустой пароль", как
  было), включая дефолтного `admin` из `schema.sql`. Требования при
  установке/смене (`validate_password_strength`, НЕ проверяются при
  входе — на уже принятые не действуют задним числом): ≥8 символов,
  буквы+цифры. `POST /users/{id}/set-password` удаляет ВСЕ ДРУГИЕ
  сессии пользователя (текущая, которой меняли, — исключена по токену
  из cookie); явно снять пароль (→ "вход запрещён") может только admin
  над чужим аккаунтом. Восстановление, если паролей/админов не
  осталось — `scripts/reset_password.py <domain_login>` (getpass,
  прямая правка БД в обход API/UI, те же правила сложности+сброс
  сессий). `GET /login-users` (публичный список ФИО/логинов) удалён —
  раскрывал логины неаутентифицированному клиенту; форма входа — текстовое
  поле, не выпадашка. `/docs`/`/redoc`/`/openapi.json` выключены по
  умолчанию, `ZHBI_ENABLE_DOCS=1` — для локальной разработки.
- **Security-заголовки/CSP + лимит загрузки** (аудит безопасности
  2026-07-23, продолжение) — весь прикладной JS вынесен из инлайнового
  `<script>` в `app/static/index.html` в отдельный `app/static/app.js`
  ради строгого `script-src 'self'` (`app/main.py`,
  `security_headers`); единственное исключение — инлайновый `<script
  type="importmap">` (bare-специфайер `"three"`), разрешённый ТОЧЕЧНЫМ
  sha256-хэшем его текста в `_CSP`. **При изменении текста import map
  хэш нужно пересчитать вручную** (иначе 3D тихо ломается —
  `Failed to resolve module specifier 'three'`, ровно так один раз и
  случилось; хэш считать по `el.textContent` из браузера, а не regex'ом
  по исходнику — переводы строк вокруг JSON тоже часть хэшируемого
  текста). `style-src` — с `'unsafe-inline'` осознанно (инлайновые
  `style="..."` для динамических цветов — массовые, не выносятся).
  Лимит размера загрузки (`/import-dxf` и др.) —
  `app/upload_limits.py`, `ZHBI_MAX_UPLOAD_MB` (по умолчанию 200 МБ).
  Rate-limit на `/login` доверяет `X-Forwarded-For` только при
  `ZHBI_TRUST_PROXY_HEADERS=1` (`app/auth.py`, `_client_ip`) — включать
  ТОЛЬКО за реальным доверенным reverse-proxy.
- **`Cache-Control: no-cache` на `/static/*`** (`app/main.py`,
  `security_headers`, с 2026-07-24) — `StaticFiles` сама по себе не
  выставляет этот заголовок, браузер иногда решает не перепроверять
  `app.js`/`index.html` даже во время активной разработки — несколько
  раз путало живую проверку правок в этой сессии (см. Docs/backlog.md).
  `no-cache` (не `no-store`) — обычная перезагрузка (F5) теперь всегда
  идёт условным `GET` по `ETag`/`Last-Modified` к серверу, жёсткая
  (Cmd+Shift+R) для подхвата новой правки больше не нужна.
- **«Рабочая дата» (backdating)** — `current_status`/`contract_id`
  элемента всегда вычисляются как значение из ПОСЛЕДНЕЙ ПО `changed_at`
  записи `status_history`, не последней по вставке. Кнопка «Сейчас» в
  тулбаре ЗАПОЛНЯЕТ рабочую дату текущим временем, но НЕ деактивирует
  поле — раньше это давало баг «статус не меняется» (застрявшая старая
  рабочая дата делала новую запись хронологически раньше уже
  существующей). Теперь есть отдельная кнопка «✕», которая ОЧИЩАЕТ
  рабочую дату (система переходит на текущее системное время), и диалог
  смены статуса всегда явно показывает и даёт поменять дату/время
  применения на месте.
- **Docker** (`Dockerfile`, `docker-compose.yml`, `.env.example`, с
  2026-07-24) — код и данные разделены БЕЗ правок Python-кода: пути к
  `data/zhbi.db`/`Input/`/`uploads/` уже были относительными
  (`app/db.py`, `app/main.py`, `app/dxf_import.py`), поэтому bind-mount
  этих же host-папок на те же пути внутри контейнера (`/app/data` и
  т.д.) достаточен. Один контейнер (монолит, как и раньше — один
  uvicorn отдаёт API и статику), сборка образа — на сервере из
  git-чекаута (`docker compose build`), НЕ через registry — ближе всего
  к прежней схеме git pull + рестарт, без логина на сервере. Старые
  venv/systemd-скрипты (`scripts/linux/install.sh`/`run.sh`/
  `zhbi.service`/`update-git-test.sh`/`update-git-prod.sh`) удалены,
  заменены на `docker-install.sh`/`update-test.sh`/`update-prod.sh`;
  `backup.sh` не изменился (bind-mount делает `data/zhbi.db` обычным
  файлом хоста, бэкап работает без docker). `.env` — машинно-специфичная
  конфигурация (порт, security-флаги), в git НЕ входит (`.env.example`
  — шаблон, входит).

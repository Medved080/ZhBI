# Полная инструкция внедрения силами Claude Code

## 1. Готовый запрос для новой сессии

Откройте Claude Code в репозитории `zhbi-tool` и передайте следующий текст:

```text
Внедри фичу из feature_shaft_panels в текущий сервис ЖБИ.

Это панели облицовки ЛИФТОВЫХ ШАХТ ГП1/ГП2 внутри объекта «Москвич»,
а не фасадные панели и не МФР. Исходник: Input/260908_ПП 5-7_Е-Ж.dxf.
Пользователь разрешил анализ именно этого DXF. Оси 5, 7, Е, Ж в нем
соответствуют осям модели объекта; привязку вычисляй автоматически.

Сначала прочитай CLAUDE.md, feature_shaft_panels/README.md,
feature_shaft_panels/DXF_FINDINGS.md, DESIGN.md и CLAUDE_CODE.md.
Выполни приложенные тесты и воспроизведи ведомость 184 панелей / 30 марок.
Не переписывай распознавание с нуля: перенеси и доработай готовый пакет.

Работай в отдельном worktree, сохрани чужие незакоммиченные изменения.
Не запускай приложение с боевой базой. Для проверки используй отдельную
копию data/zhbi.anon.db и отдельный порт. Не меняй тип объекта, не создавай
второй объект «Москвич» и не импортируй изделия в revit_elements.

Подключи миграцию, API и форму предпросмотра, новый element_type
«Панель облицовки шахты», поштучную геометрию, высоту 3D и общую модель.
Защити ОБА направления переимпорта: панели не снимают актуальность
колонн/ригелей/плит, обычный DXF не снимает актуальность панелей.

подтвержденную толщину изделия для объемов; распознавание поверхностей

Сохрани уже существующие статусы, контракты, даты, ручные поля и историю.

правилам проекта. Покажи результаты живой проверки UI и итоговый diff.
```

Нормальное начало работы — самостоятельно выполнить подготовку и тесты; запрос пользователя о внедрении не требует дополнительного подтверждения на каждое обратимое изменение. Если Claude Code технически блокирует чтение `Input/` по настройкам своего инструмента, ему следует указать конкретную причину. Не отключать ограничения на все рабочие данные ради одного файла. Отчет в комплекте позволяет изучить результат без открытия остальных файлов Input.

## 2. Подготовка

1. Снять `git status --short` и проверить текущий `CLAUDE.md`. На момент подготовки комплекта уже были чужие изменения в `app/kladr.py`, `app/objects_import.py`, `app/static/app.js`, `app/static/index.html`. Их не откатывать и не включать в случайный общий коммит.
2. Для интеграции создать отдельную ветку/worktree по правилам проекта. Основание выбрать по актуальному состоянию репозитория. Новые файлы этого комплекта могут быть еще не закоммичены — явно перенести папку в worktree, не рассчитывать, что Git сделает это сам.
3. Использовать отдельный файл БД копии, не общий `data/zhbi.anon.db` двух работающих сессий. Копию создавать SQLite backup, чтобы учитывать WAL.
4. Прочитать `Docs/DECISIONS.md` об импорте, идентичности, ручных полях, геометрии и координатах; `Docs/MAP.md` — о проверках.
5. Запустить тесты из README. Тесты намеренно не импортируют `app.main`, не запускают его startup и не требуют pytest/httpx.

Для самостоятельной локальной копии (из корня рабочей копии с доступной обезличенной БД):

```bash
.venv/bin/python - <<'PY'
import sqlite3
from pathlib import Path
source = sqlite3.connect(Path('data/zhbi.anon.db').resolve().as_uri() + '?mode=ro', uri=True)
target = sqlite3.connect('data/zhbi.shaft-check.db')
source.backup(target)
target.close()
source.close()
PY
```

Не перезаписывать существующий `zhbi.shaft-check.db`, если в нем уже есть нужная проверочная работа: выбрать новое имя.

## 4. Миграция и контракт API

В `app/db.py` в штатной последовательности миграций вызвать:

```python
from app.shaft_panels.storage import install_schema
install_schema(conn)
```

Вызов должен идти после создания/миграции `objects` и `elements`, до обработки данных и до обслуживания запросов. Не помещать его в роут анализа. Если в проекте принят другой способ добавления полей через список миграций, зарегистрировать `elements.height_mm` там, а создание двух таблиц оставить в идемпотентной функции. Не выполнять обе альтернативы без проверки существования поля.

Добавить описания `height_mm`, `shaft_panel_geometry`, `shaft_panel_imports` в `app/db_schema_doc.py`. Уточнить, что `height_mm` — вертикальный размер, а `outline_json` — горизонтальный след; это не высота этажа. Пересобрать схему `scripts/gen_db_schema_drawio.py`, руками drawio не править.

В `app/models.py` добавить в `ElementOut`:

```python
height_mm: Optional[float] = None
```

`ElementDetailOut` наследует это поле. Проверить все DTO/экспорты, где поля перечислены явно. `plan_data()` сейчас выбирает `SELECT *` и превращает `outline_json` в `outline`; `height_mm` там сохранится, если последующая фильтрация/сериализация его не отрежет. Для карточки панели добавить выдачу metadata из `shaft_panel_geometry` через текущий авторизованный `/elements/{id}` либо отдельный авторизованный роут, проверяя объект элемента.

Записи параметров, которые должны появиться на сервере автоматически после обновления, регистрировать в `app/release_tasks.py`. Импорт геометрии конкретного объекта не запускать автоматически при старте сервера: это действие пользователя после предпросмотра.

## 5. Подключение API, доступа и транзакции

После переноса адаптера подключить в `app/main.py`:

```python
from app.shaft_panels_host import router as shaft_panels_router
app.include_router(shaft_panels_router)
```

Разместить после создания `app`, не между `@app.on_event('startup')` и его функцией.

`host_adapter.py` уже связывает:

- `get_current_user` с текущими cookie-сессиями;
- `assert_object_feature(..., 'drawings', 'write')` с объектными правами;
- `backup_before_import` со штатными резервными копиями;
- `label_visibility` с новым типом;
- `zone_binding` с тем же алгоритмом зон;
- `touch_elements` с автообновлением клиентских вкладок.

Проверить текущие сигнатуры перед копированием: исходные точки зафиксированы в `integration/architecture-map.json`, но соседняя разработка может их поменять.

Для работы в областях со ступенчатой геометрией стоянок («лесенка», один исходный ярус) адаптер намеренно возвращает ошибку, а не назначает неверную зону. Если выбранный «Москвич» использует эту схему, **до завершения внедрения** расширить общий объектный API зон: загрузить сетку и вычислить те же `build_stance_level_polygons`, что использует новый стандарт DXF. Не отключать `can_recalculate` и не придумывать вторую геометрию зон. Если зон вообще нет, панели могут импортироваться без зон; положение по осям уже вычислено независимо.

Внутри `before_commit` запрещены `conn.commit()`, вызов `zone_recalc.recalculate()` (он коммитит и обновляет весь объект), `element_sync.apply_import()` и второе записывающее соединение. Ошибка hook должна откатывать **всю** операцию. Адаптер использует те же функции привязки, но обновляет только измененные панели.

Для общего журнала действий добавить посткоммитную запись `activity.log('import_dxf', ...)` с `details.kind='shaft_panels'`, объектом, пользователем, исходным файлом и сводкой. Код действия уже существует. Не писать событие успеха до commit. Можно добавить в router callback `after_apply(user, object_id, summary)`; не допускать, чтобы сбой необязательного отображения журнала после commit заставлял повторить импорт как будто он не выполнен. Транзакционный журнал `shaft_panel_imports` уже заполняется в ядре и остается первичным доказательством применения.

Вся обвязка должна сохранить общую CSRF/Origin-проверку приложения и ограничения загрузок. Файл на диске получает случайный временный каталог; имена из multipart не используются как путь. Парсер и роут ограничивают DXF 30 МиБ, очередь — 8 результатов. Текущий Docker — один worker. Для нескольких worker нужна общая атомарная реализация токенов; это не решается sticky sessions.

## 6. Защита переимпорта в обе стороны — обязательна

В `app/element_sync.py`:

1. В `analyze_import()` сразу после `load_object_elements()` отфильтровать панели:

```python
from app.shaft_panels_scope import exclude_shaft_panels
existing = exclude_shaft_panels(conn, object_id, existing)
```

Не менять глобально все читатели `load_object_elements`, если они нужны для других задач. Важно, чтобы **сверка основного DXF** не видела панели дополнительной развертки.

2. В начале `apply_import()` добавить защиту уже построенной сверки:

```python
from app.shaft_panels_scope import assert_standard_match
assert_standard_match(conn, object_id, match)
```

3. Заменить тело `_register_drawing()` делегированием:

```python
from app.shaft_panels_scope import register_primary_drawing
register_primary_drawing(conn, object_id, source_file)
```

Она сохраняет актуальность дополнительных источников панелей, обновляя основной DXF обычным образом.

4. Проверить все пути: веб-анализ/применение, одностадийный импорт, импорт из Input, rebuild/reset. Повторная загрузка основной геометрии не должна менять записи в `shaft_panel_geometry`; сброс/удаление объекта должны удалять их только в рамках существующего явно выбранного пользователем сброса, соблюдая FK.
5. Не направлять `Плиты-опалубки` в старый `LAYER_CONFIG` как обычную геометрию плана: координата Y развертки является высотой, а не Y модели. Автоматическое распознавание этого профиля в общем диалоге можно добавить как маршрутизацию в **тот же** `/shaft-panels/analyze`, не как третий бесконтрольный insert.

При переносе старый профиль импорта не должен принимать `element_type=Панель облицовки шахты` через произвольный WEB-слой. Этот тип создается специальным профилем развертки; общий тип `Панель` продолжает означать прежнее поведение.

## 7. Несколько текущих чертежей и общий вид объекта

Найти по AST и проверить места, где `is_current=1` сопровождается `fetchone()`, `LIMIT 1`, либо выбором первого источника. Анализ должен охватить `_resolve_selection_item`, `/plan-data`, дерево выбора, перечни файлов, фильтры и отчеты. Не менять запросы исторических просмотров без необходимости.

При выборе **всего объекта** сформировать элементы выбора для всех текущих `source_file`, используя `current_drawing_sources(conn, object_id)`. Для панели и основного DXF применить одни и те же права, фильтры слоев и видимость. Если одновременно выбраны объект и один его файл, не дублировать изделия по `elements.id`.

Сетка дополнительного источника уже сохраняется в координатах объекта, а не в листовых координатах DXF. Совпадающие оси нескольких выбранных источников объединять по виду/метке/координате; не рисовать удвоенные подписи.

Не копировать существующие колонны/плиты в новый источник ради общего отображения. Не менять текущий основной файл объекта на файл разверток. После импорта дерево обновить и добавить новый текущий источник в выбор пользователя, чтобы результат был виден сразу.

## 8. Форма и 3D

Импортировать ES-модуль через принятый в проекте ленивый `import()`:

```javascript
const { mountShaftImport } = await import('/static/shaft-panels.js');
const unmount = mountShaftImport(container, {
  objectId: selectedObjectId,
  request: authenticatedFetch,
  onApplied: async () => {
    // Здесь реальные существующие функции обновления дерева и модели.
  },
});
```

`authenticatedFetch` — **существующий** fetch-wrapper, возвращающий Response и сохраняющий сессионные/CSRF механизмы. Не копировать пример с незаданными именами буквально. Передать реальные зависимости из текущего `app.js`. При закрытии окна вызвать `unmount`. Кнопку разместить в меню импорта выбранного объекта ЖБИ и скрыть/заблокировать без `drawings/write`. Сам backend также проверяет права.

Форма уже показывает 184 отдельных строки, результат сравнения, замечания и явный выбор снятия актуальности отсутствующих панелей. Доработать внешний вид под текущие стили и добавить связь строк с предпросмотром контура, используя `front_xyz_mm` / `bounds` / `physical_key` из API. У мастера не должно появляться значение 60 или 300 мм по умолчанию.

В `elementExtrusionHeight()` до общего fallback:

```javascript
if (element.element_type === 'Панель облицовки шахты') {
  if (!Number.isFinite(element.height_mm) || element.height_mm <= 0) {
    throw new Error(`У панели ${element.id} отсутствует высота из DXF`);
  }
  return element.height_mm;
}
```

Эквивалент готовой функции — `panelExtrusionHeight` в ES-модуле. Можно загрузить ее вместе с 3D-зависимостями и делегировать вызов. Не делать синхронную функцию высоты асинхронной и не запускать `import()` для каждого изделия.

Проверить все места геометрии: основной буфер, легкий режим, hit-test, рамку выбора, зум на элемент, прозрачность, подписи. `height_mm` должна участвовать везде одинаково. Контур экструдируется в диапазоне `elevation_mm … elevation_mm + height_mm`; координаты Three.js `(x,z,-y)`. Искусственный fallback 3000 мм для этих панелей запрещен.

В AST-карте `integration/type-usage.json` отмечены жесткие проверки типов в JS. Проверить их по назначению: новый тип участвует в вертикальных подписях и фильтрах, но не должен внезапно стать колонной или плитой в алгоритме поиска перекрытий. `DECAL_TYPES` требует осмысленной поддержки вертикальной грани; одного добавления строки в Set недостаточно.

Если нужен режим поверхностей без толщины прямо в общей модели, это отдельное расширение рендера: `front_xyz_mm` → треугольники с тем же ID и выбором. В текущем комплекте без толщины доступен анализ/отчет, а запись объемных элементов заблокирована. Не подставлять фиктивную ненулевую толщину для обхода.

## 9. Справочники и учет

Новый тип попадет в `elements` и объектный справочник `marks`, но проверить весь путь: список типов, подтипы, настройки подписей, формы/экспорт Excel, фильтры, контрактация по паре `(element_type, mark)`, статусы и даты.

Не создавать марки глобально на все объекты. Не использовать марку как ID изделия. Не переиспользовать generic `Панель`, если это смешает разные классы существующих изделий. Не переименовывать существующие типы ради этой фичи.

Номер этажа можно назначать только по согласованной модели уровней объекта; «2 ост.» — не второй этаж. Если автоматизация этажей нужна для фильтров/графиков, добавить отдельное правило по уровням объекта с отчетом о неоднозначности; сейчас parser честно оставляет floor пустым.

## 10. Проверки до приемки

Автотесты комплекта + проверка памяти БД из README обязательны. Они проверяют реальный DXF, сопоставление марок, размерные опоры, неизвестную толщину, ошибочные оси/NaN, отражение сетки, потерю текста/дубли контура, ACL, сроки/владельца токена, HTTP-импорт, rollback, stale preview, повторный импорт, ручные поля, контракты и разные объекты.

Дополнительно после подключения:

1. Основной DXF → 184 панели → основной DXF повторно: исходные ЖБИ и панели остаются актуальными; история и число изделий стабильны.
2. Отмена анализа не меняет ни `elements`, ни `marks`, ни `object_drawings`; применение чужого/просроченного токена запрещено.
3. Изменение данных после анализа требует повторного анализа. Два одновременных Apply одного токена дают только одно применение.
4. Снять актуальность одной отсутствующей панели можно только явным действием, только в ее объекте/области. Ее история и контракт сохраняются.
5. Изменение размеров панели выдает «новая + отсутствующая», не незаметный перенос истории по ближайшему центру. Изменение марки контрактной панели блокируется до штатного решения.
6. В общей модели проверить ПП7/handle 120B: ГП1/А, низ −0,110, высота 1,130, ширина 5,700 м. Проверить стороны В/Д общей стенки отдельно, направления U и нормалей; каждой панели соответствует свой ID.
7. Включить/выключить тип, отдельную шахту/слой; выбрать/изменить статус панели; обновить страницу — результат сохраняется. Проверить основной и легкий 3D-режимы, подписи, выбор, цвета и экспорт.

9. Произвести контролируемую ошибку hook в копии: новые изделия/марки/история/реестр чертежей отсутствуют после rollback; backup есть.
